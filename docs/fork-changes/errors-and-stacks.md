# Errors and stacks



## Error stacks formatted when first read

Release: v0.26.1.

Making an error no longer formats its `stack`. The engine records the frames (function name, bytecode and position) and formats the text the first time `stack` is read, with the same result as before. Code that makes many errors and reads few of their stacks, such as the development build of React (one error per JSX element), runs much faster. On darwin/arm64, a server render of a 100-item React component took 11.2 ms at the median with the development build, against 42.1 ms before. The production build of the same component, the production build of a four-route app and a JSON and array benchmark stayed within 1% of before. Top-level code that makes 500 errors per run took 1.8 ms instead of 3.2 ms. `stack` is an ordinary writable, configurable data property, so the error has the same shape as one whose stack was formatted at once. Once read, it is the string. What is different:

- While the stack is pending, the value of `stack` is an internal object that holds the recorded frames. A pending error so carries three extra small allocations: that object, its property list and the frame record (about 150 bytes for a short stack). Assigning, defining or deleting `stack` frees them like any other value. The internal object belongs to a private class. The C patch makes it a built-in class of every runtime. In Go, its class ID is taken when the package loads, and a runtime registers the class the first time it records a lazy stack, a one-time cost of about a kilobyte.
- No code sees the internal object. Everything that reads the value of `stack` formats it first: property reads in scripts and through the C API, `Object.getOwnPropertyDescriptor(s)` and `JS_GetOwnProperty`, and redefining a frozen `stack` with a value (the engine compares the old and the new value). What only looks at keys or attributes leaves it pending: `Object.keys`, `Object.freeze`, `Object.seal`, `Object.isFrozen`, `Object.isSealed`, `propertyIsEnumerable`, `__lookupGetter__`, `__lookupSetter__`, and the checks a proxy whose target is the error makes after a `has`, `deleteProperty` or `ownKeys` trap. `stack` is not enumerable, so spreading, `Object.assign`, `Object.entries` and `JSON.stringify` skip it.
- Through a proxy, apart from those three checks, `stack` is formatted as before. A lookup of the attributes through a proxy (`Object.keys`, `Object.freeze` or `propertyIsEnumerable` on the proxy, for example) and the checks a proxy makes after a `get`, `set`, `defineProperty` or `getOwnPropertyDescriptor` trap read the error's full descriptor, which formats the stack. Results, trap calls and their order are the same as when the stack was formatted at once. The cost is memory: with almost none left, such an operation can fail with out of memory, where the upstream engine had already formatted the stack when the error was made.
- Reading a property named `stack` whose value is an object takes the slow path of the interpreter, which is where the stack gets formatted. Other property reads do not change. In a loop of 160,000 reads, `o.x` took 1% less time than before, `o.stack` holding a number 5% more, `o[k]` 1% more, and an inherited `o.x` 9% less. A read takes about 19 ns there, so no change is more than 2 ns per read.
- Until its stack is read or the error is freed, an error keeps the bytecode of every function on its stack alive, and with it the realm (global object) each function was compiled in. Most of these stay alive anyway. A function that runs once and makes an error that something keeps is the exception, together with every function it defines: one kept error from a function that defines 2,000 others kept 1.30 MB where 0.30 MB stayed before. An error made in one realm and kept by another keeps the first realm and everything its globals hold: with a 4 MiB `ArrayBuffer` in the first realm, the runtime used 4.31 MB where 67 KB stayed before, until the stack was read. Keeping only the file name and the line table would need either a copy of the line table for every frame of every error, which adds work and memory to every error made, the case this change is for, or a reference count of its own for the line table, which changes a struct of the engine and so needs a regeneration of `lib/`.
- Reading a stack frees its three allocations, but the holes they leave between objects that are still alive are reused only by later allocations of the same sizes. After making 10,000 errors, keeping them and reading every stack, the allocator held 3.60 MB, against 2.06 MB when the stacks were formatted at once.
- Errors made while top-level code (a script, an eval or a module body) is on the stack are still formatted at once, so that an error a library keeps from when it loaded does not keep that code alive. So are errors that cannot take new properties and errors that already have a `stack`.
- If there is no memory left when `stack` is first read, the read throws the out of memory error, which ends the call, and the stack stays pending, so a later read can give the text. Reading the property descriptor formats the stack the same way and so can throw too. When an error whose stack is still pending is printed (`console.log`, `JS_PrintValue`), formatting the stack never throws and never leaves a pending exception: out of memory there prints the error without its stack, and a later read can still give it. This covers the stack only. The rest of the print, such as the message, can run out of memory and leave an exception, as in the upstream engine. Printing an error whose stack is already a string works as it did before.
- If the text cannot be formatted when a stack is built at once (any allocation of the formatting can fail: growing the text buffer, converting a function or file name to UTF-8, making the final string), `stack` becomes `null` and no exception is left, in Go and in the C patch alike. The upstream engine also gives `null` when the text buffer cannot grow. When converting a function name fails, it instead keeps a half-formatted stack with the name shown as `<anonymous>` and leaves an exception pending.

Tests: `errorstack_test.go`, `errorstack_unix_test.go`, `lib/backtrace_test.go`, `lib/backtrace_round2_test.go`, `lib/backtrace_round3_test.go`, `lib/backtrace_proxy_test.go`, `internal/fixlib/main_test.go`.

### When upstream changes it

What to do when `go run ./internal/fixlib` stops on this change after an upstream release. [upgrading.md](../upgrading.md) has the whole procedure and the order in which to update the lists `fixlib` checks against.

If it reports that `_build_backtrace`, `_get_prop_string`, `JS_GetPropertyInternal`, `JS_GetOwnPropertyInternal`, the interpreter's `get_field`, `js_print_error`, `js_print_object` or `JS_ComputeMemoryUsage` changed shape, compare the new upstream `build_backtrace` with `lib/backtrace.go`, which formats the same text from the recorded frames and must change with it. If it reports that `_build_backtrace`, `_get_prop_string` or `_JS_GetFunctionBytecode` changed (a fingerprint other than the one in `internal/fixlib/backtracesites.go`), the same holds: a pending stack must still come out with the bytes `_build_backtrace` writes. Once `lib/backtrace.go` matches, put the new fingerprints in (`go run ./internal/fixlib -backtrace` prints them). A change to the C strings they use counts, a string moving in the table does not.

If it reports that a function of `ownFlagsCallers` (`internal/fixlib/main.go`) reads the value of the descriptor it gets, or uses it another way, read the function: if it now needs the value, it must call `_JS_GetOwnPropertyInternal` again, so take it off the list. Otherwise fix the count there.

`fixlib` also audits how the engine uses property slots (the `JSProperty` that holds a value), because a pending `stack` must be formatted before anything hands the value on. It parses each generated function and follows slot pointers from where they are made (an object's property array, the slot `find_own_property` returns) through variables (`=`, `:=` and `var`), stack cells, pointer arithmetic, call arguments and return values, whatever their names. A slot pointer that goes anywhere else (stored into a structure, in an assignment of several results, arithmetic on a stack cell other than a step to the next cell) is listed as a use there. For every function they reach it lists each use: reads and writes of the value or of another field, calls the pointer is passed to, stores, and which uses come before the function's first call into `lib/backtrace.go`. It also counts each function's descriptor lookups. `internal/fixlib/slotsites.go` holds the expected list with the reason each function is safe. When a release adds a function that uses slots, or changes how one does, `fixlib` stops and prints the difference: check whether the change can see a pending `stack`, wire it to `lib/backtrace.go` if so, and update the list (`go run ./internal/fixlib -slots` prints it). It also requires every property lookup in the interpreter loop (`JS_CallInternal`) to be a known guarded read or the `put_field` write. What the audit does not see: a slot pointer stored into a structure is listed as a use where it is stored, but not followed to where it is loaded again. Indirect calls are not followed. A function that no one passes a slot pointer to is not audited, so a new helper only shows up once something calls it with one. The allocator functions that resize or free the property array are listed as uses but not looked into. The order check only compares positions in the source with the first guard of the function. And slot addresses made some other way than from the property array, such as a raw offset into the object, are not recognized. So a change in these places needs a review by hand.

## Endless recursion throws RangeError

Release: v0.26.6.

Recursing without end throws `RangeError: Maximum call stack size exceeded`, worded as in V8, which a script can catch, with the default settings. It used to kill the process with a Go stack overflow: the engine sets a new runtime's stack size to 1 MB, meant as bytes, but the Go port's stack check counts TLS stack slots, so the limit was a million slots, far more than a goroutine's stack holds. A new runtime now starts with the port's own default, `lib.MaxStackSlots`, as `SetMaxStackSize` already said, and that default is 10000 slots rather than 1000: a React render of a page of tifa's example shop takes about 470. At the default, recursing without end takes up to 128 MB of goroutine stack before it throws. Running out of stack used to be `InternalError: stack overflow`. The parser and `JSON.parse` now report nesting too deep for the stack with the same `RangeError`, as V8's parser does, rather than `SyntaxError: stack overflow`. A regular expression nested too deep still fails to compile with `SyntaxError: stack overflow`.

Tests: `stackoverflow_test.go`, `internal/fixlib/stack_test.go`.

### When upstream changes it

If it reports that `XJS_NewRuntime2` or `_JS_ThrowStackOverflow` changed shape, a new runtime must still start with a stack size of 0 (the port's `MaxStackSlots`), and running out of stack must still throw a `RangeError` (`internal/fixlib/stack.go`). The same holds when it reports that the stack check of `_next_token` or `_json_next_token` changed shape: the tokenizers must throw that `RangeError` too. If it reports that the uses of `"stack overflow"` differ from `stackOverflowUses`, a new place throws that message: make it call `_JS_ThrowStackOverflow` (teach `fixStack` to), or add it to the list if it is the regexp parser.
