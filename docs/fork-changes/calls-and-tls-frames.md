# Calls and TLS frames

The engine keeps the C locals whose address is taken in a TLS frame, a part of libc's TLS stack: `bp := tls.Alloc(N)` when a function starts, freed when it returns. The stack check of the engine counts the slots of that stack, so every change here keeps the slots a stack check sees exactly as they were, and a script recurses exactly as deep as before. All of these change only the generated Go, through `internal/fixlib`, with no C form.

## Calls allocate no Go memory

Release: v0.26.12.

Calls cost less. A call of a javascript function, of a native function, of a bound function or of a native function with data used to take the room for its arguments, locals and stack with `alloca`, which the Go port implements with malloc, and on darwin, freebsd and windows also with Go memory: a closure and a slice entry per call, 1 to 4 Go allocations. Up to 768 bytes, that room is now the end of the function's TLS frame. A larger one, and any in `js_c_function_data_call` and, on 32-bit targets, in `js_call_bound_function`, which have no frame, is malloc'd and freed on return. Either way a call allocates no Go memory. And 14 hot small functions, such as `set_value`, `free_property` and `__JS_FreeValueRT`, used their TLS frame only to read a `JSValue` as a pointer or a float as bits: they now keep those bytes in a Go array, and skip `tls.Alloc`, `tls.Free` and the `defer`. The stack check counts the same TLS stack slots as before at every point, so a script recurses exactly as deep as it used to. A server render of a page of tifa's example shop takes about 11% less time on linux/amd64 (AMD EPYC) and 14% less on darwin/arm64 (Apple M4), with the same HTML, and loading the shop's bytecode into a VM about 11% less on linux. 22 more functions were added in v0.26.17, from the count of `tls.Alloc` per function in renders of tifa's example shop and test apps, such as `js_same_value_zero` (`Map` and `Set` keys, `includes`), `free_token` (the parser) and the finalizers of functions and iterators: the numbers above are from before, and what the later changes give together is under [One TLS frame per call on linux](#one-tls-frame-per-call-on-linux).

The 768 bytes bound what this costs in TLS memory on linux. Linux's libc keeps the TLS block of every call depth a VM has reached until the VM is closed, grown to the largest frame used at that depth and rounded up to a power of two, and neither `JS_ComputeMemoryUsage` nor the VM's memory limit counts it. The frame of `JS_CallInternal` is 1280 bytes on 64-bit targets, so it takes a 2 KB block with or without the room, and no block grows past 2 KB. The worst case is the same as before: a recursion to the default limit of 10000 slots holds about 20.7 MB of TLS blocks on linux/amd64, whatever its functions (without the limit, a function with 500 locals made that 164 MB). Smaller frames can grow up to 1 KB: those of `js_call_bound_function` (16 bytes) and `js_call_c_function` (160 bytes). A recursion through bound functions can so hold up to about 1 KB more per level: 1000 levels through a function bound to 44 arguments hold 5.13 MB rather than 4.14 MB. On 32-bit targets a block can take up to 1 KB where it took 256 bytes, so up to 10 MB in the worst case. Elsewhere the TLS stack keeps one block of about 1 MiB (see [memory-and-allocation.md](memory-and-allocation.md#one-block-of-tls-stack-per-vm-outside-linux)) and frees the pages past it as before. These are changes to the generated Go only (`internal/fixlib/alloca.go`, `internal/fixlib/frames.go`), with no C hunk.

Tests: `calldepth_test.go`, `callbench_test.go`, `internal/fixlib/alloca_test.go`, `internal/fixlib/frames_test.go`.

### When upstream changes it

What to do when `go run ./internal/fixlib` stops on this change after an upstream release. [upgrading.md](../upgrading.md) has the whole procedure and the order in which to update the lists `fixlib` checks against.

If it reports that the `alloca` of `_JS_CallInternal`, `_js_call_c_function`, `_js_call_bound_function` or `_js_c_function_data_call` changed shape, or that there are no longer exactly four, read the new function (`internal/fixlib/alloca.go` describes the rewrite). The room must still come from the end of the frame, allocated again right before the stack check, so that the TLS stack slots stay what they were at every point: `calldepth_test.go` pins the depth each kind of recursion reaches and that the slots balance. An alloca larger than `allocaMax` (768 bytes) stays a malloc, so that no TLS block linux keeps grows past the 2 KB the frame of `JS_CallInternal` takes. If that frame changes size, set the constant again (`TestTLSStackResidentNearLimit` checks both, and the blocks on linux).

If it reports that a function of `internal/fixlib/framesites.go` changed its TLS frame (size, number of cell uses), uses `bp` some other way, or can now reach a stack check, read the new function. Its frame may only hold values read back where they are written, and the function must not be on a call chain that checks the stack, or it would take a slot out of the count. Update the entry or remove the function from the list. `go run ./internal/fixlib -frames` prints every TLS frame of `lib/ccgo_darwin_arm64.go` and why it must stay: a line without a reason is a function that could join the list, after a review.

## Frames freed without defer

Release: v0.26.15.

Engine functions with a TLS frame no longer free it in a `defer`. ccgo frees the frame of a function (`bp := tls.Alloc(N)`) with `defer tls.Free(N)`, and Go does not inline a function with a defer, with or without PGO, so hundreds of small engine functions stayed calls. `fixlib` now frees the frame before each return, after the value is computed, and at the end of a function that can run off it, in all 13 files: 969 functions on darwin/arm64, among them the three call functions that `fixAlloca` changed (see [Calls allocate no Go memory](#calls-allocate-no-go-memory)). Go then inlines many of them, and a server render of a page of tifa's example shop takes about 10% less time on linux/amd64 (AMD EPYC), with or without PGO, with the same HTML. A PGO profile taken before this change no longer matches many of the call sites: take it again. What changes is a Go panic that goes up through the engine: a defer freed the frames on the way, and now they stay on the TLS stack. The VM puts the stack back where it was when the call into javascript started, and when javascript called a Go function, so `Close` frees all of it, and libc's memgrind check of the TLS stack holds. A panic of a Go function that javascript called is recovered there as before: no engine frame is between them. A panic in the engine itself (a bug, such as a nil pointer, or libc running out of memory) goes on to the Go code that called javascript, also when the javascript was evaluated by a Go function. That Go function used to recover it and throw an error, which walked stack frames the panic had dropped and could crash the process (it did, with a fatal fault, in `TestEnginePanicTLS/nested`). The engine's state after a panic in it is not known, so the VM is good only for `Close`, as in tifa: every later call into javascript panics. A Go function that recovers such a panic itself does not save the VM: the VM panics where the Go function returns, as it does when a call returns with engine frames left on the TLS stack, which means a frame was not freed (outside linux such a frame can break the TLS stack before the call returns). The values held by the javascript frames the panic went through are not freed, with or without the defer, and neither is the room that `alloca` mallocs for a call with more than 768 bytes of it (see `fixAlloca`), which the defer freed. The Go code written by hand that calls the engine (`lib/backtrace.go`, `quickjs.go`) frees its TLS frames before it returns as well: a defer would free the frames a panic left in place of its own. A Go function that calls `runtime.Goexit`, as `t.Fatal` does, also leaves the VM good only for `Close`, where v0.26.14 kept it usable. The generated Go is changed by `internal/fixlib/nodefer.go`, with no C hunk, and the other changes of `fixlib` see the defers as ccgo writes them.

Tests: `enginepanic_test.go`, `memgrind_test.go`, `internal/fixlib/nodefer_test.go`.

### When upstream changes it

`fixlib` frees every TLS frame before each return instead of in a defer, as its last change (`fixNoDefer` in `internal/fixlib/nodefer.go`). It first puts the defers back (`restoreDefer`), so every other change, check and report (`-frames`, `-slots`, ...) works on the frames as ccgo writes them, and it checks that putting them back gives the file it was given, byte for byte. If it reports a frame that is not freed by `defer tls.Free(N)` right after `tls.Alloc(N)` (or by the closure of `fixAlloca`), a `tls.Alloc` or `tls.Free` somewhere else, a `defer` that is not in `keptDefers`, a function literal, a bare `return` or a local with the name of the result, read the function: a defer that frees anything on the TLS stack, or a return the rewrite cannot see, would leave the stack wrong on some path. Teach `fixNoDefer` the new form, or add a defer that only frees malloc'd memory to `keptDefers`. The VM puts the TLS stack back after a panic (`tlsstack_linux.go`, `tlsstack_other.go`), which knows how libc keeps that stack: one block per slot on linux, bytes in segments elsewhere. After a libc release, run `go test -run EnginePanic .` with and without `-tags=libc.memgrind`.

## Cold paths of === and key names

Release: v0.26.15.

`===` and the names of keys take no TLS frame on their usual paths. `js_strict_eq2` (`===`, `Object.is`, `includes`, `Map` keys) and `__JS_AtomToValue` (the name of a key as a value, as `Object.keys` and `for in` need it) allocated a TLS frame on every call, though only the comparison of two BigInts and the name of an integer key pass the address of a part of it on. `fixlib` moves those two paths into functions of their own, `_js_strict_eq2_cold` and `___JS_AtomToValue_cold`, which take the same frame, and the rest of the frame becomes a Go array, as for the functions of `frameSites` (see [Calls allocate no Go memory](#calls-allocate-no-go-memory)). The paths are matched as ccgo writes them, every other use of the frame must be a load or a store of a cell, and the two functions can reach a stack check only through their cold functions, so the TLS stack a stack check sees is the same. A server render of a page of tifa's example shop takes 0.7% (with PGO) to 2% (without) less time on linux/amd64 (AMD EPYC), with the same HTML. This changes only the generated Go, with no C hunk (`internal/fixlib/cold.go`).

Tests: `lib/coldpath_test.go`, whose `testdata/coldpath.txt` is what the engine gave before the change (Node gives the same), and `internal/fixlib/cold_test.go`.

### When upstream changes it

If it reports that the cold paths of `coldSites` changed, read the new `js_strict_eq2` or `__JS_AtomToValue`: the cold path must still be the only code that passes the address of a part of the frame on, and it must still read only the parameters, from the cells the function stores them in at its entry. Then update the shapes in `coldShapes` (`internal/fixlib/cold.go`), or the frame size and cell count in `internal/fixlib/coldsites.go`, and run `go test -run ColdPath ./lib`.

## TLS frames taken per statement

Release: v0.26.16.

Reading a property, `==`, turning a value into a string or an object, and freeing an array take no TLS frame on their usual paths. `JS_GetPropertyInternal`, `JS_GetOwnPropertyInternal`, `JS_AtomIsArrayIndex`, `JS_NewAtomStr`, `js_eq_slow`, `JS_ToStringInternal`, `JS_ToObject` and `js_array_finalizer` allocated a TLS frame on every call, and so did 12 functions added in v0.26.17 from the count of `tls.Alloc` per function in renders of tifa's test apps: the conversions to numbers (`JS_ToInt32Free`, `JS_ToInt32SatFree`, `JS_ToInt64SatFree`, `JS_ToFloat64Free`), `JS_GetPrototype`, `JS_ConcatString2`, `js_sub_string`, `add_fast_array_element`, `js_object_has_name`, `js_get_regexp`, `js_regexp_get_lastIndex` and `js_thisNumberValue`. Only a few of their statements need a frame: those that pass the address of a part of the frame to a callee, and those that can reach a stack check. `fixlib` makes the frame a Go array, as for the functions of `frameSites`, and gives each of those statements a TLS frame of the same size for itself: right before the statement it allocates the frame and copies the array into it, and right after it copies the frame back and frees it. The statement reads and writes the same bytes as before, and a stack check it reaches sees the same TLS stack: one more slot, with the frame at the same place. The out parameter of `find_own_property` and `is_num_string` gets a Go pointer into the array instead, through copies of the two functions that take one (`_find_own_property_lazy`, `_is_num_string_lazy`), which only load and store through it and reach no stack check.

Why this is safe: a function is changed only when every other use of its frame is a load or a store of a cell, every address a statement passes on goes to a callee that was read and does not keep it after it returns nor return it (`addrCallees` in `internal/fixlib/lazy.go`), and every call that can reach a stack check is in such a statement. The text of those callees, of the functions the `va_list` goes on to, of the `get_own_property` methods of the engine's classes and of `JS_GetOwnPropertyInternal`, which the method of a proxy passes the descriptor to, is pinned by fingerprints (`lazyAddrSites`), so an upstream change to one stops `fixlib` until it is read again, and the frame size, cell uses and statements of each function are pinned in `lazySites`. A class registered through `JS_NewClass` with a `get_own_property` method of its own must not keep the descriptor it is given either, as in C (neither `quickjs.go` nor `lib/backtrace.go` registers one). Other changes of `fixlib` match these functions as ccgo writes them, so `fixlib` undoes this change first (`restoreLazy`) and makes it again last, and checks that undoing it gives back the text it was given, byte for byte. On 32-bit targets nine of these functions, such as `JS_ToObject` and `js_array_finalizer`, have no TLS frame and stay as they are (`lazyFrameless`). Another function of `lazySites` without a frame there stops `fixlib`. With the first eight functions, a server render of a page of tifa's example shop takes 1.6% (with PGO) and 1.1% (without) less time on linux/amd64 (AMD EPYC), and 2.6% less on darwin/arm64 (Apple M4, with PGO), with the same HTML. What the 12 added later give, together with the other later changes, is under [One TLS frame per call on linux](#one-tls-frame-per-call-on-linux). This changes only the generated Go, with no C hunk (`internal/fixlib/lazy.go`).

Tests: `internal/fixlib/lazy_test.go` and `internal/fixlib/nodefer_test.go`, with test262 and the tests of the root package for what the engine gives.

### When upstream changes it

If it reports that a function of `lazySites` changed (a frame size, a number of cell uses, of statements with a frame of their own or of out parameters other than the one in `internal/fixlib/lazy.go`), or a use of its frame that `fixLazyFrames` cannot show is safe, read the function: each statement that passes an address in the frame on or can reach a stack check must still be an expression, an assignment, a return of one value or the condition of an if, and each address must still go to a callee of `addrCallees`. Then update `lazySites`. If it reports that the functions of `lazyAddrFuncs` or a `get_own_property` method changed (a fingerprint other than the one in `internal/fixlib/lazyaddrsites.go`), read them: none may keep an address it is given after it returns, nor return it. Then put the new fingerprints in (`go run ./internal/fixlib -lazyaddr` prints them).

## One TLS frame per call on linux

Release: v0.26.17.

On linux, a call of a javascript function takes one TLS frame instead of two. `JS_CallInternal` took a frame of 1280 bytes at its entry, and for a function whose arguments, locals and stack fit in 768 bytes (see [Calls allocate no Go memory](#calls-allocate-no-go-memory)) freed it and took 1280 bytes plus that room again right before the stack check. `fixlib` makes the entry take 1280 + 768 bytes, and turns the block that freed and took the frame again into a comment.

Why this is safe: the rest of the function is the path an alloca larger than 768 bytes took before, which skips that block too. The block only copied a parameter into the new frame and set a pointer into it, and `fixlib` stops unless the entry made each of those, once, in the same words. Nothing between the entry and the block writes them again, except on paths that return or jump past the block, and `fixlib` pins that text by fingerprints (`oneFrameSites`), so a new write there stops it. The room is still at `bp + 1280`, now inside the frame the entry took, and each call holds one slot of the TLS stack at every point, as before, so a stack check sees the same count and a script recurses exactly as deep as it used to. Linux's libc keeps one block per slot, rounded up to a power of two, and 1280 + 768 bytes fill the 2 KB block the frame took already, so no block grows. On 32-bit linux (a frame of 160 bytes) a block would grow, and elsewhere the TLS stack is one run of bytes that a larger frame uses up faster, so those files are not changed. Other changes of `fixlib` match `JS_CallInternal` as `fixAlloca` writes it, so `fixlib` undoes this change first (`restoreOneFrame`) and makes it again right before the frames are freed without a defer, and checks that undoing it gives back the text it was given, byte for byte.

On its own this takes about 9% of the TLS frames out of a render of tifa's example shop on linux. Together with the 22 functions added to `frameSites` (see [Calls allocate no Go memory](#calls-allocate-no-go-memory)) and the 12 added to `lazySites` (see [TLS frames taken per statement](#tls-frames-taken-per-statement)), it takes out about a fifth: 20.6% for the shop, and 20.1% and 25.4% for tifa's test apps bench and mui. A render then takes 1.4% (shop), 2.2% (bench) and 3.1% (mui) less time than with v0.26.16 on linux/amd64 (AMD EPYC, without PGO), with the same HTML: the median of 6 rounds, each comparing the mean of three builds of the new code, whose code sits at slightly different addresses, with one build of v0.26.16. That placement alone moves the time: moving `JS_CallInternal` by 160 or 224 bytes changes the time of a render by up to 2.4%, so these numbers are good to about that much, and one build is not enough to measure changes this small. This changes only the generated Go, with no C hunk (`internal/fixlib/oneframe.go`).

Tests: `internal/fixlib/oneframe_test.go`, with `calldepth_test.go`, test262 and the tests of the root package for what the engine gives.

### When upstream changes it

If it reports that the frame of `_JS_CallInternal` is not taken as `fixAlloca` writes it (`fixOneFrame` in `internal/fixlib/oneframe.go`), that the block that takes it again runs a statement the entry does not run once, or that the function has another `tls.Alloc`, read the new function: the block may only make again what the entry made on the frame, or dropping it changes what the rest of the function finds there. If the frame of 1280 bytes changes size, `fixOneFrame` changes a linux file only while the power of two that holds the frame also holds the room of `allocaMax`, so check that the files it changes are still the ones `oneFrameFiles` lists in `internal/fixlib/oneframe_test.go`. If it reports that the text between the entry and that block changed (a fingerprint other than the one in `internal/fixlib/oneframesites.go`), read it: nothing there may write again the parameter copy or the pointers into the frame the block made, except on a path that returns or jumps past the block. Then put the new fingerprints in (`go run ./internal/fixlib -oneframe` prints them).

## TLS frames taken without a call on linux

Release: not released yet.

On linux, taking and freeing a TLS frame is no longer a call. `TLS.Alloc` and `TLS.Free` of `modernc.org/libc` cost more than Go inlines (in a function as large as `JS_CallInternal`, Go inlines only a cost of 20 or less), so every frame of the engine was two calls: about 490000 calls of `TLS.Alloc` in a render of the pages of tifa's test app bench. On linux, libc keeps one block per slot of the TLS stack, and taking a frame is only to step the index of the next slot when its block is large enough, which it nearly always is once a VM has run for a while. `lib/fastframes_linux.go` does that in `tlsTake` and `tlsDrop`, and `fixlib` writes every `tls.Alloc` and `tls.Free` of the 8 files of linux through them, but those of `JS_CallInternal`:

```go
bp := tlsTake(tls, 48)
if bp == 0 {
	bp = tls.Alloc(48) // the next block is too small: libc takes a larger one
}
...
if tlsDrop(tls, 48) {
	tlsSignals(tls) // a C signal handler was set through libc on this TLS
}
```

Go inlines `tlsDrop` everywhere, and `tlsTake` everywhere but in the largest functions, `resolve_scope_var` and `resolve_labels` of the compiler, where it is one call as `TLS.Alloc` was. `JS_CallInternal` keeps `TLS.Alloc` and `TLS.Free` (`fastFrameSkip`): Go does not inline `tlsTake` there either, and with the frees inlined at its returns the interpreter got slower, so renders of tifa's bench pages took 1.6% more time than with `JS_CallInternal` left as it is.

Why this is safe: `tlsTake` and `tlsDrop` do what `TLS.Alloc` and `TLS.Free` do on their usual path, on the same fields, so the stack, its slots and the addresses the engine gets are the same, and a stack check sees the same count at every point. When the next block is too small, `TLS.Alloc` does the rest, and when libc checks for signals on a free, `tlsSignals` takes the slot back and lets `TLS.Free` free it. The fields of `libc.TLS` they read are not exported: `lib/fastframes_linux.go` finds their offsets by name when the package starts and checks their types, and the program stops there with a message if libc changed them. `fixlib` pins the text of `TLS.Alloc`, `TLS.Free`, `TLS.StackSlots` and the two structs in `libc_musl.go` of the libc release in `go.mod` by a fingerprint (`fastFrameSites`), so a libc release that changes them stops it until they are read again. Elsewhere libc keeps the TLS stack in segments, and those files are not changed. `fixlib` makes this change last, after the frames are freed without a defer (see [Frames freed without defer](#frames-freed-without-defer)), and undoes it first, and checks that undoing it gives back the text it was given, byte for byte. Every `tls.Alloc` and `tls.Free` of a file of linux must be a statement of its own of the forms above, or it stops.

In a render of tifa's bench pages, the calls of `TLS.Alloc` go from about 490000 to the 132000 of `JS_CallInternal`, and the instructions down by 1.3%, by 1.9% for the shop's pages (callgrind). On top of [Likely and unlikely tests branch on their condition](interpreter-loop.md#likely-and-unlikely-tests-branch-on-their-condition), a render of the bench pages takes 0.990 of the time (0.985 to 0.993 over 8 rounds) and of the shop's pages 0.998 (0.995 to 1.004 over 5 rounds), on linux/amd64 (AMD EPYC, without PGO), with the same HTML: each round compares the mean of six builds (three for the shop) whose code sits at different addresses. Both changes together take 0.967 of the time of v0.26.17 for the bench pages (0.947 to 0.983) and 0.979 for the shop's (0.974 to 0.989). The call micro benchmarks of the root package (`go test -bench Call .`) go both ways: in four builds each, with code at different addresses, a call of a native function took 75 to 81 ns with this change and 79 to 82 without, but a builtin call that adds two numbers 84 to 89 ns with it and 72 to 78 without, with 1% fewer instructions. Why is not known: the VM has no CPU counters to tell, and a build that also kept the frame of `js_call_c_function` took 77 to 89 ns. This changes only the generated Go, with no C hunk (`internal/fixlib/fastframes.go`).

Tests: `lib/fastframes_linux_test.go` (the same addresses and slot counts as libc, and the signal check), `internal/fixlib/fastframes_test.go`, with `calldepth_test.go`, `enginepanic_test.go`, test262 and the tests of the root package for what the engine gives.

### When upstream changes it

If it reports a `tls.Alloc` or `tls.Free` that is not a statement of a form it knows, read the function and teach `fixFastFrames` the form, or leave the call as it is: the result of each rewrite must be used exactly as the result of `tls.Alloc` was. If it reports that the text of libc changed (a fingerprint other than the one in `internal/fixlib/fastframesites.go`), which happens with a new release of `modernc.org/libc`, read `TLS.Alloc`, `TLS.Free` and the structs against `tlsTake` and `tlsDrop`: they must still only step `sp` when the block of the next slot is large enough, and only step it back and check `checkSignals` on a free. Then put the new fingerprint in (`go run ./internal/fixlib -fastframes` prints it). If a program stops when it starts, saying that libc keeps its TLS stack in another way, the fields `sp`, `stack` or `checkSignals` of `libc.TLS` changed name or type: change `tlsLayout` and the helpers to match, or drop this change.
