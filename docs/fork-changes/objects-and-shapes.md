# Objects and shapes

A shape is the list of an object's keys in order, shared by objects with the same keys. Both changes here change only the generated Go, through `internal/fixlib`, with no C form.

## New properties of plain objects skip the generic path

Release: v0.26.13.

Defining a new property on a plain object costs less. Object literals, spread, class fields, `JSON.parse` and every new function go through `JS_DefinePropertyValue`, which handed each property on to `JS_DefineProperty` and `JS_CreateProperty` before `add_property` did the work, with a TLS frame and a deferred free at each step. Now `JS_DefinePropertyValue` first calls `objlitDefine` (`lib/objlit.go`), which calls `add_property` itself when the object is extensible and not exotic, not a fast array and not the global object, the property has no getter or setter, and the object does not have it yet. Every other case takes the old path, and so does assignment (`o.x = v`, `Object.assign`). Nothing is cached, so memory use is the same. A property of an object literal takes about 55 ns rather than 95 on linux/amd64 (AMD EPYC), and a server render of a page of tifa's example shop about 6% less, with the same HTML. `fixlib` puts the call into all 13 files and takes the object bit fields `objlitDefine` checks from each file's `JS_NewObjectFromShape`, checked against the checks of the same bits in the old path, so 32-bit and big-endian targets get their own layout. This changes only the generated Go, with no C hunk (`internal/fixlib/define.go`).

Tests: `lib/objlit_test.go`, `lib/objlit_memgrind_test.go`, `internal/fixlib/define_test.go`.

### When upstream changes it

What to do when `go run ./internal/fixlib` stops on this change after an upstream release. [upgrading.md](../upgrading.md) has the whole procedure and the order in which to update the lists `fixlib` checks against.

If it reports that `JS_DefinePropertyValue`, `JS_DefineProperty`, `JS_CreateProperty`, `add_property`, `find_own_property` or `find_own_property1` changed (a fingerprint other than the one in `internal/fixlib/definesites.go`), read the new code against `objlitDefine` in `lib/objlit.go`. For a new data property of an extensible object that is not exotic, not a fast array and not the global object, the old path must still end in `add_property` with the `C_W_E` bits of the flags and then store the value, and every other case must still fail one of the checks of `objlitDefine`. Change `objlitDefine` if it no longer matches, then put the new fingerprints into `definesites.go`: `go run ./internal/fixlib -define` prints them, for the files with all of `fixlib`'s other changes made. Any edit to those functions changes the fingerprint, even one that does not matter here, and so does a change to another `fixlib` step that touches them (`fixUp` does). If it reports that `JS_DefinePropertyValue` has a new signature, update the call (`defineCall`) and `reDefineValueHead` in `internal/fixlib/define.go`. `objlitDefine` reads `extensible`, `is_exotic` and `fast_array` through constants that `fixlib` takes from the bit fields `JS_NewObjectFromShape` sets (the second, fourth and fifth, all in one byte), and checks against the checks of those bits in `JS_CreateProperty` and `JS_DefineProperty`. If it reports that `JS_NewObjectFromShape` changed shape, that one of those checks is gone, or that a check disagrees with `JS_NewObjectFromShape`, then the layout of `JSObject` moved or `JS_NewObjectFromShape` sets the fields in another order: find where the three bits are now and update `objectBits` and its patterns in `internal/fixlib/define.go`.

## Kept shapes

Release: v0.26.16.

A VM keeps the shapes of plain objects once their objects are gone. The shape of an object is its keys in order, and an object literal goes through one shape for each key. `add_property` grew a shape in place when only its object used it, so the shapes in between were gone once the object had its keys, and the last one went with the last object: the next literal with the same keys copied and grew them all again. Now `js_free_shape0` keeps a shape whose count drops to zero in a ring of the last n, with a count of one, and `add_property` copies a shape that only its object uses instead of growing it, so that the shapes in between are kept too (`lib/shapecache.go`). The next literal with the same keys finds every shape it needs in the shape hash table, and makes none. The times in this entry were all taken without PGO, on linux/amd64 (AMD EPYC). A copy costs an allocation and the keys so far, which an object that gets keys no other object has, one at a time, pays for each key and never gets back: such objects took 22% longer to build. So each shape `add_property` finds earns one copy, up to 64, and without credit the shape grows in place. The shapes in between are then still kept, only later: the shape an object leaves when it finds the next one kept is kept. Objects of keys no other object has now take about 6% longer to build than with the cache off, and object literals with the same keys 30% less. Only shapes whose prototype is the `Object.prototype` of the VM, that have at most 32 keys and no key that is a symbol not registered are kept, so a kept shape holds nothing alive but that prototype and the atoms of its keys, and a `WeakRef` or `FinalizationRegistry` whose target is a symbol sees it go as it would without the cache. Shapes the cycle collector frees are not kept, and `JS_FreeRuntime` lets every kept shape go. The ring is in the state of the runtime, next to the [front cache](memory-and-allocation.md#a-front-cache-for-small-blocks). In `lib` it is off until `JS_SetShapeCache(ctx, n)`, which refuses a ring whose size does not fit in a `size_t`. A new VM keeps `DefaultShapeCache` (2048) shapes, `VM.SetShapeCache` changes it, and `VM.Close` turns it off before it frees the context.

Memory: one VM of the shop holds 647 KiB more after a GC, and with the front cache as well 722 KiB more (8.03 MiB rather than 7.33). With 1024 shapes it was 190 KiB and 461 to 502 KiB more, and with 4096 shapes and the front cache 1.26 MiB more. How the blocks fall in the arenas moves these by up to 0.5 MiB from one run to another, with the same shapes and objects left. Loading the shop's bundle alone keeps about 1250 shapes, so a ring of 1024 is full before the first render. Kept shapes count against the memory limit of the VM, and they are not let go when an allocation fails: an allocation in `add_property` can come right before the object takes a shape that only the cache holds. A shape of 32 keys of about ten characters, that no other object has, takes about 3 KiB with the atoms of its keys, so 2048 of them take about 6 MiB, and the atom table keeps the size it grew to after they go. A script that runs close to its memory limit can run out of memory with the cache on where it would not without it: give such a VM a smaller cache, or none. Without PGO, on linux/amd64 (AMD EPYC), with the same HTML, the shape cache alone makes a render 3.6% faster, and with the front cache and the [interrupt countdown](interpreter-loop.md#the-interrupt-countdown-inside-the-interpreter) a render takes 4.5% less time than without the three (six rounds). Two VMs on two hardware threads of one core render 2.9% more pages a second. Generated Go only, no C hunk (`internal/fixlib/shapecache.go`).

Tests: `lib/shapecache_test.go` (reuse, which shapes are kept, symbol keys, the ring, the credit for copies, the cycle collector, `JS_FreeRuntime` with the cache on, out of memory, a ring too large for a `size_t`, 8 runtimes on 8 goroutines), `shapecache_test.go` (the memory limit, and objects built in many ways that read the same with the cache on and off) and `internal/fixlib/shapecache_test.go`.

### When upstream changes it

If it reports that the functions of `shapeFuncs` or `JSShape` changed (`internal/fixlib/shapesites.go`), read them against `lib/shapecache.go`: `add_property` must still copy a shape whose count is not one, link the copy into the hash table, and take a shape it finds there on the line `shapeFound` is put before. A shape whose count is not one must still never change in place: `js_shape_prepare_update` copies it, and `resize_properties` and `compact_properties` change only a shape of count one that an object has. Outside the cycle collector a shape must still be freed only through `js_free_shape0` (`free_object` frees the shape of an object that way, and `JS_NewObjectFromShape` takes the count it is given), `js_new_shape2` must still grow the hash table when it is half full, `__JS_NewAtom` must still put the index of a symbol that is not registered in its `hash_next`, where `js_get_atom_index` and `JS_FreeAtomStruct` read it and which `JS_ResizeAtomHash` leaves alone, and the cycle collector must still free the shapes of a cycle itself while `gc_phase` is `JS_GC_PHASE_REMOVE_CYCLES`. Then run `-shape`. If it reports that `gc_phase` is not the byte right after `tmp_obj_list`, change `gcPhaseOffset` in `lib/shapecache.go` to where it is.
