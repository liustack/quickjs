# The C engine

English · [简体中文](c-engine.zh-CN.md)

`engine/` is the engine of the module: QuickJS at the pinned commit with the changes of liustack/quickjs, compiled to Go assembly by the generator. The tables below are what it does differently from upstream QuickJS, the fixes it took from upstream and quickjs-ng, and what a user of v0.28 or earlier sees against the engine they ran, QuickJS translated to Go by ccgo (the "previous engine" below). The changelogs have the same list for users.

## Differences from upstream QuickJS

| Change | What changes for a program | Checked by |
| --- | --- | --- |
| The engine builds with `-ffreestanding -nostdinc` against `engine/libc` | `Math.*` gives the same bits on linux/amd64 as the previous engine did. On darwin/arm64 it can differ in the last digit (see "The small libc") | `check-symbols.sh`, `libc-test.sh`, `math.sh` |
| `Date` and the seed of `Math.random` come from `host_now` | the Go host answers with the clock of the VM | the native host, `HOST_CLOCK` |

## The small libc

`memcpy` is not musl's: it is written here (overlapping loads and stores of one width up to 128 bytes, then a loop of 128 bytes with the destination aligned to 16, SSE2 and NEON moves only), because musl's is slow for the strings the engine builds. See its [README](../../engine/libc/README.md).

The whole engine is built with `-ffp-contract=off` too, and the generator refuses an `llvm.fmuladd` or `llvm.fma` and any fast-math flag (`reassoc`, `nnan`, `ninf`, `nsz`, `arcp`, `contract`, `afn`, or the `unsafe-fp-math` attributes) in the IR, and on arm64 a fused instruction (`fmadd`, `fmsub`, `fnmadd`, `fnmsub`, `fmla`, `fmls`) in llc's text. What is tested, and what is not:

- linux/amd64: `engine/test/math.sh` checks, bit for bit, 100000 inputs for each of 33 functions of libc and for 33 `Math` operations as JavaScript sees them, against hashes kept in `engine/test/math`. They were first recorded from the previous engine, and the C engine gave the same bits on every result. The JavaScript check writes a NaN as the one NaN of JavaScript, so it does not check the sign and payload of a NaN. The libc check does, so it runs on x86-64 only.
- macOS arm64: `math.sh` checks the JavaScript hashes there. The libc results are the same except for the sign of a NaN, which the processor chooses (positive on arm64, negative on amd64), so that part is not checked on arm64.
- The engine runs on amd64 and arm64 only, so the same last digit on both is shown.


`snprintf` reads a whole conversion, flags to conversion letter, and checks it before it takes any argument for it, a `*` included. It calls `abort` on a floating point conversion, `%n`, a positional argument, a length on `c`, `s`, `p` or `%`, any flag, width or precision written on `%` (a `*` there counts, whatever it would be given), a format that ends inside a conversion, and a width or precision that does not fit an int. A width of INT_MIN given for a `*`, and an output longer than INT_MAX, abort too, but only after the arguments are taken, since they depend on them. A new format in the engine cannot print the wrong thing. It is the `abort` of the small libc, which asks the host like every other abort, and not a trap, which in Go would end the process. `libc-test.c` lists the formats that abort and counts the arguments taken before each one does, and `api-test.c` checks that one reaches the host. The only trap left in `engine/` is the one after the `host_call` in `abort`, for a host that returns.

A format is checked before it can reach that `abort`. The engine files are built with `-Werror=format` and `-Werror=format-nonliteral` (`engine/test/flags.sh`), so a format agrees with its arguments, and is either a string constant or the format of a function that has the `printf` attribute and passes it on (`JS_ThrowError2`, `JS_ThrowError` and `js_parse_error_v` have it, with the `va_list` form `format(printf, 3, 0)`). The two helpers behind `JS_ThrowTypeErrorAtom` and `JS_ThrowSyntaxErrorAtom` pass their format with the name of an atom in place of their arguments, which clang cannot follow, and a pragma turns the check off for just those two.

`check-symbols.sh` proves the symbol level only. The engine files, with the libc, leave undefined nothing but the callbacks of `engine/host.h` and `host_memory_grow` of `engine/heap.h`. The allocator ([allocator.md](../allocator.md)) is among the engine files, and the engine calls no malloc: `dbuf` and `CharRange` have no default allocator, and `stdlib.h` of the libc declares none. It does not prove that the machine code uses no thread local storage, no system call instruction and no fixed address. Those checks come with the generator, not before.

## Time, abort and the host

`engine/host.h` declares what the engine asks of its host. `host_now(vm, kind)` gives the wall clock or a monotonic one in nanoseconds. `host_call(vm, &this, argc, argv, magic)` calls a function of the host, and a magic below 0 is a request of the engine: `HOST_CALL_ABORT` for `abort()`. The this value goes by address, and a request of the engine has none and passes NULL: a JSValue by value is two words, which with the shadow pointer, `vm`, `argc`, `argv` and `magic` makes 7, and the generated code passes a callback at most 6 words in registers in the `body` calling mode. `Math.random` asks no clock: it starts from the seed `JS_NewRuntime` was given, the same in every context of the runtime. `abort` does not know its VM and passes 0. `host_memory_grow` is in `engine/heap.h` and comes with the allocator. Three kinds of `host_call` below 0 are the allocator's: `HOST_CALL_MEMORY_RELEASE` gives a dedicated chunk back, `HOST_CALL_MEMORY_REMAP` grows one (linux, when the host said so with `JS_SetHostRemap`), and `HOST_CALL_MEMORY_PRESSURE` asks the host to give back the memory it holds for the VM outside the heap, which the memory limit counts (`JS_GetHostLimit`, see [allocator.md](../allocator.md)). They run no user code and do not call back into the engine. `host_poll` is where Go stops the goroutine in the engine and where an interrupt reaches it (see [Polls and interrupts](#polls-and-interrupts)). `JS_FreeRuntime` returns the blocks still in use, 0 when nothing leaked. An object that a reference is still held to, such as a value the host never freed, does not abort it as the assert of upstream did: it stops before it frees the rest, and the host takes the memory back as a whole.

## Depth of calls and of C recursion

The engine never reads the stack pointer. The generated assembly runs on a Go stack, which moves and grows, and keeps the locals whose address is taken on a shadow stack of its own, so an address on the stack says nothing about how deep the engine is. It counts instead, with two counts in the runtime, and throws `RangeError: Maximum call stack size exceeded` past either. Neither is ever reset: each level that is entered is left on every path, and a level that cannot be entered counts nothing, so the error path recurses no further.

- **The call depth** counts each call of a function while it runs. `JS_CallInternal` counts before it sends a call to a class, so a built-in function, a bound function and a proxy count a level as a JavaScript function does. A function of bytecode counts its level where it is entered: at the start of `JS_RegvmRun` for a call from C, and in the call ops of the register loop for a call from one JavaScript function to another. The interpreter counts the level itself when it calls a plain C function without `JS_CallInternal` (see [How the interpreter calls a C function](#how-the-interpreter-calls-a-c-function)). A constructor that `JS_CallConstructorInternal` sends to a class counts there. The fast path of `JS_IteratorNext2`, which calls the C `next` of a built-in iterator directly, counts a level too: a chain of iterator helpers recursed through it with no other count. The exported functions that run code (`JS_Call`, `JS_CallConstructor`, `JS_CallConstructor2`, `JS_Invoke`, `JS_Eval`, `JS_EvalThis`, `JS_EvalFunction`, `JS_ExecutePendingJob`) count one level for the entry of the host, so that a host function that calls back into the engine adds a level even when the path to the next call is long, as in the parser of `JS_Eval`. The engine itself calls forms of them that do not count (`js_call` and the like). The limit is 5000 by default (`JS_DEFAULT_MAX_CALL_DEPTH`) and at most 10000 (`JS_MAX_CALL_DEPTH_LIMIT`). `JS_SetMaxCallDepth(rt, n)` sets it, and returns -1 and changes nothing when `n` is out of that range or the runtime is running code. A plain recursive function gets 2 levels short of the limit when the host started it with `JS_Eval`: one for the entry and one for the global code.
- **The internal depth** counts the recursions of C that make no call: the parser (`js_parse_unary`, `js_parse_postfix_expr`, `js_parse_assign_expr2`, `js_parse_statement_or_decl`, `js_parse_destructuring_element` and `js_parse_function_decl2`, which cut every cycle of it: the binary and logical operators are read in loops), making the functions of a script (`js_create_function`, and `get_closure_var` for a variable of a function around), `json_parse_value`, `internalize_json_property`, `js_json_to_str`, the parser of regexps (`re_parse_disjunction` and `re_parse_nested_class`, through `lre_depth_enter`), modules (`js_resolve_module` for their imports, `js_create_module_function`, `get_exported_names` for a namespace, `js_resolve_export1` for an export, linking and evaluation), `JS_ReadObjectRec` and `JS_WriteObjectRec`, `JS_FlattenIntoArray`, the methods of a proxy that go on to the target (all but call and construct, which count as calls, and the prototype, which `JS_GetPrototype` asks the proxy by name), `JS_OrdinaryIsInstanceOf` on a bound function, `JS_GetFunctionRealm`, making a lazy property (`JS_AutoInitProperty`, whose value defines properties that can be lazy too: the tables of built-in objects bound that, the call graph does not) and the define of a property of a String object or an arguments object, which goes on to the ordinary define with `JS_PROP_NO_EXOTIC` (`js_define_own_property_ordinary`: the call graph does not see the flag). Most are a wrapper that counts around the original function, renamed with a `1` at the end (`js_resolve_export1`, whose name has one already, wraps `js_resolve_export2`). The limit is `JS_MAX_INTERNAL_DEPTH`, 2000, and it is a constant of the build, not a setting like `JS_SetMaxCallDepth`: the bound on the stack the engine can use multiplies it by the stack of the deepest of these recursions, and a bound needs one fixed biggest value for any call depth. A host cannot change it, and `JS_SetInternalDepth` (below) moves the point the count starts from, not the limit. A regexp too deep throws `SyntaxError: stack overflow`, as it did.

Each runtime counts for itself, and the Go stack that the runtimes of one host share sees them all. A host that runs code of one runtime from inside a call of another therefore hands the depths over, so that the chain is held to one limit and not to one limit for each runtime in it. `JS_GetCallDepth(rt)` and `JS_SetCallDepth(rt, n)` read and write the call depth, and `JS_GetInternalDepth` and `JS_SetInternalDepth` the internal depth. Around the call, the host reads both depths of the runtime that calls, sets those of the other runtime to them, makes the call, and sets the other's old depths back (the other runtime may be in the chain already, when two runtimes call each other, and its old depths are then its own outer levels). A write takes 0 up to the limit (`JS_MAX_CALL_DEPTH_LIMIT`, `JS_MAX_INTERNAL_DEPTH`) and returns -1 and changes nothing for anything else. A depth above the limit of that runtime (the other one has a bigger limit) is kept, and the next call in it is a `RangeError`: the chain is deeper than it allows. Unlike `JS_SetMaxCallDepth`, the writes work while the runtime runs code, which is when a host makes them, and a depth that was set must be set back before the code that was running goes on, since each call that ends counts one level off whatever the depth is by then. The internal depth is handed over too: the bound on the Go stack adds the internal levels of everything on it, and runtimes that counted their own would add up to the limit once for each runtime in the chain. `unit.c` runs two runtimes that call each other until a `RangeError`: with the depths handed over the chain is one limit long, and without it twice that.

How deep nesting goes with the limit at 2000, measured on the native host by nesting one form in itself until the next level throws (`RangeError`, a `SyntaxError` for a regexp):

| Form (each nested in itself) | Levels that fit | Counted per level |
| --- | --- | --- |
| Parentheses `((1))`, calls `f(f(1))`, arrays `[[]]` | 665, 665, 666 | 3 (an assignment expression, a unary one and a postfix one, whatever operators are between) |
| Object literals `({a: {a: 1}})` | 664 | 3 |
| Arrow functions `() => () => 1` | 998 | 2 |
| Function expressions `(function () { return (function () { return 1 }) })` | 249 | 8 |
| Blocks `{{}}`, and `if (1) if (1) ;` | 2000, 1997 | 1 |
| Labeled blocks `L0:{L1:{}}` | 1000 | 2 |
| `JSON.parse` and `JSON.stringify` of nested arrays | 2000, 2000 | 1 |

JSON nested past the limit (`JSON.parse`, its reviver and `JSON.stringify`) throws `RangeError: JSON nesting too deep`, so the error names the data and not a call that recursed. A stack that runs short first, or any other recursion, still throws `RangeError: Maximum call stack size exceeded`. Of the engines measured on a Mac, V8 parses any depth (its parser has no recursion since v7.6) and stringifies about 6200 levels, Bellard's QuickJS 2026-06-04 parses 6500 and stringifies 4300, and QuickJS-NG 0.17 parses 8100 and stringifies 4600, all with a stack overflow error.

Real code stays far under it. Of 79525 files (npm packages, JSX compiled by esbuild, the output of emscripten, wasm2js, peggy, ajv and the like, and JSON), the deepest parse reaches 632, in the asm.js build of sql.js, which writes the cases of a big `switch` as 290 labeled blocks inside each other. No other file goes past 282, one in a thousand reaches 100, and the middle file 17. A C program with a `switch` of more than about 1000 jump targets, built to asm.js, would not parse. Rendering the pages of tifa's example shop takes the parser 110 levels deep, its MUI pages 99, the bench pages 62 (with the Intl polyfill), and all of test262 256. Everything else stays small on those pages: regexps 49 counted on top of the parser that compiles them, closures 15 (`get_closure_var`), making functions 8, JSON 6, `JS_GetFunctionRealm` 2. The call depth of those renders stays under 600.

Each count also checks the stack left. `__shadow_remaining()` gives the bytes left: the generator turns it into the room left on the shadow stack, and the native test host gives the room left on its thread's stack. Entering either depth needs `JS_STACK_MARGIN` (64 KiB) left, and an `alloca` of a call (the arguments of a C function and of a bound function) needs its size on top, or it throws the same `RangeError`. So a dynamic alloca never crosses the end of the shadow stack, whatever the depths allow.

A few recursions must not fail, so a count that throws does not fit them, and each is a loop or has a bound that a proof gives. Ropes are read, hashed, made flat and freed by loops (`string_buffer_concat_rope` copies the strings of a rope in order). A concatenation that makes a rope deeper than `JS_STRING_ROPE_MAX_DEPTH` (60) rebuilds it from its strings in order by a binary count, at most 30 deep whatever their lengths (upstream's rebuild by lengths could leave one 53 deep, and recursed). The parse records of `JSON.parse` with a reviver and the definitions of functions are freed by loops. The case conversions, the decompositions and the emoji sequences of the Unicode tables, and the strings of `\q{...}` in a class of a `v` regexp, are loops. The value printer recursed too and is left out (`CONFIG_PRINT_VALUE` above). Freeing an object can free others: `free_zero_refcount` frees in a loop of its own every object whose count reaches zero while it runs, and nothing it calls starts a collection, so it is never entered twice. `js_nest_enter(rt, JS_NEST_FREE, 1)` counts it and aborts past 1, which cannot happen: a finalizer of the host that asks for a collection gets none (see [A collection asked for while objects are freed](#a-collection-asked-for-while-objects-are-freed)), and the engine's own finalizers start none (`cycles.sh`).

The property layer (properties, atoms, conversions, errors, string buffers, big integers and the collector) was one cycle of 173 functions in the static call graph, bounded by its data and not by a count. It is cut, and `engine/test/cycles.txt` is empty: `cycles.sh` finds no cycle that a count does not cut. No count was added to a hot path. The cuts:

- **Making an error.** `JS_ThrowError2` allocates, and running out of memory there makes the out of memory error with `JS_ThrowError2` again. A slot of its own, `JS_NEST_ERROR` (`JS_NEST_ERROR_MAX`, 2), counts the errors being made, and a third one, which only a bug could start, is thrown as running out of memory (null, uncatchable) and does not recurse. The bound of 2 rests on two facts that `internal/goasm/cmd/cycles` checks on the call graph: making an error runs no JavaScript and reads no interrupt flag (`JS_ThrowError2` reaches neither `JS_CallInternal` nor `JS_ThrowInterrupted`, nor a function that reads the flag), and a collection throws nothing (`JS_RunGC` and `JS_RunYoungGC` do not reach `JS_ThrowError2`, and the job of a `FinalizationRegistry` is queued with memory that does not throw). So the message and the stack of a new error are added with `add_property`, and the names of a stack are converted to UTF-8 by `js_string_to_cstring`, which takes a string and converts nothing.
- **Calls the data never makes**, split off so that the call graph does not see them: the element of a fast array read and written by the generic property paths (`js_get_fast_array_element`, `js_set_fast_array_element`, the fast paths of `JS_GetPropertyValue` and `JS_SetPropertyValue`), a canonical numeric key converted to a number and back (`js_string_to_number`, `js_number_to_string`), ToString of what `ToPrimitive` gives (`js_primitive_to_string`), the array length of a number (`js_number_to_array_length`), and the empty string, taken from its atom.
- **Ropes** are made flat by a loop (above).
- **Two counts of the internal depth** (above): `JS_AutoInitProperty` and `js_define_own_property_ordinary`.

The checks: `unit.c` (see [testing.md](../testing.md#the-c-tree-and-its-native-test-host)) and test262, whose 58 known errors stay the same.

### Go stack room

The generated code runs on the stack of the goroutine that calls it, and the Go runtime ends the whole process, with no panic to recover, when that stack passes its limit of 1 GB (the default on 64-bit targets). The two counts keep the engine far below it. At their largest settings (call depth 10000, internal depth 2000), one VM uses about 65 MB of Go stack, taken from the stack use per level measured on the generated code: a bit over 6% of the limit, and less with the defaults (call depth 5000). Many VMs called from inside each other on one goroutine share one stack, and the hand over of the depths above holds the chain to one limit, so that about 100 of them would be needed to reach 1 GB.

This is a measurement and not a proof. The bound the design started from (5600 bytes for each call level and 4704 for each level of the internal depth, 62.4 MiB at the largest settings) was worked out for the engine before calls were inlined, and has not been worked out again for the code that is checked in. The proof, and a check of it by the generator, are to be redone after the switch to the new engine. Until then the room (15 times what a VM uses) is what holds.

## When the engine fails

C can fail where Go code cannot, and a Go process ends for most of it: a read or a write at an address mapped to nothing prints "unexpected fault address" and exits, since only an address below 0x1000 is a panic by default, and a trap instruction (`ud2` on amd64, `brk` on arm64) is SIGILL or SIGTRAP, which the runtime never lets a program recover. The generated engine is held to this: every way it can fail is a panic that the host recovers, or cannot happen. A VM that failed is broken, as after any panic that leaves through engine frames: it refuses every call but `Close`, and the process and the other VMs go on.

| The C does | What the host sees |
| --- | --- |
| Reads or writes an address mapped to nothing: a wild pointer, or the guard page above the shadow stack | A `runtime.Error` panic that names the address. `Enter` of `internal/gohost` turns on `debug.SetPanicOnFault` for the goroutine, and the `Leave` that matches it puts back what the goroutine had. A pointer that is not canonical on amd64 faults with no address and is a panic too. Below 0x1000, as through a NULL pointer, the panic is that of a nil dereference and names no address |
| Divides by zero (undefined in C) | amd64 raises a divide error, which Go always turns into a panic. arm64 has no such fault and gives 0 |
| Calls `abort` | `host_call` with `HOST_CALL_ABORT` panics with `gohost.ErrAbort` |
| Reaches a trap | None is left in the output. The shadow-stack pass puts a call of `host_trap(sp)` where the C has `__builtin_trap` (the one after the `host_call` in `abort`) and where its own check on a dynamic `alloca` would cross the end of the shadow stack. It panics with `gohost.ErrTrap` |
| Runs out of the shadow stack | The counts throw `RangeError` first. The guard page is the net behind them |

The generator holds this: its checks refuse `ud0`, `ud1`, `ud2`, `hlt` and `int3` in the text and in the decoded code, in llc's object and in the linked binary of amd64, and `brk`, `udf`, `hlt` and `dcps` on arm64, in the text and as words of the assembled object, which the post-link check of arm64 holds the linked code to word for word. `debugtrap` and `ubsantrap` stop the pass, and so does a trap in a register-entry leaf, which has no shadow pointer to call `host_trap` with.

On windows the system writes the state of the CPU at a fault below the stack pointer, and Go keeps less room there than a CPU with AMX needs ([golang/go#81238](https://github.com/golang/go/issues/81238)). The generated engine makes that room itself, so a fault in it is the same panic there (see [Room for a fault on windows](#room-for-a-fault-on-windows)).

Not covered, as in a program written in C: a write through a bad pointer to memory that is mapped changes that memory and nothing tells; a loop that never ends runs until the host interrupts it (see [Polls and interrupts](#polls-and-interrupts)); the runtime ends the process when a goroutine stack passes 1 GB, which the counted depths keep the engine from; and the system may kill the process for memory.

Turning on `SetPanicOnFault` takes two calls of the runtime, 3.5 ns at each entry from Go into the engine (an entry and its `Leave` go from 2.5 to 6.0 ns, and a script that does next to nothing, 1.5 µs, takes 10 ns more), and an entry from a callback inside the engine takes nothing. The scripts of the speed set take 0.3 to 0.8 s and enter the engine a few times, so it cannot be seen there. It sits in `Enter` and not where a pool lends a VM because the setting belongs to the goroutine, and a VM may be lent to a different goroutine each time. `TestFault*` in [testing.md](../testing.md#the-go-host-of-the-generated-engine) run each failure on the real engine.

### Functions without a stack check

Every generated function that calls something starts with Go's stack check. The only functions without one (NOSPLIT) are the three register-entry leaves (`memcpy`, `memmove`, `memset`) and the leaves the Go assembler marks NOSPLIT by itself: 174 on amd64 and 172 on arm64, each a function that calls nothing and has no frame. A fault in one of them becomes a call of `runtime.sigpanic` that the signal handler pushes onto the goroutine's stack where the fault is, and sigpanic's stack check may call morestack, which needs 16 bytes on amd64 and 24 on arm64 above the bottom of the stack and ends the process with "split stack overflow" when they are not there. The leaf's caller passed its stack check, which leaves at least 800 bytes, so the room is the same as for a nil pointer in any Go program.

The generator used to choose more functions to go without a stack check, 446 on amd64 and 456 on arm64: any function whose address was not taken, that made no call through a pointer, was on no cycle of calls, and whose chain of NOSPLIT calls fit the 792 bytes the linker allows with 64 bytes kept free below the deepest frame for the fault. The deepest chain, under `JS_FreeRuntime`, left exactly those 64 bytes, a number read from the runtime of Go 1.27.2, which Go does not promise and which a newer Go could change without any build failing. It does not choose any now (`MarkNoSplit` in `internal/goasm/gen/nosplit.go`), and fails when a function on the list calls anything but a register-entry leaf, or when such leaves call each other in a cycle or take 128 bytes or more below their entry. The post-link check still holds every entry's stack check to the list, so a Go assembler that marks other leaves by itself, or stops marking these, fails the check. The generated code is the code before the change with `NOSPLIT` taken off those functions, and some functions move to the next file.

What it costs, measured on linux/amd64 on an engine made from main at 053d158e with the same list. Callgrind counts the instructions of a render in tifa's `BenchmarkAppCG`. The whole program moves by up to 0.4% between two builds of the same engine, from the work of the young collections, so the cost counted is what the functions that lost NOSPLIT run more: about 3.2 instructions for each check.

### Room for a fault on windows

At a fault, windows saves the state of the CPU on the stack of the thread that faulted, below its stack pointer, before it calls the handler of the Go runtime: a `CONTEXT` with the extended state of the CPU (`CONTEXT_EX`, what XSAVE stores), an `EXCEPTION_RECORD` and the frames of `KiUserExceptionDispatcher`. In the engine that stack is the goroutine's stack: the generated code runs on it, and the shadow stack holds only the frames of the C. Go keeps 4,096 bytes below the guard of each stack for the system on windows (`stackSystem`), so the guard is 5,024 bytes above the bottom of the stack on windows/amd64. How large the state is depends on the CPU: CPUID leaf 0xD gives the XSAVE size of the features the system turns on. On Intel with AMX the tile data adds 8,192 bytes and its config 64 to the 2.7 KiB of AVX-512, `CONTEXT_EX` takes 11.6 to 11.7 KiB, and the system writes 12,816 bytes below the stack pointer in all, as measured on the windows runners of GitHub ([golang/go#81238](https://github.com/golang/go/issues/81238)). Near the bottom of a stack that write goes past the stack into the heap.

The generated engine makes the room itself. In the assembly of windows only (`#ifdef GOOS_windows`), every unified function checks, right after Go's prologue, that its stack pointer less 12 KiB (`RoomBelow` of `internal/goasm/gen/emit.go`) is above the guard of the goroutine, and calls `goasm_room` when it is not: a function that does nothing, with a frame of 12,416 bytes, whose own stack check makes the runtime grow the stack. A function on the NOSPLIT list loads g first. So a body has at least 12,288 + 5,024 = 17,312 bytes below its stack pointer, and a register-entry leaf it calls (`memcpy`, `memmove`, `memset`, which take less than 128 bytes and the return address) at least 17,176. That is 4,360 bytes more than the 12,816 of AMX, and more than 16 KiB.

The room holds while the stack moves. The runtime grows a stack by copying it, which keeps the room. It shrinks a stack only where the goroutine stopped for the runtime at a call, never in the middle of assembly. In the engine that is the stack check of a generated function, which runs the room check again when it goes on, or a callback of the host, which makes the room again before it returns into the engine (`makeRoom` in `internal/cengine/host.go`). A function that returns to its caller leaves the caller at least the room it had itself, since the caller's stack pointer is higher.

What it does not cover: a fault in Go code. A nil pointer in a Go function of the host or of a program has only the 4 KiB of Go below it, as in any Go program on windows, until Go fixes golang/go#81238 (the fix under review keeps the size `InitializeContext` reports plus 2 KiB). A fault in the Go code of the host is a bug of the host, as a fault in the engine is a bug of the engine. The tests that fault in Go code on purpose call `faulttest.Room`, a function with the frame of `goasm_room`, right before the fault. The two cases of `TestRegistry` that fault inside `ByStack` cannot, and skip on windows (`faulttest.Unsafe`).

Linux and darwin are not changed: their code is the same, byte for byte, apart from where functions sit, so tifa's pages, the known test262 errors and the call depth stay as they were. The depth is counted by the engine and does not depend on the Go stack.

What it costs on windows: 4 instructions at each call of a generated function (a `LEA`, a `CMP`, a branch taken and a one-byte no-op), 2 or 3 more in the 176 functions on the NOSPLIT list to load g, and a call of `goasm_room` when a callback returns. Measured on linux/amd64 (AMD EPYC 7B13) with the windows code turned on (`-asmflags=github.com/liustack/quickjs/internal/cengine=-D=GOOS_windows`), 6 rounds that take turns, the median of the changes of each round, with the spread of the rounds:

| Render | Change |
| --- | --- |
| React SSR of `compare/engines` | +0.0% (-0.6% to +1.4%) |
| tifa's shop, the studio workbench page | +1.0% (-0.8% to +3.0%) |
| tifa's shop, the store home page | +2.4% (+1.1% to +2.9%) |
| tifa's shop, a product page | +1.7% (+0.7% to +2.7%) |

The stack of a goroutine in the engine has 12 KiB more below it. A goroutine that runs a tiny script takes 32 KiB of stack in place of 8 KiB, and one that renders React SSR or recurses 2,000 levels deep takes what it took (64 KiB and 1 MiB), 64 goroutines measured with the collector off. The generated code of windows is 36 KB larger (2,662,176 to 2,698,336 bytes, +1.4%).

Tests: `TestRoomCheck` checks the check `funcHeader` writes for each kind of function and that `faulttest.Room` has the frame of `goasm_room`, and `TestRoomCheckAssembles` that the assembler of windows/amd64 takes it before a long body (it loops forever on a branch to a `PCALIGN` in Go before 1.26.11 and 1.27.4, [golang/go#81792](https://github.com/golang/go/issues/81792), which the one-byte no-op avoids). The post-link check of a windows binary holds each unified function to the check and `goasm_room` to its frame: `TestPostLinkFormats` gives a windows binary a check that asks for less, a check without its call and a `goasm_room` 8 bytes short, and requires each to be refused. `TestCallbacksMakeRoom` (`internal/cengine`) requires every callback the generated code calls to make the room last. The fault tests of [testing.md](../testing.md#the-go-host-of-the-generated-engine) run on windows again.

### Which panics break a VM

The Go API marks a VM broken when a panic or a `runtime.Goexit` leaves a call into the engine that has not returned, whatever the panic is. Each call into the engine that the Go API makes adds 1 to `inEngine` of the VM before it and takes it back after it returns, and a Go function that javascript calls counts its own calls from 0 (`enterGo` in `hostcall.go`). `leave` in `entry.go`, which ends every method that runs javascript, and `called` in `hostcall.go`, which ends every Go function javascript calls, mark the VM broken when the count is not back to 0. `outer`, which wraps a call made outside any method that runs javascript, marks it broken when its call did not return, as `run` of `internal/cengine` does. A panic of Go code between two calls into the engine, such as the `MarshalJSON` of an argument, and the panic of a Go function that javascript called, which the engine turns into an uncatchable error and which goes on after the engine has returned, went through no frame of the engine and leave the VM as it is. A fault in the Go code of a Go function that javascript called, outside its calls into the engine, is a panic of that function like any other.

It used to be decided by the panic: a value with an `Addr` method, which `SetPanicOnFault` gives a fault. The runtime gives that only to a fault at 0x1000 or above. Below it, `sigpanic` (`runtime/signal_unix.go`, and `signal_windows.go`) makes the panic of a nil dereference before it looks at `SetPanicOnFault`, and the divide error of amd64 has no address either. So a NULL pointer in the C, which faults in the first page, left the VM usable once the caller recovered the panic, with the engine stopped halfway: the next call ran on that state. In a Go function that javascript called, such a fault in a call the function made became the uncatchable error of a panic of the function, and the engine that called the function went on, though the call the function made had stopped halfway.

An engine left halfway is not entered again. Every call into the engine goes through `toEngine` (`engine.go`), which panics as on a broken VM when the VM is broken or a call into the engine of this level has not returned (`abandoned`), and `jsFreeValue` and `jsFreeAtom` do nothing then. This holds for the defers that free values while the panic goes up, before `leave` marks the VM broken (`Call`, `CallValue`, `SetProperty`, `Then`, the conversions of arguments and values, and the other methods that free in a defer), and for a Go function that recovers the panic of its own call into the engine and goes on. Those frees used to run on the state that a fault, a kill, an abort or a trap left: a fault that had made the context unusable faulted again in the free and took the place of the first panic, and a free on a heap left halfway could change it further. What the values held goes back with `Close`. The reads that a killed VM still answers (`killedReads`) read counters only and do not go through `toEngine`.

Cost: two additions to a field of the VM around each call into the engine, and the check of `toEngine` before it. `BenchmarkCall` and `BenchmarkBuiltinCall` (8 runs each on an M4, darwin/arm64) show no change: the cases of 17 to 32 ns a call move by less than 1 ns, some up and some down. With the check of `toEngine` too, every case ran no slower than main, 1 to 3 ns faster in that run, which is within the noise between runs.

Tests: `TestLowFaultBreaksVM`, `TestHostLowFaultBreaksVM` and `TestNestedLowFaultRecoveredBreaksVM` (`broken_test.go`) give the engine a context at address 0, so that its first read faults below 0x1000, in a call of `Eval`, in a call a Go function makes from javascript, and in an `Eval` of a Go function that recovers the fault. Each checks that the panic names no address and that the VM is broken. They failed before the change. `TestLowFaultInCallFreesNothing` makes the fault in the conversion of an argument of `Call`, with the context still at 0 while the defers of `Call` run, so that a free that entered the engine would fault again and stay counted: it checks that one call is left halfway, not two. `TestHostLowFaultRecoveredRefusesEngine` has a Go function recover the fault of its own call and call into the engine again, which panics as on a broken VM. Both failed before the engine refused a VM left halfway.

### When the system refuses memory

The VM asks the system for memory in chunks (`host_memory_grow`), and a refusal ends the call that needed the chunk with the uncatchable out of memory error, the same as hitting the memory limit. `TestMapRefusedSweep`, `TestMapRefusedAmongVMs`, `TestReleaseRefused` and `TestRemapRefused` (`-tags testhooks`, they fail the calls through `hostmem.SetFault`) hold what that does:

- A script that asks for 13 chunks, with every chunk from the nth on refused, ends in out of memory for every n up to 13. The VM then runs a small script, `Close` returns nil and leaves nothing mapped, and the next VM runs the whole script.
- A single refused chunk mostly goes unseen: the engine asks again for less and the script finishes with its result.
- With 4 VMs on goroutines of their own, each making a new VM for every render, refusing every chunk to one goroutine for 400 ms fails only that goroutine's renders. The other three do not fail once, and the first renders again when the refusal ends.
- Refused `release` calls do not panic: `ReleaseMemory` gives back less. A refused `remap` ends the call with its result or with out of memory, never a panic.

### The size of the shadow stack

The shadow stack is 32 MiB (`-shadow-size-log2=25` of the generator), fixed when the engine is generated. A call from one JavaScript function to another takes none of it: the register interpreter keeps the frames of such calls on [the register stack](#the-register-stack), in memory of the VM, so the arguments, locals and temps of a function no longer cost shadow stack, whatever their number. What still takes shadow stack is a level that goes through C: a native function that calls back into JavaScript (`sort`, `map`, `apply`, a getter or setter, `toString`, a proxy trap, `eval`, a generator), a call with more than 32 arguments (passed in an array, through `OP_apply`), and the recursions of C itself. `TestShadowStackAtDepth` and `TestShadowStackInternalDepth` measure the highest point the stack reached, from the highest word that is not zero. Measured on linux/amd64 and darwin/arm64 at a depth limit of 10000 (amd64 first, arm64 in brackets):

- Recursions of JavaScript calling JavaScript, whatever their frame (a plain call, a method, `call`, a bound function, `new`, a tagged template, 20 to 250 locals, 20 arguments, 100 operands), use 7 to 11 KB of the stack at any depth: what the entry of the run took. A function with 250 locals reaches the depth limit.
- A level through C takes 419 bytes (275) for a call of 100 arguments, about 450 to 610 (390 to 580) for an iterator, a getter, `toString`, `apply`, a spread, a proxy trap or `map`, 737 to 881 (544 to 833) for a setter, a promise executor, a generator or `toJSON`, 1,265 (1,089) for `eval`, 1,713 (1,393) for a `replace` callback and 1,921 (1,809) for a `sort` comparator that sorts again. That last one is the most: 9.6 MB, 28.6% (27.0%) of the stack, since `sort` and the comparator each count a level. A limit of 5000 uses half as much.
- The recursions of C (the parser, JSON, the regexp parser, `flat`, stringify, a chain of proxies) end at their internal depth with under 3% used. A string made of arrays nested 100000 deep takes 13.4% (14.3%).
- So the depth limit of 10000 ends every recursion with more than 70% of the stack left, and the guard page is never reached. A frame of any size fits, since frames are on the register stack.

Under the stack interpreter, up to v0.30.1, every call level took shadow stack, about 1.25 KB plus 16 bytes for each argument, local and operand slot: functions with few locals used 37% to 62% of the stack at the limit of 10000, those with 100 locals 85%, one with 250 locals stopped at 6379 levels, the nested string took 47%, and a render of the 18 pages of the example shop at most 0.85 MiB. Those numbers no longer apply.

## Arguments and results by name

The generated functions read their arguments and write their results by name through Go's FP pseudo-register (`MOVQ a0+0(FP), R12`, `MOVQ AX, ret+24(FP)`), with the names of their Go declarations in `engine_decl_<arch>.go`. That is the way Go promises to reach the arguments of an assembly function ([doc/asm.html](https://go.dev/doc/asm)). The amd64 code used to read them at a fixed offset from SP, written into the bytes of the body: the frame, the base pointer Go saves and the return address, so a function of `$64-32` read its first argument at 80(SP). That offset is how the assembler lays out a frame now (`cmd/internal/obj/x86/obj6.go`), not a promise, and if it changed every call would read the wrong words. The arm64 code already read and wrote them by name.

What changes is the `.s` files of amd64. Each move of an argument or of the result is a Go instruction in place of its bytes (8,039 of them in the 1,375 unified functions), and the data after the code of a function follows a `// data` line. The size bound of a file counts each function as it is written all in bytes, so every function stays in its file and in its place in the binary. The arm64 files stay the same.

Why it is safe: the generated code is the same instructions at the same places. The lowered text keeps each move at the offset Go uses now, so clang lays out the branches around it as before, and the Go assembler encodes the move by name with the same registers and the same displacement. Compared with the engine before, built into a test binary of `internal/cengine` (`-tags goasmkeep`) for each system, every generated function sits at the same address with the same instructions: on linux/amd64, linux/arm64 and darwin/arm64 the same bytes, and on darwin/amd64 and windows/amd64 the same bytes but for the displacements of references to data that moved, which reach the same symbol and offset (the line table of the Go code grew, and the data after it moved). So the speed, tifa's pages, the 33 known errors of test262, the call depth and the timing layouts stay as they were. The post-link check holds each move to where Go's prologue puts the argument area in the binary, as it did before.

What it does not cover: the length of a move depends on its displacement, one byte up to 127 and four past it. If Go laid out a frame differently, a move near 128 bytes would change length and shift the branches over it, which are written as bytes: the arguments would still be found, but the code would not run. The post-link check compares the bytes with each Go release that `scripts/go-versions.sh` runs, and `internal/goversion` stops a Go newer than 1.27. A new patch release of 1.26 or 1.27 is not stopped: such a change in it is found when `scripts/go-versions.sh` runs with it, not when a program builds with it. The arguments of the calls the engine makes stay at 0(SP) and up, where the caller writes them in ABI0, as in Go's own example in doc/asm.html.

With the names, `go vet -asmdecl` no longer reports the 634 functions of amd64 whose result it did not see written, which is what let `go vet` check the generated files ([go vet checks the generated assembly](#go-vet-checks-the-generated-assembly)).

Tests: `TestEngineArgsByName` (`internal/goasm/gen`) decodes the bytes of every generated function of both architectures and fails on any instruction that reaches past the locals of the frame from SP. `TestEmitFPMoves` checks the moves emit writes, and that it refuses an access of the saved base pointer or the return address, of a word that is no argument or result, of the wrong width or through the wrong kind of register. `TestFPMovesAssembleAsLowered` builds a function of each kind of frame (one that calls, a NOSPLIT leaf without a frame, one with a frame and one past an 8-bit displacement) for linux, darwin and windows on amd64 and finds each body in the binaries as it was lowered. Two cases of `TestPostLinkCheck` load an argument from the next word and store the result into an argument word, and the check refuses both.

## go vet checks the generated assembly

`go vet -asmdecl` finds nothing in the assembly of the generated engine, so `go vet ./...` runs it on every commit and in CI, no longer with `-asmdecl=false`. It checks that every argument and result a function names is the one of its Go declaration, at its offset and of its size, that every function with a result writes it, and that every function with a frame has a Go declaration. Before, it reported the amd64 code, which read its arguments at an offset from SP ([Arguments and results by name](#arguments-and-results-by-name)), and four functions without a Go declaration.

The generator writes two things differently for amd64:

- The register-entry leaves `memcpy`, `memmove` and `memset` say `NOSPLIT|NOFRAME, $0-0`, as they already do on arm64. They have no frame and call nothing, so Go writes no prologue for them either way, and NOFRAME is what the check wants of a function with no Go declaration. A leaf with a frame, or one that calls another leaf, keeps the BP that Go saves for it and would need a Go declaration instead. No leaf of the engine is like that now, and `TestEngineAsmDecl` would find one.
- `goasm_room` is in `engine_room_windows_amd64.s`, no longer inside `#ifdef GOOS_windows` in `engine_room_amd64.s`, which every amd64 system built. Its Go declaration is in `room_windows_amd64.go`, so the names of the two files build the function and its declaration on the same system. The room checks of the other files call it only inside `#ifdef GOOS_windows` of an amd64 file, that is on windows/amd64, where it is. The other way, a Go declaration on every amd64 system, would declare a function that is not there off windows.

Why it is safe: the machine code is the same. In test binaries of `internal/cengine` (`-tags goasmkeep`) built before and after, every generated function has the same bytes at the same address, on linux, darwin and windows for amd64 and on linux and darwin for arm64. On linux/amd64 `.text`, `.rodata`, `.gopclntab` and `.data` are the same bytes. The files of arm64 do not change.

What it costs: the check takes a second or two more. With the packages already compiled, `go vet ./...` took 1.1 s without it and 2.1 s with it on an arm64 Mac (darwin/arm64), and 5.4 s and 7.4 s on two cores of a linux/amd64 machine, with Go 1.27.2.

Tests: `TestEngineAsmDecl` (`internal/goasm/gen`) runs `go vet -asmdecl` over `internal/cengine` for linux, darwin and windows on amd64 and linux and darwin on arm64, and wants no report. `TestRoomCheck` checks the TEXT of a leaf without a frame, with one and with a call, and that the file of `goasm_room` builds on windows/amd64 only.

## LR is saved once on arm64

Release: v0.30.3.

On arm64 the generated code no longer saves and loads LR (x30) itself in each function that calls: Go's prologue and epilogue already do it. llc keeps x30 like a callee-saved register, so a function that calls stores it in its frame and loads it back before each return. The generator turns each return into a branch to the end of the function, where the Go assembler writes its epilogue, and the epilogue of a function that calls loads LR from 0(RSP), where Go's prologue saved it (`cmd/internal/obj/arm64/obj7.go`, the `ARET` case of `preprocess`). llc's store and load of x30 were dead, about two instructions for each call. The lowering drops them (`internal/goasm/gen/arm64_lr.go`): a `str` or `ldr` of x30 goes, and an `stp` or `ldp` that pairs x30 with another register keeps that register as a `str` or `ldr` at its offset. The amd64 code has no LR and stays the same, byte for byte.

Why it is safe: the lowering proves it on its own output and stops the build when the proof fails. No instruction left names x30, and no instruction left reads, writes or takes the address of a byte of a slot it dropped, so on every path the slot was written only from x30 and read only into x30, both gone. x30 itself is read only by Go's `RET`, after the epilogue loaded it. A function that makes no call is a leaf to Go, whose epilogue does not load LR, and then nothing in it writes x30, which holds LR from the entry to the return. Nothing in Go's runtime reads llc's slot: the unwinder that a stack copy, a signal's traceback and a callback into Go go through takes the return address of a frame from 0(RSP) of that frame (`runtime/traceback.go`, `unwinder.resolveInternal`), and `morestack` runs before the function's own frame exists, with the caller's LR passed in R3 (`runtime/asm_arm64.s`). The slot's 8 bytes stay in the frame, so every frame has the size it had, the call depth and the shadow stack do not change (the depth floors of `TestRegvmDepth` and `TestCCallDepth` give the same depths, and the shadow frame of `JS_RegvmRun` is still 176 bytes), and llc's text, the pass's report and the register facts are the same files as before.

What it changes in the generated files of arm64, against the same C before: 1,364 of the 1,570 functions lose 2,485 instructions, none names x30 any more, the frame of every TEXT is the same, and the `.s` files are 0.40% smaller (11,059,028 to 11,014,478 bytes). What it gains: see [performance.md](../performance.md#lr-saved-once-on-arm64).

A negative build shows the proof works: `GEN_DROP_LR_PAIRS=1` also drops the other register of a pair that holds x30, and the build stops on the first function that loads that register back. `GEN_DROP_LR_PAIRS=unchecked` skips the proof and writes a package marked as a negative build, which needs `-tags goasmnegative` to compile, and the engine's tests fail on it. `-release` refuses both.

Tests: `TestLowerARM64EngineLR` (`internal/goasm/gen`) lowers every form llc writes (a pair that allocates the frame, a load that frees it, x30 first or second in a pair, a single slot, a function that calls nothing) and checks that no x30 is left, the other register keeps its offset and the frame keeps its size. `TestLowerARM64EngineLRRefused` refuses x30 as a w register, twice in a pair, in arithmetic, with a writeback form other than the frame's own, through another base register and beside the frame, a load of x30 from a slot it was never stored to, and a slot that another load, a byte load, another store, a pair or the address of a tuple reaches, and the address of a tuple that is read past a label or where a branch goes, that a branch reads, that reaches an indirect branch or a label outside the function, or that lives in a register a register-entry leaf keeps across a call. `TestLowerARM64EngineLRTuple` takes a tuple spill beside the slot and refuses one over it. `TestLowerARM64EngineLRTuplePaths` follows the address past branches and labels: it takes one written again on both paths of a branch, one that reaches a call through a branch or a loop, and one that a path returns with, and refuses one that reaches the slot where a branch goes, and one a register-entry leaf (`memcpy`) takes as an argument, in a straight line or past a branch. `TestLowerARM64EngineLRNegative` checks both values of the negative build and `TestLowerARM64EngineLRLabel` that a label whose name ends in `sp` is no use of the stack. `TestDropLRPairsFromEnv` and `TestReleaseError` (`cmd/engine`) check the switch.

## Results only in registers

Release: v0.30.5.

Since v0.29.6 a direct call of a generated function takes the result from the registers the callee returns it in. Two more steps of the generator finish that path:

- A call through a pointer takes its result from registers too. Before, it loaded the result back from the Go stack, where the callee had stored it a few instructions earlier. 215 calls through a pointer on amd64 and 214 on arm64 return a result, and none of them loads it any more.
- A generated function that no Go code calls stores no result to the Go stack. Only generated code calls it, and that code reads the result from registers. Go code calls 91 functions of the engine. The other 1,489 of 1,582 on amd64 and 1,483 of 1,576 on arm64 store none: 1,181 of them return a result, 1,646 result words on amd64 that each return no longer stores.

Why it is safe:

- A pointer reaches only a lowered unified function. Every such function stores its result from the registers of its type and then runs only Go's epilogue, which touches BP and SP (FP and LR on arm64), and the Go runtime never stops assembly at a point it chooses, so the registers still hold the result where the caller reads it. The generator's README gives the lines of Go 1.26.6 and 1.27.2 this rests on. The generator refuses a function pointer, taken by the code or held in engine_rodata, to anything else: a host callback (Go code), a callback of the generator, a register-entry leaf or a place inside a function (`CheckPointerTargets`), and both post-link checks refuse it again in the binary. A stub may be a target, since it calls `goasmMissing`, which panics: both checks hold every stub to that.
- The registers of the result are the ones llc uses. On amd64 the check holds the registers llc reads the result of each call through a pointer from to the ones every lowered function of that result type returns it in, from their probes. On arm64 the lowering holds every return in llc's facts to x0, x1 or d0, by the type.
- The list of the functions Go code calls is made from the sources, not by hand (`internal/cengine/gocalls.txt`, `go run ./internal/goasm/gen/cmd/gocalls`): every Go file and every hand-written assembly file of the module, the modules in it too, as a call, a value, a `//go:linkname` or a `#define`. `TestGoCallsList` fails when Go code calls a function the list does not have, and when the list has one Go no longer calls. A name too many only keeps a result store.
- A function off the list is declared to Go without a result, so Go code that reads its result does not compile, and `go vet -asmdecl` holds its TEXT to the size of its arguments. Both post-link checks take no result store at its returns, still hold the registers llc returns in to the ones its callers read, and refuse a call that loads a result from the Go stack where it could reach such a function: a direct call of one, and any call through a pointer.
- Nothing else moves. Every TEXT keeps its frame (only the size of the arguments and results changes), the shadow frame of `JS_RegvmRun` is 256 bytes on amd64 and 176 on arm64 as before, the seven depth floors of `TestRegvmDepth` give the same depths and `TestCCallDepth` passes. A packed function whose block no Go code makes loses its Go wrapper (24 to 2 wrappers on amd64, 218 to 9 on arm64) and keeps its plain name.
- The poison build stores every result and loads every result back, as before, and a build without `-go-calls` (the `-src` builds of the generator's tests) stores every result.

What it changes in the generated files, against the same C: the `.s` files are 0.74% smaller on amd64 (11,644,354 to 11,558,760 bytes) and 0.42% on arm64 (11,120,506 to 11,074,094). What it gains: see [performance.md](../performance.md#results-only-in-registers).

Tests: `TestCheckPointerTargets` refuses a pointer to a host callback, a callback of the generator, a leaf, nothing or a place inside a function, in the code and in engine_rodata, through aliases too. `TestCheckCases` (amd64, from hand-written llc code) refuses the address of a leaf or of a host callback, a call through a pointer whose result load is there or missing against its record, and llc taking such a result from another register, and for the functions that store none: a record that says otherwise either way, a return llc gives in another register, and a direct call or a call through a pointer that loads the result. `TestCheckARM64FunctionPointer`, `TestCheckARM64Rodata`, `TestCheckARM64ICallRegResult`, `TestCheckARM64NoResult` and `TestCheckARM64Stub` do the same on arm64, and `TestLowerARM64EngineFacts` and `TestLowerARM64EngineNoResult` hold the lowering. `TestGoCalls` runs the scanner over a small module (calls, values, closures, shadowed names, fields, keys, imports of the same name, tests, other packages, nested modules, linkname, macros and assembly of other packages), and `TestPostLinkCheck` generates a C file with `-go-calls` naming one function, checks the declarations, runs the post-link check on it, refuses the same binary to a check that wants every result stored, and refuses a list with a name the engine does not have.

## A collection asked for while objects are freed

`JS_RunGC` and `JS_RunYoungGC` return at once, doing nothing, while the engine frees objects, that is while `gc_phase` is not `JS_GC_PHASE_NONE`: in `free_zero_refcount`, which frees the objects whose count reached zero, in `free_zero_refcount_first`, which frees at once an ordinary object whose count reached zero (see [objects-and-shapes.md](objects-and-shapes.md)), in `gc_free_cycles`, which frees the cycles a collection found, and in both as the runtime is freed. The collection the threshold asks for when an object is made goes through `JS_RunGC`, so an object made then starts none either. The threshold does not move, and it is checked again when the next object is made after the free.

The host runs code there: the finalizer of a class it made with `JS_NewClass`, and `host_release` for a function of `JS_NewHostFunctionRelease`. The collector keeps its state in the runtime (the list of objects whose count reached zero, the list of the cycle being freed, the phase), and a collection started from a finalizer used that state again while the free that called the finalizer was in the middle of it. In `free_zero_refcount` the inner collection entered `free_zero_refcount` a second time, which `JS_NEST_FREE` stops with an abort, and a young collection first freed every object on the list, the one whose finalizer was running among them. In `gc_free_cycles` the inner collection restarted the list the outer one was going through and freed objects it then read again: AddressSanitizer reports a read of freed memory. The engine's own finalizers start no collection (`cycles.sh` checks `free_zero_refcount` against both), so only a host written in C, such as the native test host, could reach it. The Go API cannot: it makes no class, and the only Go code that runs during a free is `gohost.Release`, which clears the handle and runs no code of the user.

Upstream QuickJS and quickjs-ng have the same entry points, with no check. Bellard fixed one path of the engine that reached a nested collection, a `FinalizationRegistry` job queued with memory that could throw (bellard/quickjs#494, `5022f2b`), and liustack/quickjs queues that job with memory that does not throw as well. CPython and Lua do what this change does: `gc.collect()` returns 0 while a collection runs, and Lua stops its collection steps and `lua_gc` while a finalizer runs.

Why it is safe: a skipped collection frees nothing, and what it would have freed is garbage still, freed by the next collection. The threshold does not move and is checked again at the next object made after the free, which starts the collection when the heap is still past it. A full collection that did the free sets the threshold again at its end, as it always does. A host that called `JS_RunGC` from a finalizer gets no collection and can ask again after the call that freed the object has returned. A finalizer may also call `JS_ComputeMemoryUsage` and `JS_DumpMemoryUsage`, which read the list of live objects, and the free does not touch that list. What a finalizer must still not do is QuickJS's rule: run JavaScript, free the runtime, or make an object while the runtime is freed, which leaves that object in use when the runtime is gone.

What it costs: nothing on a path that runs often. The check is in `JS_RunGC` and `JS_RunYoungGC`, and in the copy of `JS_RunGC` that `js_trigger_gc` puts into `JS_NewObjectFromShape` and `JS_CallInternal_block`, where it comes after the test of the threshold, so an object made below the threshold runs no new instruction. The generated engine differs only in those four functions, and the frame of `JS_CallInternal_block` is the same (amd64 $496, arm64 $504). Counted with callgrind on tifa's four apps (shop, store, mui, bench), the instructions of a render change by -0.00%, +0.10%, -0.01% and +0.03%, and those of `JS_CallInternal_block` by +0.03% to +0.07%, from its code laid out again around the new block. Most of the +0.10% of store is the collector of the Go runtime, outside the engine. The 16 pages of those apps give the same HTML.

Tests: `test_gc_in_free` of `unit-white` runs each of `JS_RunGC`, `JS_RunYoungGC`, an object made with the heap past the threshold, and `JS_ComputeMemoryUsage` with `JS_DumpMemoryUsage`, from a finalizer of the host and from `host_release`, in nine kinds of free: the last reference to an array dropped by the host, the last reference to each young object and to each old object dropped by the host (one by one, through `free_zero_refcount_first`), a cycle in `JS_RunGC`, a cycle in `JS_RunYoungGC`, an old array whose last reference a young cycle held (it waits for the end of the young collection and goes in `free_zero_refcount`), the value of a `WeakMap` whose key died (`gc_remove_weak_objects`), the value of a `WeakMap` whose key is in a cycle (`gc_ephemeron_prune`, then `gc_free_cycles`), and the runtime freed with a pending exception and a cycle through the global object. `JS_GC_RUN`, which is empty in the engine, counts in `white.c` the full and the young collections that pass the check of the phase. Each case checks that every object was finalized and every function released once, that no collection ran during the free but the one the case started, that the next object after the free starts the collection the threshold asks for when the free did not set the threshold again, and that the runtime then collects, works and frees with no block left. Each case runs in a process of its own, the test started again with the case as its arguments, so that it starts with no lock of the host held and with its own watchdog. A finalizer must not make an object as the runtime is freed, so that case is left out, which leaves 35. Before the change 26 of them failed: every case that starts a collection. The engine aborted in all the kinds of free but a cycle in `JS_RunGC` and the value of a `WeakMap` whose key is in a cycle, where the plain build crashed with a segmentation fault and AddressSanitizer reported freed memory read and written in `gc_free_cycles`. The nine cases of `JS_ComputeMemoryUsage` passed before the change too.

## Polls and interrupts

The Go runtime stops a goroutine, for a collection or to run another one, only where a function checks its stack, and it never stops Go assembly anywhere else. A loop of the engine that calls no function would hold up every collection of the process for as long as it runs. The C takes part only in the interpreter, which counts its bytecode itself (below).

- The counter is a word of the shadow-stack region, 384 bytes from its base (`gen.PollCounterOffset`), which the code finds by clearing the low bits of its shadow pointer. Each loop keeps the count where that costs fewer instructions, by LLVM's estimate of how often each of its blocks runs: in a register, read where the loop is entered and written back where it is left, and written back and read again around each call in the loop that may poll, or in memory, read and written at each count. So a loop that calls a function that may poll on most of its runs counts in memory, and so does a loop that runs in chunks (below), which counts once a chunk, and a loop whose hot code already needs about all the registers. An inner loop counts in the register of the loop around it, if that one has one.
- Each edge that goes back in a loop counts one, but in the interpreter.
- The interpreter, `JS_RegvmRun`, counts 32 (`POLL_WEIGHT`) in memory at its entry, at each call, at each jump that does not go forward, at each return from a `finally` block (`GORET`), at each catch of an exception (`rv_unwind`) and at each `POLL`, the op that an `OP_nop` becomes. The C marks these places (`poll_count` in `cutils.h`), and the pass puts a count at each mark and none on the way back into the dispatch, which stays short enough for llc to copy into the end of every handler. Between two counts the interpreter only goes forward in the bytecode. The compiler puts an `OP_nop` into each path forward of more than 127 instructions (`insert_polls` in `quickjs.c`), and the bytecode of every function is checked before it can run, the compiler's and what `JS_ReadObject` reads (`check_polls`): no path between two counts is longer than 128 instructions (`POLL_RUN`), every opcode is one the interpreter has, every jump lands at the start of an instruction, and the last instruction does not run off the end. `JS_ReadObject` fails on other bytecode with `SyntaxError: invalid bytecode`. `OP_ret`, which takes the place to go back to from the stack, goes only to the instruction after an `OP_gosub`: `check_polls` marks those places of each function in a bitmap, one bit for each byte of its code (only for a function with an `OP_gosub`), and `OP_ret` to any other number throws `InternalError: invalid ret value`, so that bytecode read with a number of its own on the stack cannot take the interpreter into the middle of an instruction or onto a path the check did not follow. So a count of 32 stands for at most 4 instructions of bytecode, a few hundred machine instructions as in the C, and at the default interval a poll comes within 40,000 instructions of bytecode, where it came within 10,000 when the dispatch counted each one. In loops it comes sooner than before: a loop of fewer than 32 instructions counts more than one for each. A Go test (`TestRegvmJumpsCount`, see [testing.md](../testing.md#the-go-host-of-the-generated-engine)) holds `JS_RegvmRun` to this: `pc` moves only a constant step forward, by a jump that counts first when it goes back, or at a few places the test lists.
- A loop needs no count of its own when LLVM's scalar evolution proves it short: innermost, calling nothing, and at most 256 instructions for each entry. Whatever enters it again counts. Any other innermost loop that calls nothing runs in chunks of that size, and the end of each chunk counts the whole chunk. So a count stands for at most a few hundred instructions, and the interval bounds the time between two polls.
- `memcpy`, `memmove` and `memset` of a length that may be over 256 KiB go through helpers that do 256 KiB at a time and count each piece. These functions have no shadow pointer and no count.
- The pass checks its output on its own: in each function, with the blocks that count or poll taken out and the back edges of the loops it proves short, no cycle is left. In the interpreter the edges into its dispatch are taken out too, its entry must count, and each mark must come right after a count of its weight. And each count takes at least 1 and polls whenever it is 0 or less: its branch tests that and calls `host_poll` on the side taken. And it follows the count through each function: each count takes from the count as it stands, each write to the counter writes the count as it stands, and each call that may poll and each return find it in memory. A count kept in a register that a callee did not see, or that is written over what a callee counted, would let more than the interval of counts pass between two polls.

`host_poll` sets the counter back to the interval of the VM (`SetPollInterval`, 10000 by default). The interval does not change the speed, only how often a poll comes.

`JSRuntime` holds an interrupt flag, whose address `JS_GetInterruptFlag` gives the host. `Interrupt` in Go records the time, and the next `host_poll` writes 1 into the flag. Only the goroutine that runs the script writes the flag, so the C reads it with plain loads. The native test host does the same with threads: a stop asked from another thread (`host_interrupt`, or the thread that ends a test after 120 seconds) waits in the host, and the engine, built for that host with `JS_HOST_POLL`, calls the host's `host_poll` at each read of the flag (`poll_flag` in `cutils.h`), where the host writes it on the engine's thread. Built for Go, `poll_flag` is a plain read, and the generated code is the same as without it. Only a call that runs a script is killed. The host enters the engine for it with `EnterScript`, and for anything else, a collection, a memory report or a release of memory, with `Enter`, whose polls only set the flag: a watchdog that calls `Interrupt` during a long collection does not break a VM that runs nothing of a page. What the outermost entry is decides for the calls inside it. `EnterScript` with a timeout also sets a deadline on the monotonic clock, and the first `host_poll` past it acts as `Interrupt` at the deadline would have: the flag is set and the grace counts from the deadline. An `Interrupt` later than the deadline does not move it on: the grace counts from the earlier of the two. A script that a callback runs inside it has the time that is left.

`host_poll`, `host_trap` and the abort find their VM by the shadow pointer alone. `gohost.New` writes the VM's id and its complement in the first 8 bytes of the shadow stack, and the host rounds the pointer down to the size of the stack, reads that header and checks that the VM it names has its stack there: no lock and no write to memory other VMs read, so that VMs polling on many cores do not slow each other. The host's scratch and the engine's frames start above the header. The VMs by id are in a table of atomic pointers (`internal/idtable`), and the id of a closed VM goes to a later one.

Measured on linux/amd64 (an AMD EPYC 7B13 on GCP, Go 1.27), each script pinned to one core, against the same engine built with `-poll=false`:

- Collections. While a tight loop runs (a `for` loop of the interpreter, typed array searches, `fill` and `copyWithin`, regexps, string searches, `repeat`, the sort of a typed array, react), a collection waits at most 0.33 ms for the engine to stop, where it waited up to 1.3 s without polls. Scripts that allocate a lot (`JSON.parse` of 2Mi numbers, a sort with a comparator) have rare waits up to 2.6 ms, with the 99th percentile under 0.25 ms. Straight code of the interpreter, functions of 3000 statements with no loop, where a poll can take up to 40,000 instructions of bytecode to come, makes a collection wait at most 0.1 ms.
- Interrupt, with `GOMAXPROCS=1`, 100 ms into the script: a `for` loop, regexps, typed array searches, `fill`, `copyWithin`, react and straight code of the interpreter stop within 0.3 ms (straight code within 0.15 ms), and a kill comes within 0.2 ms of the end of the grace. The stop comes later while the engine works where it reads no flag: a collection of the engine's own heap, which the allocation of the error may start (about 18 ns for each element of the arrays the heap holds: 19 ms with two arrays of 1Mi numbers, so a sort of 1Mi numbers stops after 8 to 19 ms), or a long loop such as `Array.prototype.slice` (about 40 ns for each element).
- Speed, with the other hyperthread of the core idle, as the median over 8 code positions: react and the render scripts take 5% longer, fib 4%, a `for` loop 14%, `JSON.parse` of 2Mi numbers 17%, and with the text built first 12%, the sort of a typed array 10%, string searches 8%, and regexps within 2%. Typed array `indexOf` takes 25% longer, `repeat` up to 9%, and `fill` and `copyWithin` within 1%. A tick on every run of the loops that now run in chunks would cost react 6% and regexps 20% more.

## The register interpreter

Release: v0.30.2.

JavaScript runs in a register interpreter, and the stack interpreter of QuickJS is gone. QuickJS keeps the values an instruction works on on a stack: each instruction pops its operands and pushes its result, and a read of a variable copies the value onto the stack. The register interpreter keeps them in numbered slots of the frame of the function (registers), and an instruction names the slots it reads and writes. So a read of a variable needs no instruction, a compare and the jump after it are one instruction, and a call from one JavaScript function to another runs in the same loop and makes no call of C. The compiler, the bytecode and its format are as they were: a function is still compiled to the bytecode of QuickJS, and that is what `JS_WriteObject` saves and `SharedBytecode` shares. The register code is made from it in memory, when the function is first called.

Where it is:

- `engine/regvm.h` has the frame and the list of ops and includes the rest. `engine/regvm-func.h` has the register code of a function (`RVFunc`) and `rv_entry_fast`, the test a call makes.
- `engine/regvm-pass.h` and `engine/regvm-fold.h` convert a function (the pass). `engine/regvm-run.h` is `JS_RegvmRun`, the loop, with the returns and the unwinding of an exception (`rv_unwind`). `engine/regvm-entry.h` has the register stack and the entries into the loop.
- The ops are in `engine/regvm-ops-*.h`, one file for each area, listed in `engine/regvm-areas.h`. Each file is read once for each part (the names, the cases of the pass, the handlers), so an op is written in one file. `engine/regvm-bodies.h` has the handlers of upstream's interpreter that the loop still runs for the ops that have no register form of their own (below).
- `JS_CallInternal` in `engine/quickjs.c` is no longer an interpreter. It converts a function that is not converted yet, enters `JS_RegvmRun` for a function of bytecode, and sends a C function, a bound function or a proxy to its class.

### How a function is converted

The first call of a function of bytecode converts it (`rv_convert`). The call is made by `JS_CallInternal`, by the test of a call from C (`rv_entry_fast`) or by a call op of the loop, so the first run of a function is in the loop too, the top level of a script among them. The register code (`b->rv` of its bytecode) is freed with the function. A conversion runs no script and makes no object. It allocates from the heap of the VM, working in one scratch block that the runtime keeps from one conversion to the next ([allocator.md](../allocator.md#layers)). When it runs out of memory, that call throws the out of memory error and the next call of the function tries again. The pass refuses only code no compiler makes (see [Catch offsets and jumps stay in their function](#catch-offsets-and-jumps-stay-in-their-function)), and each call of such a function throws.

The pass reads the final bytecode of the function in order, with a model of the stack of QuickJS. Each entry of the model is one of three things: a temp (a slot of the frame that holds a value the entry owns), a local, an argument or `this` read where it is, or a constant read where it is. A read of a variable or a constant emits nothing and takes no reference. The instruction that uses it names the slot, and an op that needs an owned value takes the reference itself. Before a store to a local, each entry that still reads it is copied into a temp, and a local that a closure captures is copied at once, before anything can run that writes it. At the end of a block every entry is in the temp of its depth, so that all the ways into a block agree. A store right after the instruction that made the value makes that instruction write the local (the ops with an `L` in the name), and a call whose result is dropped drops it (the ops with a `D`).

### The frame and the window of a call

```
F[-fofs]              func
F[-fofs + 1 ...]      the arguments
F[-(var_count + 1)]   this
F[-var_count ...]     the locals
F[0 .. 2]             the header: caller, return pc, register code, constants, the slot of the result, argc, closure variables
F[3 ...]              the closure state, only when locals are captured
F[temp0 ...]          the temps
```

An operand is a signed byte, a slot counted from F, so every handler reaches func, the arguments, the locals and the temps from one pointer. A frame of more than 128 slots uses the ops with a 16-bit slot (`MOVW`, `SETLW`, `CHKLW`, `LOADKW`, `JMPW` and `CLW`, `engine/regvm-ops-wide.h`). A frame has at most 124 temps. A stack deeper than that is folded into Arrays, as [the limits of a function](#the-limits-of-a-function-in-the-register-loop) say.

A call op names a window, the temps of the caller where the old stack has its operands: func, then the arguments. The frame of the callee starts at the window, so the arguments are in place and nothing is copied. Its `this` and locals go above them. When the callee is a function with register code of the same realm, and the checks of a call pass (the interrupt flag, a pending uncatchable error, the call depth, room on the register stack), the op writes the header and goes on in the same loop with `F` and `pc` of the callee. A callee called with more arguments than it has parameters, or one that reads its arguments, takes the slow entry (`rv_enter_args`): the extra arguments stay below func, in order. Anything else is called out of the loop (`RV_CALL_OUT`): a C function directly, `call` and a bound function with no bound arguments are taken apart and made as the call they stand for, `hasOwnProperty.call` and `charCodeAt` are answered in place ([charCodeAt answered in the register loop](#charcodeat-answered-in-the-register-loop)), and the rest through `JS_CallInternal`. A call counts one level of call depth, as before. A return frees func, the arguments, `this` and the locals, each only if its tag says it has a reference count (`RETN`, for a frame of up to 8 slots from func to the last local, frees them in straight code), writes the result into the slot the caller named, and goes back to the return pc. A tail call is a call followed by a return.

A call from C (`js_call`, `JS_Call`, a callback of a built-in) runs `JS_RegvmRun`, which makes an entry frame: func, the arguments and `this` copied with a reference. Its return goes back to C. A generator or an async function runs as the entry frame of a run of its own, and its state is moved between its heap frame and the register stack at each suspension and resume (`engine/regvm-ops-gen.h`).

### The register stack

Frames live on a register stack of their own, not on the shadow stack: a call from one function of the loop to another takes none of the shadow stack and no Go stack. A frame never moves, since the references to its closure variables and the arguments of a C function point into it, so the stack is not one block that grows. It is a list of segments from the heap of the VM, the first of 32 KiB, each next twice as large up to 256 KiB (or more for a call that needs more). A call whose frame does not fit in the segment starts the next one, and its return steps back. The segments count in `MemorySize` and under the memory limit, but not toward the threshold of the collector, which cannot free them. When the outermost run returns, the first segment is replaced by one as large as the run needed, so that the same page again steps onto no next segment (`engine/regvm-entry.h`). The stack bounds nothing: how deep a recursion goes is set by the call depth and the memory, as before, and no recursion stops sooner.

### Exceptions, stack traces, polls

Each instruction that can throw has an entry in the pcmap of the function: where the instruction ends, the pc of the old bytecode that names it, so that lines, columns and the stack of an error are the ones QuickJS gives, and the mask of the temps that own a value across it. `rv_unwind` walks the temps of the mask from the top, frees each, and stops at a catch offset. At a catch the exception goes into the temp of the offset and the loop goes on at the catch. A frame with no catch closes its closure variables, frees its slots and the walk goes on in its caller at its call. An uncatchable error passes every catch. A stack trace walks the frames through their headers.

The loop counts toward the next poll at its entry, at each call, at each jump that does not go forward, at each return from a `finally` block and at each catch, and the compiler still holds the bytecode to a bound of instructions between two counts. It reads the interrupt flag at the calls, the jumps and the places it counts. [Polls and interrupts](#polls-and-interrupts) has the rule and the tests.

### The ops

There are about 200 ops and the returns for each size of frame (`RV_OP_COUNT`, `engine/regvm.h`). In groups:

- Moves, constants, arithmetic and compares, each with the forms for a constant operand (`K`) and for a result into a local (`L`). A compare and the conditional jump after it are one op (`JLTF`, `JEQT`, `JSEQKF` and the like), and so are the cases of a `switch` on strings (`CASES`) and `local += value` (`ADDLOC`).
- Reads and writes of properties and elements (`GETF`, `PUTF`, `GETEL`, `PUTEL`), objects, globals, `in` and `instanceof`.
- Calls and returns: `CALL`, `CALLM` and `CALLML` for a method, each with a form that drops the result, `CALLS` for a call that copies its last arguments itself, `NEW` for a construct call, and `RET`, `RETN` and `RETCT` for the returns of a frame with and without closure variables.
- Closures, `try`, `catch` and `finally`, generators, `arguments`, `with` and direct `eval`.
- An old instruction that is rare or long gets no op of its own. The pass puts its operands in the temps where the old stack would have them (the window of the op) and the loop runs the handler of upstream's interpreter on them: `W_OBJECT_LIT`, `W_ARRAY_FROM`, `W_FOR_IN_START` and the other `W_` ops, and `OLD` for the rest. [upgrading.md](../upgrading.md#taking-upstream-quickjs-into-engine) says how a commit of upstream QuickJS that changes such a handler is taken in.

The table of `engine/test/regvm/opcodes.txt` has a line for each opcode of QuickJS that says which of these it takes: an op of its own, the model of the pass alone, a window op, `OLD`, or none for an opcode no function that runs has.

### Why it gives the same results

The pass changes where a value is kept, not what is done with it. Instructions run in the order of the old bytecode. An op that reads or writes a property, calls, converts or compares does it with the functions of the stack interpreter, and the handlers of the window ops and `OLD` are its own handlers. A value is read in place, without a reference, only where no code that can run before its use can write its slot (the rules are in [A key in a local is read without a reference](#a-key-in-a-local-is-read-without-a-reference) and the sections next to it). Each way out of an instruction that can throw leaves every owned temp named by its pcmap entry, so the unwinding frees what the stack interpreter freed.

What this is checked against is what the stack interpreter gave. The goldens of `engine/test/regvm/golden` were recorded from it at the last commit that had it (`deb70815`), for the cases where the two loops agreed. Every script of the corpus gives, byte for byte, its output, its result, its exception and stack, the exceptions of its jobs and the objects the runtime still holds when it ends and after a collection, run three ways (as is, with the fused opcodes of the compiler off, and as strict code). The same holds for the programs of `rvgen` of 1,000 fixed seeds in each mode, and for the places where a throw is injected (below). test262 keeps its 33 known errors, and the HTML of the pages of tifa's shop, MUI and bench apps is the same.

What a program can see is the same but for these, which [CHANGELOG.md](../../CHANGELOG.md) lists for users. A function the register loop cannot run is refused at compile time (above, and [the limits of a function](#the-limits-of-a-function-in-the-register-loop)). A recursion through big frames goes as deep as the call depth allows. `f.call(...)`, `call.bind(f)` and a bound function make the call they stand for ([errors-and-stacks.md](errors-and-stacks.md#calls-through-call-and-bound-functions-leave-no-line-in-the-stack)). A `for-of` over a plain array does not call `next` for each element, and a loop of `charCodeAt` calls stops at its jump back. A VM holds more memory (next).

Render times in tifa, one warm VM on one core, against the stack interpreter, the geometric mean of the medians of the pages of each app: on linux/amd64 (an AMD EPYC 7B13 with 4 cores) 0.701 of the time on the React page, 0.858 on the shop's storefront, 0.888 on its workbench and 0.864 on MUI. On an Apple M4 (darwin/arm64) 0.767, 0.800, 0.834 and 0.825. The HTML is the same everywhere. [performance.md](../performance.md#the-register-interpreter) has how these were measured, the reading against v0.30.1 and the numbers of the changes since.

## Where the interpreter and the regexp matcher sit

After Go's prologue every generated function has a `PCALIGN $16`, so its body starts on 16 bytes and moves within its lines of 64 bytes whenever code linked before it grows. The body of `lre_exec_backtrack` starts at 16 bytes into its line, the fastest place measured. The no-ops run once per call: 69 bytes. The post-link check holds each body that has a place to it and the padding before it to no-ops, and a test builds bodies 8 bytes off their place and sees the check refuse them. The stack interpreter, `JS_CallInternal`, had a place too, 40 bytes into its line (0 until a JSValue was copied in two moves of 8 bytes, see [below](#how-a-jsvalue-is-copied)), and 66 bytes of no-ops. The register loop `JS_RegvmRun` has none: its place is not measured yet (see [performance.md](../performance.md#where-to-continue)), so its body starts on 16 bytes after its `PCALIGN $16` and moves with the code linked before it.

The constant pool and the jump tables a function keeps after its code are aligned by `.p2align`, which counts from the start of the function. A body at 40 bytes into its line starts 8 bytes past a multiple of 16, so the pool of the interpreter used to sit 8 bytes off 16 where it runs. Nothing read it with an instruction that needs 16 bytes (a `paddd` or a `movdqa` with the pool for its memory operand faults on a pool off 16), so nothing failed. A build in which LLVM does (a profile-guided one made 19 such reads in the interpreter) died with SIGSEGV at the positions that keep the body 8 bytes off. The generator now puts a function in its lowered object at the place its body takes in the binary (`.p2align 6` and `.skip 40` for the interpreter, `FuncPlace`), so the alignment of every pool and table holds in the binary. For `JS_CallInternal` that moves its pool 8 bytes in the body: the only generated file that changed is the one that holds it, in the displacements of the jump table and the 8 bytes of padding. The post-link check on both architectures requires every constant pool and table to sit at a multiple of its alignment in the binary, and `TestSampleRuns` runs functions that read their pool with `paddd` and `pxor` from bodies at 8, 16 and 40 bytes into a line (`testdata/run/vecpool.c`). The `front:` positions of `xform` that are not a multiple of 16 (8 and 24) move the body and its pool together, so a build whose interpreter reads its pool with such an instruction must not be run at them. Generate it with `-align64 JS_CallInternal:48` or `:0` for those two places, which keeps the pool on 16 bytes. (`JS_CallInternal` was the interpreter then, and the loop is `JS_RegvmRun` now.)

A change elsewhere in the engine moves the body of the matcher by whole lines only. It still changes their speed somewhat, as other code and data move: see [performance.md](../performance.md#code-positions) for the numbers and for how the code positions of a measurement work with the fixed places.

The register loop `JS_RegvmRun` dispatches with a computed goto, as upstream's interpreter did: each handler ends with `goto *rv_table[*pc++]`, and llc copies that short block into the end of every handler (`DispatchCopies` in `internal/goasm/gen/poll.go`). An earlier patch of the ccgo engine turned it off for native builds, and with it off alone the V8-v7 score fell to 0.91 (gcc 15.3) and 0.88 (clang 22.1.8) of unpatched C ([numbers](../history.md#native-c-patch-cost)). Keep it on.

## How a call sets and frees its values

This section, [The end of a call skips the values with no reference count](#the-end-of-a-call-skips-the-values-with-no-reference-count) and [A call sets its locals eight to a turn](#a-call-sets-its-locals-eight-to-a-turn) are about the loops of the stack interpreter, `JS_CallInternal`, in the releases that had it. The register interpreter ([above](#the-register-interpreter)) sets the locals of a frame to `undefined` with `rv_undefined` and frees a frame with `rv_exit_scan`, each slot by its tag, in straight code for up to 8 slots.

`JS_CallInternal` sets each local variable of a bytecode function to `undefined` when the call starts, and frees the local variables and the operands left on the stack when it returns. `OP_call` and `OP_call_method` free the function, `this` and the arguments once the call is back. Each of these loops did one value a turn. In the generated code a turn that set a local took 9 instructions: LLVM read `b->var_count` again after every store, since a store of a JSValue might have changed it, and the poll pass cuts a loop whose count it does not know into chunks with a count of their own. A turn that freed a value took about 10. An average render of the six workbench pages of tifa's example shop enters `JS_CallInternal` 113,866 times, runs bytecode in 67,076 of them, sets 520,962 locals and frees 581,838 values at the ends of the calls: the two loops took about 6.5% of its instructions.

The locals are now set four to a turn, then the two and the one left over, from a count read once, and the values at the end are freed two to a turn, while at least two are left (`sp - pval >= 2`: a tail call leaves the stack full, and `pval + 1 < sp` would then point past the frame, which C does not allow). The calls free the function and `this` on their own before the loop over the arguments. Per render, callgrind counts 167.0 M instructions for the six workbench pages rather than 171.4 M (2.5% fewer), 3.1% fewer for `r_react_ssr` and 4.8% fewer for `r_bench_table`. `q_int_arith` does not change. `q_func_call`, whose function has no local, runs 3.0% more, about 13 instructions a call: the entry keeps `b` on the stack, and tests for the two and the one left over. Reading the count once without the turns of four gave React 1% fewer instructions, cost 3.9% more on a loop of arithmetic, and was not kept. The time is in [performance.md](../performance.md#calls-for-in-and-hasownpropertycall).

Rounding the room of the locals up to four values, so that the turns need no remainder, was left out: 48 bytes more a frame would end a deep recursion of big frames sooner on the shadow stack (see [The size of the shadow stack](#the-size-of-the-shadow-stack)).

## How the interpreter calls a C function

`OP_call` and `OP_call_method` below are those of the stack interpreter. The call ops of the register loop make the same direct call (`js_call_c_direct`, from `RV_CALL_OUT`), with the same checks, and the stack debt works as described.

`OP_call`, `OP_call_method` and their tail forms used to send every call to `JS_CallInternal`, which found a C function by its class and passed it on to `js_call_c_function` through the class table. For a C function that entry did no work of its own and still ran its whole prologue: 105 instructions on amd64 (`r_react_ssr` makes 452,219 such calls in a run, 28% of the entries of `JS_CallInternal`), with the stack check of Go, the no-ops of its place, the argument block and the shared return.

The interpreter now calls a plain C function itself (`js_call_c_direct`): a function of class `JS_CLASS_C_FUNCTION`, at a level of call depth under the limit and with the stack left that `JS_CallInternal` would check for it. A bound function, a function with data (`JS_CLASS_C_FUNCTION_DATA`), a proxy, a constructor call and a call near either limit go through `JS_CallInternal` as before, and so does every call from C (`JS_Call`, `js_call`). The direct call does what the entry of `JS_CallInternal` did for a C function, in the same order: it counts `POLL_WEIGHT` towards the next poll (`poll_count`, so a call still counts once), reads the interrupt flag, returns at once while an uncatchable exception is pending, counts a level of call depth, calls `js_call_c_function` with no flags and leaves the level. `sf->cur_pc` is set before either path, and `js_call_c_function` makes the frame that the stack of an error shows and changes the realm, as before. `js_call_c_function` is never inlined, so that its frame does not join the frame of the interpreter.

The stack is the part that needed care. `JS_CallInternal` takes its frame on the shadow stack before its check, so the old call checked with that frame taken, and the C function and all it called ran with that much less stack: 1472 bytes on amd64. Without it, a recursion with big frames through a C function went deeper before the stack ran out (a recursion through `f.call` with 300 locals reached 4999 levels where it ended at 4168), against the rule that a script recurses as deep as before. So the runtime measures that frame when its first context is made (`js_measure_call_frame` calls `JS_CallInternal` with `JS_CALL_FLAG_FRAME`, which only writes the stack it finds left), and `rt->stack_debt` holds the sum of it over the direct calls running. Every check of the stack (`js_stack_short`) counts that sum as taken. The measure comes right after the count of the entry and before the checks, so a host can make the first context with the call depth at its limit, an interrupt asked or little stack left, as before. It sits in the branch for a function that is not an object, which tests the type before the checks (`js_call_checks`, the same in both branches), so a call of a function pays nothing for it. Counted with callgrind (amd64, tifa d90d1fe), `JS_CallInternal` itself runs 0.86 million fewer instructions in a render of `r_react_ssr` and 0.30 million fewer in a render of the shop's workbench than before the measure was moved, where a test of the flags at the top of the entry made it run 3.5 million more. Each recursion of `TestShadowStackAtDepth` and 98 recursions through `call`, `apply`, `map`, `sort` and `Math.max` with 1 to 300 locals at limits of 5000 and 10000 end at the same depth, with the error at the same place, as before, on linux/amd64 and darwin/arm64. The debt costs one instruction at each check. `JS_CallInternal` is `no_inline`: with the old loop gone it is small, and with the constant arguments of the measure only its test of the type is left, so clang inlined it into `js_measure_call_frame`, which then measured 0 and let a recursion through C functions go deeper on a short stack (on a native thread of 1 MiB, 1568 levels through `f.call` where `JS_CallInternal` stopped at 1284). Every other caller called it out of line already. unit-api's `test_c_call_recursions` holds both ways to the same depth on the main thread and on a thread of 1 MiB, and `test_call_frames_measured` holds both measures above 0.

The debt belongs to one runtime. A native C host that calls from one runtime into another on the same thread hands over the call depths (`JS_SetCallDepth`) but not the debt, so each runtime counts only its own direct calls against the stack of the thread, and a recursion that hops between them may go somewhat deeper before the stack check stops it than it did. The Go host has no such case: each VM runs on a shadow stack of its own.

`JS_SetDirectCCalls(ctx, 0)` makes a runtime call every C function through `JS_CallInternal` again (its frame can never fit), for tests. `TestCCallDepth` runs recursions through `call`, `apply`, `map`, `sort`, `Math.max`, an `abs` called with no receiver, and the tail calls `return [1].map(f)` and `return apply(f, null, [])`, with 0 to 300 locals at limits of 5000 and 10000, with direct calls on and off, and requires the same depth and the same stack of the `RangeError`. ### A C function that call, apply or a bound function calls

`Function.prototype.call` and `apply`, `Reflect.apply` and bound functions call the function they are given from C. When that function is a plain C function, the call no longer goes through `JS_CallInternal` but through `js_call_c_hop`, which does the same checks in the same order (the count of the poll, the interrupt flag, a pending uncatchable exception, a level of call depth) and calls `js_call_c_function`. Its frame is smaller than that of `JS_CallInternal`, and it counts the rest of that frame as taken while the function runs (`rt->c_hop_debt`, measured with the other one by `js_measure_call_frame`), so that a recursion through such calls ends at the same depth. A call that would throw on its way in goes to `JS_CallInternal`, which throws what it threw. This is the way core-js calls the methods it keeps (`call.bind(fn)`): two calls of a C function from C for each call of `fn`. Per render (counted on the native C tree, linux/arm64), `JS_CallInternal` is entered 36,456 times on a page of tifa's shop store rather than 118,718 (82,263 of those calls take the new path), 9,273 times on a workbench page rather than 22,640, 1,925 times on a MUI page rather than 2,536, and as before 274 times on React's page. The HTML of the pages does not change.

Only those C functions call through `js_call_fwd`, which has the new path. `js_call`, which the rest of the engine uses, stays as it was: inlined in more than a hundred callers, a larger `js_call` changed what clang inlined into them (`JS_CallFree` was called out of line in 34 places on amd64, `js_invoke` on arm64), and some recursions would have ended sooner. For the same reason the window of the call with a spread (`rv_w_apply`) inlines the body of `js_function_apply` (`js_function_apply_in`). llc gives every other function the frame it had, on both architectures.

The entry of `JS_CallInternal` for a C function, a bound function or a proxy makes the checks of `js_call_enter` inline (`js_call_checks_in`, which counts in `js_call_enter_in`), with only the `RangeError` out of line: about 20 instructions fewer at each such entry, and its frame stays 96 bytes on arm64 and 112 on amd64.

`JS_RegvmStat(ctx, 12)` gives the debt of `js_call_c_hop`, -1 with the direct calls off (`JS_SetDirectCCalls(ctx, 0)`), when these calls go through `JS_CallInternal` too. `TestCCallDepth` and unit-api's `test_c_call_recursions` add recursions that go from `Reflect.apply` to `call`, to `apply`, and to a bound `call` and then to the function, and require the same depth with the direct calls on and off. On the native test host a recursion through a bound function goes a few levels deeper with them on (500 against 496 on a thread of 1 MiB): `js_call_bound_function` has an `alloca`, below which a native build pushes the arguments of `JS_CallInternal` that do not fit in registers at each call, 16 bytes the call of `js_call_c_hop` does not need. The generated engine passes arguments in the frame of the callee and gives the same depth. Under AddressSanitizer, which aligns its stack objects to 32 bytes, `JS_RegvmRun`, `js_call_c_function` and `js_call_bound_function` (and `JS_CallInternal` on x86_64) set their stack pointer down to a multiple of 32 bytes and push the arguments of `JS_CallInternal` that do not fit in registers at each call. `js_measure_call_frame` is left out of the sanitizer, so that it measures the frames alone and not the 16 bytes it would push itself. It measures from two places 16 bytes apart and keeps the smaller, since a frame set down takes 16 bytes more or not by where it is called, and both debts are rounded down to a multiple of 32, the least a skipped frame saves when the next frame is set down. A direct run there never ends less deep and may end up to 2 in 100 levels deeper, and the plain build keeps the same depth. `test_c_call_hop_checks` checks that each such call reads the interrupt flag once and that an interrupt or a pending uncatchable exception stops it before the function runs, and `TestRegvmFrame` and `test_call_frames_measured` that the new path is on when the direct calls are.

### charCodeAt answered in the register loop

Release: v0.30.2.

A loop that scans a string with `s.charCodeAt(i)` calls a C function for each character, and in the generated engine each such call costs several hundred instructions: the checks of a call, a level of call depth, the frame of `js_call_c_function` and the conversions of `this` and of the index. Parsers, hashes and the plain build of emotion (which hashes every style in JavaScript) spend most of their time there. The register loop now answers `String.prototype.charCodeAt` itself (`rv_fast_call`, from `RV_CALL_OUT`) when `this` is a string, or a rope that an earlier call made flat, and the index is an int: it gives the code unit at the index, or `NaN` out of range. Every other call is made as before.

Why it gives the same result: for these values `charCodeAt` runs no script, throws nothing and allocates nothing. The first call that reads a rope makes it flat and keeps the flat string in it (`js_linearize_string_rope`), so the calls after it find it flat and take the new path. The loop knows the function by a mark that `JS_NewCFunction3` puts on the object when it makes `charCodeAt`, in any realm (`JSObject.rv_fast`, in bits that were free, so no object grows). A `charCodeAt` that a script replaced, wrapped in a proxy or bound is another object, without the mark, and is called. A String object, a number or `null` as `this`, an index that is a double, a string, an object, a Symbol or a BigInt, and a call with no index go to the call too. While an uncatchable exception is pending, the call is made and fails, as it did. The answer takes no level of call depth, so a recursion through it can only go deeper, and it does not count toward the next poll: the loop counts at its jumps back, so a loop of nothing but `charCodeAt` calls still stops at an interrupt, at its jump back, where it used to stop inside one of the calls.

`Function.prototype.call` has the same mark, and [hasOwnProperty.call](objects-and-shapes.md#hasownpropertycall-answered-in-the-interpreter) is answered in the same place. One call for both keeps the code of the loop as it was. A second call, before the stores of the frame that a call needs, made LLVM keep one more value on the stack on arm64, about 0.8% more instructions for each instruction of the loop.

### Built-ins answered in the register loop

Release: Unreleased.

The register loop answers more built-ins itself, at the call site where it answers `charCodeAt` (`RV_CALL_OUT`): `Math.clz32`, `has` of `Map`, `Set`, `WeakMap` and `WeakSet`, `get` of `Map` and `WeakMap`, `Array.isArray`, `Array.prototype.push`, `includes` and `indexOf` of an Array, `indexOf`, `includes`, `startsWith` and `endsWith` of a string, `Object.hasOwn`, `Object.prototype.hasOwnProperty`, and `String` called with a string. These are the C functions tifa's pages and React call most from JavaScript. Each call costs a C call of about 70 to 250 instructions more than the answer: the checks of a call, a level of call depth, the frame of `js_call_c_function` and the conversions of `this` and the arguments. `JS_NewCFunction3` marks each function by what it is (`rv_fast_kind`, in the bits of `JSObject.rv_fast`), in every realm. A function a script replaced, bound or wrapped in a proxy is another object and is called.

Each answer is found first, for the kinds of `this` and arguments where the C function runs no script, throws nothing, makes nothing that can be seen and reads no interrupt flag:

| Built-in | Answered for | Called for the rest, such as |
| --- | --- | --- |
| `Math.clz32` | an int or a double | a value that converts |
| `has` and `get` of the four collections | a `this` of the class, a key whose search reads no flag | a rope key, string compares that add up to a step, a `this` of another class |
| `Array.isArray` | any value but a proxy | a proxy, which can be revoked |

Then the loop makes what `js_call_c_direct` makes before it calls a C function, in the same order (`rv_fast_enter`): the depth and stack check, where the call is made if it fails and throws as before, the count of a poll, the read of the interrupt flag and the check of a pending uncatchable error. A push that must grow its array makes these checks, then the call of `push` after them as `js_call_c_direct` makes it (`js_call_c_counted`): one level of call depth, the debt of a direct call (`rt->c_direct_debt`) and `js_call_c_plain`, and `push` grows the array or throws as before.

Why it gives the same results: the answer is found with the compares and searches of the C function (`js_quick_strict_eq` and `js_strict_eq2` for `indexOf` and `includes`, `js_same_value_zero` for the collections, `js_string_find` for the strings, the search of `__JS_NewAtom` for a key), and gives up wherever the C function would read the interrupt flag, so that the call made next finds what it would have found. An exception only comes from the call that is made, with its own stack and message. A stop, the count of polls and the depth a recursion reaches are those of the call. `hasOwnProperty.call(o, k)` keeps its own path ([hasOwnProperty.call answered in the interpreter](objects-and-shapes.md#hasownpropertycall-answered-in-the-interpreter)), which now finds the atom of a key the same way. In the generated engine the loops of a search count toward the next poll, as in the C function: where a search gives up after part of its work, the call does that part again, so a poll can come up to one step of work sooner. A key that is not an atom yet is searched in the atom table only up to 64 characters for that reason.

What it costs: nothing for a call of any other function, since the test of `rv_fast` was there. The new built-ins are answered in a function of their own, `rv_fast_builtin`, and the loop takes the function for each kind from a table (`rv_fast_fns`) at its one call site, so `rv_fast_call` keeps its frame and the built-ins pay no second call. `charCodeAt` takes about 8 instructions more a call on arm64 through the table, where one function for all the kinds cost it 12 and a call from one function to the other cost the built-ins about 33. `rv_fast_builtin` takes a Go frame of 168 bytes on arm64 and 208 on amd64, `js_key_atom_quiet` 168 and 160, and `js_has_own_call` 16 bytes more on amd64. ## The end of a call skips the values with no reference count

The end of a call of a bytecode function frees its local variables and the operands left on the stack (see [above](#how-a-call-sets-and-frees-its-values)). Most of them have no reference count to give back: a local that no code set is `undefined`, and the rest are numbers, booleans and `null` as often as strings and objects. The loop still looked at them one pair at a time, 15 instructions a pair. It calls a function in its body, so LLVM kept the pointer, the count and the poll counter on the stack around the call and read them back at the head of each turn, also in the turns where nothing was freed. A function with 200 locals, none set, took 2,314 instructions more to call than a function with none: 11.6 for each local, of which about 7.5 were the free.

The tag of a value that has a reference count is negative, and every other tag is not (`JS_TAG_FIRST` is -9 and a `_Static_assert` holds the tags of the other values at 0 or more). So the tags of eight values or'd together are negative only when one of the eight needs a free. The end of a call counts its values (`i = sp - local_buf`) and goes over them eight at a time with a loop that has no call in it, so the generated code keeps its variables in registers. A group of eight with a count in it is looked at as two groups of four, and the four of a group that has one are freed one by one with `JS_FreeValue`, from the first to the last, as the loop before did, so what is freed, how often and in which order has not changed. At most seven values are left over, freed in a group of four, two and one by the bits of `i`. Nothing points past the frame: the loop tests the count of what is left, not a pointer (when the stack is full, `sp` is the end of the frame).

A function with 200 locals, none set, now takes 1,466 instructions more than a function with none (7.3 for each local). The slowest case found is a function with every fourth local holding an object, where each group of four has a value to free: with 200 locals it takes 2.4% more instructions than before (5,530 against 5,403 a call), with 32 locals 1.5% more. ## A call copies its last locals into its window

Release: v0.30.3.

The register loop passes the arguments of a call in its window, the temps where the frame of the callee starts. An argument that is a local, an argument of the caller or `this` was put there by a `MOV` right before the call, one dispatch for each. `CALLS` and `CALLSD`, a `CALL` and a `CALLD` that copy their last arguments themselves, now take up to four such copies into the call: the converter writes the slots after the operands of the call, and the call copies each, with a reference, from the last argument back. `return f(a, b)` with two locals runs one instruction where it ran three. A method call, an argument that is a constant or a temp, and the arguments before it keep their `MOV` or `LOADK`.

Why it gives the same values: the converter folds only an entry it still reads lazily, a slot that no instruction has copied yet, so nothing it emitted is taken back. Such an entry is read right before the call, with nothing between, and holds the value of its slot then: a store to the slot copies the entry first (`rv_before_store`), and a slot a closure can write is never read lazily. The arguments object read lazily is not folded, since its first read makes it. The call makes its copies before any check that can leave the instruction: the call depth and the stack, a call out of the loop through `JS_CallInternal`, the unwrap of `call` and bound functions, more arguments than parameters, a new segment of the register stack, a throw at any of them. Each way out finds the window as the `MOV`s left it, with the same references in it. The first call of a function not converted yet converts it and goes on after the copies, where `CALL` runs the instruction again: running `CALLS` again would copy twice.

A first form also took constants, and tested the count from four down. Telling a slot from a constant at each copy, with the tests of the count, made a call with one copy cost more instructions than the `MOV` it saved, and most calls that copy copy one. So a constant keeps its `LOADK`, and a call with one copy tests the count once. In llc's output of the generated engine, a call with 1, 2, 3 and 4 copies runs 0, 6, 12 and 20 instructions fewer than a `CALL` and its `MOV`s on arm64, and -1, 6, 13 and 22 on amd64.

Per render, 40% to 54% of the calls copy, and the loop runs 4.5% to 7.6% fewer instructions of its own (dispatches). Instructions retired per warm render, generated engine on darwin/arm64 (the median of eight rounds, each the mean over the pages), against `167dd40c`:

## Opcodes that do a few instructions at once

The compiler still makes these opcodes. The register pass reads each as the instructions it stands for and makes its own ops of them (`GETF`, `CASES`, `TYPEIS`), so the dispatch counts below are those of the stack interpreter.

Two kinds of instruction sequence that tifa's pages run often now take one dispatch of the interpreter: a read of an argument or a local and the property read by name after it, and a `typeof` test.

### A read of a local and its get_field, and the case of a switch on a string

After the compiler has done its own rewrites (`resolve_labels`) and put in the polls (`insert_polls`), `fuse_code` turns the first instruction of each of these runs into one opcode:

| Run | Opcode |
| --- | --- |
| `get_arg0` `get_field` | `get_arg0_get_field` |
| `get_arg1` `get_field` | `get_arg1_get_field` |
| `get_loc0` `get_field` | `get_loc0_get_field` |
| `get_loc8 n` `get_field` | `get_loc8_get_field n` |
| `dup` `push_atom_value` `strict_eq` and `if_false8`, `if_true8`, `if_false` or `if_true`, the case of a `switch` on a string | `dup_case_atom` |

Only that one byte changes. The new opcode has the size, stack effect and format of the instruction it replaces, and the rest of the run stays in the code as it was. So every instruction keeps its place: the jumps, the line and column table, the polls and the stack size of the function are the same as before. A run is left alone when a jump lands inside it, after its first instruction (the targets of every jump, and the instruction after a `gosub`, are marked first).

What the opcodes do:

- The four reads look at the value of the local without taking a reference to it, and follow the path of `get_field` for a property found with nothing run: an own data property, or one on the prototype chain past objects that are not exotic, or the prototype of a string or a number, or the end of the chain. Then they push the property and step over the `get_field`. In every other case, a getter, a setter, a proxy, an exotic object, `undefined` or `null`, the `stack` of an error, they push the local as the read alone does, and the `get_field` after it runs as it always did, with its own errors and line and column.
- `dup_case_atom` compares the value of the `switch` with the string of the case when the answer needs no characters: atoms are unique in a runtime, so a string that is an atom is equal only when it is the same atom, a string of another length is not equal, and a value that is not a string never is. Then it branches as the jump of its run does, poll included. Otherwise (a string that is not an atom, a rope) it does the `dup` and the rest runs. When the instruction it comes to next, by the branch or past it, is another `dup_case_atom`, it goes on with that case in the same dispatch, so a chain of cases takes one dispatch. Going on with the next case is what its own dispatch would do: nothing runs between the two, each case branches and reads the interrupt flag as its jump does, a jump back counts, and a value that is not an atom stops the chain with the `dup`, so the rest of that case runs as its instructions do. A case with a body of its own ends with `if_false8`, or `if_false` past a long body. Cases that share a body jump to it with `if_true8`, or `if_true` when many cases come before the body, and these were most of the cases React DOM compares (53K of 83K a render, see [below](#what-it-gains)).

Why borrowing is safe: on the fast path nothing runs between the read of the local and the push of the property, so nothing can change or free the local in between. Whatever can run (a getter, a proxy trap, a collection inside them) runs on the slow path, which takes the reference first, as the two instructions did. `fuse_code` runs on finished code, so the `arguments` object, closure variables and the checks of `let` and `const` before their declaration compile as before: a local in its temporal dead zone is read with `get_loc_check`, which is not fused.

The bytecode version went from 6 to 7 with these opcodes, and from 7 to 8 when `dup_case_atom` took the three other jumps. It is 9 since [regexps keep where they start to look](regexp.md#where-a-regexp-starts-is-worked-out-once) in their bytecode, and 10 since [long lists of alternatives that start with a literal](regexp.md#long-lists-of-alternatives-that-start-with-a-literal) keep their tables there. `JS_ReadObject` checks code it reads with `poll_scan`, which now also rejects a fused opcode not followed by the rest of its run (`invalid bytecode: a fused opcode without the instructions it reads`), so bytecode written by a host cannot make the interpreter step over an instruction it did not check.

`JS_SetFusedOps(ctx, 0)` makes a runtime compile the runs apart again, for tests.

### typeof as one opcode

`typeof x == "<name>"`, with `==`, `===`, `!=` or `!==`, is one opcode for any string: `typeof_is_undefined` and `typeof_is_function` as before, and the new `typeof_is`, which holds the atom of the string, for the others. A negated test takes the other branch after it, or is followed by `lnot`. Before, only `"undefined"` and `"function"` were joined, and a negated test only when `if_false` came after it. `typeof x < "u"` and `typeof x > "u"` are `typeof_is_undefined`, negated for `<`, since `"undefined"` is the only result of `typeof` that does not sort before `"u"`. Minifiers write these forms: the bundles of tifa's shop hold 189 tests for `"string"`, 165 for `"function"`, 112 for `"object"`, 65 for `"number"`, 35 of `< "u"` and 11 of `> "u"`, among others. The string first (`"string" == typeof x`) is rare in them and stays as it was.

`typeof` never throws and a comparison of two strings runs nothing, so the opcode gives what the instructions gave, the result of `typeof` for an object marked as `document.all` included. `JS_SetFusedOps(ctx, 0)` also leaves the new forms as they were before.

## Checks of the temporal dead zone that cannot fail

A `let`, `const` or `class` local read or written before its declaration throws a `ReferenceError`, so the compiler reads and writes it with `get_loc_check` and `put_loc_check`, and sets it uninitialized with `set_loc_uninitialized` where its block starts. Most reads come after the declaration, in code that cannot be entered any other way, and need no check. `tdz_checks`, called by `resolve_labels` before it rewrites the code, turns those into `get_loc` and `put_loc`.

The rule, for a check u of a local: there is an instruction p before u that leaves the local initialized (a `put_loc` or `set_loc` of it, or a check of it, which throws when it is not), and the smallest stretch of code from p to past u that holds every jump to a label inside it starts after p. No label in the stretch is the target of a `catch` (an exception can arrive from anywhere its `try` covers) or the place a `ret` goes back to after a `gosub`, and no `set_loc_uninitialized` of the local is in it. Then every way to u went through p. The stretch only grows as the walk goes on, so it is one pass over the code, not a data flow analysis, and the walk over labels has a budget (64K plus 8 a byte of code), past which the checks stay.

What keeps its checks:

- A case of a `switch`: the cases share one block, and the dispatch at the head jumps past the declarations of the cases before.
- A read before the declaration, in its own initializer (`let a = a + 1`), and in a closure. A closure reads the local through its reference and keeps its own check. The closure cannot set the local uninitialized again, so the function that declares it drops its own checks after the declaration.
- The head of a loop the local is declared in, and the code after a `catch` or a `finally` the stretch holds.
- `this` (the derived constructor before `super()`), and everything when `JS_SetFusedOps(ctx, 0)` is set.

A `yield` or an `await` goes on at the instruction after it, so generators and async functions follow the same rule.

When a local is left with no check, no other read, no capture by a closure, and the function has no direct `eval`, its `set_loc_uninitialized` is dropped too: nothing reads the slot before the first write. The instruction also frees the value the slot held, so it stays where the code can run it again, in a loop or in a `finally` (a jump back or a `ret` to before it): dropped there, the value of the run before would live until the next write, and two of them could be alive at once. Run once, the slot holds the `undefined` the frame starts with. A `with` block or an `eval` keeps it too.

The pass asks for its memory without throwing. With none, the checks stay, and the compile goes on as before. It gives up on code with a jump it does not know the target of. The bytecode is valid for the engine before the change too, so its version does not change.

## Locals that share a slot

A frame has a slot for each local of its function, which a call sets to `undefined` and frees at its end. Minified code declares its locals once for the whole function, and the big functions of React DOM's server renderer hold many that are only used in one branch: `pushStartInstance` has 138 locals and `renderElement` 92. `share_local_slots`, called by `resolve_labels` after `tdz_checks`, gives two locals one slot when no run of the code needs both values at once. `pushStartInstance` then has 11 slots and `renderElement` 27, and the 2021 functions of the bundle of tifa's shop 9983 slots where they had 12191 locals.

A local is live at an instruction when some run of the code from there reads it before it writes it: a data flow over the blocks of the code, back from the reads. Two locals share a slot when neither is written where the other is live, a write that nothing reads included. Then each read finds what the last write of its own local left there, or the `undefined` the frame starts with: a local read before any write on some path is live from the start of the function, so no other local is written on that path while it is. The locals are taken in the order of their index and each gets the first slot that none of the locals it conflicts with has. A local never gets a higher index than it had, and the code keeps the size of each instruction: the pass rewrites the index of the long instructions of phase 2, before `resolve_labels` picks the short forms, which now reach more locals.

A local keeps a slot of its own when anything but the instructions that name it reads or writes it, or when its slot holds more than its value:

- a closure captures it, or a function in the constant pool, compiled already, names it.
- the start of the function writes it: `this`, `new.target`, the home object, the active function, `arguments` and the name of a function expression.
- a check of the temporal dead zone is left on it, which reads the state of the slot and names the local in its error, or a `close_loc`.
- it is a private name of a class.
- it is live where a `catch` or a `finally` block starts, since an exception can leave the code of its `try` at any instruction. The blocks after each `gosub` are all taken to follow each `ret`.

A function with a direct `eval`, a `with` block or a mapped `arguments` object, the code of an eval or a module, more than 1024 locals, or code the pass does not know keep their slots as they are (`js_frame_plain`), and so does every function with `JS_SetFusedOps(ctx, 0)`. A `yield` or an `await` goes on at the instruction after it, with the frame as it was, so generators and async functions follow the same rule.

What changes with the slots: the code, the indexes the function keeps (`this_var_idx` and the others), the closure variables of the functions in its constant pool that name its locals (`var_idx`), and the list of its locals. A slot keeps the name of its first local, for the error of a check of the temporal dead zone (whose local has a slot of its own) and the dumps of the bytecode. Error stacks name functions and lines, not locals, so they do not change, and the engine has no debugger (`debugger` is skipped). A `set_loc_uninitialized` that `tdz_checks` dropped now keeps its place with an index past every local (`LOC_DROPPED`), since two locals that share a slot can have one dropped and one kept. The bytecode is valid for the engine before the change, so its version does not change.

A value is freed when the next local that shares its slot is written, where it lived to the end of the call, and a frame takes less of the stack. So a `WeakRef` whose target only a dead local held can give `undefined` sooner than before. It does not show within one job, since a `WeakRef` keeps its target to the end of the job ([weak-collections.md](weak-collections.md#a-weakref-keeps-its-target-to-the-end-of-the-job)): it shows in an async function or a generator, whose frame lives on from one job to the next.

The pass asks for its memory without throwing. With none, nothing changes, and the compile goes on.

## Captures that never change

Release: v0.30.3.

A closure reads a variable of the function around it through a `JSVarRef`, which the frame and every closure of the variable share, so that a write on either side is seen on the other. Most captured variables are never written once a closure has them: a parameter, a `const`, a function declaration, a `let` set once before the closure is made. `capture_by_value` finds them. It runs on the final code of each function, after `share_local_slots`, when the compiler makes the function and when `JS_ReadObject` reads code it has not read before with the checks. It marks a captured argument or local of a function `by_value`, and the closure variable of each function that captures it, when:

- no path of the code goes from an instruction that makes such a closure (`fclosure`, or `push_const` of a class) to a write of the variable without a `close_loc` of it on the way (a `for` with `let` gives each round a binding of its own). Paths follow the jumps, go from a `ret` to the instruction after each `gosub`, and from every instruction to every `catch` of the function, so a write in a `catch` counts wherever the closure is made. A `yield` or an `await` goes on at the next instruction, so generators and async functions follow the same rule.
- no function below it writes it, down any chain of closures (a direct `eval` in one counts as a write), and each function that captures it is held by the function alone.
- the function has no direct `eval` (an indirect one cannot see it), does not map the argument into a mapped `arguments` object, and takes no reference to it (`make_loc_ref` and `make_arg_ref`, which an assignment in a `with` block makes).

A chain of closure variables more than 32 functions deep keeps the variable a `JSVarRef`. Code the pass does not know (a `push_const` of a class constructor with no `define_class` right after it, or a `define_class` with no such `push_const` right before it or with a jump to it, where only the `nop` of a poll may come between the two) and a flow past a budget of work leave every variable as it is. When the pass gets no memory, the compile or the read fails with out of memory, so the marks depend on the code alone: a read compares them with those of the file.

The pass trusts that an exception lands only on a `catch` of the function, which holds for all code the compiler makes. A read refuses code in which a catch offset could leave its place, to be stored, returned or passed to another function ([catch offsets and jumps stay in their function](#catch-offsets-and-jumps-stay-in-their-function)).

The marks go into the bytecode file with the code, one bit in the flags of each closure variable, and `BC_VERSION` went to 11 (it is 12 since [an object rest is made at its final shape](objects-and-shapes.md#an-object-rest-is-made-at-its-final-shape)). A read without `JS_READ_OBJ_POLLS_CHECKED` (`EvalBytecode`, and the first read of a `SharedBytecode`) makes them again and refuses the file with `SyntaxError: invalid bytecode: code no compiler makes` when a mark of the file is not the one it made, either way (`cbv_check_file`): a closure variable left a `JSVarRef` below one that holds the value would count a reference on the cell. The reads of a `SharedBytecode` after the first, one for each VM of tifa's pool, take the marks from the file and do not run the pass. Read so, the bytecode of the store bundle (6.3 MB) takes 38.9 M instructions where it took 151.3 M, MUI 18.5 M where 72.3 M, React 2.1 M where 6.4 M: what a VM of the store paid for the pass at load came to about 0.8 of a render. The first read checks the marks for 0.25% more than it took, 0.9 M on the store bundle.

Counted on tifa's pages, 11,298 of the 14,157 variables a render of the store pages captures pass, 7,639 of 8,454 for the workbench pages and 9,897 of 12,401 for the MUI pages. A build that kept the value of each at the capture and compared it with the variable at the free found none of them changed.

A closure holds the value of each variable so marked itself, not a `JSVarRef` shared with the frame. The value sits in a cell of 24 bytes (`JSValueCell`: the value and a pointer to it), placed after the closure's array of closure variables in the same block, which only that closure frees and marks. The entry of the array points 8 bytes before the cell, so that the pointer of the cell is where the `pvalue` of a `JSVarRef` is: the register loop reads it through `pvalue` as before, and the finalizer and the collector tell a cell from a `JSVarRef` by whether the entry points into the block. The block is not zeroed: `js_closure2` writes each entry and each cell, and on a failure clears those it did not reach. The function gets the block only then, since a collection can run while the entries are written (an error is made, a global variable defined) and would read what the block held before. The frame makes no `JSVarRef` for such a variable, keeps none in its list and closes none when it ends, and a variable down a chain of closures takes its value from the closure above it. So such closures no longer keep a suspended generator or async function alive: an object only its frame holds can be freed earlier, which a script sees only through `WeakRef` and `FinalizationRegistry`, whose timing nothing promises. The counts of the runtime that the corpus records after each script (`mem-end` and `mem-gc`) are the same for all 636 runs.

Per render, counted by callgrind with tifa's URL cache (without it in brackets), against the engine before (167dd40c): the store runs 0.87% fewer instructions (0.55%), the workbench 1.05% (0.91%), MUI 0.89% (0.85%) and React 0.01% (0.01%). For each such variable the frame no longer makes and frees a `JSVarRef` (`get_var_ref` and `free_var_ref`, about 170 instructions), and the closure spends about 21 more to make its cell and about 45 more to free it. The value in a whole `JSVarRef` of 48 bytes, in a block that was zeroed, gave about half of that: the store 0.45%, the workbench 0.55%, MUI 0.50%.

`JS_ReadObject` refuses a function of more than 65,534 closure variables, the most the compiler makes, so that the count of the cells of a closure fits its 16 bits.

A build with `-DRV_CBV_CHECK` also makes the `JSVarRef` of each such variable and compares the two at every read and when the closure is freed, and stops on a difference (`js_value_ref_check` in `engine/quickjs.c`, `RV_VREF` in `engine/regvm.h`). It ran test262, the corpus three ways, the unit programs, the 23 pages of tifa's examples and the React page, the 3,000 fixed rvgen seeds and 1,500 new rvgen programs with closures kept past their function, and found no difference.

## How a JSValue is copied

A JSValue is 16 bytes, a value and a tag. The interpreter writes one to the value stack as two stores of 8 bytes, since the value is in a register and the tag is a constant. LLVM copies one with a single 16-byte SSE move. It makes that move in two ways: the SLP vectorizer joins two moves of neighbouring 8 bytes, and a struct copy becomes a `memcpy` of 16 bytes that LLVM expands. On Zen 3 a load of 16 bytes cannot be served from two stores of 8 bytes that are still in flight: it waits until both reach the cache (24 cycles in a loop that does nothing else, against 1 for a load of 8 bytes of a store of 8). A load of 8 bytes of a store of 16 is slow too, 11 to 13 cycles.

A trace of every load and store (valgrind lackey) of short runs counted the loads fed by two or more stores in the 120 instructions before, and the loads of less than 16 bytes fed by a 16-byte store. 95% to 99.8% of them are in `JS_CallInternal`. Per 100 instructions, the first kind and then the second: `v8_richards` 0.45 and 0.87, `q_func_call` 0.28 and 0.55, `q_int_arith` 0.44 and 0.88, `r_react_ssr` 0.13 and 0.24. The opcodes that hold most of them are the calls (`call_method`, `call1`, `call`, `tail_call_method`: they copy the function and `this` into the argument block of the callee), `put_field` (it passes the object and the value by value), `put_loc*` (the copy of the top of the stack into the local), `inc_loc` (it copies the local to a temporary and reads its halves), `get_loc*` and, in string loops, `add`.

The feature tells LLVM that an unaligned move of 16 bytes is slow. A JSValue is aligned to 8 bytes only, so LLVM now expands its copy into two loads and two stores of 8 bytes, which a load of 8 bytes can be served from. The moves the SLP vectorizer makes are not expanded again, so it is off. The same trace of the generated engine finds at most 1.5% of them left (`r_react_ssr` 4,541 and 14,349 against 433,938 and 813,223, `v8_richards` 776 and 2,056 against 408,409 and 790,662, `q_func_call` 538 and 740 against 100,676 and 201,060), and no SSE move is left in `JS_CallInternal`.

What is left out, and why:

- **The small libc and the other C files.** The `memcpy` and `memmove` of the libc move 16 bytes at a time on purpose, and with the feature a copy of 17 to 128 bytes becomes 8-byte moves, twice the loads and stores. The other files hold no JSValue.
- **The feature with the SLP vectorizer on.** It leaves 29 SSE moves in `JS_CallInternal` (the copies the vectorizer made, in `put_loc` and others), and made `r_shiki_regexp` 2.8% to 3.3% slower, at 7 or 8 of 8 positions.
- **The vectorizer off alone.** It leaves 201 SSE moves in `JS_CallInternal`, the expanded `memcpy`.
- **arm64.** Not given the flags: the feature is x86 only, and nothing was measured there.

The instructions grow a little, since a copy is four instructions in place of two: against the engine before, 0.03% to 1.8% more on 13 of the 14 scripts counted, 5.3% on `q_prop_write`, and 0.7% on `r_react_ssr`. The time goes down where the copies were on the way, see [performance.md](../performance.md#the-c-engine-copies-a-jsvalue-in-two-moves-of-8-bytes).

The change moved the best place of the interpreter's body. With the code of before it was 0 bytes into its line. With 8-byte copies, 40 was the fastest of the 8 places tried on the render scripts (see [above](#where-the-interpreter-and-the-regexp-matcher-sit)).

## Atomics without threads

`Atomics.wait` converts its arguments in the order the specification gives and then throws `TypeError: cannot block in this thread`. `Atomics.notify` converts its arguments and returns 0. test262 gives the same 58 known errors as before with 66 tests excluded in `engine/test/test262.conf`, all of `built-ins/Atomics/wait` and `notify`: 7 wait on the main thread for a time out, and 59 start agents with `$262.agent.safeBroadcast`. That function begins with an `Atomics.wait` on a value that differs, which must return at once and now throws. In 53 of the 59 an agent also waits for a wake up or a time out. In 6 nobody waits and only that probe keeps them out. `api-test.c` keeps what those 6 say that still holds: `Atomics.notify` gives 0 when nobody waits, and `Atomics.wait` converts its arguments in the order of the specification (the array and its shared buffer, the index, the value, the timeout) and throws what a conversion throws before it throws that it cannot block. It also checks that a wait with a value that differs, or with no timeout, throws the same.

`Atomics.pause` is the one function of `Atomics` that is a hint and not an operation. It used to run `pause` (x86) or `yield` (arm64) as inline assembly, which the generator cannot take, so it was the last function the generator had to stub. ecma262 has an engine send the hint only if its platform supports signaling the CPU, so the function now does nothing. Its argument is still checked: undefined or an integral Number, else a `TypeError`. The test262 the tree is pinned to tests that (`non-integral-iterationnumber-throws.js`), but ecma262 dropped the argument in June 2026 (pull request 3847) and test262 stopped testing it a few weeks later (pull request 5075), so the check can go when the pin moves.

## The C API of a Go host

A Go host calls the engine through the generated code, which passes no variable arguments and takes no C function pointer from Go. So the tree has these for it:

- `JS_NewHostFunction(ctx, name, name_len, length, id)` makes a function shaped as a built-in: its name and length, no `prototype`, not a constructor, `[native code]` in `toString`. A call of it is `host_call(vm, &this, argc, argv, id)`, with at least `length` arguments readable in `argv`. The id is an int32 of 0 or more, kept in the function object next to the 16-bit magic of the built-ins (cproto `JS_CFUNC_host`). A negative id throws a `RangeError`: `host_call` keeps the negative magics for the engine's own requests. With no memory for the function, its name or its properties, it returns the exception with the out of memory error pending, as `JS_NewCFunction2` and the others that make functions do.
- `JS_NewStringChars(ctx, len, wide)` makes a string whose characters the host writes in place before the string is used. An 8-bit string gets its NUL. `len` 0 gives the empty string, a length past the most a string holds throws a `RangeError`, and no memory throws the out of memory error.
- `JS_ThrowErrorKind(ctx, kind, msg, len)` throws an error of a `JSErrorKind` (one per native error constructor) with the message cut where `JS_ThrowTypeError(ctx, "%s", msg)` cuts it: at a NUL byte and at 255 bytes. A kind it does not know throws an `InternalError`.
- `js_host_layout`, a table of int64 indexed by `JS_HOST_LAYOUT_*`, holds what a host reads and writes in place: where the reference count is from the address a value holds (-4), the mask of the length and the wide bit in the first word of a string, where its characters start (12), the most characters a string holds, and the numbers of the built-in atoms the Go API names (`message`, `stack`, `then` and the like). Nothing in the engine reads it. The generator reads it from llc's text and writes it into `engine_decl_<arch>.go` as Go constants (`layoutStringChars`, `atomMessage` and so on), and stops when the table has more or fewer entries than it has names for (`gen.HostLayoutNames`). Add an entry at the end of both.
- `JS_NewHostFunctionRelease(ctx, name, name_len, length, id)` makes the same function for an id that is a handle of the host, something the host keeps for it such as a Go function. When the engine frees the function, at the drop of its last reference, in a collection or when the runtime is freed, it calls `host_release(vm, id)` (`host.h`) once, from its finalizer. `host_release` runs no script and does not call the engine. A call that fails made no function and releases nothing: the handle is still the host's.
- `JS_NewEscapeTextFunction(ctx, name, name_len)` makes the function of `VM.RegisterEscapeText`: React DOM's `escapeTextForBrowser` in C, shaped as a built-in like the host functions, with length 1. It is a C function of the engine, called without `host_call`, so a call costs about what a call of an empty JavaScript function costs, not what a Go function costs. The argument is converted as `"" + text` converts it, the five characters become entities one UTF-16 unit at a time, and a string with none of them comes back as itself. The loops read the interrupt flag every 4096 units. See [go-api.md](go-api.md#registerescapetext).
- `JS_NewCopyPropsFunction(ctx, name, name_len)` makes the function of `VM.RegisterCopyProps`: the loop with which React copies the keys of a config into the props of an element, in C, shaped as a built-in with length 4. `js_copy_props` answers true after it copied and false when it changed nothing, and it copies only where it knows the loop can do nothing else: the config, the props, `Object.prototype`, `hasOwnProperty` and `Function.prototype.call` are checked in the call, with no state kept between calls but the five atoms in `JSContext.copy_atoms` (`key`, `ref`, `__self`, `__source`, `call`). It is bounded by 32 keys of the config and 64 slots of the shape of the props and of `Object.prototype`, so it reads no interrupt flag. See [go-api.md](go-api.md#registercopyprops).
- `JS_NewStartTagFunction(ctx, name, name_len)` and `JS_NewEndTagFunction(ctx, name, name_len)` make the functions of `VM.RegisterStartTag` and `VM.RegisterEndTag`: the start tag React DOM's `pushStartGenericElement` writes, with its attributes, style and text, and the end tag of `endChunkForTag`, in C, shaped as built-ins with length 6 and 1. `js_start_tag` builds the tag in a `StringBuffer` on a buffer the cache keeps (`js_emit_buf_take`, `js_emit_buf_end`), copies it into a string of its length, since `__js_realloc` never moves an arena block to a smaller class, and adds it to the end of the target array in place, and returns its `decline` argument, having changed nothing, wherever React's functions could do something else. The two functions share one cache per context (`JSContext.emit_cache`, made by the first of them, with no script run: `js_emit_make_builtin` makes `Function.prototype.call` and `Array.prototype.push` through `JS_AutoInitProperty` when they are still to be made, and the cache goes into the context only once it is whole): three atoms, and three tables made at their first entry and doubled when half full (open addressing): how up to 512 attribute names and 512 style names are written, and up to 256 end tags found by the address of the tag string. A full table is emptied and fills again. A call is bounded by 32 keys of the props and 32 of the style, and reads the interrupt flag every 4096 units of a long string it escapes or trims and every 524,288 units of one it copies. See [go-api.md](go-api.md#registerstarttag-and-registerendtag).
- `JS_FreeModuleTopLevel(ctx, m)` frees the function of the top level of a module that has run to its end without an exception, with the code of the top level and its variables that no function of the module and no export holds (the module keeps its exports apart, in its export entries, once it is linked). QuickJS keeps the function until the module goes, which for a module of the context is when the runtime is freed. It does nothing to a module that has not run, still waits at a top-level `await`, or threw.

On the Go side, `host_call` of `internal/cengine` gives an id of 0 or more to the `HostFunc` registered with `SetHostFunc`, once, from an init function, and the requests of the engine to `gohost`. The function gets the shadow pointer of the call: what it passes the engine by address, and the frames of a call back into the engine, go above it.

## Strings built by appending

QuickJS grows a string in place in one case only: `x += y` on a local (`add_loc`) whose string nothing else holds. Every other append copies the whole string while the result is shorter than 8192 characters (`JS_STRING_ROPE_SHORT2_LEN`), and then makes a rope, two strings joined only when the result is read. At the `+` of `x = x + y`, or of `x += y` on an argument or a closure variable, both the variable and the stack hold the string, so its reference count is 2 and it is always copied. A string built by n short appends is so copied n times, and the copies add up to the square of its length.

That is how React builds a page: `renderToString` appends each piece of HTML, 1 to 15 characters long, to a closure variable (`push(u) { a += u }`). With any character past Latin-1 on the page the string is 16-bit. A render of the `r_react_ssr` script copied 780 MB in 400,000 copies, 96% of all its `memcpy`. Upstream QuickJS (2026-10-26) and quickjs-ng (2026-10-24) do the same. V8 makes a rope (`ConsString`) of any result of 13 characters or more.

The engine now finds the variable instead:

- `OP_add` with a string of at least 64 characters on the left whose reference count is 2 (`JS_STRING_APPEND_MIN`) reads the next instruction, after one `dup` if there is one: a `let` that a closure checks for its temporal dead zone is stored by `dup` and `put_var_ref_check`. When it stores into a local, an argument or a closure variable whose value is that same string, the other reference is the variable's, which the store drops (`js_add_string_store`).
- `JS_ConcatStringAppend` then appends in place when the block has room. Else it copies the string with room for half its length again, so the next appends go in place. `add_loc`, when its in-place append fails, takes the same copy.
- A right side of more than 512 characters makes a rope as before, and anything else (a rope on the left, other holders, a store into anything else) goes to `JS_ConcatString`.
- A property name (an atom) is never grown, see the row above.

A string built by n appends is then copied about log1.5(n) times. A string of 64 characters or more that was copied with room keeps up to a third of its block unused until it is freed. A string `+` whose left side is a string runs about 2 more instructions in the interpreter for the checks. What it gains and costs is in [performance.md](../performance.md#strings-built-by-appending).

## JSON.parse reads keys and plain strings from the text

`JSON.parse` made a string for every key and every string value of its text in a `StringBuffer` that starts with room for 32 characters, grows, and shrinks to its length at the end. A key then went through `JS_ValueToAtom`, which hashes the string, finds the atom and frees the string. A table of rows repeats the same few keys thousands of times, so most of that work found an atom the parse had just found.

Now, without the JSON superset (`JSON.parse` and `JS_ParseJSON`):

- A key that is a string of ASCII characters with no escape, that does not start with a digit and that a `:` follows is read from the text by `json_scan_key`. `json_key_atom` takes its atom from a cache of 64 slots, chosen by the length of the key and three of its bytes, with one comparison of bytes, or else from its characters with `JS_NewAtomLen` (which looks for the atom before it makes a string), and puts the atom in its slot. The `:` token is skipped.
- A string value of ASCII characters with no escape is made at its length in one copy (`js_new_string8_len`). A string that goes on with an escape or a character of more than one byte starts its buffer with the run of ASCII it began with, and goes on as before.
- `json_plain_run` finds where such a run ends 8 bytes at a time: three tests on a word mark the bytes below 0x20, the quotes and the backslashes, the high bit marks the bytes above 0x7f, and the lowest mark is the first byte that ends the run (a borrow can only mark a byte after one that was found).
- An element after the last one of the new array goes in with `add_fast_array_element`, which is what `JS_DefinePropertyValueUint32` ends up calling, without the lookups before it.
- The text is made a C string 8 bytes at a time when it is 8-bit: the bytes above 0x7f are counted by words, and runs of 8 ASCII bytes are copied as words. The loop over a 16-bit text asks whether it is time to read the interrupt flag once a step of 65536 characters, not at every character.

### Why it gives the same values and errors

- The atom is the one the string would give: a key of ASCII that does not start with a digit is never an index, so `JS_NewAtomStr` would have looked it up by its characters as `JS_NewAtomLen` does. Keys that are indexes or look like numbers (`"0"`, `"4294967294"`, `"-0"`, `"01"`), keys with an escape, a character above 0x7f or 65535 bytes or more, and every key of the JSON superset still go through the token, as before. A key in the cache is compared byte for byte with the 8-bit string of its atom, and only 8-bit atoms go in.
- The steps happen in the same order: the key's atom is taken where the loop took it from the token, after the object is made, and the `:` is a token that cannot fail. Whitespace before the key and around the `:` is the whitespace JSON allows, which `json_next_token` skips. When the text is not a plain key and a `:`, nothing moves and the token reads it, so every error has the same message and position.
- Repeated keys, `__proto__` and the order of keys do not change: the property is defined by the same `JS_DefinePropertyValue`, and a repeated key, with or without an escape, is the same atom.
- The cache lives in `JS_ParseJSON3`, on the stack, and each slot holds a reference to its atom. `json_key_cache_free` gives them back at the end of the parse, on every path (a value, a syntax error, out of memory, an interrupt), so no atom outlives the parse and nothing is kept from one parse to the next. A reviver runs after the parse, on the values it made.
- The interrupt flag is read at the same places. A plain run is shorter than 65535 bytes, so the string it makes had no reading of the flag before either, and the words of the C string are counted in the same steps of 65536 characters. The units of work that `white.c` counts between two readings are the same, to the unit, on tables of 8-bit, Latin-1 and 16-bit text.
- Running out of memory throws the same uncatchable error. A string is now asked for at its length, not at 32 characters and then grown, so the place where a memory limit is reached can move by a few bytes.
- The depth of nesting that throws "JSON nesting too deep" is the same, 1999 objects or arrays.

### What it gains

`JSON.parse` of a table of 1000 rows (92 KB) runs 60% fewer instructions, and of the orders that tifa's shop workbench loads (11 KB) 31% fewer. The numbers, for texts that are not tables too, are in [performance.md](../performance.md#jsonparse-reads-keys-and-plain-strings-from-the-text).

In `engine/test/unit-white.c`, `test_json_plain_run` checks `json_plain_run` against a byte loop at every length up to 40, at every place a run can end and on random texts, and its limit of 65535 bytes. `test_json_key_cache` checks that every key atom the cache held is given back after a parse that returns, one that throws, one with a reviver, and one where each allocation in turn fails, and `test_poll_work_gaps` the units of work between two readings of the interrupt flag on 8-bit, Latin-1 and 16-bit tables.

## Calls of more than 32 arguments pass them in an array

Release: v0.30.2.

A call with more than 32 arguments, such as `f(a1, ..., a40)`, and a tagged template with more than 30 substitutions now pass the arguments past the first 32 in an array, as a call with a spread does: the compiler emits `array_from` for the first 32, then `define_array_el` for each one after them, and makes the call with `OP_apply`, or `OP_apply_eval` for a direct `eval`. An array literal already builds its elements past the first 32 this way. The operand stack of a function then holds at most 32 arguments of one call, where it held all of them, so that the frame of every function fits the 124 temps the register loop names with a byte (`engine/regvm-pass.h`). `JS_CALL_ARGS_ON_STACK` in `engine/quickjs.c` is the limit.

Why this is safe: the arguments are read in the same order, before the callee is called, and `OP_apply` passes them to it as `OP_call`, `OP_call_method` and `OP_call_constructor` do, with the same `this` and `new.target`. The array is the engine's own and defines its elements, so a setter on `Array.prototype` does not run. A call with more than 65535 arguments before its first spread still fails to compile with `SyntaxError: Too many call arguments`. A tagged template with more than 65535 substitutions failed to compile with `InternalError: stack overflow`, and now throws `RangeError` at the call, as a call with a spread of that many arguments does.

What it costs: such a call makes an array and copies the arguments out of it again. A loop of a million calls of 40 arguments to a function that reads `arguments.length` takes 0.47 seconds where it took 0.20 with the register loop off, and 0.49 where it took 0.16 with it on (user time of the native host on the Mac, best of three), about 0.3 microseconds more a call. A call of 32 arguments or fewer is unchanged. The pages of the scoreboard (React, tifa's table and spiral, the shop and MUI apps, `engine/test/regvm/score.sh`) run the same dispatches both ways before and after: none of their calls has more than 32 arguments.

The change is in C (`engine/quickjs.c`, `js_parse_postfix_expr1` and `js_parse_template`). `engine/test/compare/call_many_args.js` makes calls of 31 to 300 arguments of every kind: a function, a method, an optional call, `new`, `super`, a direct `eval`, a tagged template and a spread among them, the order in which the callee and the arguments are read, a throw in an argument past the limit, and a setter on `Array.prototype`. Its file is what Node 24 prints, and the engine before the change prints it too. `engine/test/regvm/js/l-args.js` runs the same kinds with the register loop off and on.

## The limits of a function in the register loop

Release: v0.30.2.

The register loop folds a stack deeper than its temps into Arrays, in as many levels as the stack needs, up to `JS_STACK_SIZE_MAX` (`engine/regvm-fold.h`). A catch offset (one for a `try`, three for a `for-of` with its iterator and next method) stays in a temp of its own, and so does the part of the stack under it, frozen into one Array. The register loop is the only interpreter, so the parser refuses at compile time each function it could not run, with the error it already gives for its own limits:

- Parameters and locals together past 32,765 (with `this`, the function and `new.target`, the 32,768 slots that MOVW, SETLW and CHKLW name with 16 bits): `InternalError: too many local variables` or `InternalError: too many arguments`, whichever is added last. The parser's own limit is 65,534 of each.
- A stack deeper than 118 values whose catch offsets take more than 48 temps (`RV_FOLD_PINS_MAX`, `engine/regvm-func.h`): `InternalError: stack overflow`. Around `r += a` that is 118 nested `try` (119 around nothing) or 39 nested `for-of`, where the catch offsets themselves make the stack too deep, and around an expression 130 deep, 49 nested `try` or 17 nested `for-of`. A `try` under a `for-in` takes one temp more for the enumerator under it.

The numbers are the same in sloppy and strict code, in a generator and in an async function. Before the old interpreter loop was removed, every one of these functions compiled, and the ones the register loop refused ran in the old loop.

Why this is safe: the check is in `add_var`, `add_arg` and `compute_stack_size` (`engine/quickjs.c`), with the same counts that the register pass uses (`rv_build` and `rv_chain_bslot`, `engine/regvm-pass.h` and `engine/regvm-fold.h`). The part of the stack above the innermost catch offset takes at most 70 temps at any depth (`RV_FOLD_TOP_MAX`), which leaves 48 of the 118 for the catch offsets.

`test_rv_frame_limits` and `test_rv_nesting_limits` of `engine/test/unit-api.c` compile each limit and one under it in sloppy and strict code and in a generator, and check that the one under it runs, in register code for a plain function. `engine/test/regvm/js/f3-fold.js` runs stacks folded in several levels, and `test_regvm_fold_oom` of `engine/test/unit-oom.c` fails each allocation of a fold in turn.

## Catch offsets and jumps stay in their function

Release: v0.30.3.

`JS_ReadObject` runs the register pass on each function it reads and refuses with `SyntaxError: invalid bytecode: code no compiler makes` code the pass cannot take (`rv_read_check`, `engine/regvm-entry.h`). Three more kinds of such code are refused now (`engine/regvm-pass.h`):

- A catch offset read by an instruction other than those that drop it (`drop`, `nip`, `nip1`, `nip_catch`, `iterator_close`) or read the entries around it and leave it in place (`for_of_next`, `for_await_of_next` and the iterator ops of `yield*`) (`rv_catch_reads_ok`). A catch offset is a value on the stack like any other, so a function could return it, store it in a local or pass it to a call, and the register loop would take it for one of its own when an exception passes it (`rv_unwind`, `engine/regvm-run.h`): it jumps to the place the number names in the code of the function where the exception is. The offset of `for_of_next` that names its iterator is held to the same rule, so it cannot take a catch offset for the iterator and pass it to a `next` method as `this`.
- An `iterator_get_value_done` with no iterator under it. It writes the catch offset of an iterator again where it reads one, so it could make a catch offset out of any value: the read wants that of a `for_of_start` or a `for_await_of_start` there, as the compiler puts it.
- A jump whose target is before the start of the code (`rv_old_target`). The pass checked a target past the end, but took one before the start for no jump at all. The same check covers every jump the pass reads: `goto`, `if_true`, `if_false` and their short forms, `catch`, `gosub` and the `with_` ops. A `ret` goes back to the instruction after a `gosub`, which `ret_bits` names, and the iterator ops name the stack, not the code.

A `ret` goes back to the end of its `gosub` only when the depth and the innermost catch under its return address are those the pass found at the end of the `gosub`, and throws `InternalError: invalid ret value` when they are not (`rv_ret_target`, `engine/regvm-ops-except.h`). The return address is an int that any code can make, and a `finally` that changed what lies under it would hand the code after the `gosub` a catch offset in place of a value. A `finally` the compiler makes leaves the stack under its return address as it was. GORET carries the two numbers, 8 bytes, and makes two compares more.

The compiler makes none of this code: test262, the corpus, the 23 pages and the rvgen seeds run as before, and a function the pass refused would throw at its first call. It is what lets [captures that never change](#captures-that-never-change) trust that an exception lands only on a `catch` of its function.

Tests: `test_regvm_crafted` of `engine/test/unit-white.c` changes one byte of code the compiler made for each kind (`white_crafted_jump`, `engine/test/white.c`) and checks that the read refuses it: the `drop` of a catch offset made a `return`, a jump and a `catch` made to go before the start of the code, and the offset of a `for_of_next` made to name the catch offset of a `try` around it. `test_regvm_crafted_code` puts code of its own in a function (`white_crafted_code`): an `iterator_get_value_done` with no iterator under it, which the read refuses, a `finally` that leaves a catch offset of its own under its return address, whose `ret` throws, and one that returns at once, which runs as before.

## Jump tables on arm64 take 4 bytes an entry

Release: v0.30.3.

llc writes a jump table of arm64 with 1 or 2 bytes an entry when the distances fit (each entry the steps of 4 bytes from the lowest target, read by `ldrb` or `ldrh`), and with 4 bytes otherwise (the distance in bytes from the `adr` of the dispatch, read by `ldrsw`). It picks the form from the sizes of the code it writes. The lowering then adds code inside the function, so a table that fit llc's code can end too narrow for the lowered one: a switch of `js_start_tag` came to 272 steps, past the 255 a byte holds, and llvm-mc refused the engine. llvm-mc refuses such an entry only when it knows the distance as it reads the entry. With an alignment of the code between the two labels it works the distance out later and writes its low bits without a word (LLVM 22.1.8), so a table past its width could have jumped to the wrong place. None did: the check below, run on the arm64 engine of v0.30.2 with the narrow forms on, finds every entry within its width. But which change of C would break a table next was luck.

The generator now has llc write every table with 4 bytes an entry (`-aarch64-enable-compress-jump-tables=false`; LLVM 22.1.8 has one switch for both narrow forms). The 2-byte form holds 256 KiB, three times the largest function (JS_RegvmRun, 79 KiB), so only the byte form was at risk, but it cannot be turned off alone. The dispatch is as long in every form (`adr`, a load, an `add`, `br`): the engine has the same instructions, frames and SHADOW as before, and its tables take 10,060 bytes more (1,830 entries of a byte and 2,285 of two bytes become 4 bytes each). amd64 does not change.

The generator does not rest on the flag. The lowering sizes its own code (4 bytes an instruction, a label nothing, an alignment counted from where the function is placed, a multiple of 16 bytes or its place on 64, and not made past its max-skip) and refuses a function with a jump table entry whose distance does not fit its width, or that a narrow form would reach backward, naming the table, the entry and the steps it came to (`a64CheckJumpTables`, `internal/goasm/gen/arm64_jumptable.go`). With the narrow forms back on, it refuses `js_start_tag` at the same 272 steps llvm-mc found.

Tests: `TestA64CheckJumpTables` takes the farthest distance each width holds and refuses one step more, after an alignment too, and refuses a backward entry, a label that is not in the code and code it cannot size. `TestLowerARM64EngineJumpTable` lowers a function whose table of bytes fits llc's code, 250 steps, and is refused once 5 calls in its span grow the lowered code.

## SSE reads that need 16 bytes stay on 16

Release: v0.30.5.

An SSE instruction with a 16-byte memory operand faults when the address is not on 16 bytes, except `movups`, `movupd`, `movdqu` and `lddqu`. The amd64 engine has 382 such instructions: 327 read the constant pool of their function through RIP (in 70 functions), and 55 read a local through a register made from the shadow stack pointer. None reads the heap or the Go stack. After linking, every one of them reached an address on 16 on linux, darwin and windows, but nothing said it had to: the pool was on 16 only because each body happened to start on 16 and `.p2align 4` counts from the start of the function, and the shadow stack pointer was rounded in three places by hand.

Now each of the three is held by design and by a check:

- The data of a function. The generator writes a `PCALIGN $16` in front of the data after the code (`emitData`, `internal/goasm/gen/emit.go`). It adds no byte: the generator refuses data that starts off 16 in the lowered object, where the PCALIGN would pad it away from the RIP displacements in the code, and the post-link check refuses a body whose data would start off 16 in the binary (`dataPlaced`). The post-link check also refuses each aligned SSE instruction whose RIP target is not on 16 in the binary, and names the function, the instruction and the address (`checkAlign16`). A `front:` of `xform` that is not a multiple of 16 is refused, as before, since it would now pad the data away from its code.
- The shadow stack. The base of the region, the space `tmp` takes and the stack pointer a host function gets are rounded by one function, `cengine.AlignSP`, to `cengine.SPAlign` (16). `cengine.CheckSP` panics on a pointer off 16 at each entry and in `host_call`, only in a build with `-tags testhooks`: in the normal build it is an empty function the compiler inlines, so it costs nothing.
- Everything else. The pass refuses, on amd64, a load, store, atomic or memory intrinsic that the IR marks aligned to 16 or more, of any width, unless its address comes from a local or a global (`heapAligned`, `internal/goasm/gen/pass/shadow.cpp`). The engine has none today. A pointer from the heap can be on 8 bytes only, so such an access could make llc write a `movaps` that faults. The width does not matter: llc merges two reads of 8 bytes into one `movapd` when the IR says the first is on 16. The rule sits in the IR, where the alignment comes from, and not in the machine code, because llc moves the address of a local through other registers: 37 of the 55 reads of locals today are not the register the shadow pointer comes in (r12) plus a constant.

arm64 does not change: its `ldr q` and `str q` need no alignment, and the pass rule is for amd64 only.

Cost: none. The generated amd64 files gain one `PCALIGN $16` line in each of the 323 functions with data, which add no byte: the checks above refuse any layout where they would.

Tests: `TestCheckAlign16` decodes `movaps`, `movdqa`, `xorpd` and `paddd` that read RIP-relative addresses off 16 and must be refused, and `movups`, `movdqu`, `movsd` and `ucomisd` that must pass. `TestPostLinkCheck` builds a pool off 16 (`vecpool`) and the check must refuse it. `TestEmitDataAligned` and `TestDataPlaced` refuse data off 16 in the object and in the binary. `TestRejectSamples` refuses `testdata/reject/heap_aligned.c`, a vector load through a pointer, and `merged_aligned.c`, two reads of a `double` through a pointer said to be on 16, which llc would merge into a `movapd`. `TestAlignSP` checks the rounding, the first stack pointer of a VM and the one a host function gets, and `TestCheckSP` (testhooks) the panic.

There is no new branch on the path: the test of a temp chose between two reads of the slot before.

What it gains: MUI's orders page runs 0.52% fewer instructions a render, the other pages 0.06% to 0.13%, with the same HTML on the 23 pages of the shop and MUI. The numbers are in [performance.md](../performance.md#a-key-in-a-local-without-a-reference).

## A string key that is its own atom is read as a named property

Release: v0.30.5.

`o[k]` with an object `o` and a string `k` that is an atom (GETEL, GETELT, GETELK and GETELKT of the register loop, when the fast paths of an array or a typed array do not answer) went through `rv_getel_slow`, `JS_GetPropertyValue`, `JS_ValueToAtom`, which took a reference to the atom, the generic `JS_GetPropertyInternal`, and `JS_FreeAtom`. Most such keys come from `for in`, `Object.keys` and literals, so they are atoms already. The loop now calls `rv_getel_atom` for them: when the key is an atom of the type string, not empty and not starting with a digit (the strings `JS_ValueToAtom` takes as their own atom, so never an index), it takes the atom's index from the string and looks for it on `o` and its prototypes the way GETF reads `o.name`: a plain data property gives its value, the end of the chain gives `undefined`. Anything else on the way, an accessor, a closure variable of the global object, a property made on first use, the `stack` of an error, or an exotic object other than an array or `arguments` (a typed array, a Proxy, a String object, a module namespace), sends the read back to `rv_getel_slow`, which does it from the start as before.

This is not an inline cache. Nothing is kept from one read to the next and no shape is held: each read looks the key up as GETF does. The three caches that were tried and dropped ([performance.md](../performance.md#what-was-tried-and-not-done)) kept a shape and a slot for each place that reads a named property, to skip a lookup that costs about as much as checking the entry. This change skips no lookup. It removes the work around it that only the keyed read paid: the call of the generic path, the reference taken on the atom and let go, and the tests of a key that may be anything.

Why this is safe: the answer is the one `JS_GetPropertyInternal` gives for the same atom, since the walk is the same as its own for the cases it answers, and it stops at every case it does not. Which strings count as their own atom is decided by the test `JS_ValueToAtom` and `hasOwnProperty.call` use ([hasOwnProperty.call answered in the interpreter](objects-and-shapes.md#hasownpropertycall-answered-in-the-interpreter)): `"0"`, `"10"`, `"01"` and `"4294967295"` start with a digit and keep the old path, and `"-0"`, `"1e3"`, `"Infinity"` and `"NaN"`, which are names on an ordinary object, are canonical numbers on a typed array, which the walk does not pass. A symbol is not a string and keeps the old path. No code runs before the value is taken, so the key, which its slot keeps alive (a temp of the instruction, a local no code can write during the read, see above, or a constant of the function), keeps its atom alive, and no reference is taken on it. A key in a temp is freed after the read, not before it as `JS_GetPropertyValue` frees it, which no code can see. An instruction the throw injection of the tests is to throw at takes the old path, as with the other fast paths. `rv_getel_atom` is a function of its own, so the frame of `rv_getel_slow`, on which a getter or a Proxy trap runs, keeps its size (192 and 200 bytes before and after on amd64 and arm64), and the register loop keeps its frame (SHADOW 256 on amd64, 176 on arm64). An array index, a typed array element and every other key take the paths they took. The loop calls `rv_getel_atom` after its own fast paths with nothing but the operands of the instruction, and `rv_getel_atom` tests the tags of the object and the key itself. With the two tag tests in the loop, the object and the key stayed live past the array element path, and LLVM gave that path other registers: 6 more generated instructions for each `arr[i]` on amd64 (callgrind of a bundle of 200K such reads a render), which a native build does not show. With the tests in the leaf, the loop runs the same instructions as before on a page without keyed reads by string.

What it gains: one keyed read with an atom key on an own data property costs 115 native instructions instead of 210 (amd64, callgrind), against 25 for `o.c`. The pages make 2.8K (React) to 31K (MUI, 55K on the orders page) such reads a render. 77% (MUI) to 100% (React) of them find an own data property, up to 16% one on a prototype (the storefront) and up to 22% nothing (MUI). On the product, an Apple M4, the pages run 3.4% fewer instructions on MUI, 0.9% on React, 0.7% on the workbench and 0.5% on the storefront, with the same HTML on the 24 pages. The numbers are in [performance.md](../performance.md#keyed-reads-with-an-atom-key).

The change is in C (`engine/regvm-ops-object.h`). `engine/test/regvm/js/o-getel-atom.js` reads 20 keys (names, the empty string, indexes and number-like strings, `length`, `stack`, `__proto__`) on 30 kinds of objects and primitives, with the key in a local, a temp and a constant, and compares each read with `Reflect.get` and with the same key made again as a string that is not an atom, counting the getters and Proxy traps that run. Its goldens were written by the engine before the change (plain, strict and without fused ops). `unit` checks that no atom is left or freed early when the key is the last reference to its atom or one of many kept keys (`test_getel_atom_refs`).

## A string keeps the atom it is as a key

Release: v0.30.5.

A string now holds `key_atom`: the number of its atom when `JS_ValueToAtom` takes the string as its own atom (an atom of the type string, not empty, not starting with a digit), and 0 for every other string. `__JS_NewAtom` sets it when a string becomes an atom, and a new string has 0. The keyed read of the register loop (`rv_getel_atom`, see above) and `hasOwnProperty.call` (`js_has_own_call`) read it once, where they tested the type of the atom, the length and the first character and then looked the string up in the hash table of atoms for its number. The keyed read also runs before the loop stores its top, pc and sp for the frame, as the array element path does: it runs no code and starts no collection. Why this is safe: a string becomes an atom only in `__JS_NewAtom`, whether it is turned into the atom in place or copied, and both ways set the field. ## Array destructuring with no iterator

Release: v0.30.3.

`const [a, b] = arr` gets an iterator of `arr`, reads two elements through its `next` and closes it. The parser makes that `for_of_start`, `for_of_next` and `drop` for each element, then `iterator_close`, and each of them cost the call of `values`, an Array Iterator object, a lookup of `Symbol.iterator`, of `next` and of `return`, and a call of the window op for each element: about 1,350 instructions for two elements, where reading `arr[0]` and `arr[1]` takes about 100. The pages of the shop, MUI and React destructure arrays 135 to 2,261 times a render, always arrays made by the page itself with nothing changed on them.

The register loop now takes such an array apart with no iterator (`engine/regvm-ops-dst.h`). `DSTART` is the `for_of_start` of a destructuring. When the value is a fast Array of the function's realm with the shape of a new array (no own property but `length`, `Array.prototype` as its prototype), `Array.prototype[Symbol.iterator]` is the built-in `values` as a data property and `%ArrayIteratorPrototype%.next` is the built-in `next` as a data property, made first if the engine has not made it yet, as the read of `next` would (`js_dst_ok`, `engine/quickjs.c`), it keeps the array in place of the iterator, the built-in `next` as the `next` method, as the record would, and in place of the catch offset 0 of an iterator the index of the next element, as a catch offset below 0 (`JS_DST_REC`). `DNEXT` is `for_of_next` then `drop`: while the array is fast and has the element, it polls once, as the read of an Array Iterator does, and takes the element. At the end of the array (an index at or past its length) the array is let go and the reads after give `undefined`, as the iterator does. Any other case (a hole of an array whose length was made longer, an array no longer fast) makes the Array Iterator in place, with the array and the index (`js_dst_iter`), and the code of the real iterator goes on from there. `iterator_close` and the unwinding of an exception (`rv_unwind`, `engine/regvm-run.h`) look for a `return` on `%ArrayIteratorPrototype%` and its prototype chain first: with none, and no exotic object there, the close only lets the array go. Otherwise they make the Array Iterator and close it as before.

A `for-of` loop and `yield*` are not changed: the pass makes `DSTART` only for a `for_of_start` whose next instruction is not a `goto` or a `drop`. Neither is a destructuring with a `yield` in a default, whose `return` takes the catch offset off with `nip_catch` before it closes the record.

### Why it gives the same results

The checks are those of GetIterator: `Get(arr, @@iterator)` finds `values` on `Array.prototype`, as the shape of the array has no `Symbol.iterator` of its own. The call of `values` does nothing a script can see (ToObject of an object, and CreateArrayIterator). `Get(iterator, "next")` finds the built-in `next`, as a new Array Iterator has no property of its own. The property of `Array.prototype` and that of `%ArrayIteratorPrototype%` are found by the index where they were last time, checked by their key, their kind and their value, since QuickJS changes a shape no one shares in place. Once the record is made, the specification keeps that `next` in it, so what a default changes on `Array.prototype` or `%ArrayIteratorPrototype%` later does not change this destructuring. What can change it is the array itself, judged at each read as it is then, and the `return` of the close, read at the close. The Array Iterator made at a read is the one the real iterator would be at that point: same array, same index, same `next`.

No script can read the array where the iterator should be. The pass gives such a record only where `for_of_next` and `iterator_close` of it alone read it (`rv_dst_scan`, `engine/regvm-pass.h`): code read by `JS_ReadObject` that drops the catch offset of a record, or takes it off with `nip_catch`, gets the old `W_FOR_OF_START` for that record. A catch offset below 0 is made by nothing else: that of every other record is 0, and that of a `catch` is a place in its function, which the read of bytecode checks. The index is a number, so freeing it and the marking of the collector do nothing with it, and the record holds the `next` method as long as the old one did, which a `WeakRef` to it can see. An index past 2^31 - 2 has none, and an array that long is read by its Array Iterator.

What changes and is not seen by a script: a destructuring polls once less (the call of `values` polled) and takes no level of call depth, so a recursion through it can only go deeper. An empty pattern in a loop with no call stops at an interrupt by the poll of the loop's jump back. The Array Iterator that is not made is an allocation less, so under a memory limit an out of memory error can come at a later place, where the iterator is made. A script that destructures arrays and makes no iterator otherwise holds one shape less, the shape of an Array Iterator.

### What it gains

Counted with callgrind on the native C tree on linux/arm64 against the engine before the change (4922b91a), three timed renders of each page after two warm ones with a young collection after each, the share of a render's instructions it saves: 0.71% on the workbench pages (0.48% to 0.85% a page), 0.33% on the storefront (0.14% to 0.51%), 0.27% on MUI (0.21% to 0.29%) and 0.31% on React. With the URL stand-in of the measurement (`urlmemo.js`, which the shop's pages run for the URL polyfill that tifa will not have) the workbench saves 0.84%, the storefront 0.53% and MUI 0.26%. No page runs more instructions, and the bytes in use after the renders are the same.

Timed in tifa's `test/ssr` on linux/amd64 (an AMD EPYC 7B13 server, one core, 60 renders of each page, the P50, 5 rounds with the two builds in alternating order), the gain is below what the timing can show: the pages took 0.988 of the time on MUI, 0.996 on the storefront and 1.001 on the workbench (sums of the pages, medians of the rounds), where the engine before the change against a copy of itself took 0.982, 0.994 and 1.001. No page took more than 1.007 of the time.

## Fewer argument words into hot calls

Release: Unreleased.

In the generated code every argument word of a call is stored by the caller and loaded by the callee through Go's stack area. On arm64 a function that takes more than five words, besides the pointer of the shadow stack, takes them in a block on the shadow stack, which adds a store and a load that depend on each other. Two hot calls now pass fewer words:

- The interpreter's direct call of a C function (`js_call_c_direct`) and `js_call_c_hop` call `js_call_c_plain(p, this_obj, argc, argv)`: the object of the function rather than its value, no context (the call sets the realm of the function as its context anyway) and no flags (neither path makes a constructor call). That is 5 words where `js_call_c_function` takes 8, so arm64 passes them in registers. `js_call_c_function` stays the call of the class `JS_CLASS_C_FUNCTION`, which `JS_CallInternal` and constructor calls use. Both are the same body, `js_call_c_body`, inlined into each.
- The engine's own `JS_GetProperty` (the macro of `quickjs.h` passes the object as `this` too) calls `JS_GetPropertyObj(ctx, obj, prop, throw_ref_error)`: 5 words where `JS_GetPropertyInternal` takes 7. The exported `JS_GetPropertyInternal` does not change, and both are the same body, `js_get_property`. `js_invoke` still calls `JS_GetPropertyInternal`: with the shorter call, clang on amd64 inlined it into its callers and their frames on the shadow stack grew by 112 bytes.

Why it gives the same results: each new entry runs the body the old one ran, with the same values. In the old `js_call_c_function` the context passed in was used only to find the runtime, and the body set the realm of the function as its context before anything else used it. `js_call_c_plain` takes the runtime from that realm, which belongs to the same runtime.

The depth of a recursion is what needed care. A direct call counts the frame of `JS_CallInternal` it skips as taken while the C function runs, so that a recursion through C functions ends at the same depth either way ([How the interpreter calls a C function](#how-the-interpreter-calls-a-c-function)). That rested on both ways running the same `js_call_c_function`. Now one runs `js_call_c_plain` and the other `js_call_c_function`, and a compiler need not give the two the same frame: native clang gives `js_call_c_plain` 192 bytes and `js_call_c_function` 160 on arm64, and a recursion through direct calls ended about 1.4% less deep on the native test host (unit-api's `c_call_same` failed 36 of its checks). `js_measure_call_frame` now measures the two frames as well, where their shared body starts (an `argc` below 0, on `Function.prototype`, a C function every context has), and the direct call and `js_call_c_hop` add the difference to what they count as taken (`rt->c_direct_debt`, `rt->c_hop_plain_debt`). The checks of the stack before such a call are as before. A debt below 0 would let a call go past the end of the stack, so it turns its path off, as a frame of `js_call_c_hop` larger than that of `JS_CallInternal` does: `JS_RegvmStat` 17 and 18 give the two debts, -1 when their path is off, and unit-api's `test_call_frames_measured` and `TestRegvmFrame` fail when either path is off with the direct calls on. In the generated engine the two frames are the same size, so the debts are as before: 112 bytes for a direct call and 16 through `js_call_c_hop` on amd64, 96 and 16 on arm64. Under AddressSanitizer the two debts are measured from the same two places as the frame of `JS_CallInternal`, and each is the smaller of its two sums rounded down to a multiple of 32, as the others are.

Frames: no function takes more of the shadow stack on either architecture, and the SHADOW of `JS_RegvmRun` stays 176 bytes on arm64 and 256 on amd64. On arm64, 42 functions take less, 2448 bytes in all, as their callees no longer take a block of arguments (`JS_GetPropertyValue` 96 bytes to 32).

What it gains, timed on linux/amd64 over 16 code layouts: the fourteen store pages of tifa's shop 0.67% less time, the workbench, MUI and React pages the same within their spread, with 0.30% to 0.51% fewer instructions per render. The numbers are in [performance.md](../performance.md#fewer-argument-words-into-hot-calls).

The change is in C (`engine/quickjs.c`, `engine/quickjs.h`, `engine/regvm.h`). Tests: unit-api's `test_c_call_recursions` and `test_call_frames_measured`, `TestCCallDepth`, `TestCCallDepthAfterExits`, `TestRegvmFrame`, `compare.sh` with `unit-api` and `unit-white`, and the HTML of the pages of the shop, MUI and React.
