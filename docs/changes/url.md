# URL and URLSearchParams

English · [简体中文](url.zh-CN.md)

QuickJS has neither `URL` nor `URLSearchParams`. Package `url` adds them for a VM that calls `url.Register(vm)`, the way `intl.Register` adds `Intl`. Go parses and keeps nothing: a URL lives in the VM.

## URL and URLSearchParams on a Go parser

Release: v0.30.3.

A bundle that resolves links with `new URL(path, base)` otherwise carries a polyfill, and core-js's costs 42 to 87 µs a URL on this engine. TanStack Router calls it 100 to 170 times in one render of tifa's shop pages, and reads protocol, username, password, origin, pathname, search and hash of each. core-js looks for a good native `URL` first and installs nothing when it finds one, so a host registers this package before the bundle runs and the bundle needs no change.

What a script gets is the whole standard, not what those pages call: the constructor with and without a base, `URL.canParse` and `URL.parse`, every getter and setter, `searchParams` linked both ways, `toString` and `toJSON`, and `URLSearchParams` with its three constructor forms (a string, a sequence of pairs, a record), `append`, `delete` and `has` with the optional value, `get`, `getAll`, `set`, `sort`, `forEach`, `keys`, `values`, `entries`, the iterator, `toString` and `size`. The classes have the shape WebIDL gives them (`TestShape` holds what each property is).

### How a URL is kept

- `new URL(input, base)` calls one Builtin. It parses in Go and answers an array of 11 strings, the href, protocol, username, password, host, hostname, port, pathname, search, hash and origin, and a number whose four bits say what the getters do not: whether the URL has a host (which can be empty), an opaque path, a query and a fragment (each of which can be empty). `url.js` keeps the array in a private field, and every getter is a read of it. Go keeps nothing, so a URL is VM memory under the memory limit, and the garbage collector frees it. No Go finalizer and no registry is needed.
- A setter hands Go the part, the new value and the record of the URL: its protocol, username, password, hostname, port, pathname, search and hash as the getters have them, and the four bits. Go makes the record from them without parsing anything (`whatwgurl.FromParts`), applies the setter of the standard (the basic URL parser with a state override) and answers a new array. `FromParts` takes only the parts of a URL: parts that it gives back as they came, whose href is ASCII and parses to the same record (but for the two records below), and that are at most 65,536 units in all. Other parts, bits that say other than the parts, and a part number that is not a setter's are a TypeError, and the URL stays as it was (`TestFromPartsRefuses`, `FuzzFromParts`, `TestForgedRecord`).
- The record, and not the href, is what a URL is, as in the standard. A setter can make a record that the parser does not make from its href: after `protocol = "file"`, `http://localhost/` is a file URL whose host is `localhost`, which the parser makes the empty host, and `http://h/C|/x` one whose first segment is the drive letter `C|`, which the parser writes `C:`. A URL kept as its href would lose them at the next setter. `FuzzParse` checks that what the parser makes serializes and parses to itself, and `FuzzSetters` that what a setter leaves is made again from its parts.
- No script reaches the record or the Builtins, so none can hand Go parts of its own. The array is in the private field `#r` of the `URL` class, which only the methods of the class read: a subclass, a `Proxy`, `Reflect` with another receiver and an object made from `URL.prototype` do not have it, and reading it through them is a TypeError, as for any private field. Go makes the array with its elements as own properties (`VM.NewArray` defines them, as an array literal does), so no getter or setter of `Array.prototype` or `Object.prototype` sees it, and `url.js` never gives it to a script. The five Builtins are the arguments of the function that `url.js` is, and a property of nothing. A value whose `toString` changes the URL runs before the setter reads the record, so the setter works on the URL as the conversion left it. A VM is one realm, and the Go API refuses a value of another VM. `TestStateIsUnreachable` walks every object a script reaches from the global object and from a URL, its list and an iterator, and finds neither the record nor a Builtin. It then traps the index properties of `Array.prototype` and `Object.prototype`, `Symbol.iterator` and the methods of `String.prototype`, runs every member of both classes, and none of the traps is called.
- A `URLSearchParams` is its list, a flat array of names and values in a private field, and the URL it belongs to when it came from `url.searchParams`. The two stay in step as the standard says: a change of the list sets the `search` of the URL through the same Builtin, and a change of `search` or `href` makes the list again. `url.js` splits a query string and keeps, sorts and serializes the list. Go decodes or encodes one name or value at a time, for the `application/x-www-form-urlencoded` parser and serializer.
- A change of the list of a URL is made on a copy, and the list becomes the copy once the URL took its serialization, so a change the URL refuses leaves both as they were.

### Taking it in with Register

`Register(vm, opts ...Option) error` has the shape of `intl.Register` and `temporal.Register`: it must come before the page runs, a second call on the same VM is an error, and nothing needs releasing, as `Close` does it. It has no options yet. Differences from `intl.Register`: it installs `URL` and `URLSearchParams` at once, where `intl` puts stand-ins and installs the rest at the first use. A VM that registers `url` and never makes a URL carries 37 KiB more (`MemoryUsedSize` 75 KiB to 113 KiB on a new VM), and spends 243 µs more (see Cost and gain). A page of tifa's shop makes URLs in every render, so a stand-in would only move the cost.

The script is compiled once per process, without its source or debug information (so `toString` shows `[native code]`), and every VM loads the same bytecode with `EvalBytecodeValue`, as `intl` does. It does not use `SharedBytecode`: a stripped script has no source or line tables to share. VMs on any number of goroutines share the bytes and a VM copies them into its own memory when it loads them. A pool of VMs that load shared bytecode of a bundle works as before: the registration is per VM and does not touch the bundle.

### A page that changes the built-ins

`url.js` takes `Reflect.apply`, `Object.defineProperty`, `String.prototype.toWellFormed` and the other built-ins it uses when `Register` runs it, before any page code, and uses nothing else: object and array literals, arrays without a prototype for what it appends to, index loops, no template literals (QuickJS makes them calls of `String.prototype.concat`), no spread, destructuring or `for...of` on its own arrays. A URL and a list are in private fields, which no page can read, forge or replace. `TestTamper` runs a battery of calls on VMs whose page replaced `Array.prototype` methods and index setters, `Object.prototype` accessors, string methods, `Object` and `Reflect` functions, `Function.prototype.call`, `apply` and `bind`, `JSON`, `String`, `Object`, `Array` and `Symbol` globals, and the `URL` globals themselves. The battery answers the same on each, and none of the traps the page set was called. What a page does see is what a browser shows too: the sequence form of `URLSearchParams` reads `Symbol.iterator` of what it is given.

### The limits

The work of a parse is in Go, where the polls of the engine do not reach and the memory limit does not count what Go allocates. The package keeps the limits by making every call of Go short, with its memory known before it starts, and not by checking inside Go's loops.

- **A string is at most 65,536 UTF-16 units, going in and coming out.** Every string a Builtin takes goes through one function, `admit` in `url/door.go`. It reads the length the engine keeps for the string (`Args.StringLen`, which reads the length of a rope, a string the engine holds in pieces, without joining it), refuses the call when a string is longer than `whatwgurl.MaxUnits`, checks the room once, and only then reads the strings, into `whatwgurl.Input` values, which nothing else makes. The parser refuses to make a URL whose href would be longer than the limit, and the form serializer an encoding that would be, so every string the package answers can be given back to it: a URL a script holds can always be changed, read into a list and set to itself.
- **What a script sees past it.** A `data:` URL of more than 64 KiB, such as a small image, is not a URL here. Browsers take longer ones: Chromium up to 2 MiB, Firefox up to 1 MB and 32 MB for `data:` URLs.

  | Call | Past the limit |
  | --- | --- |
  | `new URL(input, base)` | TypeError, when the input or the base is longer than 65,536 units as given (the spaces, tabs and newlines the parser would remove count), or when the href would be. 7,281 CJK characters in a path are too long: each is 9 units once percent-encoded |
  | `URL.parse`, `URL.canParse` | `null`, `false` |
  | a setter other than `href` | the URL is left as it was |
  | the `href` setter | TypeError |
  | a host of a special scheme that is not ASCII | the host of `http`, `https`, `ws`, `wss`, `ftp` or `file` goes through IDNA, and is not a host when it is longer than 1,024 units after percent-decoding, or once IDNA maps it, or once it is normalized: 1,024 soft hyphens, which the mapping deletes, or 1,024 full-width digits that would make an IPv4 address, are too long, and so are 257 of U+3300, which maps to four katakana: a domain whose mapped form passes 1,024 units is refused. An ASCII host, and the host of another scheme, which IDNA does not process and is only percent-encoded, have no limit but the URL's: `URL.canParse("x://" + "é".repeat(1025))` is true, and false with `http://` (`TestDomainLimit`) |
  | a name or a value of a query string | RangeError from the constructor of `URLSearchParams` when it is longer than 65,536 units and has a `+` or a `%` (one without them is not decoded, and has no limit), and from `toString` when its encoding would be longer |
  | `append`, `delete`, `set` and `sort` of the list of a URL | RangeError when the href would be longer than the limit, and neither the list nor the URL changes |

- **Time.** With strings that short, a call of Go is over in a few milliseconds. Its work is in proportion to its input, but for the IDNA of a host, which the limit of 1,024 units bounds. The slowest call is a path of CJK characters at the limit: 2.0 ms on an Apple M4 and 5.6 ms on an x86-64 server, inside the 12.5 ms the engine aims for between two checks of its stop flag, a quarter of the kill grace of 50 ms. IDNA of a host at its limit takes at most 0.24 ms on the M4. Each call looks at the stop flag once, as it starts. The engine counts toward its next poll the bytecode it runs, not the time a Go function takes, so a loop around a call of a few milliseconds made 9 to 75 calls between two polls. With the look, the eval timeout and `Interrupt` end the script at the next call, or at the next poll of the javascript between, whichever comes first.
- **Punycode in n log n.** The Punycode encoder of RFC 3492, as golang.org/x/net has it, goes over a label once for each code point that is not ASCII, so a label of different code points costs the square of its length: 4 µs a unit at 1,024 units, 16 to 29 µs at 8,192. The encoder here (`internal/whatwgurl/idna/encode.go`) gives the same output and counts with a Fenwick tree, in time n log n: 48 to 60 ns a unit.
- **The loops over a list are in javascript.** Go never sees a list or a whole query string. `url.js` splits a query string at `&` and `=` with the `indexOf` and `slice` it captured, calls Go only for a name or a value that has a `+` or a `%`, and sorts, walks and serializes the list itself. These loops run under the polls and the memory limit of the engine, as any script does.
- **Memory.** Before it reads a string, a call checks against `vmhook.Room` 160 bytes for each unit it admits, 128 KiB for each host it may parse (two for a parse with a base, two for the `host` and `hostname` setters, one for the other setters, whose record has a hostname that `FromParts` parses again, and none for the other calls), and 16 KiB more, and ends with the out of memory error (`vmhook.OutOfMemory`) when that does not fit. A host has room of its own because IDNA costs the most for each unit, and a short string can make a long domain: U+FDFA maps to 18 units, the most of any code point in the tables (`idna.Widest` finds it), so 57 of them make a domain of 1,026 units. The domain is refused as soon as its mapping passes 1,024 units, so what follows works on 1,024 units at most, whatever the string. The most Go allocated for one host in the tests is 81 KB, for a label of Punycode that decodes to characters of two units each. The room is for what Go holds at once while a call runs. The tests measure what Go allocates in all during the call, which is more, so the check errs on the safe side. The tables of the first normalization of a process (190 KB) are built by `Register`, and not in the first call that needs them, which has not checked room for them.
- **The parts of a record are at most 65,536 units in all.** A setter admits the value and the eight parts of the record, each at most 65,536 units. The parts of a URL sum to less than its href, so to at most the limit, but they come from javascript, and the door checks it, before it reads them: a call whose parts sum to more is a TypeError (`TestDoorSumsTheParts`). The room is checked for all nine strings.
- **Nothing outlives the call.** What Go makes for a parse is garbage when the Builtin returns. No variable of the package holds what a script gave or anything that changes (`TestNoPackageState` reads the source and fails on one that is not a Builtin, the compiled script or a hook of a test). The parsed bases that an earlier version of this package kept in a cache, to save a parse of `http://localhost` 100 times a page, are not kept: they were Go's memory, counted in no VM and kept after its VM closed.
- **The buffers of package quickjs.** `Args.String` writes the UTF-8 of a string of more than 64 units into a buffer it takes from a `sync.Pool` and puts back for the next string, so the bytes of a string Go read may stay in it. A read of n units puts back the buffer it took when that had room for 3n bytes, or else one of exactly 3n bytes (`TestScratchPutBack` in the root package), so through the door, where n is at most 65,536, a call of the package makes no buffer larger than 192 KiB. A larger one in the pool was made by a longer string read elsewhere in the process, and none is larger than 3 bytes a unit of 2^18 units: a longer string is read a piece at a time, through a buffer of 48 KiB of its own, not one of the pool. A call refused for its length reads nothing. How many buffers the pool keeps, and for how long, is Go's: it may drop any of them at a collection or at any time. They are the process's memory: no VM's limit counts them, and they do not go when the VM closes.

The tests of the limits:

- `TestDoorIsTheOnlyWayIn` reads the source: it fails when a file of `url` other than `door.go` reads an argument, makes a string for javascript or makes an `Input`, when one imports `internal/whatwgurl/idna`, and when `internal/whatwgurl` exports a function that takes a string other than `NewInput`. `TestDoorCheckCatches` checks it finds each of these in a new file.
- `TestDoor` gives every entry a string of 65,537 units, of 16 times the limit, and a rope of 2^30 − 1 units, the longest string of the engine: each call answers as the table says, allocates under 1 KiB in Go and takes under 200 µs, the same for each length, with the rope not joined. At the limit, each is made. `TestStringLen` checks the length the door reads against the one javascript sees. `TestDoorNineLikeOne` checks that a call of nine strings allocates no more in the door than one of one string: none (`Args.StringLen` allocates nothing).
- `TestRoomCoversGo` measures what Go allocates in every call of a Builtin, for 31 entries on 44 shapes of input at the limit, and fails when a call took more than the room it checked. The most is 43% of it (a userinfo of CJK characters). Eight shapes are hosts: of the code points `idna.Widest` finds in the tables, the one that maps to the most units and the one that decomposes to the most (U+FDFA to 18, U+01D6 to 3, which `TestWidest` checks), at the limit of a domain as given and once mapped, and labels of Punycode that decode to characters of two units. `FuzzRoom` does the same for text the fuzzer makes, a unit repeated a number of times it chooses, seeded with those code points. `TestFirstNormalizationCounted` runs in a new process and checks the first host that needs NFC stays in its room.
- `TestTimeout`, `TestInterrupt` and `TestOutOfMemory` run 14 scripts that never end, each stuck in the work of a URL or a list: a parse, a setter and IDNA at the limit, a query string of 16 MiB split again and again, a list of 262,144 pairs sorted, walked and serialized, and the list of a URL changed. Each ends with the interrupt within 50 ms of its timeout, or, with 8 MiB of room, with the out of memory error, and the VM is good after. `TestStopAtNextCall` asks to stop inside the fifth call of Go of each, and checks that no call starts after it. `TestNoRoomNoRead` checks a call with too little room ends before Go reads its strings.
- `TestAtTheLimit` and `TestOwnOutputGoesBack` check the table above at the limit and one unit past, and that a URL at the limit can be changed, set to itself and read into a list. In `internal/whatwgurl`, `TestNewInput`, `TestSpacesCount`, `TestNothingLonger`, `TestDomainLimit` and `TestFormEncodeLimit` do the same for the parser (`TestDomainLimit` also for a domain at the limit once mapped), and `TestWorstAtLimit` times a parse of each of 36 shapes at the limit, and of the hosts of the code points the tables grow the most, against 12.5 ms (times how much slower than usual the machine is just then).
- `TestEncodeRandom` compares the Punycode encoder with the one of RFC 3492 on 200,000 random labels, up to 1,024 code points, and `TestEncodeWPT` on every label of the IDNA files of web-platform-tests and what each Punycode label of them decodes to. `TestEncodeLinear` checks that a label of 1,024 different code points takes at most 10 times one of 256 (the encoder of the RFC took 16).

### The parser

`internal/whatwgurl` is the parser of the URL standard of 2026: the basic URL parser with state overrides, the host parser (IPv4, IPv6, opaque hosts), the percent-encode sets, the serializer, the setters of the API and the origin. [SOURCES.md](../../internal/whatwgurl/SOURCES.md) says what came from where.

- It started as `url/` of github.com/nlnwa/whatwg-url v0.6.2 (Apache-2.0, 2025-03). That library passed its own WPT data of 2023 in full and, on today's, missed 15 of 904 cases of `urltestdata.json`, 11 of 278 setter cases and 7 of 87 of `toascii.json` (with golang.org/x/net v0.62). Those come from three changes of the standard of 2024 to 2025, which are in: an opaque path keeps its trailing spaces as `%20` when `?` or `#` follows, `^` is in the path percent-encode set, and a domain that is ASCII does not go through IDNA when the domain to ASCII is not strict, so a `xn--` label with invalid punycode is kept as written.
- It was then rewritten, not patched. The library reads its input as a list of runes, copies the whole input to check what follows a character, adds to the userinfo string by string (so that a long password costs the square of its length), keeps options, an encoding override and a list of validation errors, and has no stop check. The state machine here reads the UTF-8 where it is, with a byte offset as the pointer. On `http://localhost` and a shop path it takes 0.55 µs and 14 allocations, against 1.9 µs and 44.
- The IDNA code is `idna/` of golang.org/x/net v0.62.0 with one profile (CheckBidi and CheckJoiners on, no transitional processing, the algorithm of UTS #46 revision 35), the Unicode 17 tables on every Go release (x/net takes Unicode 15 before Go 1.27), the Bidi tables and rule of golang.org/x/text v0.44.0, and NFC from `internal/gointl`. No new module is needed. The punycode decoder keeps x/net's limit of 1,024 characters in a label.

The data is the URL data of web-platform-tests at commit `8af128e` of 2026-11-12 (`internal/whatwgurl/testdata`). `TestWPTParse`, `TestWPTSetters`, `TestWPTToASCII` and `TestWPTPercentEncoding` run it on the parser, and each case is compared on href, every part and the origin. They pass in full but for 7 cases of `IdnaTestV2.json`, listed in `testdata/known-failures.txt`: the file is made from a newer `IdnaTestV2.txt` than Unicode 17, in which U+3E8AC and U+3F8CD are valid, and the tables here call them disallowed. A case that passes while listed fails the test, so the list only shrinks.

`url/` runs the same data in a VM (`TestWPT`): the 23 files `url-constructor`, `url-origin`, `url-setters`, `url-setters-stripping`, `url-statics-canparse`, `url-statics-parse`, `url-tojson`, `url-searchparams`, `urlencoded-parser`, the 11 `urlsearchparams-*`, `historical`, `IdnaTestV2` and `IdnaTestV2-removed` of `url/` of web-platform-tests, as they are, on a few functions of testharness.js (`testdata/harness.js`). 4,747 tests run. 81 are in `url/testdata/known-failures.txt`, each with its reason: 72 call `Request`, `Response`, `FormData` or `DOMException`, which belong to the host, not to the engine, 2 need `structuredClone`, and 7 are the IDNA cases above. The check of core-js runs `internals/url-constructor-detection.js` of core-js 3.50.0 as it is, and `URL.canParse` as `web.url.can-parse` tests it (`TestCoreJSDetection`): both say the native one is good.

### What a script sees that is not core-js

- `Object.getOwnPropertyNames(url)` is empty. tifa's build of core-js keeps its state in a property (`'\0tifa-core-js-property-state'`) that a script can see, and browsers keep none.
- The host is processed by UTS #46 with the mapping, CheckBidi and CheckJoiners, where core-js has only punycode: full-width letters, `xn--` labels and the corners of IPv4 hosts come out as a browser makes them. On the relative paths that tifa's pages pass, which are ASCII, nothing changes.
- The errors are `TypeError`s, as in a browser, with other words.
- An input, a base or an href longer than 65,536 UTF-16 units is not a URL, a host of a special scheme that is not ASCII and longer than 1,024 units, as given or once IDNA maps it, is not a host, a name or a value of a query string that long is a RangeError when it has a `+` or a `%`, and so is one whose encoding would be, and a punycode label above 1,024 characters is refused (x/net's limit): the standard has none of these. See the limits.
- `URL.createObjectURL` and `URL.revokeObjectURL` are not there: the VM has no Blob. core-js has stubs that throw.
- core-js wraps `fetch` and `Request` when it installs its own `URLSearchParams`, to give a body of that type its content type. With the native one it does not, and whatwg-fetch does it by testing for `URLSearchParams` itself.
- `structuredClone` only compares with `URL.prototype`, so it is not changed.

### Differences from Node, and the size

The parser was also compared with Node 24 (ada 3.3.0, ICU Unicode 16) on 60,000 random inputs against 8 bases, and the URL of the VM on 60,000 random URLs changed by one setter, 60,000 by two and 60,000 by three, with random values and values that reach the corners of the setters (file, localhost, drive letters, empty hosts, default ports). Node differs from the standard in these places, and this package follows the standard (and so Chromium, which checks the Bidi rule):

- Node does not apply CheckBidi: `new URL("http://example.com\u0627")` (Latin letters with an Arabic one in a label) is a URL in Node and a failure here, as it is in a browser.
- Node 24 fails a domain that is ASCII and has a `xn--` label with invalid punycode (`http://xn--a`). The standard of 2025 keeps it as written, as here.
- Node resolves an input that has a `#` in it against a base with an opaque path (`new URL("0x#@", "data:text/plain,x")` is `data:text/0x#@`). The standard fails, as here: only an input that starts with `#` can be resolved against such a base.
- Setting `host` or `hostname` of a URL that has no host (`x:/`) to an empty value or one that starts with `/` leaves the URL as it was in Node. The standard gives it an empty host (`x:///`), as for `view-source+http://example.net/foo`, which web-platform-tests tests.
- Node keeps a URL as its href and parses it again (ada's `url_aggregator`), so a record the parser does not make from its href is lost at a later setter: after `protocol = "file"` on `http://localhost/` or `http://h/C|/x`, Node makes the host empty or the drive letter `C:` at the next setter, and refuses to change the protocol back. The standard and this package keep both, and so does Chromium, which writes the | as `%7C` in any path.
- Setting `pathname` to a value that starts with `//`, on a URL with no host, drops its query and fragment in Node. The standard leaves them.
- Node keeps the `/.` in front of a path that starts with `//` when the URL then gets a host (`x://C/.//`). The standard writes it only when there is no host (`x://C//`).

Leaving out the inputs that hit the first three, the two agree on all 60,000 parses. Of the URLs changed by one, two and three setters, 100, 243 and 341 differ, each in one of the last four ways: an empty host on a URL with none (438), the href Node parses again (184), the query or fragment dropped (60) and the `/.` (2).

Package `url` links `internal/gointl` for NFC, and with it the data go-intl embeds. A program that links `url` and not `intl` is 8.1 MB larger (8.1 MB to 16.2 MB on darwin/arm64 with a VM and one `Eval`). A program that links `intl` already has it, and pays nothing more.

### Cost and gain

Measured on an Apple M4 with `GOMAXPROCS=1` unless said otherwise.

**In Go.** `BenchmarkShopURL` (`internal/whatwgurl`): parsing a shop path against a parsed `http://localhost` and serializing it with its parts takes 0.55 µs and 14 allocations. The library this started from took 1.9 µs and 44 allocations on the same machine (measured when the parser was chosen).

**In a VM.** `BenchmarkShop` (`url`): `new URL(path, "http://localhost")`, a write of `pathname`, and reads of protocol, username, password, origin, pathname, search and hash take 4.67 µs, with 49 allocations and 1,816 bytes in Go. The check that the record a setter is handed is a URL's, which parses its href again, takes 0.66 µs, 12 allocations and 432 bytes of it: without it the same takes 4.01 µs. core-js's polyfill takes 42 to 87 µs for the same.

**What Register costs a VM.** `BenchmarkRegister` (`url`), 3 runs of 2 s each: `NewVM` alone takes 81 µs, `NewVM` and `Register` 324 µs, so `Register` takes 243 µs once the bytecode is compiled (the first call of the process compiles it). `MemoryUsage` of a new VM: `MemoryUsedSize` 77,128 bytes without it and 115,465 with it (37.4 KiB more), `MallocSize` 202,872 and 318,072 (112.5 KiB more), 94 more objects of the engine's own count (164 to 258 objects, 116 to 154 shapes). A program that links `url` and not `intl` is 8.1 MB larger (see above).

**In tifa.** A scratch copy of tifa, pointed at this work tree by a `replace`, registers the package before the bundle runs (`internal/ssr.Load`). Warm renders of the 23 pages of the shop and MUI examples with and without it, 6 rounds that alternate the two (the order turned each round), one process per group and head, `GOMAXPROCS=1`, with the lanes of the machine held but other work beside them (load average 4 to 7). | --- | --- | --- | --- | --- |
| store, 14 pages (7 pages in 2 languages) | 107 (69 to 169) | 19.88 | 13.30 | -33.1% |

The time saved per URL is 61 µs in the store pages (6.5 ms over 107 URLs) and 50 µs in the workbench pages, which is what the polyfill costs less the 5 µs that remain. The best page of the store, the journal of zh-CN, is 43% of its time (7.75 ms to 3.30 ms), and the product list of zh-CN goes from 36.09 ms to 23.78 ms with 169 URLs. The HTML of all 23 pages is byte for byte the same with and without the package, in every round (the SHA-256 of the first render of each process). The counts are of `new URL` calls in one warm render, counted with a `Proxy` on the global in a run of its own.

The instructions the processor retires say the same (macOS counts them for `/usr/bin/time -l`). One process for each group and head renders every page 5 times after 5 warm renders, and another renders it once: the difference is 4 renders of every page. ### Tests

`go test ./url ./internal/whatwgurl/...`, also with `-race` and with `GOTOOLCHAIN=go1.26.6`. In `internal/whatwgurl`: the WPT data, the tests of the limits above, `TestPartsKeepTheRecord`, `TestFromPartsTakes` and `TestFromPartsRefuses` (the two records the parser does not make from their href are made again from their parts, the parts of URLs of every kind are taken, and 46 kinds of parts that are not a URL's are refused with an error: a protocol, a port, a host, a user, a path, a search or a hash not as the serializer writes it, bits that say other than the parts, parts longer in all than the limit), `TestPunycodeLabelChecks`, `TestParallel` (16 goroutines, hosts that need NFC) and four fuzz targets, and in `idna` the three tests of the encoder and `TestWidest`. In `url`: `TestWPT`, `TestCoreJSDetection`, `TestCoreJSKeepsNative`, `TestBattery` and `TestTamper`, `TestShape`, `TestParallelVMs`, `TestConversion...`, `TestSequenceConvertsFirst`, `TestManyURLsCountedInVM`, `TestSettersKeepTheRecord` (a setter after a change of protocol keeps the host `localhost` and the drive letter `C|`), `TestForgedRecord` (29 kinds of forged arguments of `set`, each a TypeError that leaves the URL as it was), `TestStateIsUnreachable` (see how a URL is kept) and the tests of the limits above. In the root package, `TestScratchPutBack`.

The fuzz targets are seeded from the WPT data. In `internal/whatwgurl/fuzz_test.go`: `FuzzParse` (an input of at most 65,536 units never panics, and what it makes is ASCII, at most 65,536 long and parses again to the same record), `FuzzSetters` (each setter leaves a record that its parts make again and whose href is a URL, and one it refuses as too long is the URL as it was), `FuzzFromParts` (the parts of a URL with one replaced and the bits flipped: `FromParts` never panics, and what it takes it gives back and passes the checks of `FuzzSetters`) and `FuzzLimit` (a parse, or a setter on a long URL, of an input of 65,536 units made of a prefix, a unit repeated and a suffix, takes at most 12.5 ms times how slow the code runs just then). In `url/room_test.go`: `FuzzRoom` (what Go allocates in a call is within the room it checked). Run one with `go test -run '^$' -fuzz '^FuzzParse$' -fuzztime 3m ./internal/whatwgurl`. A failing input goes into `testdata/fuzz/<target>/`, which `go test` then runs as a test, with the fix.
