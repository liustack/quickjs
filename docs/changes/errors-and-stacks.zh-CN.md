# 错误和调用栈

[English](errors-and-stacks.md) · 简体中文

## 错误的 stack 在第一次读取时才格式化

发布版本：v0.26.1。

创建错误时不再格式化它的 `stack`。引擎只记录栈帧（函数名、字节码和位置），第一次读取 `stack` 时才格式化出文本，结果和以前一样。创建很多错误、只读其中少数 stack 的代码，例如 React 的开发构建（每个 JSX 元素一个错误），跑得快得多。在 darwin/arm64 上，用开发构建服务端渲染一个 100 项的 React 组件，中位数是 11.2 ms，以前是 42.1 ms。同一组件的生产构建、一个四路由应用的生产构建和一个 JSON 与数组的基准，都和以前相差不到 1%。每次运行创建 500 个错误的顶层代码用时 1.8 ms，以前是 3.2 ms。`stack` 是普通的可写、可配置的数据属性，所以这个错误的形状和一开始就格式化了 stack 的错误一样。一旦读过，它就是那个字符串。有区别的地方是：

- stack 还没格式化时，`stack` 的值是一个内部对象，里面存着记录下来的栈帧。所以一个待格式化的错误多出三次小的分配：这个对象、它的属性列表和栈帧记录（短 stack 约 150 字节）。对 `stack` 赋值、定义或删除，会像释放其他值一样释放它们。这个内部对象属于一个私有类，是每个运行时都有的内置类。
- 没有代码能看到这个内部对象。所有读取 `stack` 的值的操作都会先格式化它：脚本里和通过 C API 的属性读取、`Object.getOwnPropertyDescriptor(s)` 和 `JS_GetOwnProperty`，以及用一个值重新定义已冻结的 `stack`（引擎要比较旧值和新值）。只看键或属性特性的操作会让它保持待格式化：`Object.keys`、`Object.freeze`、`Object.seal`、`Object.isFrozen`、`Object.isSealed`、`propertyIsEnumerable`、`__lookupGetter__`、`__lookupSetter__`，以及目标是这个错误的 proxy 在 `has`、`deleteProperty` 或 `ownKeys` trap 之后做的检查。`stack` 不可枚举，所以展开、`Object.assign`、`Object.entries` 和 `JSON.stringify` 都会跳过它。
- 通过 proxy 时，除了上面这三种检查，`stack` 和以前一样会被格式化。通过 proxy 查找属性特性（例如对 proxy 调用 `Object.keys`、`Object.freeze` 或 `propertyIsEnumerable`），以及 proxy 在 `get`、`set`、`defineProperty` 或 `getOwnPropertyDescriptor` trap 之后做的检查，都会读取错误的完整描述符，这会格式化 stack。结果、trap 的调用和调用顺序，都和一开始就格式化 stack 时一样。代价在内存上：几乎没有内存时，这样的操作可能因内存耗尽而失败，而上游引擎在创建错误时就已经格式化了 stack。
- 读取名为 `stack` 且值是对象的属性，会走解释器的慢路径，stack 就是在那里被格式化的。其他属性读取不变。在 160,000 次读取的循环里，`o.x` 比以前少用 1% 的时间，`o.stack` 持有数字时多 5%，`o[k]` 多 1%，继承来的 `o.x` 少 9%。这里一次读取约 19 ns，所以每次读取的变化都不超过 2 ns。
- 在 stack 被读取或错误被释放之前，错误会让它栈上每个函数的字节码一直活着，连带每个函数编译所在的 realm（全局对象）。这些大多本来就活着。例外是只运行一次、创建了一个被别处保留的错误的函数，以及它定义的所有函数：一个定义了其他 2,000 个函数的函数，只保留一个错误就多留了 1.30 MB，以前只留 0.30 MB。在一个 realm 里创建、被另一个 realm 保留的错误，会让第一个 realm 和它全局里持有的一切都留着：第一个 realm 里有一个 4 MiB 的 `ArrayBuffer` 时，运行时用了 4.31 MB，以前只留 67 KB，直到 stack 被读取。只保留文件名和行表有两种办法。一是给每个错误的每一帧复制一份行表，这会给每个创建的错误增加工作和内存，而这个改动要优化的正是这种情况。二是给行表单独加一个引用计数，这要改引擎的一个结构体。
- 读取 stack 会释放那三次分配，但它们在仍然活着的对象之间留下的空洞，只会被之后相同大小的分配重用。创建 10,000 个错误、全部保留、再读取每个 stack 之后，分配器占了 3.60 MB，一开始就格式化 stack 时是 2.06 MB。
- 在顶层代码（脚本、eval 或模块体）还在栈上时创建的错误，仍然立刻格式化，这样库在加载时保留下来的错误不会让那段代码一直活着。不能加新属性的错误和已经有 `stack` 的错误也一样。
- 第一次读取 `stack` 时如果没有内存了，这次读取会抛出内存耗尽错误，这会结束调用，stack 保持待格式化，所以之后的读取还能得到文本。读取属性描述符会同样地格式化 stack，所以也可能抛出。打印一个 stack 还没格式化的错误（`console.log`、`JS_PrintValue`）时，格式化 stack 从不抛错，也不留下待处理的异常：这时内存耗尽会打印不带 stack 的错误，之后的读取仍然能得到它。这只针对 stack。打印的其余部分，例如 message，仍可能内存耗尽并留下异常，和上游引擎一样。打印 stack 已经是字符串的错误，和以前一样。
- 如果一开始就格式化 stack 时文本格式化不出来（格式化中任何一次分配都可能失败：扩大文本缓冲区、把函数名或文件名转成 UTF-8、生成最终的字符串），`stack` 变成 `null`，也不留下异常。上游引擎在文本缓冲区扩不动时同样得到 `null`。转换函数名失败时，上游则保留一个格式化到一半的 stack，函数名显示为 `<anonymous>`，并留下一个待处理的异常。

## 无限递归抛出 RangeError

发布版本：v0.26.6。

无限递归会抛出 `RangeError: Maximum call stack size exceeded`，措辞和 V8 一样，默认设置下脚本可以捕获它。`SetMaxStackSize` 设置调用最多嵌套多深：默认 5000，最大 10000（tifa 示例商店一个页面的 React 渲染需要约 470）。解析器和 `JSON.parse` 对嵌套过深也报同样的 `RangeError`，和 V8 的解析器一样，嵌套过深的正则表达式则编译失败，报 `SyntaxError: stack overflow`。深度怎么计算、每种形式能嵌套多深，见 [c-engine.md](c-engine.md#depth-of-calls-and-of-c-recursion)。
