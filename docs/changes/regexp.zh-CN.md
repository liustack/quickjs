# 正则表达式

[English](regexp.md) · 简体中文

引擎把正则编译成字节码，在回溯机里运行。`engine/` 里的 C 树用 C 实现了这些，每一节会说明。

## 跳到正则可能匹配的位置

发布版本：v0.26.15。

不是 sticky 的正则，不再在回溯机里尝试字符串的每个位置。它的字节码开头原来是一个循环：在一个位置尝试匹配，跨过一个字符，再尝试。非多行模式下以 `^` 开头的正则只在位置 0 运行。Unicode 正则（`u`、`v`）、忽略大小写或多行的正则（`i`、`m`），以及第一个 op 是其他类型的正则，在 [分支](#不会匹配的分支不入栈) 那次改动之前都走旧路径。`lreSkip` 每查看 65,536 个字符就检查一次中断，回溯机则是每 10,000 步检查一次，所以在长字符串上反复运行的正则，仍然会被eval 超时和 `Interrupt` 停下。在 linux/amd64（AMD EPYC）上，tifa 示例商店一个页面的服务端渲染少用约 3% 的时间，HTML 相同。

改动在 C 里（`engine/libregexp.c`）：`lre_skip`、`lre_first_set`、`lre_find` 和 `lre_run`，由 `lre_exec` 调用。8 位字符串里，正则开头的字符用 `memchr` 查找。`lre_first_set` 用自己的列表而不是递归去走各个 split 的分支，得到同样的集合和同样的预算。`engine/test/compare.sh` 会运行 `testdata/regex.js`、`regexsplit.js`、`regexpv.js`、`shikire.js` 和 `engine/test/compare/regexskip.js`（比一个块更长的字符串，8 位和 16 位，超过两种预算的多分支）。

## 不会匹配的分支不入栈

发布版本：v0.26.17。

由多个分支组成的正则，不再尝试在某个位置上不可能匹配的每个分支。像 `(red|blue|...)` 这样的多分支会编译成一串 split op，每个 split 在机器尝试某个分支之前，先为下一个分支压入一个状态，所以字符串的每个位置，机器都要为每个分支压入和弹出一个状态。react-spring 用来测试值的 148 个颜色名（`new RegExp('(' + names.join('|') + ')(?!\\w)', 'g')`），每个位置就是 147 个状态。

- `lre_exec_backtrack` 的 split op 先问 `lreSplit`，它要压入的那条路在这个位置上能不能开始：如果这条路以一个字符或一个字符类开头，前面只有保存捕获组的操作，而这个位置上的字符不匹配，那么这条路一弹出就会失败，这时什么也不压入。当机器走的那条路是另一个 split op（像多分支那样），`lreSplit` 在同一次调用里接着看那一个，最多看 4096 个 split op，超过后把它停在的那个交还出来，照常压入。它读字符的方式和机器一样，测试的方式和 op 一样，忽略大小写的正则用同样的 `lre_canonicalize`，所以这对每个正则和每个标志都成立，包括 lookbehind 和 sticky 正则。
- `lreSkip` 认得更多的第一个 op。`lreFirstSet` 从正则的开头出发，沿着每个 split 的两条路，越过保存操作和断言（`^`、`$`、`\b`、lookahead 和 lookbehind，直到它们后面的 op），走到每条路径上第一个读字符的 op，收集匹配可以以哪些字符开头：256 个 Latin-1 单元的集合加上代表所有其他字符的一个位。遇到以下情况它会放弃，这个正则走旧路径：某条路径可以不读字符就走到末尾（正则可以匹配空字符串）、遇到往回的跳转、遇到它不认识的 op（`.`、`\s`、反向引用、忽略大小写的类等）、以及超过 1024 个 op 之后。忽略大小写的字符，如果是 ASCII，就算作它自己和它的小写：在非 unicode 模式下，`lre_canonicalize` 不会给其他单元一个 ASCII 的规范形式（`engine/test/unit.c` 里的 `test_canonicalize_ascii` 检查了每个单元）。忽略大小写或多行的正则现在也走这条路径。然后 `lre_exec` 调用 `lreRun` 来代替机器：它在第一个可能开始匹配的位置尝试匹配，不经过字节码开头的位置循环，失败时在 Go 里找下一个这样的位置再试，对 `lreSkip` 处理的、以一个字符或字符类开头的正则也是如此。这就是循环做的事：依次尝试每个位置，每次从循环之前的捕获状态（全部清空）开始，`lreRun` 在每次尝试之前再清一次。它在每次失败的尝试后轮询机器的中断计数器，并且每查看 65,536 个字符检查一次中断。

为什么安全：不入栈的状态，本来弹出后在第一个字符就会失败，而之前的保存操作在失败时会被机器撤销。被跳过的位置，是正则的任何路径都无法读它的字符的位置。结果、捕获组、`lastIndex` 和正则抛出的错误都相同。机器在每个 `goto`、每个循环和每次失败的弹出处计一步并检查中断，贪婪的 `x+` 通过 split op 往回跳，所以在长字符串上，它原来只通过压入过的状态的弹出来计数。因此不压入任何东西的 split op 要自己计一步并检查，一次很长的匹配仍然会在eval 超时触发或调用 `Interrupt` 时停下。不同的是计了多少步：每次什么也不压入的 `lreSplit` 调用计一步，不管它越过了多少个 split，而机器原来是每弹出一个状态计一步。所以中断会在不同的 op 数之后让匹配停下。而且不入栈的状态不占回溯栈的空间，所以接近内存上限的正则，现在可以继续运行，而以前会内存耗尽。

`BenchmarkRegexColors` 为 react-spring 的颜色名正则计时一次 `replace`：在 linux/amd64（AMD EPYC，单核）上，值里没有颜色名时用 5.9 µs，以前是 44.5，有颜色名时用 8.5 µs，以前是 20.2（10 次运行的中位数）。不开 PGO，HTML 相同、VM 内存相同，tifa 示例商店的一次渲染少用约 1% 到 2.5% 的时间，tifa 测试应用的 MUI 页面少用约 3% 到 5%。对比 `a84c8ed`（split op 还没把步数计入中断检查时），10 轮的中位数是商店 0.989（各轮 0.981 到 1.015），MUI 页面 0.946 到 0.954，对比 `80261af` 跑两次，商店是 0.983 和 0.987，MUI 页面是 0.947 到 0.965。计入步数之后，对比 `de42e83` 跑两次，每次 3 轮，商店是 0.983 和 0.975，MUI 页面是 0.962 到 0.993。bench 页面的变化小于它们自己的噪声（table 各轮之间自己就差 10%）。这几轮期间，机器的其他核上还在跑别的任务（平均负载最高到 6）。

改动在 C 里（`engine/libregexp.c`）：`lre_exec_backtrack` 的 split op 调用 `lre_split`，op、预算和中断步数都相同。

## 正则从哪里开始找，编译时算一次

发布版本：v0.30.2。

[跳过](#跳到正则可能匹配的位置) 要知道一个正则的两件事：用哪种方式找开始位置，以及匹配可以以哪些字符开头。这两件事只取决于字节码，但 `lre_exec` 每次调用都重新算一遍：每次 `test`、`exec` 和 `replace` 里的每次匹配，`lre_first_set` 都要把字节码走一遍。现在 `lre_compile` 在 `lre_plan` 里算一次，存在紧跟字节码的 36 个字节里。扫描再用它多做两件事：

- 匹配以一个字符类开头，或者以一组字符中的某一个开头的正则，在 8 位字符串里找开始位置时查一张 256 位的表：每个字符测一位，原来是每个字符对字符类做一次二分查找。16 位字符串里，字符类仍然用二分查找，因为表里只有 256 以下的字符。
- 以几个字符的字面量开头的正则，比如 emotion 的 `label:\s*([^\s;{]+)\s*(;|$)`，和以前一样用 `memchr` 找第一个字符，然后比较后面的字符（最多 255 个），只在字符串里有完整字面量的位置才运行回溯机。忽略大小写的正则不走这条路，因为它的第一个 op 不是普通字符，unicode 和 sticky 的正则也不走，它们没有可以跳过的循环。

为什么安全：表里的集合就是 `lre_first_set` 给出的集合，所以尝试的位置相同。字面量不完整的位置，回溯机在读过字面量之前就会失败，之前的保存操作会被撤销，捕获组仍是清空的。匹配、捕获组、`lastIndex` 和错误都相同。扫描仍然每 65,536 个字符读一次中断标志，16 位字符串里的字符类每 16,384 个读一次（四分之一），因为它的二分查找每个字符的开销最多是查表的四倍。被字面量排除的位置，仍然像一次失败的尝试那样轮询回溯机的计数器。原来，在一个 32 Mi 字符、从不匹配的字符串里，seroval 那个字符类的二分查找会让 11 到 14 次轮询看到停止请求，而 eval 超时只允许 `stepStopPolls` 次。现在每种扫描方式都在这个次数之内停下。

这些信息只取决于字节码。共用字节码的正则，同一个字面量的各个对象、`new RegExp(re)`，以及 [缓存](#按-vm-保存编译好的正则) 给出的对象，不管在运行时的哪个 realm 里，读的都是同一份，`lre_compile` 之后没有代码再写它。这 36 个字节是字节码字符串的一部分，所以算进 VM 的内存上限和缓存的字节数，随字节码一起释放。

函数的字节码里含有它的正则字面量的字节码，所以字节码版本从 8 升到 9：旧版本 `Compile` 写出的字节码不能再读入（`SyntaxError: invalid version`），要重新编译。读回来的就是写入方算好的那一份：回溯机本来就照原样使用读入的正则字节码，这份信息没有增加需要信任的东西。

## 以字面量开头的一长串分支

发布：v0.30.2。

像 react-spring 的 148 个颜色名 `(aliceblue|antiquewhite|...|yellowgreen)` 这样的分支，除第一个分支外，每个分支编译成一个 split 操作，一个接一个排着。机器每到一个位置，`lre_split` 都要把它们挨个走一遍，看哪些分支能从这里开始，不管是什么字符都走 147 步。现在 `lre_compile` 找出每一段至少 15 个这样的 split 操作（16 个分支）、分支全都以一个字面量字符开头的连续片段，在 plan 后面为它记下：以每个字符开头的第一个分支是哪个，以及每个分支之后下一个以同一字符开头的分支是哪个。`lre_split` 只读一次字符，直接跳到第一个能以它开头的分支，没有就跳过整段。机器压入一个分支后回到下一个 split 操作，`lre_split` 从同一字符的下一个分支接着找。

- 遇到不以字面量开头的分支，这一段就结束：字符类、点、`\d` 或 `\b` 这样的转义、空分支、改变 `i` 的修饰符分组。它后面的分支另成一段。每个正则最多保留 4 段，取代码里靠前的。
- 带 `i` 时，分支以折叠后的字符开头（`char_i`），`lre_split` 像机器那样折叠字符串里的字符，所以 `K` 和 `k` 找到同样的分支，带 `iu` 时开尔文符号也一样。忽略大小写的分支和不忽略的不会混在一段里。带 `u` 和 `v` 时，U+FFFF 以上的字符像机器那样整个读。
- 256 及以上的字符共用一项。`lre_split` 再像以前那样逐个测试这些分支。
- lookbehind 里的分支是倒着读的，分支以退一步开头，所以不成段。分支前面有 lookbehind 不影响这个分支。

为什么安全：只有当一个分支的第一个字符不是字符串里那个字符时才跳过它，这时 `lre_split` 本来也会测它并且什么都不压入。所以每次调用 `lre_split` 交给机器的，和逐个走 split 操作时一样：压入同样的分支、顺序相同，所以同一字符开头的分支之间仍保持模式里的顺序（`a|ab` 仍然先选 `a`），什么都不压入的调用也一样多，机器在这样的调用后读中断标志。它还把跳过的每个 split 操作计入一次调用的 4096 步，在逐个走会停下的地方停下。匹配、捕获、`lastIndex`、错误以及读标志的次数都不变。

每段占 8 字节，再加 257 项和它的每个 split 操作各 2 字节，颜色名是 816 字节，放在字节码字符串里：计入内存上限和缓存的字节数。函数的字节码带着它的正则字面量的字节码，所以字节码版本从 9 升到 10：旧版本 `Compile` 写出的字节码不能再读入（`SyntaxError: invalid version`）。

在 linux/arm64 上用 callgrind 数一次渲染里引擎的指令，和 `641f7dc7` 比，HTML 相同：商店的工作台页面（react-spring 在这里测它的颜色名）少 1.36%（172.32M 到 169.98M），匹配器里从 4,877K 降到 2,601K。别的页面上没有正则带这样的一串分支，匹配器一次渲染最多多跑 69K 条指令，用在测一个正则有没有段上：英文店面首页 +0.02%，中文商品列表 +0.01%，MUI 订单页 +0.02%，`r_react_ssr` +0.01%。

在 darwin/arm64（Apple M，机器上同时有别的工作）上跑 `BenchmarkRegexColors`，6 轮、每轮两个构建轮流跑，取中位数：带颜色名的值 3,971 ns 到 1,921 ns（0.48），不带颜色名的阴影 3,132 ns 到 878 ns（0.28）。`BenchmarkRegexShapes` 里的形状没有这样的一串分支，变化小于各轮之间的波动。


改动在 C 里（`engine/libregexp.c`）：`lre_compile` 调用的 `lre_chains`，以及读这些段的 `lre_chain_next` 和 `lre_split`。`lre_get_groupnames` 和 `lre_dump_bytecode` 跳过它们，`engine/quickjs.c` 的 `BC_VERSION` 是 10。`engine/test/unit-white.c` 检查保留了哪些段（`test_regexp_chains`），以及在每种段的每个 split 操作上、对互相折叠的字符、256 及以上和 U+FFFF 以上的字符、在字符串末尾、对 4095 到 4097 个 split 操作的段，`lre_split` 给出的都和逐个走一样（`test_regexp_split_same`）。`engine/test/unit.c` 检查读标志的次数和以前一样。`engine/test/regvm/js` 的 `q3-regexp-alt.js` 给出这类正则在每个内置函数下的匹配和捕获，和 Node 一样，`TestRegexLongScanStops` 停下一次这样的长扫描。

## 按 VM 保存编译好的正则

发布版本：v0.27.0。

VM 保存它编译过的正则的字节码。每次调用都为同一个 pattern 新建一个 `RegExp` 的代码，以前每次都要编译：每次渲染都新建一个语法高亮器（react-markdown 就是这样），每个页面都要把它语法里的正则重新编译一遍。

为什么安全：字节码是一个字符串，`lre_compile` 写好之后引擎从不修改它，而 `lastIndex` 是每个对象自己的属性，所以从缓存创建的对象共享字节码，和同一个字面量的对象以及 `new RegExp(re)` 本来就共享一样。只有 pattern 是扁平字符串、标志是 undefined 或扁平字符串时，才会查找和保存：转换其他任何东西都可能运行脚本或分配内存，`js_compile_regexp` 在编译之前会做这些，而 rope（几段字符串连成的树，读的时候才拼成一段）也要经过转换。编译失败的不保存，所以抛出 `SyntaxError` 的 pattern 每次都抛。不同之处：命中缓存时可能成功，而重新编译会因为内存或栈不足而失败。

缓存最多保存 256 个正则，共 1 MiB，每个条目、它的 pattern、标志和字节码都计入，先放掉最久没用过的。它的哈希链表不在这些字节里：每个能放进去的条目一个指针，最多 65,536 个（64 位目标上 512 KiB），不管上限允许多少个条目，并且计入 VM 的内存上限。默认值下它占 2 KiB。这些上限来自测过的页面：tifa 示例商店里高亮 CSS 的 journal 文章，每次渲染要编译 392 个正则，其中 162 个互不相同，占 714 KiB，所以放得下，还有富余。商店的其他页面和基于 MUI 的应用，每次渲染最多编译 83 个，最多 11 种 pattern，不到 15 KiB。新 VM 在 `DefaultRegExpCacheBytes` 里保存 `DefaultRegExpCache` 个正则，[`VM.SetRegExpCache`](go-api.zh-CN.md#setregexpcache-和-defaultregexpcache) 可以改它。`JS_FreeRuntime` 先放掉每个条目。

内存：条目保存在 C 内存里，在运行时的状态中，紧挨着 [shape 缓存](objects-and-shapes.zh-CN.md#保留-shape)，所以它们计入 VM 的内存上限。分配失败时不会放掉它们：释放一个字符串可能会释放一个 atom（引擎给属性名和常用字符串的编号），而失败的那次分配可能正处在扩大 atom 表的途中。所以接近内存上限运行的脚本，开着缓存可能内存耗尽，不开则不会：给这样的 VM 一个更小的缓存，或者不给。商店的一个 VM 在 GC 之后多占 12 KiB（12.84 MiB，以前是 12.83，用 tifa 的 `TestShopVMMemory` 测得），渲染过 CSS 文章的 VM 会占着它 162 个正则的 714 KiB。

不开 PGO，在 linux/amd64（AMD EPYC 7B13，单核）上，对比 `ff35232`（v0.26.17 的引擎），CSS 文章渲染用时是原来的 0.893：3 种代码布局跑 6 轮的中位数，各轮 0.841 到 0.903。其他页面在第一次渲染之后不再编译任何正则，渲染用时不变：商店是 1.003，商店的其他页面是 1.000，MUI 页面是 0.999，都在代码布局造成的 1% 波动之内。HTML 相同。

改动在 C 里（`engine/quickjs.c`）：`JSRuntime` 的字段 `regexp_cache`、`js_compile_regexp` 里的 `js_regexp_cache_get` 和 `js_regexp_cache_put`、`JS_SetRegExpCache(rt, n, bytes)`、`quickjs.h` 里的默认值 `JS_REGEXP_CACHE_ENTRIES` 和 `JS_REGEXP_CACHE_BYTES`，以及 `JS_FreeRuntime` 会放掉每个条目。`engine/test/compare.sh` 会运行 `testdata/regexcache.js`，`engine/test/unit.c` 检查相同 pattern 的正则只有在缓存开着时才共享字节码。它还检查条目数和字节数的上限，设置它们会放掉每个条目，缓存放掉某个正则的字节码之后这个正则仍然能用，缓存在分配依次失败之后仍然保有它的条目并能正常工作，以及它比填充它的 context 活得更久。

## 带 v 标志的正则的类

发布版本：v0.28.3。

解析器按规范读取带 v 标志（unicodeSets）的正则的类。以前它对规范允许、Node 也接受的三件事抛出 SyntaxError：

- 在类里，``& ! # % , : ; < = > @ ` ~``（ClassSetReservedPunctuator）中某个字符前的 `\` 就是那个字符本身，如 `[\&\;]` 或 `[\!\|]`。`get_class_atom` 原来已经接受 `\-`，对其他的抛出 "invalid escape sequence"。在类之外，以及带 u 标志的正则的类里，这些转义仍然是 SyntaxError，和规范一致。
- `get_class_atom` 也会读类之外的字符，并且按类里的规则检查它：连写的标点如 `&&`，以及 `( ) [ ] { } / - |`，在那里也会抛错，所以 `/-/v`、`/a&&b/v` 和 `new RegExp('/', 'v')` 都编译不了。这是上游的提交 a479eff（"fixed regexp unicode set parsing"，在这个分支所跟的版本之后），它只在类里检查这些。
- `\q{...}` 按类之外的规则读它的字符。只有 a479eff 的话，`\q{(}`、`\q{-}` 和 `\q{&&}` 就能编译了，而 Node 拒绝它们。现在改成按类里的规则读，这也让 `\q{\-}` 和 `\q{\&}` 能够编译。

shiki 的 JavaScript 引擎，在没有 WebAssembly 的地方（比如这个引擎）用来代替它的 Oniguruma 引擎，它会把要高亮的语法转成满是这类转义的、带 v 标志的正则：它为 bash、css、go、html、json、typescript 和 yaml 的语法生成了 552 个正则，引擎对其中 204 个抛了错。现在除了 3 个之外都能编译，那 3 个的捕获组比一个正则能容纳的多（见 [最多 254 个捕获组](#最多-254-个捕获组)）。

为什么安全：以前能编译的 pattern 编译出同样的字节码。只有以前会抛错的 pattern 现在能编译，而且只限规范允许的那些，`engine/test/compare/recorded/regexpv.js` 拿 Node 对照检查过：每个标点转义和不转义的情形，在类里和类外，在 `\q{}` 里，带 v 标志、带 u 标志和都不带。打了补丁的 C 的原生构建，给出和 Node 相同的记录。

## 最多 254 个捕获组

一个正则最多有 254 个捕获组，和上游 QuickJS 与 QuickJS-NG 一样，超过就抛出 `SyntaxError: too many captures`。V8 允许 32,767 个。shiki 的 JavaScript 引擎为 typescript（551 和 555 个组）和 html（912 个组）的语法生成了三个超过这个数的正则，所以这两个语法在这个引擎里仍然高亮失败。

这个上限保留，因为提高它会改变每个正则的字节码格式。字节码用一个字节保存组的下标：在保存组起止位置的 op 里、在量词重复前清除组的 op 里、在反向引用的组列表里，以及保存数量的头里。每处都改成两个字节，每个组多 2 字节，每个清除 op 多 2 字节，反向引用的每个组多 1 字节，头多 2 字节。一次匹配为每个组占 16 字节堆内存，用于保存组起止位置的数组，而回溯栈只在匹配改变某个组时才保存它，所以没有哪个栈会随组数增长。用两字节下标、上限 32,767 的 C 原生构建，给出和 Node 相同的记录，用 shiki 高亮 `testdata/shiki/input.md` 的代码和 Node 一样，包括 typescript 和 html，带组和不带组的正则运行用时相同，差别在噪声之内。
