## Searches skip to where the string is

Release: v0.27.3 (timings in this entry were taken on the engine of that release, before the C engine).

`String.prototype.includes`, `startsWith`, `endsWith`, `indexOf` and `lastIndexOf` skip to where the string they look for is. Upstream compares the whole string with `string_cmp` at one index after the other, and `string_cmp` reads each character of both strings through `string_get`, so a search that finds nothing costs a call and a few character reads for each character of the string it looks through: about 3 ns a character. tifa looks for the marker of a Suspense boundary in the whole HTML of a page after each render, which was about 1% of a render of tifa's example shop.

Why it gives the same results: the loop still makes its own comparison at the index the search returns, so a match is only ever one `string_cmp` confirms, and the search returns the first index in the loop's direction where the characters are the same, which is the first one the loop would have found. A string of 16-bit characters may hold only characters below 0x100, so the widths of the two strings do not decide whether there is a match. `string_indexof`, which `split`, `replace` and `replaceAll` use, is left as it is: it already skips to the next index of the first character, and its strings are mostly short, where a call costs more than it saves.

A loop of `indexOf`, `lastIndexOf` or `includes` that finds nothing in a string of 1 MB used to stop 170 ms, 6.9 s and 170 ms after a 10 ms timeout, and 340 ms in a string of 16-bit characters: each search was one poll however long the string. They now stop within 20 ms of the start, building the string of 1 MB included. `startsWith` and `endsWith` compare at one index and count nothing. Over 6 rounds in 3 code layouts against the search without the count, the median of each search of about 20 characters takes 0.98 to 1.02 of the time, as much as `replace` and `split` move, which run none of the changed code (1.031 and 1.006), and searches through 1 KB and 100 KB 0.995 to 1.002. A miss of `indexOf` or `lastIndexOf` came out 1.7% slower in both of two builds of the count, about 2 ns, which is inside that spread but may be real.

Looking through 100 KB of HTML that does not hold the string takes 81 µs rather than 320 µs, and 87 µs rather than 271 µs when the HTML has 16-bit characters. A miss in a string of about 20 characters takes 108 ns rather than 164 with `indexOf` and 102 rather than 119 with `includes`, `lastIndexOf` in 1 KB 1.6 µs rather than 3.1, and `startsWith` 102 ns rather than 107 (linux/amd64, AMD EPYC 7B13, one core, without PGO, each a loop in javascript of the same call). In a Go CPU profile of tifa's six shop workbench pages, `String.prototype.includes` went from 1.06% of the samples to 0.27%: its own search from about 0.75% to 0.13%, and what is left is mostly making the rope of the HTML one string, which the render then reads anyway. On the MUI pages of tifa's test app it went from 0.63% to 0.11%. A render of the six shop pages takes 0.995 of the time (0.975 to 1.032 over 6 rounds in 6 code layouts), and the MUI pages 1.003 (0.970 to 1.024), without PGO: the gain is smaller than the spread between code layouts, which alone moves a render by about 2%. No page and no micro benchmark got slower.

The change is in C (`engine/quickjs.c`), with a search of its own: `js_string_indexOf` and `js_string_includes` call `js_string_find`, which returns only an index where it compared the whole needle, so that index is taken without comparing it again. One character is looked for with `memchr`, or a loop in a string of 16-bit characters and toward the start. A string of up to 8 characters is looked for by finding its first character that way and comparing the others there, at most 8 units of work for each index, which spares the work the Two-Way search does on the needle first (about 20 ns a search). A longer string is looked for with the Two-Way search of musl's `memmem`, written for 8-bit and 16-bit characters, for a needle of the other width and for both directions. Its time is linear in the lengths of the two strings whatever they hold, also for a needle that matches almost everywhere: on linux/amd64 (AMD EPYC 7B13), comparing the needle at each index where its first character is took 2.5 s for `'a'.repeat(131072).indexOf('a'.repeat(65536) + 'b')`, and the Two-Way search takes 0.5 ms. A search with one index to look at, as `startsWith` and `endsWith` have and as two strings of the same length have, compares the needle there and does not check the interrupt counter: that is linear in the length of the needle, as `===`, concatenation and the other operations linear in the length of a string are, and none of them checks it. `engine/test/compare/stringsearch.js` (run by `engine/test/compare.sh`) searches with long needles of few letters that repeat, and `engine/test/unit.c` checks that searches in a long string run the interrupt handler, that one long search calls it many times, with a match or none, in strings of each width and in one of each, and ends with the error `interrupted` when it asks to stop, which `try` and `catch` do not catch, that the context runs scripts and searches again once the handler is gone, that a search with one index to look at does not call it, and that needles that match almost everywhere take a fraction of a second, forward and back, in strings of each width and in one of each.


## A symbol has a string of its own

Release: v0.30.2.

`Symbol(s)` turned the string `s` itself into the symbol, even while an array, a variable or the function that holds a string literal of digits (`Symbol("12")`, which every run of the function shares) still held it. And `description` gave the symbol itself back as a string. Either way a string held by the script kept the symbol alive: a `WeakRef` to it never emptied and a `FinalizationRegistry` never called back, for as long as the string lived. Node frees such a symbol at the next collection.

Now a symbol and the strings the script sees never share their characters. `JS_NewSymbol` (`engine/quickjs.c`) gives `Symbol(s)` a copy of `s` when something else holds `s` or when `s` is an atom, and `description` (`js_symbol_get_description`) gives a copy too. The other uses of the string of a symbol, its name in a message, `String(symbol)` and the name `[desc]` of a method, already made a new string of it or kept it only for their call, and still share it. A copy of more than a million characters is made in steps that read the interrupt flag (`js_string_copy`, through `js_sub_string_long`). What cannot die keeps the old sharing: a registered symbol (`Symbol.for`), which cannot be held weakly and the symbols of the runtime, such as `Symbol.iterator`. A string atom is still made of the string itself whoever holds it: it is the same string to every holder.

The cost: the argument of `Symbol` holds the string passed to it while `Symbol` runs, so a symbol of a string is always a copy, one allocation the length of the description. A literal that is not all digits, such as `Symbol('react.element')`, is an atom and was copied before too. Each read of `description` allocates its copy, where it shared the string. Upstream QuickJS shares the string both ways.

`engine/test/compare/symbol_shared_string.js` (run by `engine/test/compare.sh`) checks that the symbols of strings held by an array, a variable and a literal of digits, and a symbol whose description is held, are freed after the job that made each `WeakRef` ends (`clearKeptObjects()`), that the strings stay strings, the description and `Symbol.for` of them, and descriptions of millions of characters, of 8 and 16 bits. Its file is what Node 24 prints. `test_symbol_copy_oom` in `engine/test/unit-oom.c` runs out of memory at each point of making symbols of held strings and of reading their descriptions, and finds the out of memory error and nothing left behind.

## The hash table of atoms holds one atom for two buckets

Release: Unreleased.

An atom is the number the engine gives a property name or a string it keeps once. Making a key from a string, such as `o['key' + i]`, a JSON key or a name in the parser, looks the string up in the hash table of atoms (`__JS_NewAtom`) and walks the chain of its bucket. Upstream doubles the table when it holds two atoms a bucket, so a lookup walks up to about two atoms on average, each a load from the array of atoms, before it finds its own or none. Now `JS_ATOM_COUNT_RESIZE` in `engine/quickjs.c` doubles it at one atom for two buckets. In a counting build of the native C tree, the steps along the chains fall from 87K to 16K a render on MUI's orders page, 38.5K to 5.4K on MUI's home page, 10.1K to 1.8K on the workbench studio page and 6.7K to 0.9K on the shop's English home page.

Why it is safe: only the size of the table changes, never which atom a string gets, its number or the order of keys. The table grows by the same `JS_ResizeAtomHash` at another count, and when it cannot grow the atom is made in the table it has, as before. The HTML is the same on the 24 pages of the shop, MUI and React, and test262 gives the same 33 known errors.

What it costs: the table takes four times the room. After 20 renders and a full collection, on the native C tree, a VM of the shop holds 196 KB more (13.65 MB rather than 13.45 on its home page) and one of MUI 49 KB to 73 KB more. The footprint does not change. The smallest room in which a new runtime makes 600 names (`test_key_names_oom`) moved from 62,096 to 68,240 bytes.

What it gains: the instructions of a render do not move by more than the noise of the rounds (tifa's `test/ssr` on an Apple M4, three rounds, within 0.3% on each group). Fewer steps along the chains are fewer loads, each a likely cache miss, so any gain shows in time, not in instructions.

Tests: `test_key_names_oom` in `engine/test/unit-oom.c` sweeps a script that makes 600 names from no room to 80 KiB, so that some room lets it work with the larger table, and every other check of `unit`, `unit-api`, `unit-white` and `unit-oom` passes as before.

## An empty string on the left of `+` gives the string on the right

Release: Unreleased.

`'' + x` is how React and much other code make a string of a value, and a template literal that starts with a substitution (`` `${x}px` ``) compiles to the same `+` after an empty string. QuickJS gave back the left string when the right one was empty, and the right one when the left was empty and the right a rope. An empty left and a flat right went to `JS_ConcatString2`, which grows the left string in place when it can. The empty string is almost always the atom's, which never grows in place, so it allocated a new string and copied the right one into it. `JS_ConcatString` (`engine/quickjs.c`) now frees the empty left string and gives back the right one when the right is a flat string of at most 512 characters. A longer right side still makes a rope, as before: it is rare on the pages.

Why it is safe: a string has no identity a script can see, and the result has the same characters and the same width. The right string now has one more holder, so the appends that grow a string in place, which ask for no holder but the ones they know of (`js_concat_string_in_place`), copy it rather than change it. An atom's string can now be the result, and those appends refuse an atom already. What keeps the result now keeps the right string itself: `new RegExp(p, f + 'g')` with an empty `f` puts the atom's `'g'` in the regexp cache rather than a copy, so three scripts of the corpus (`q3-regexp-prefix.js`, `q3-regexp-skip.js` and `shikire.js`) end with one more atom and the same objects, and their goldens were written again.

What it gains, counted on the native C tree at 3ae98161 (linux/amd64 callgrind, the whole process, the difference of three and one timed renders after one warm render): React's page renders 2,151 such sums a render and runs 1.28% fewer instructions, MUI's three pages 4,306 and 0.49%, the fourteen store pages 2,426 and 0.17%, the six workbench pages 1,018 and 0.21%, about 150 to 210 instructions a sum. The table is in [performance.md](../performance.md#an-empty-string-on-the-left-of-a-sum).

Tests: `test_string_empty_left` in `engine/test/unit-white.c` checks that `'' + s`, `e + s` and `t = t + s` with an empty local, `''.concat(s)` and `` `${s}` `` give back the string `s` itself, and that an append to the result in place (`add_loc`, and an add into a local) leaves `s` as it was (`s` has 76 characters, past the 64 below which nothing is appended in place). With the check of `js_concat_string_in_place` loosened by one holder, the add into a local changes `s` and the test fails.
