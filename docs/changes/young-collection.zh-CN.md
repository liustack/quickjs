# 年轻代回收

[English](young-collection.md) · 简体中文

发布版本：v0.27.3。

年轻代回收只访问上次回收以来新建的 GC 对象。完整回收 `JS_RunGC` 会把每个对象访问两遍，在 tifa 示例商店的一个 VM 上，还没有任何垃圾时就有 bundle 的约 30,000 个对象。一次只做一件事的嵌入方，比如渲染页面，可以在每次之后做一次年轻代回收，偶尔做一次完整回收，每次回收花的时间大约只和这一件事产生的垃圾相当。

## 怎么做

`add_gc_object` 把新的 GC 对象放进运行时的 年轻代列表，而不是 `gc_obj_list`。`JS_RunYoungGC` 只对 年轻代列表执行 `JS_RunGC` 的试探删除：减去年轻对象互相持有的引用，这样年轻对象剩下的计数就来自 年轻代列表之外（旧对象、栈、Go、不是 GC 对象的值）。这些对象和它们能到达的东西保留，其余是垃圾环，由 `gc_free_cycles` 像 `JS_RunGC` 那样释放。幸存者移到 `gc_obj_list` 的末尾。旧对象从不被访问，所以试探删除期间它的计数不变，也不需要写屏障。

`JS_RunGC`、引擎在阈值处自己运行的 GC、`JS_FreeRuntime`、`JS_ComputeMemoryUsage` 和 `JS_DumpMemoryUsage` 先把 年轻代列表移到 `gc_obj_list` 的末尾，这样它们看到的每个对象，顺序和以前一样，都是创建的顺序。从不调用 `JS_RunYoungGC` 的程序，回收的方式和以前完全一样。

年轻对象和旧对象通过头里的标记位（`ephemeronMarkMask`）区分，在回收之外，每个 GC 对象的这一位都是 0。年轻代回收在 年轻代列表上设置它，在释放任何东西之前清除幸存者的这一位，垃圾保留它，和 `JS_RunGC` 一样。

只被垃圾持有的旧对象，在垃圾被释放时计数会降到 0。`JS_RunGC` 让这样的对象留在原处，因为在那里每个这样的对象都是垃圾。在年轻代回收里，它可能是垃圾之外的旧对象：它带着计数 0 留在 `gc_obj_list` 上，当弱引用清理移除以它为键的弱 map 条目时，`js_weakref_free` 会在它还在列表里时就把它释放。所以这种情况下 `__JS_FreeValueRT` 和 `async_func_free` 会调用 `youngDefer`，把这个对象移到它自己的列表里，年轻代回收在释放垃圾之后再释放它，就像引擎在回收之外释放对象一样。

## 弱引用

年轻代回收运行时，[完整回收](weak-collections.zh-CN.md)的 ephemeron 阶段是关着的，所以弱 map 的值是它所在 map 的强子节点。可达的或旧的弱 map 的条目保住它的值，并通过值保住这个值指回的键，直到下一次完整回收，那时再按原来的办法判断。没有别的东西持有的键，是年轻代回收的垃圾。垃圾释放之后，年轻代回收运行 `gc_remove_weak_objects`，它移除弱 map 条目，清除 WeakRef，把已经没有的对象的 FinalizationRegistry 任务排进队列，并释放弱引用为它们留下的外壳。它不运行 JavaScript。

所以完整回收能释放的东西，经过任意多次年轻代回收之后，它仍然会释放，年轻代回收也不会释放完整回收会保留的东西。年轻代回收会保留而完整回收会释放的有：穿过旧对象的环，以及弱 map 的值和它们持有的东西。嵌入方时不时做一次完整回收来处理这些，例如年轻代回收之后的 `MemorySize` 比上次完整回收之后大了很多的时候。

研究用的原型在试探删除之前运行弱引用清理，和 ephemeron 修复之前的 `JS_RunGC` 一样，并让计数为 0 的旧对象留在 `gc_obj_list` 上。当一个旧对象是某个弱 map 条目的键，而这个 map 被年轻垃圾持有时，`js_weakref_free` 在它还在列表上时就释放了它，之后的完整回收读到了已释放的内存。

## 收益和代价

测量方法见 [Measuring in tifa](../performance.zh-CN.md#在-tifa-里测量)，在 tifa 里不开 PGO，用 AMD EPYC 7B13：当时 tifa 的池，在一个 VM 持有的内存达到上次回收后剩余的 1.5 倍时，在渲染之间做一次完整回收。对照的是同一个池改成每次渲染后做一次年轻代回收，年轻代回收后剩下的内存达到存活大小的 1.5 倍时、引擎自己回收过的那次渲染之后、以及每 256 次渲染，做一次完整回收。一个 VM 在一个线程上，或两个 VM 在一个核的两个线程上，3 种代码布局轮流跑 6 轮。每轮把每个页面先渲染 256 次预热，再测量 300 次。HTML 逐字节相同。

| 页面，VM | 一次渲染的 P99，各页面之和 | P50，各页面之和 | CPU | 峰值 RSS |
| --- | --- | --- | --- | --- |
| 商店的 10 个页面，1 个 VM，每遍页面顺序重新随机 | 0.748 (0.714 到 0.804)，386.6 ms，对比 529.5 | 1.010 | 0.994 | 0.872 |
| 商店，1 个 VM，每遍顺序相同 | 0.994 (0.972 到 1.003) | 0.999 | 1.015 | 0.874 |

| MUI，1 个 VM，顺序相同 | 0.975 (0.953 到 0.992) | 1.005 | 1.001 | 0.874 |
| MUI，2 个 VM，顺序相同 | 0.919 (0.916 到 0.945) | 1.005 | 1.000 | 0.824 |

在这些页面上，渲染之间的完整回收要 6 到 11 ms，等它的那次渲染要背上这段时间。页面顺序每遍相同、只有一个 VM 时，它每次都落在同一个页面上，商店上是 `product-en`，所以其他页面的 P99 看不到它，总和变化很小：`product-en` 降到它 P99 的 0.719，`weekend-stats` 升到 1.48（8.9 到 13.1 ms）。随机顺序和两个 VM 时，它会落在每个页面上，和服务器上一样，商店小页面的 P99 从 28 到 30 ms 降到了 13 到 15 ms。

商店的一个 VM 在回收后持有 14.2 MB，以前是 15.5，MUI 页面是 6.6 MB，以前是 8.5：完整回收留下的是上一次渲染持有的东西，渲染后的年轻代回收则不会。商店小页面的 P50 是 8 到 11 ms，一个 VM 时升高 4% 到 5%，约 0.5 ms，较大页面升高不到 1.5%。商店跑一轮要做 2252 次年轻代回收和 8 次完整回收，以前是 113 到 131 次完整回收。总 CPU 在 1.5% 以内不变。每 64 次渲染做一次完整回收，会让商店的 P99 升高 1.5% 到 4%，每 1024 次的 P99 和内存与每 256 次的相同。

## 测试

根包里的 `younggc_test.go` 检查 Go API：400 轮随机图，带闭包、Map、Set、数组、旧对象、一个旧的闭包变量和一个旧的 WeakMap，每次年轻代回收之后、以及每第七次完整回收之后，都保留根能到达的东西，最后一次完整回收释放的量和没有年轻代回收时一样多（`TestYoungGCKeepsReachable`）。年轻代回收像完整回收一样释放年轻的环，并保留一个暂停的 generator，它的帧里有一个环（`TestYoungGCFreesCycles`）。它释放只被年轻垃圾持有的旧对象，连同它的弱 map 条目、WeakRef 或注册（`TestYoungGCFreesWhatOnlyGarbageHeld`）。除非键本身就是垃圾，否则 ephemeron 测试的每种情形都留给下一次完整回收处理（`TestYoungGCEphemeron`）。

`engine/test/compare/young_gc.js` 的 `suspended async frame` 用例，创建一个暂停在不可达 promise 上的 async 调用，并导出一个工厂函数，用来创建对其局部载荷的闭包。完整 GC 让这个帧和附在它上面的 var-ref 变成旧对象。一个只被年轻自环持有的新闭包，成为这个 var-ref 唯一的所有者。释放这个闭包会在年轻代清扫期间释放旧的 var-ref，所以 `async_func_free` 必须推迟释放旧的帧。这个测试先检查旧帧处于暂停状态且有一个引用，再检查它离开了 GC 列表，并且它载荷的 WeakRef 被清除。在 darwin/arm64 上，用 Go overlay 只去掉 `async_func_free` 里的 `youngDefer` 调用，这个用例就会失败，旧列表上留下一个计数为零的对象。只去掉 `__JS_FreeValueRT` 里的调用，同一文件里 `leavesNoZeroCount` 的六个用例都会因同样的不变量被破坏而失败。这些变异检查没有改动生成的文件本身。
