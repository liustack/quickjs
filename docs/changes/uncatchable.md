# Uncatchable exceptions, out of memory and interrupts

English · [简体中文](uncatchable.zh-CN.md)

An embedder that sets a memory limit or a timeout needs the call to end when either is hit, whatever the page code does. These changes make sure no `catch`, `finally`, rejection handler or Go function of the script can take such an exception, and that the VM stays usable or at least closable after it. The Go API reports why a call ended this way (see [go-api.md](go-api.md#error-says-why-a-call-ended)).

## No leak when converting a string runs out of memory

Release: v0.26.0.

A VM that runs out of memory inside `JSON.parse`, or anything else that converts a string with non-ASCII characters to UTF-8, no longer leaks that string. `JS_ToCStringLen2` kept a reference to its argument when allocating the UTF-8 copy failed, so the string outlived `VM.Close`. QuickJS, quickjs-ng and libquickjs still had this bug when the fork was made.

## Interrupts cannot be caught through promises or iterators

Release: v0.26.6.

Page code can no longer catch an interrupt (`VM.Interrupt` or the eval timeout) through a promise or an iterator. The engine already skipped every `catch` and `finally` block for an interrupt, but its own handlers of an exception went on with it: an async function and a promise job turned it into a rejection, which an `await`, a `.catch` or a `.then` handler then received, and so did the `Promise` constructor, `Promise.try`, `Promise.all` and the other combinators, async generators and modules. A built-in that runs an iterator's `return` method on an error (`Array.from`, ...) ran it, then threw the interrupt again as an error a `catch` could take, and any later error replaced it. Now an uncatchable exception stays pending until the Go call that ran the script takes it, and while it is pending every call into javascript fails at once. So no `catch`, `finally`, iterator `return`, generator `finally` or rejection handler runs, and the call returns the interrupt, as it does for a script without promises. Where a built-in only records the error, such as a resolve function that rejects its promise when reading `then` throws, the code after it runs on until its next function call, which fails. `ExecutePendingJobs` stops at the job that failed with an interrupt and leaves the rest queued, where it used to run them all.

## Out of memory is uncatchable

Release: v0.26.6.

Running out of memory is uncatchable too, like an interrupt, and the call returns `*Error{Name: "InternalError", Message: "out of memory"}`. Page code used to catch it, so a framework catching every error to show a fallback reported it as an error of the page, and a `finally` block or a rejection handler ran with no memory left. Every way the engine runs out of memory now ends this way: the engine's own out of memory error, the regexp engine running out of memory (it used to throw `InternalError: out of memory in regexp execution`, or a `SyntaxError` when compiling a pattern), and an error the engine could not build. That last case used to throw a catchable `null`, and an error whose message could not be allocated got the exception marker as its message, which read back as nonsense. Now the engine builds the message first, and if the message, the error object or setting the message fails, it throws `null`, uncatchable, which the VM reports as the same out of memory error. A script that throws `null` itself still gets `null`. Page code cannot fill memory on purpose and catch the failure any more: allocating until it fails ends the call. The VM stays usable after the call, and `Close` frees everything.

## Interrupts and out of memory inside Go functions

Release: v0.26.6.

An interrupt or running out of memory inside a Go function that javascript called ends the whole call too. That covers converting the function's arguments or result, and javascript the function evaluates on the same VM (`Eval`, `Call` and the like), from a function registered with `RegisterFunc` or `RegisterHostFunc`, a `Then` callback, or the module loader and normalizer. The Go function still gets the error, but the exception stays pending until it returns, so further calls into javascript fail at once. Whatever the function returns, the script that called it gets the original uncatchable exception. It used to get a catchable `TypeError` wrapping the message (for example `calling take: argument conversion error: InternalError: out of memory`), or the function's own result when it dropped the error, so a timeout in nested javascript could be caught or lost and the script ran on. The `intl` package now takes its host functions off the global object before its install changes anything, so that an install cut short this way leaves none of them in sight once the next use has installed.

Tests: `hostuncatchable_test.go`, `intl/install_test.go`.

## A panic in a Go function

Release: v0.26.6.

A panic in a Go function that javascript called (`RegisterFunc`, `RegisterHostFunc`, a `Then` callback) no longer unwinds through the engine. The VM recovers it, ends the javascript with an uncatchable `InternalError` (`panic in Go function <name>: <value>`) as for an interrupt, and panics again with the same value in the Go code that called javascript: in `Eval` or the like, or in the Go function one level up when a Go function called the javascript. Page code sees no catch or finally run for it. The panic used to unwind through the engine, which kept pointing at stack frames that were gone. The VM looked fine after a recover, but the next error it made walked those frames, forever when a new frame took the place of an old one, so the eval timeout of that VM never fired again. The panic value is the same, but its stack trace now starts where the VM panics again.

Tests: `hostpanic_test.go`.

## Compiling with little memory left

Release: v0.26.6.

Compiling a script, a function body, `eval` code or a regexp with little memory left fails with the same out of memory error. The engine used to crash there (a Go panic on a write before or past the code buffer, or a double free), report a `SyntaxError` the script does not have, or, in `Compile`, return bytecode cut short, bytecode with the out of memory error left pending, or `errors.New("OOM")`. The parser went on after its code buffer failed to grow and patched code in place at positions it had noted, past what the buffer held (a Go panic on an empty buffer, or a write past the end of a full one), and the passes after it assumed the buffer was whole. Now the parser stops at the next token once the code buffer of the function it parses failed, and checks it before each patch that does not wait for a token, the buffer takes no more bytes once it failed, and each pass that reads it back stops with the out of memory error. A scope the parser fails to push marks the function's code lost too, and its scopes then stay as they are, each later push failing with the out of memory error: the pop after a failed push used to take off the scope around it, until a pop read before the scope array. The pass that resolves jumps frees, when it fails, the jump records of the labels it has not reached yet, which used to leak. When shrinking the line table of a function fails, the compile keeps the table and leaves no error behind: it used to work and leave the out of memory error pending, for the next call to report.

## Nested calls keep the outer deadline

Release: v0.26.2.

A Go function that evaluates more javascript on its own VM, such as `intl` installing its code from inside the page's first call, no longer sets the eval timeout again or drops an `Interrupt` asked for meanwhile. The VM counts how deep the calls into javascript go, and only the outermost one sets the deadline and clears the request (see [architecture.md](../architecture.md#the-eval-timeout-and-interrupt)).

## The eval timeout runs on the monotonic clock

Release: v0.26.7.

The eval timeout (`SetEvalTimeout`) runs on the monotonic clock. It used to run on the wall clock, so setting the system clock while a script ran (NTP, a person, a machine waking from sleep) moved the deadline: set back, the timeout fired that much later or never, and set forward, at once. Even without a jump the two clocks drift apart by a few microseconds per 100 ms, so a server that keeps its own deadline on Go's monotonic clock could see the engine interrupt before that deadline. A timeout too long for the clock, up to `math.MaxInt64`, never fires: the deadline used to wrap around to the past and interrupt the call at once.

Test: `clock_test.go`.

## Interrupt is safe during and after Close

Release: v0.26.10.

`VM.Interrupt` can be called from any goroutine while the VM closes and after `Close`, where it does nothing. It used to read the address of the interrupt flag, which `Close` frees and then clears, so a watchdog firing just as the script finished could write to freed memory or panic on a nil pointer. The race detector also reported a race when `Interrupt` stopped a script and the VM was closed after the call returned. That one was not real: the two goroutines are ordered by the atomic flag, but the flag is in C memory, outside Go's heap, where the race detector ignores atomic operations. `Interrupt` and `Close` now meet at a mutex in Go memory that `Close` never clears.

Test: `interrupt_test.go`.

## Compiling a regexp counts toward the interrupt check

Release: v0.27.2.

The eval timeout and `Interrupt` stop a loop that compiles regexps within a few milliseconds, and stop one long compile in the middle. The interpreter calls the interrupt handler once every 10000 polls, and a compile was one poll however long the pattern, as it is upstream. A loop that built `new RegExp` from a new long pattern each time ran thousands of compiles between two checks: with a 10 ms timeout, `'(a|b|c)+d'.repeat(200)` stopped after 170 ms on a Mac, 225 ms on linux/amd64 (AMD EPYC) and over 2 s on a loaded machine, a pattern of 2000 alternatives after 3.6 s, and a class of 3000 CJK characters after 184 s. One compile of 100000 alternatives ran its full 8.5 s.

The regexp parser now counts a step on the counter of the context for each term, alternative and atom of a class, and one more for each 256 bytes of code or ranges the step moves (an alternative moves the code before it to insert its split, an atom of a class copies the ranges before it, a term of a lookbehind moves in front of the terms before it), through `lre_poll_interrupts`. When the counter runs out it calls the handler through `lre_check_timeout`, as `lre_exec` does. When the handler asks to stop, the parse fails with the message `interrupted`, the compile frees what it built as for any syntax error, and `js_compile_regexp` throws the uncatchable interrupt, the same error the interpreter throws, so a catch block does not see it. A lookup in the regexp cache counts the bytes of the pattern it hashes and compares (see below). On the same machine every one of those loops now stops 10 to 12 ms after it started, and the long compile at 10 ms.

## Parsing and building strings count toward the interrupt check

Release: v0.27.2.

A loop of built-in calls that parse source or build long strings stops within a few milliseconds of the eval timeout or `Interrupt`. Each such call was one poll of the interrupt check however much it did, so with a 10 ms timeout on linux/amd64 (AMD EPYC) a loop of `JSON.parse` of 60 KB stopped after 8.6 s, `JSON.stringify` after 11.7 s, `eval` of 500 functions after 10 s, `new Function` after 5.3 s, `'x'.repeat(1e6)` after 13 s, `padStart` after 18 s, `replaceAll` after 18.7 s and `join` of 100000 numbers after 37.5 s.

`js_charge_interrupts` counts steps on the counter of the context and leaves the call of the handler to the next poll of the interpreter, so it throws nothing where it is called. The counter stops at 0, so a huge charge cannot wrap it to a large count. `js_parse_init` counts a step for each byte of the source it is given, for `eval`, `new Function`, scripts, modules and `JSON.parse`: parsing and compiling cost far more for each byte than copying, and one step for each 32 bytes left a loop of `eval` 10 to 15 ms late, and 130 ms late on a loaded machine. `string_buffer_init2` and `string_buffer_realloc` count a step for each 8 characters of room they make, for `JSON.stringify`, `join`, `repeat`, `padStart`, `replaceAll` and every other built-in that builds a string in a `StringBuffer`. The regexp cache counts a step for each 32 bytes of each pattern it looks up. A step counted too many only calls the handler, which reads a flag and the clock, a little earlier. Those loops now stop 10 to 15 ms after they started on the same machine. One call still runs to its end: one `JSON.parse` of 13 MB takes 385 ms, one `repeat` of 200 million characters 620 ms, one `eval` of 50000 functions 1.1 s, and the timeout stops the script right after. `indexOf`, `lastIndexOf` and `includes` of strings count the indexes they look through ([strings.md](strings.md#searches-skip-to-where-the-string-is)). The other built-ins that scan or sort without building a string (`indexOf` and `includes` of arrays, `split`, `fill`, `sort` of arrays and typed arrays) do not count yet: a loop of them stops 3 to 29 s late with such inputs.

Neither change slows a render. Without PGO, on linux/amd64 (AMD EPYC), against v0.27.1, in 6 rounds over 3 code layouts with the order of the two builds flipped each round, the sums of the P50 render times take 0.993 of the time on the pages of tifa's example shop (0.978 to 1.002) and 0.997 on the MUI pages of its test app (0.989 to 1.007), with the same HTML and the same memory. Compiling one regexp of 900 KB takes 23 ms where it took 21 ms, and a compile of 100000 alternatives no longer than before. A script that ran past its deadline inside one long compile used to finish when nothing polled after it: `eval` of 50000 functions under a 10 ms timeout returned after 1.1 s, and now throws the interrupt right after the compile.


## Every method that can run javascript has the eval timeout

Release: v0.29.5.

`GetProperty`, `GetPropertyValue`, `SetProperty`, `SetPropertyValue` (and the `Value` methods that call them), `Value.MarshalJSON`, `Value.Any` and `ErrorFromValue` ran with no eval timeout. They entered the engine as a call that runs no script (`outer`), so a getter, a setter, a proxy trap, `toJSON`, a replaced `BigInt.prototype.toString` or a `toString` that `ErrorFromValue` calls on an error could run as long as it liked. With a 10 ms timeout, a getter and a setter of 200 ms ran to the end and returned 42 and no error, where `Eval` of the same loop returned the interrupted error after 10 ms.

Now each of them enters as `Eval` and `Call` do (`enter` and `leave`), so the outermost one arms the deadline, a pending `Interrupt` stops it, and a script that keeps running past the grace is killed. The conversion of the result to a Go value and the reading of an error are inside the same call and share its time. `ErrorFromValue` leaves a field empty that the timeout cut off, and panics on a VM a kill left good only for Close, as it did. Reading the error of any other call that comes back to Go outside a script (`RegisterFunc` on a name that cannot be defined, `RegisterCopyProps`, `RegisterEscapeText`) is bounded by `ErrorFromValue` too, which `takeException` calls.

`SetPropertyValue` and `SetProperty` return the exception the setter threw as their error. They used to return `failed to set property` and leave the exception pending in the context, for the next call that took one to find.

Test: `apitimeout_test.go` (`TestAPIEntriesHaveTheEvalTimeout`) runs each method with a 10 ms timeout on loops of 300 ms and requires the interrupted error within 150 ms, `killed_test.go` (`ErrorFromValue` after a kill).
## Loops over a long string read the interrupt flag in steps

Release: v0.29.5.

The loops listed here read the interrupt flag at least once in every step of work, so that a script stops within a few polls of `Interrupt` or the eval timeout, far inside the 1000 polls and 50 ms after which a poll kills it. Loops that are not listed have no such bound (see the end).

The steps are about 65,536 characters, and not exactly: a leaf of a rope counts for one more than its length, an escape of a JSON string is counted when it is whole (up to 5 bytes past the step), a surrogate pair counts for one in `JSON.stringify` and the conversion of a wide text to a C string reads the flag after a whole pair (65,537 units), and a character of 8 bits that is looked at and then copied into a buffer of 16 bits counts for two (`JSON.parse` and `JSON.stringify`, so such a run is read every 32,768 characters). The steps are for the hash of a key of a Map, a Set or an object, for the compare of two strings or ropes, for the loops of a pad, for the runs, escapes and wide characters of the string of a JSON text, for the widening of a buffer to 16 bits, and for the runs and escapes of `JSON.stringify` of a string. 1,048,576 characters for the scan and the copy of a long piece (`slice`, `trim`, `split` and the like). 1,048,576 bytes for the copy of a buffer that grows.

Where a step of work is the end of one phase and the start of the next, the budget goes on or the flag is read between them: the end of a scan goes on into the copy, the last leaf of a rope into the first of the next, the hash of a key is followed by a read of the flag before its compares, the compares of the candidates of a chain of a hash table share one budget (a compare that ends at a difference counts the step it made), and the flag is read before the first step of the copy of a buffer that grows, so that the scan that filled the buffer is not added to it. A JSON string keeps one budget for its runs and its escapes, and so a string of short runs and escapes, or of nothing but escapes, is read every 65,536 bytes too.

A string shorter than a step is compared at once and hashed at once: that is a window of fewer than 65,536 characters for each string, fixed by the limit of 65,536 that the hash of a key (`map_hash_key_poll`, `js_new_string_atom`, `JS_NewAtomLen`), the compare (`js_string_eq_polls`) and the search (`js_string_find`) all use. A loop that makes many such compares keeps a budget (`js_short_eq_budget`): the elements of an array, and the records of a chain of a Map or Set, add the length of each pair of strings of one length they compare, and the flag is read when the sum would reach a step, so that the budget given to a compare of ropes (`js_string_rope_compare`) is always less than a step. The hash of many keys of fewer than 65,536 characters one after the other, by a loop of the engine that is not bytecode, is not counted (see the end).

What is covered, by what it was:
- `===`, `!==`, `==`, `!=` and `switch` on two strings of which one is a rope or both are longer than a step, and the key compare of a Map or Set: they used to compare the whole strings in one call. The operators of the interpreter (`js_strict_eq_slow`, `js_eq_slow`) and the Map and Set code call `js_string_rope_compare` with its `poll` argument, which reads the flag and can throw.
- `Array.prototype.indexOf`, `lastIndexOf`, `includes` and `Object.is` on strings: of a step or more with `js_string_rope_compare`, and shorter ones with the budget of `js_short_eq_budget` (`js_strict_eq2_poll`).
- `indexOf`, `lastIndexOf`, `includes`, `startsWith`, `endsWith`, `replace`, `replaceAll` and `split` with a pattern of the length of what is left of the string, so that one index is left to compare (`js_string_find_at`).
- A property key of 65,536 characters or more: its hash, and its compare with the atom of an equal string (`js_new_long_string_atom`).
- `JSON.parse`: the text as a C string (`js_string_to_cstring_json`, a copy of `js_string_to_cstring` with the reads: a text shorter than a step is scanned and encoded with no count and no read), the runs, escapes and wide characters of a string, and the widening of the buffer when a character above 0xff follows a long ASCII run (`string_buffer_widen`). `padStart` and `padEnd` write a narrow string into a wide buffer the same way (`string_buffer_write8_wide_long`, for a string of a step or more: a shorter one is copied by the loop of `string_buffer_write8`, which counts its length).
- `JSON.stringify` of a string: the runs and escapes (`json_quote_run`).
- A string buffer holding more than 1 MiB that has to grow is copied by `string_buffer_realloc2` in steps of 1 MiB, with a read of the flag before the first, and not by the allocator in one call. It needs the new block while the old one is there. The allocator needed that too when it could not extend the block in place, but it could remap a block of its own chunk with no second block, which the copy cannot, so the memory in use can be higher for the time of the copy, by about the old block. That is not an upper bound to count on: it depends on what the allocator and the host do with the chunks. The check of the heap, of its count against the limit of the memory, is the one of `heap_realloc`, against the count less the old block: `js_malloc_moving` raises the limit by what the heap counts for the old block (its size and its header) for the one request, and puts it back before the out of memory error is made. A buffer that fits the limit once the old block is freed still grows, and the count is over the limit for the time of the copy, until the old block is freed. The check is only that of the heap. The footprint limit counts the new block while the old one is there, and the host may refuse the mapping of another block, so near those limits the growth can fail where `heap_realloc` would have remapped the block. The tests drain the caches and give the limit exactly at the check of `heap_realloc` and one byte below, and see the limit put back after the growth and after the failure.
- `replace` and `replaceAll` with a string for the pattern search a string of at most 256 characters with a plain loop, which compares at most 256 times 256 characters in all and so needs no read of the flag, and a longer one with the search of `indexOf`.
- A Map or Set looks for a key that is a rope or a string of a step or more with the compare that reads the flag (a record of another length is known to differ), and for any other string with the compare of `js_short_eq_budget`. A key that is not a string is compared at once.

Making an error reads no interrupt flag, and `engine/test/cycles.sh` checks that `JS_ThrowError2` reaches no function that does. The loops above are therefore kept out of what an error needs: `JS_NewStringLen`, which makes the message and the stack of an error, decodes a text with a character above 127 twice (to count the units, then to write them) into a string of the exact size, and not into a string buffer; and the conversion of the text of `JSON.parse` to a C string is `js_string_to_cstring_json`, a copy of `js_string_to_cstring` with the reads, not a flag of it.

Tests: `test_poll_work_gaps` in `engine/test/unit-white.c` does not count the reads of the flag but the work between two of them. The loops say what they did with `JS_WORK(n)` (nothing in the engine), `white.c` adds it up between two reads of the flag, and a call must keep the longest stretch, the one before the first read and the one after the last included, to the step, and add up to the work it has to do. Every case gives its total. The cases are a pad whose filler ends in the middle of a step, a slice whose scan ends in the middle of a step, keys made of leaves of 65534, 65536 and 65535 characters, strings of 65537 and 131071 characters hashed and then compared, 64 keys of one hash that differ from the key asked for at the first step, the strings of a JSON text of one run, of escapes only, of short runs and escapes and of `\u` escapes, a wide character or a wide escape after 70,000 ASCII characters, a pad with a wide filler, `JSON.stringify` of runs, escapes and wide characters, the searches, `indexOf` and `Object.is` on equal strings of 200,000 characters, an array of 40 elements that are one string of 65,535 or of 65,536 characters searched for another that differs in the last one, two flat strings of 32768 characters followed by a rope of that length in an array (the budget is used up exactly before the rope), 32 keys of one hash and 65,535 or 65,536 characters in a Map, a Map and an object, and JSON runs of narrow characters into a buffer that is wide already (parse and stringify). `test_buffer_copy_work` also gives the work of a copy that follows 60,000 units of work, and `test_buffer_limit` grows a buffer at the limit that has the room for the new block and not for both and one byte below. `test_buffer_copy_work` gives the work of the copy and the widening of a buffer of 1,500,000 characters. Putting back, one at a time, the escape count of a JSON string, the polls of the widening, the count of a compare that ends at a difference, the read of the flag between a hash and its compares, the polls of `js_string_find_at` and the polls of the compare in `Array.prototype.indexOf` makes a test fail, and so does taking out, one at a time, the read of the flag before the copy of a buffer, the budget of the short compares (`js_short_eq_budget`), the doubled count of a narrow run into a wide buffer, and the room of the old block in the limit (`js_malloc_moving`). `test_rope_polls`, `test_rope_key_compare_polls`, `test_long_key_polls` and `test_long_ops_polls` in `engine/test/unit.c` stop each call at a set read of the flag, and `TestInterruptStopsLongBuiltins` and `TestInterruptStopsLongKeys` (`internal/cengine`) stop it at six places of its polls in the generated engine, each key with a VM of its own, as the first use of a string as a key makes it an atom. A case may allow a later stop for the trials that have a reason: the first two of `padEnd`, which writes the 64 MiB of the string with one `memcpy` first, and the first of `padStart` with a filler of 32M characters, which lands in the allocation of its buffers. `padStart` with one wide filler has its trials in the last 40 % of the call, which is the copy of the string into the wide buffer (`string_buffer_write8_wide_long`), and a stop there takes at most 16 polls.

Not covered, and the bound is the length of the input:
- The compare of two equal strings by the entries that return a boolean and cannot report an exception and use `js_strict_eq2`, `js_same_value` or `js_same_value_zero`: the checks of `Object.defineProperty` and `Reflect.defineProperty` on a value, the invariants of a Proxy, `JS_IsStrictEqual`, `JS_SameValue` and `JS_SameValueZero` of the C API, and the like.
- `<`, `>`, `<=` and `>=` on two flat strings that are equal to the end (`js_string_compare`).
- The copy of a long piece of 8 bits into a string buffer of 8 bits when the buffer has the room (`memcpy` in `string_buffer_write8`, of tens of millions of characters), the copy of a piece of 16 bits (`string_buffer_write16`: the scan for a character above 0xff and the copy, which `JSON.stringify` of a string of 16 bits counts once), and the final shrink of a buffer by `string_buffer_end`. The copy of a piece of 8 bits into a buffer of 16 bits is covered (`string_buffer_write8_wide_long`).
- The rehash when a Map or Set doubles its table (about 1,100 polls at 8 million entries, which a VM of the default 128 MiB cannot hold), and the free of a very large result after a stop (about 1,700 polls for 8 million small objects, likewise).

## The start and end tags read the interrupt flag in every long loop

Release: v0.30.0.

The functions of [RegisterStartTag and RegisterEndTag](go-api.md#registerstarttag-and-registerendtag) went through a long string in four places without reading the interrupt flag, so a call on long strings ran on after `Interrupt` or the eval timeout. With a 10 ms timeout, `TestTagsStop` stopped its loops 53, 60 and 119 ms after they started on the linux/amd64, darwin/arm64 and darwin/amd64 runners of CI, past the 50 ms it allows. The four places:

- The check of the tag against React's tag regexp scanned the whole tag.
- The scan of a style name for a character that is not ASCII ran before the hyphens, which read the flag.
- The finished start tag, and a style name, were copied out of their buffer into a string of their length with one `memcpy`, of tens of millions of characters.
- The white space before a URL, and the tabs and new lines between its letters, that `isJavaScriptProtocol` skips.

Now every loop of the two functions over a string longer than its step reads the flag before each step and after the last, so that the work of one loop does not run into the next: 4,096 units for the escape and the hyphens of a style name, 524,288 units (1 MiB of 16-bit units) for the scan of a tag or a style name and for each copy (a long tag, a style name, an end tag, the finished start tag). The white space around a style value and before a URL is counted as it is skipped: the flag is read before it when the string is longer than 4,096 units, then every 4,096 units of a longer run and at its end. A long piece copied into the buffer of a call first makes the buffer large enough for all of it, so the buffer grows once. A string of one step or less is done at once, with no reading, as before, so a normal tag does not read the flag at all.

A stop throws the uncatchable interrupt and leaves `target` as it was: the tag is pushed only once it is whole. A style name or an end tag stopped while it is made is not kept, and the next call makes it. The text is the same, byte for byte (`start_tag.js` of `compare.sh`).

## A long rope is made flat in steps

Release: v0.30.1.

A string made by `+` from long strings is a rope: a tree of the strings, kept until something needs the characters in one block. Then the rope is made flat, its strings copied one after the other into a new string. Each string was copied with one `memcpy`, and the interrupt flag was read only between two strings, so a rope of two strings of 32M characters held off `Interrupt` and the eval timeout for the whole copy. With a 10 ms timeout, the case "style value" of `TestTagsStop`, whose value of 64M characters is a rope, stopped 68 ms after the call started on the darwin/amd64 runner of CI. On an Apple M4 the engine ran up to 26 polls (of 10,000 ticks each) after the request before it stopped, where the same value made flat first stopped at the first.

Now a rope of 65,536 characters or more is copied in steps (`string_buffer_concat_rope_long`): at most 65,536 characters between two readings of the flag, each string of the rope counting one more than its length, as for its hash, with a reading before the first step and after the last. The step is the one of the other loops over the characters of a rope, so a step that ends in the middle of one string goes on in the next. When a wide string is appended to a buffer of 8 bits that holds fewer than 65,536 characters, the buffer is widened at once with no reading of the flag, so its length counts in the step of that piece. Both copies of a rope take it: `js_linearize_string_rope`, which makes a rope flat for `JS_ToString`, `JS_ToPropertyKey`, `ToNumber` and every built-in that reads a string, and `string_buffer_concat_value`, which appends a rope to a string buffer (`String.raw`, `new Function`, `$&` in the replacement of `replace`, the gap of `JSON.stringify`). A rope shorter than 65,536 characters is copied as before, a string at a time, with one more test of its length.

A stop throws the uncatchable interrupt and frees the new string. The rope stays as it was: it is made to point at the flat string only once the copy is whole, so the next use makes it flat again. Every caller of the two functions already handled a failed copy, as the copy could already run out of memory. The flat string is the same, byte for byte. With the change, the case "style value" stops at the first poll after the request in every run, on the M4 and under Rosetta.

Cost: tifa's pages make ropes of 65,536 characters or more flat, so they take the new path. Counted by callgrind on linux/amd64 (3 renders of every page, against v0.30.0), the string buffer functions run 1,160 (bench) to 5,973 (store) more instructions a render, less than 0.001% of the 214 million to 1.44 billion of a render, and the interpreter's own code runs the same. The whole program moved by -0.50% to +0.68%, all of it in the young collections that tifa runs after a render in another goroutine, which land inside or outside the counted renders by the timing of that goroutine (shop ran more of them, store fewer).

The keys of a Map or Set that are ropes are hashed in steps too (`hash_string_rope_poll`). The rehash of the keys when a table grows (`hash_string_rope`) is not, as the list of the previous section says.

Tests: `test_poll_work_gaps` in `engine/test/unit-white.c` makes ropes flat with `String` and appends them with `String.raw`: strings of 200,000 and 70,000 characters (the first ends 3,392 characters into a step), with a string of 600 between them, the short one first, a wide string between two narrow ones, whose characters of 8 bits are written into a buffer of 16 bits, and a wide string after 200,000 characters of 8 bits appended to a buffer, which is widened, and after 40,000, which is widened at once. Each must keep every stretch to 65,536 and give its total: the characters and one for each string, and the characters widened. The ropes of the other cases of that test are made flat in the setup, so that each case counts the work of its own call. `test_rope_flat_polls` in `engine/test/unit.c` makes ropes of 6M to 10M characters flat by `JS_ToString` from C and by `String.raw`, requires a number of readings of the flag, and stops each at its first reading, its middle one and its last: the call throws `interrupted`, uncatchable, the rope is still a rope with the same characters, the same call then gives the flat string, and the runtime is freed with no leak. Before the change those calls read the flag 2 to 133 times, below what the test requires. `TestTagsStop` (`tags_test.go`) runs the case "style value" through the Go API.

## repeat reads the interrupt flag every 65,536 characters

Release: v0.30.1.

`String.prototype.repeat` read the interrupt flag every 1,048,576 characters, and only between two whole copies of its string. It writes a string of one character one character at a time, about one tick of the 10,000 of a poll for each, so `'x'.repeat(1 << 20)` ran 105 polls with no reading, and a string longer than that was copied whole between two readings (16M characters in 13 polls). A call of fewer than 1,048,576 characters read nothing, so a loop of `'x'.repeat(1e5)` stopped only at the next call, up to 11 polls after the request.

Now a result of 65,536 characters or more is written in steps of 65,536 characters, as the filler of `padStart` is, with a reading before the first step and after the last (`js_string_repeat_long`). A string of more than one character is copied a piece at a time, a piece ending at the end of the string or of the step, so a string longer than a step is copied in steps too. A shorter result is written at once, as before, with no reading. A stop throws the uncatchable interrupt and frees the buffer. The string is the same, byte for byte.

Cost: no page of tifa repeats a string to 65,536 characters, so `js_string_repeat_long` does not run there (callgrind, 3 renders of every page), and a shorter repeat runs the code it ran before with one more test of the length.

Tests: `test_poll_work_gaps` in `engine/test/unit-white.c` repeats one character, two, a string of 70,000 characters (pieces that cross the end of a step) and a wide one, and requires every stretch to keep to 65,536 and the total to be the length of the result. `test_string_loop_polls` in `engine/test/unit.c` requires 255 readings of the flag for repeats of 16M characters, of one character, of two and of a string of 8M, which read it 3 to 17 times before, stops each in the middle, and checks what the repeats make. `TestBuiltinWorkStops` runs a loop of `'x'.repeat(1e5)` with the eval timeout.

## Compiling one long regexp reads the interrupt flag in every long loop

Release: v0.30.1.

The regexp parser reads the interrupt flag at each term (see [above](#compiling-a-regexp-counts-toward-the-interrupt-check)), but the work around the parse, and the loops inside one term, read none. A pattern of 13.2M characters (`'(?:a|b|c)+d'` 1.2 million times) runs about 2,300 polls of 10,000 cycles, and in four stretches the flag was not read: the conversion of the pattern to UTF-8 (41 polls), the copies of the code as its buffer grows (stretches that grow by half each time, up to 45 polls), the scan of the code for its registers (`compute_register_count`, 1,320 polls), and the copy of the code into its string (46 polls). A stop asked for in the scan of the registers came after more than the 1000 polls after which the Go host kills the script: the call ended with `ErrKilled` and the VM was good only for `Close`, where it should have ended with the interrupt. Inside one term, the digits of a count (`a{000…1}`), of `\u{…}` and of a group name, the operands of `&&` and `--` in a class, and the strings of `\q{…}` were read in one pass, however long, and a string of `\q{…}` was compared with each string of the same hash and length before it with no reading. A lookup in the regexp cache hashed the pattern and compared it with the one of an entry in one pass too.

Now each of those loops reads the flag in steps, and a stop throws the uncatchable interrupt, as the parse does:

- The pattern becomes UTF-8 by `js_string_to_cstring_poll`, the conversion of `JSON.parse`, which reads the flag every 65,536 characters. A pattern without the flag `u` or `v` keeps the CESU-8 it had.
- Room in the code buffer is claimed by the compiler before each write, once for all the bytes of an instruction (`re_dbuf_claim`), and a block of 1 MiB or more that grows is copied 1 MiB at a time with a reading after each (`lre_realloc_code`). The buffer does not call it through its realloc function: every buffer of the engine calls that one through the same pointer, and making an error must reach no function that reads the flag (`engine/test/cycles.sh`). When the flag is set the request fails, and the parser tells that from running out of memory by the flag.
- The moves of the code (the split of an alternative, the code a quantifier puts in front of its atom, the terms of a lookbehind) move 1 MiB at a time.
- The scans of the code for its registers and for an atom with a quantifier, the scan of the pattern for its groups, and the digits of a count, of `\u{…}` and of a group name read the flag every 16,384 bytes. A scan takes about a cycle for each byte, so a step is under 2 polls.
- Each operand of `&&` and `--` reads the flag, and so does each character and each string of `\q{…}` as it is parsed, made lower case, merged into the class and turned into code. A lookup in the table of strings reads the flag every 16,384 units of its chain, each string it passes one and each byte it compares one, as a `memcmp` of the engine takes a cycle for each byte: the strings of one hash and one length, which a pattern can be made of, were compared with no reading, up to 31 strings of 128 KiB for each string added in `TestRegExpCacheStops`. A string of 1 MiB or more is copied 1 MiB at a time.
- The code is copied into its string 1 MiB at a time.
- The cache hashes the pattern 65,536 characters at a time, as a key of a Map is hashed, and compares it with the one of an entry in steps. A compare that ends inside the step is the flat compare it was. A pattern whose characters alone take more than the bytes of the cache is not looked up, as the cache cannot keep it, and the hash is made once for the lookup and the entry.

A write to the code that fails, by a stop or by running out of memory, now leaves the offsets after it unpatched: the parser patched the jump of an alternative, and the jumps of the strings of a class, at the place the failed write would have taken, past the end of the buffer.

A regexp compiles to the same code as before, byte for byte, and a stop frees what the compile made. Every stop of the pattern of 13.2M characters, at 214 places across its compile on darwin/arm64 and 203 on linux/amd64, comes within 3 polls of the request, and none kills the VM. The digits, the escape and the group name of 8M zeros stop within 2 polls, the operands of `&&` and `--` within 1, a lookup in the cache of a pattern of 900,002 characters within 7, the step of 65,536 characters of a hash, and the class of 32 strings of one hash in `TestRegExpCacheStops`, which stopped 76 and 107 polls after the request before, within 7, the step of the conversion of its 1M characters.

Cost: counted by callgrind on linux/amd64 (3 renders of every page of tifa, against the engine before the change), store compiles 271 regexps a render and looks up 895 in the cache, mui looks up 225 and compiles none, and shop and bench do neither. The compiles and the lookups run 110,373 more instructions a render on store, about 400 for each compile (the room claimed before each write and the steps of the scans), 0.008% of the 1.43 billion of a render, and 12,989 more on mui, about 56 for each lookup (the hash in steps), 0.002%. The conversion to UTF-8 runs the same, moved out of `JSON.parse` into its own function, and so does the interpreter's own code. The whole program moved by -0.02% (bench) to +0.52% (store), and the +0.52% is all in the young collections that tifa runs after a render in another goroutine (`JS_RunYoungGC` and the frees and marks under it), which land inside or outside the counted renders by the timing of that goroutine.

Tests: `test_poll_work_gaps` in `engine/test/unit-white.c` compiles a pattern of 2.2M characters of groups, a group of 2M characters with a quantifier, an alternative of 2M characters, a name used before its group, 1M wide characters, a count, an escape and a group name of 2M leading zeros, looks up a pattern of 900,002 characters in the cache, and compiles a class of 32 strings of one hash and one length. ## A class of a regexp reads the interrupt flag however many characters or strings it has

Release: v0.30.1.

A class of many characters or of many strings of `\q{…}` still had stretches with no reading of the flag after the change above, and one of them took a time of n * n:

- Each character or range of a class was merged into the ranges of the class so far by making all of them anew (`cr_union_interval`), one pass over them with no reading. A class of 60,000 characters that are not next to each other took 557,426 polls of the engine (each 10,000 ticks) to compile, the passes near its end 18 polls each, and the intersection of two of them 1,126,723.
- The strings of `\q{…}` were sorted by their length with `rqsort`, which reads no flag: up to 146 polls for 262,144 strings of 4 to 67 characters on darwin/arm64.
- Their table grew by moving every string in one pass: up to 34 polls for 524,288 strings of 4 characters. A list filled from another in the order of its table holds the strings of the first part of the hashes only, so most of its buckets are empty, and the walk of an empty table read the flag only at a string: the second `&&` in `[[\q{…}]&&[\q{zz}]&&[\q{yy}]]`, after the first left none of 524,288 strings, ran 51 polls with no reading.
- When a stop ended the compile, the strings were freed one by one: up to 139 polls for 524,288 of them.
- An inverted class moved all its points up by one at once: 10 polls for 330,000 characters.

Now:

- A character or range after the last range of the class is added at its end, and one that starts in the last range or where it ends makes that range longer, so a class in order costs one step for each. Any other goes to a list of its own, unsorted, and that list is sorted with `rqsort_stop`, merged and joined with the ranges of the class at once, before anything reads them: a class in any order takes a time of n log n. The 60,000 characters compile in 51 polls upward, 137 downward, and the intersection in 115.
- The ranges of a class carry the interrupt flag (`CharRange.stop` in `engine/libunicode.h`, NULL for the other ranges of the engine), and so do the ranges a class makes case-insensitive: `cr_op` and the merge of the ranges that touch read it every 4096 points when they go through more than that, and `cr_invert` moves the points 1 MiB at a time with a reading between two moves. The code of the ranges is written with a reading every 16,384 bytes.
- The strings are sorted with `rqsort_stop`, which gives the order of `rqsort` and reads the flag at each step. The new table of a growth is cleared 1 MiB at a time, and the move reads the flag every 16,384 buckets and strings: a stop there leaves strings in neither table, which is safe because nothing walks them any more. The other walks of the buckets of a table read the flag at each bucket.
- The strings are taken from blocks that are freed together, 256 bytes for the first and twice the size of the one before up to 64 KiB, and a longer string in a block of its own. A string taken out of a list by `&&` or `--` stays in its block until the list is freed.

## Out of memory in the return method of an iterator that an exception closes

Release: v0.29.11.

An exception that leaves a `for...of` loop, or a default of an array pattern, closes the iterator: the interpreter runs its `return` method with the exception pending, then looks for a `catch` or a `finally` in the same function. It decided whether to look once, before the close. When the `return` method ran out of memory, the out of memory error took the place of the exception, and the `catch` of the same function took it, so a script could catch running out of memory. An interrupt was not caught this way: the flag stays set, and the interpreter reads it again as soon as the `catch` starts.

Now the unwind reads the flag again right after the close, and when an uncatchable exception is pending it stops looking, so the call ends with it. What is left on the stack is freed by the same code that frees it when the search finds nothing. The iterators of the loops further out are not closed, as for any uncatchable exception. Upstream QuickJS has no uncatchable out of memory, and its out of memory error is caught there by design.

The check is one test of a flag the unwind has in hand, on a path that only runs while an exception leaves an iterator. The frame of the interpreter stays $496 on amd64 and $504 on arm64.

Test: `test_iterator_close_oom` in `engine/test/unit-white.c` leaves a loop and a pattern by a `throw`, and a loop in a generator, in an async function and under a `finally` block, with an iterator whose `return` method allocates, and fails each call of the allocator in turn: the run gives the closes and the exceptions in order, or fails with the out of memory error.
