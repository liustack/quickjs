# 无法捕获的异常、内存不足与中断

[English](uncatchable.md) · 简体中文

设置了内存上限或超时的嵌入方，需要无论页面代码做什么，调用都在碰到上限时结束。这些改动保证脚本里没有 `catch`、`finally`、rejection 处理函数或 Go 函数能接住这样的异常，并且 VM 在这之后仍然可用，至少可以关闭。Go API 会报告调用为什么这样结束（见 [go-api.md](go-api.zh-CN.md#error-说明调用为什么结束)）。

## 转换字符串时内存不足不再泄漏

发布版本：v0.26.0。

VM 在 `JSON.parse` 里，或者在任何把含非 ASCII 字符的字符串转成 UTF-8 的地方内存不足时，不再泄漏那个字符串。`JS_ToCStringLen2` 在分配 UTF-8 副本失败时仍然保留着对参数的引用，所以这个字符串比 `VM.Close` 活得更久。QuickJS、quickjs-ng 和 libquickjs 在分叉时仍有这个 bug。

## 中断无法穿过 promise 或迭代器被捕获

发布版本：v0.26.6。

页面代码不能再通过 promise 或迭代器捕获中断（`VM.Interrupt` 或 eval 超时）。引擎本来已经为中断跳过每个 `catch` 和 `finally` 块，但它自己对异常的处理函数仍然带着它继续往下走：async 函数和 promise 任务把它变成 rejection，随后被 `await`、`.catch` 或 `.then` 处理函数接住，`Promise` 构造函数、`Promise.try`、`Promise.all` 和其他组合函数、异步生成器和模块也一样。出错时运行迭代器 `return` 方法的内置函数（`Array.from` 等），运行了它，然后把中断作为 `catch` 能接住的错误再抛一次，而之后的任何错误会取代它。现在无法捕获的异常一直挂起，直到运行脚本的那个 Go 调用取走它，而它挂起期间，每个进入 javascript 的调用都立刻失败。所以没有 `catch`、`finally`、迭代器的 `return`、生成器的 `finally` 或 rejection 处理函数会运行，调用返回中断，和没有 promise 的脚本一样。内置函数只是记录错误的地方，比如读取 `then` 抛错时让 promise 被拒绝的 resolve 函数，它之后的代码会一直运行到下一次函数调用或向后跳转，在那里失败（[没有调用的循环也会在挂起的无法捕获的异常处结束](#没有调用的循环也会在挂起的无法捕获的异常处结束)）。`ExecutePendingJobs` 在因中断而失败的那个任务处停下，其余任务留在队列里，它过去会把它们全部运行完。

## 内存不足无法捕获

发布版本：v0.26.6。

内存不足同样无法捕获，和中断一样，调用返回 `*Error{Name: "InternalError", Message: "out of memory"}`。页面代码过去能捕获它，所以一个为了显示后备界面而捕获所有错误的框架，会把它报告成页面的错误，而 `finally` 块或 rejection 处理函数会在没有内存的情况下运行。现在引擎内存不足的每种方式都这样结束：引擎自己的内存不足错误，正则引擎内存不足（它过去抛 `InternalError: out of memory in regexp execution`，编译模式时是 `SyntaxError`），以及引擎造不出来的错误。最后一种情况过去抛一个可捕获的 `null`，而消息无法分配的错误，把异常标记当作它的消息，读回来是一堆乱码。现在引擎先构建消息，如果消息、错误对象或设置消息失败，就抛 `null`，无法捕获，VM 把它报告为同样的内存不足错误。自己抛 `null` 的脚本仍然得到 `null`。页面代码不能再故意填满内存然后捕获失败：一直分配到失败，会让调用结束。调用之后 VM 仍然可用，`Close` 释放所有东西。

## Go 函数里的中断和内存不足

发布版本：v0.26.6。

javascript 调用的 Go 函数里的中断或内存不足，也会结束整个调用。这包括转换函数的参数或结果，以及函数在同一个 VM 上求值的 javascript（`Eval`、`Call` 等），不论来自用 `RegisterFunc` 或 `RegisterHostFunc` 注册的函数、`Then` 回调，还是模块加载器和规范化函数。Go 函数仍然得到这个错误，但异常在它返回之前一直挂起，所以后续进入 javascript 的调用立刻失败。不管函数返回什么，调用它的脚本得到的都是原来那个无法捕获的异常。它过去得到的是包着消息的可捕获的 `TypeError`（比如 `calling take: argument conversion error: InternalError: out of memory`），或者在函数丢掉错误时得到函数自己的结果，所以嵌套 javascript 里的超时可能被捕获或丢失，脚本继续运行。`intl` 包现在在安装做任何改动之前，先把它的宿主函数从全局对象上拿掉，这样被这类情况打断的安装，在下一次使用完成安装之后，不会在眼前留下任何一个。

测试：`hostuncatchable_test.go`、`intl/install_test.go`。

## Go 函数里的 panic

发布版本：v0.26.6。

javascript 调用的 Go 函数里的 panic（`RegisterFunc`、`RegisterHostFunc`、`Then` 回调）不再穿过引擎向上展开。VM 恢复它，用无法捕获的 `InternalError`（`panic in Go function <name>: <value>`）结束 javascript，和中断一样，并在调用 javascript 的 Go 代码里以同样的值再次 panic：在 `Eval` 之类里，或者当是 Go 函数调用的 javascript 时，在上一层的 Go 函数里。页面代码看不到任何 catch 或 finally 为此运行。panic 过去会穿过引擎展开，而引擎一直指着已经不存在的栈帧。VM 在 recover 之后看起来没问题，但它造的下一个错误会走过这些栈帧，当一个新栈帧占了旧栈帧的位置时就永远走不完，所以那个 VM 的 eval 超时再也不会触发。panic 的值相同，但它的栈轨迹现在从 VM 再次 panic 的地方开始。

测试：`hostpanic_test.go`。

## 内存很少时编译

发布版本：v0.26.6。

内存所剩无几时编译脚本、函数体、`eval` 代码或正则，以同样的内存不足错误失败。引擎过去在那里崩溃（Go 的 panic，往代码缓冲区之前或之后写，或者重复释放），报告脚本里没有的 `SyntaxError`，或者在 `Compile` 里返回被截断的字节码、挂着内存不足错误的字节码，或 `errors.New("OOM")`。解析器在它的代码缓冲区增长失败后继续往下走，并在它之前记下的、超出缓冲区所容纳范围的位置就地修补代码（在空缓冲区上是 Go 的 panic，在写满的缓冲区上是往末尾之后写），而它之后的各遍都假定缓冲区是完整的。现在，一旦它正在解析的函数的代码缓冲区失败，解析器就在下一个 token 处停下，并在每个不等待 token 的修补之前检查它，缓冲区失败后不再接收字节，而每个回读它的 pass 都以内存不足错误停下。解析器压入失败的作用域，也把函数的代码标为丢失，它的作用域于是保持原样，之后每次压入都以内存不足错误失败：失败的压入之后的弹出过去会取走它外面的作用域，直到某次弹出读到作用域数组之前。解析跳转的 pass 在失败时，释放它还没走到的标签的跳转记录，这些记录过去会泄漏。缩小函数行表失败时，编译保留这张表且不留下错误：它过去能工作，却留下挂起的内存不足错误，等下一个调用去报告。

## 嵌套调用保留外层的截止时间

发布版本：v0.26.2。

在自己的 VM 上求值更多 javascript 的 Go 函数，比如 `intl` 在页面的第一次调用里安装它的代码，不再重新设置 eval 超时，也不再丢掉这期间发出的 `Interrupt`。VM 数着进入 javascript 的调用有多深，只有最外层的那个设置截止时间并清除请求（见 [architecture.md](../architecture.zh-CN.md#eval-超时和-interrupt)）。

## eval 超时用单调时钟

发布版本：v0.26.7。

eval 超时（`SetEvalTimeout`）用单调时钟。它过去用墙上时钟，所以脚本运行期间设置系统时钟（NTP、有人手动调、机器睡眠后醒来）会移动截止时间：往回调，超时会晚那么多触发，或者永远不触发，往前调，则立刻触发。即使没有跳变，两个时钟每 100 ms 也会差开几微秒，所以一个在 Go 的单调时钟上保存自己截止时间的服务器，可能看到引擎在那个截止时间之前就中断了。对时钟来说太长的超时，最大到 `math.MaxInt64`，永远不会触发：截止时间过去会绕回到过去，让调用立刻被中断。

测试：`clock_test.go`。

## Close 期间和之后 Interrupt 是安全的

发布版本：v0.26.10。

`VM.Interrupt` 可以在 VM 关闭期间和 `Close` 之后从任何 goroutine 调用，此时它什么也不做。它过去会读中断标志的地址，而 `Close` 释放它然后清空，所以一个恰好在脚本结束时触发的看门狗，可能写入已释放的内存，或者因空指针而 panic。当 `Interrupt` 停住了一个脚本、而 VM 在调用返回后被关闭时，竞态检测器也报告过一次竞态。那次并不是真的：两个 goroutine 由原子标志排好了顺序，只是标志在 C 内存里，在 Go 堆之外，竞态检测器会忽略那里的原子操作。`Interrupt` 和 `Close` 现在在一个 Go 内存里、`Close` 从不清空的互斥锁处相遇。

测试：`interrupt_test.go`。

## 编译正则计入中断检查

发布版本：v0.27.2。

eval 超时和 `Interrupt` 在几毫秒内停住一个编译正则的循环，并在中途停住一次长的编译。解释器每 10000 次轮询调用一次中断处理函数，而一次编译不管模式多长都只算一次轮询，上游也是这样。一个每次都用新的长模式构建 `new RegExp` 的循环，在两次检查之间运行了几千次编译：超时 10 ms 时，`'(a|b|c)+d'.repeat(200)` 在 Mac 上 170 ms 后才停，在 linux/amd64（AMD EPYC）上 225 ms，在负载高的机器上超过 2 秒，一个有 2000 个选择分支的模式 3.6 秒后才停，一个有 3000 个 CJK 字符的类 184 秒后才停。一次有 100000 个选择分支的编译，跑满了它的 8.5 秒。

正则解析器现在为每个项、每个选择分支和类里的每个原子，在上下文的计数器上计一步，并且对步骤所移动的每 256 字节代码或范围再多计一步（选择分支要移动它前面的代码来插入它的 split，类的原子要复制它前面的范围，后行断言的项要移到它前面各项的前面），通过 `lre_poll_interrupts` 进行。计数器用完时，它像 `lre_exec` 那样，通过 `lre_check_timeout` 调用处理函数。处理函数要求停止时，解析以消息 `interrupted` 失败，编译像对待任何语法错误那样释放它构建的东西，`js_compile_regexp` 抛出无法捕获的中断，也就是解释器抛的同一个错误，所以 catch 块看不到它。正则缓存里的一次查找，对它哈希并比较的模式的字节计数（见下）。在同一台机器上，这些循环现在每一个都在开始后 10 到 12 ms 停下，长的那次编译在 10 ms 停下。

## 解析和构建字符串计入中断检查

发布版本：v0.27.2。

一个解析源码或构建长字符串的内置调用循环，在 eval 超时或 `Interrupt` 之后几毫秒内停下。这样的每次调用，不管做了多少事，都只算中断检查的一次轮询，所以在 linux/amd64（AMD EPYC）上超时 10 ms 时，一个对 60 KB 做 `JSON.parse` 的循环 8.6 秒后才停，`JSON.stringify` 11.7 秒，对 500 个函数做 `eval` 10 秒，`new Function` 5.3 秒，`'x'.repeat(1e6)` 13 秒，`padStart` 18 秒，`replaceAll` 18.7 秒，对 100000 个数字做 `join` 37.5 秒。

`js_charge_interrupts` 在上下文的计数器上计步，并把调用处理函数留给解释器的下一次轮询，所以它在被调用的地方不抛任何东西。计数器停在 0，所以一次很大的计费不能让它绕回成大的计数。`js_parse_init` 为它拿到的每个源码字节计一步，用于 `eval`、`new Function`、脚本、模块和 `JSON.parse`：解析和编译每个字节的代价远高于复制，而每 32 个字节计一步，会让 `eval` 的循环晚 10 到 15 ms，在负载高的机器上晚 130 ms。`string_buffer_init2` 和 `string_buffer_realloc` 为它们腾出的每 8 个字符的空位计一步，用于 `JSON.stringify`、`join`、`repeat`、`padStart`、`replaceAll` 和所有其他在 `StringBuffer` 里构建字符串的内置函数。正则缓存为它查找的每个模式的每 32 个字节计一步。多计的一步只会让处理函数早一点被调用，它读一个标志和时钟。这些循环现在在同一台机器上，开始后 10 到 15 ms 停下。有一次调用仍然跑到结束：一次对 13 MB 的 `JSON.parse` 要 385 ms，一次 2 亿个字符的 `repeat` 要 620 ms，一次对 50000 个函数的 `eval` 要 1.1 秒，超时在它之后马上停住脚本。字符串的 `indexOf`、`lastIndexOf` 和 `includes` 计它们所查看的下标（[strings.md](strings.zh-CN.md#搜索直接跳到字符串所在的位置)）。其他扫描或排序而不构建字符串的内置函数（数组的 `indexOf` 和 `includes`、`split`、`fill`、数组和类型化数组的 `sort`）还不计数：用这样的输入，它们的循环晚 3 到 29 秒才停下。

这两项改动都不会让渲染变慢。没有 PGO，在 linux/amd64（AMD EPYC）上，对比 v0.27.1，3 种代码布局各 6 轮，每轮交换两个构建的顺序，P50 渲染时间之和：tifa 示例商店的页面是 0.993 倍的时间（0.978 到 1.002），其测试应用的 MUI 页面是 0.997 倍（0.989 到 1.007），HTML 相同，内存相同。编译一个 900 KB 的正则花 23 ms，原来是 21 ms，而一个有 100000 个选择分支的编译不比以前更长。一个越过截止时间、还在一次长编译里的脚本，过去在它之后没有东西轮询时才结束：对 50000 个函数做 `eval`，超时 10 ms，过去 1.1 秒后返回，现在在编译之后立刻抛中断。


## 每个能运行 javascript 的方法都有 eval 超时

发布版本：v0.29.5。

`GetProperty`、`GetPropertyValue`、`SetProperty`、`SetPropertyValue`（以及调用它们的 `Value` 方法）、`Value.MarshalJSON`、`Value.Any` 和 `ErrorFromValue` 过去没有 eval 超时。它们是以不运行脚本的调用（`outer`）进入引擎的，所以 getter、setter、proxy 陷阱、`toJSON`、被替换的 `BigInt.prototype.toString`，或者 `ErrorFromValue` 对错误调用的 `toString`，可以想跑多久就跑多久。超时 10 ms 时，一个 200 ms 的 getter 和 setter 会跑到结束并返回 42，没有错误，而同样的循环用 `Eval` 在 10 ms 后返回被中断的错误。

现在它们每一个都像 `Eval` 和 `Call` 那样进入（`enter` 和 `leave`），所以最外层的那个设置截止时间，挂起的 `Interrupt` 会停住它，而在宽限之后仍在运行的脚本会被杀死。结果转成 Go 值，以及错误的读取，都在同一个调用里，共用它的时间。`ErrorFromValue` 当时把被超时截断的字段留空（现在返回被中断的错误，见[读取异常时遇到的无法捕获的异常结束调用](#读取异常时遇到的无法捕获的异常结束调用)），并在被杀死后只能 `Close` 的 VM 上 panic，和以前一样。脚本之外返回到 Go 的任何其他调用的错误读取（对不能定义的名字调用 `RegisterFunc`、`RegisterCopyProps`、`RegisterEscapeText`），也受 `ErrorFromValue` 限制，`takeException` 调用的就是它。

`SetPropertyValue` 和 `SetProperty` 把 setter 抛出的异常作为它们的错误返回。它们过去返回 `failed to set property`，并把异常留在上下文里挂起，等下一个取异常的调用去发现。

测试：`apitimeout_test.go`（`TestAPIEntriesHaveTheEvalTimeout`）用 10 ms 的超时在 300 ms 的循环上运行每个方法，要求在 150 ms 内返回被中断的错误，`killed_test.go`（被杀死后的 `ErrorFromValue`）。

## 对长字符串的循环按步读中断标志

发布版本：v0.29.5。

这里列出的循环在每一步工作里至少读一次中断标志，这样脚本在 `Interrupt` 或 eval 超时之后几次轮询内就会停下，远在轮询 1000 次和 50 ms 之后才杀死它的界限之内。没有列出的循环没有这样的界限（见末尾）。

一步大约是 65,536 个字符，并不精确：rope（几段字符串连成的树，读的时候才拼成一段）的一片叶子算比它的长度多一，JSON 字符串的一个转义在它完整时计数（最多超出这一步 5 个字节），`JSON.stringify` 里一个代理对算一个，宽文本转 C 字符串在读完一整个代理对之后读标志（65,537 个码元），而被查看后又复制进 16 位缓冲区的 8 位字符算两个（`JSON.parse` 和 `JSON.stringify`，所以这样的一段每 32,768 个字符读一次）。这样的步长用于 Map、Set 或对象的键的哈希，用于两个字符串或 rope 的比较，用于填充的循环，用于 JSON 文本里字符串的连续段、转义和宽字符，用于把缓冲区加宽到 16 位，以及用于 `JSON.stringify` 字符串的连续段和转义。长片段的扫描和复制（`slice`、`trim`、`split` 等）是 1,048,576 个字符。增长的缓冲区的复制是 1,048,576 个字节。

当一步工作是一个阶段的结束和下一个阶段的开始时，预算接着算，或者在两者之间读标志：扫描的结束接着进入复制，rope 的最后一片叶子接着进入下一片，键的哈希之后、它的比较之前读一次标志，哈希表一条链上各候选项的比较共用一个预算（在差异处结束的比较，算它走完的那一步），而增长的缓冲区在复制的第一步之前读标志，这样填满缓冲区的那次扫描就不会加到复制上。JSON 字符串的连续段和转义共用一个预算，所以由短连续段和转义组成的字符串，或者只有转义的字符串，也是每 65,536 个字节读一次。

比一步短的字符串一次比较、一次哈希完：这就是每个字符串少于 65,536 个字符的一个窗口，由 65,536 这个限制固定，键的哈希（`map_hash_key_poll`、`js_new_string_atom`、`JS_NewAtomLen`）、比较（`js_string_eq_polls`）和搜索（`js_string_find`）都用它。做许多这种比较的循环保存一个预算（`js_short_eq_budget`）：数组的元素，以及 Map 或 Set 一条链上的记录，把它们比较的每对等长字符串的长度加进去，当总和将达到一步时读标志，这样给 rope 比较（`js_string_rope_compare`）的预算总是小于一步。由不是字节码的引擎循环一个接一个地哈希许多个少于 65,536 个字符的键，不计数（见末尾）。

覆盖了什么，原来是什么样：
- 其中一个是 rope 或两个都比一步长的两个字符串上的 `===`、`!==`、`==`、`!=` 和 `switch`，以及 Map 或 Set 的键比较：它们过去在一次调用里比较整个字符串。解释器的运算符（`js_strict_eq_slow`、`js_eq_slow`）以及 Map 和 Set 的代码，调用带 `poll` 参数的 `js_string_rope_compare`，它会读标志并可能抛错。
- 字符串上的 `Array.prototype.indexOf`、`lastIndexOf`、`includes` 和 `Object.is`：一步或更长的用 `js_string_rope_compare`，更短的用 `js_short_eq_budget` 的预算（`js_strict_eq2_poll`）。
- `indexOf`、`lastIndexOf`、`includes`、`startsWith`、`endsWith`、`replace`、`replaceAll` 和 `split`，当模式的长度等于字符串剩下的长度、所以只剩一个下标要比较时（`js_string_find_at`）。
- 65,536 个字符或更长的属性键：它的哈希，以及它和相等字符串的 atom（引擎给属性名和常用字符串的编号） 的比较（`js_new_long_string_atom`）。
- `JSON.parse`：文本作为 C 字符串（`js_string_to_cstring_json`，`js_string_to_cstring` 加上读取的副本：短于一步的文本不计数、不读，直接扫描和编码），字符串的连续段、转义和宽字符，以及一个长 ASCII 连续段之后跟着大于 0xff 的字符时缓冲区的加宽（`string_buffer_widen`）。`padStart` 和 `padEnd` 以同样的方式把窄字符串写进宽缓冲区（`string_buffer_write8_wide_long`，用于一步或更长的字符串：更短的由 `string_buffer_write8` 的循环复制，它对自己的长度计数）。
- 字符串的 `JSON.stringify`：连续段和转义（`json_quote_run`）。
- 容纳超过 1 MiB、必须增长的字符串缓冲区，由 `string_buffer_realloc2` 按每步 1 MiB 复制，第一步之前读一次标志，不再由分配器一次调用完成。它在旧块还在时需要新块。分配器在不能原地扩展块时也需要这样，但它可以不用第二个块就重新映射自己内存块里的一个块，而复制做不到，所以复制期间使用中的内存可能更高，大约多出旧块那么多。这不是一个可以指望的上界：它取决于分配器和宿主对内存块做什么。对堆的检查，也就是它的计数对着内存上限的检查，是 `heap_realloc` 的那个，对着减去旧块的计数：`js_malloc_moving` 对这一次请求，把上限提高堆为旧块所计的量（它的大小和它的头），并在内存不足错误产生之前放回去。旧块释放之后放得下上限的缓冲区仍能增长，而计数在复制期间超过上限，直到旧块被释放。这个检查只是堆的检查。占用上限把新块和旧块一起算，而宿主可能拒绝映射另一个块，所以在这些上限附近，增长可能在 `heap_realloc` 本来能重新映射块的地方失败。测试排空缓存，把上限正好设在 `heap_realloc` 的检查处和低一个字节处，并看到增长之后和失败之后上限被放了回去。
- 用字符串作模式的 `replace` 和 `replaceAll`，对最多 256 个字符的字符串用一个简单循环搜索，总共最多比较 256 乘 256 个字符，所以不需要读标志，更长的用 `indexOf` 的搜索。
- Map 或 Set 查找键，如果键是 rope 或一步或更长的字符串，用读标志的比较（长度不同的记录已知不同），其他任何字符串用 `js_short_eq_budget` 的比较。不是字符串的键立刻比较。

创建错误不读中断标志，而 `engine/test/cycles.sh` 检查 `JS_ThrowError2` 到不了任何读标志的函数。所以上面这些循环被排除在错误所需要的东西之外：创建错误的消息和栈的 `JS_NewStringLen`，把含有大于 127 的字符的文本解码两次（先数码元，再写入），写进刚好大小的字符串，不写进字符串缓冲区，而 `JSON.parse` 文本转 C 字符串的是 `js_string_to_cstring_json`，它是 `js_string_to_cstring` 加上读取的副本，不是它的一个标志。

测试：`engine/test/unit-white.c` 里的 `test_poll_work_gaps` 不数标志的读取次数，数的是两次读取之间的工作。循环用 `JS_WORK(n)` 说明它做了什么（在引擎里什么也不是），`white.c` 把两次读标志之间的值加起来，而一次调用必须把最长的一段，包括第一次读取之前和最后一次读取之后的，保持在这一步之内，并加起来等于它该做的工作。每个用例给出它的总数。这些用例有：填充物在一步中间结束的 pad，扫描在一步中间结束的 slice，由 65534、65536 和 65535 个字符的叶子组成的键，65537 个和 131071 个字符的字符串先哈希再比较，64 个哈希相同、在第一步就与所找的键不同的键，只有一个连续段的、只有转义的、由短连续段和转义组成的以及由 `\u` 转义组成的 JSON 文本字符串，70,000 个 ASCII 字符之后的一个宽字符或宽转义，宽填充物的 pad，连续段、转义和宽字符的 `JSON.stringify`，搜索，200,000 个字符的相等字符串上的 `indexOf` 和 `Object.is`，一个有 40 个元素的数组，其元素是一个 65,535 个或 65,536 个字符的字符串，去找另一个最后一个字符不同的字符串，两个 32768 个字符的扁平字符串，后面在数组里跟着一个同样长度的 rope（预算恰好在 rope 之前用完），Map 里的 32 个哈希相同、65,535 个或 65,536 个字符的键，一个 Map 和一个对象，以及进入已经是宽的缓冲区里的 JSON 窄字符连续段（解析和 stringify）。`test_buffer_copy_work` 还给出紧跟在 60,000 个单位工作之后的一次复制的工作，`test_buffer_limit` 在上限正好够放新块而放不下两个块的地方和低一个字节的地方增长缓冲区。`test_buffer_copy_work` 给出 1,500,000 个字符的缓冲区的复制和加宽的工作。一个个地放回 JSON 字符串的转义计数、加宽的轮询、在差异处结束的比较的计数、哈希与它的比较之间的标志读取、`js_string_find_at` 的轮询以及 `Array.prototype.indexOf` 里比较的轮询，都会让一个测试失败，一个个地拿掉缓冲区复制之前的标志读取、短比较的预算（`js_short_eq_budget`）、窄连续段进入宽缓冲区时翻倍的计数，以及上限里旧块的空位（`js_malloc_moving`），也会让测试失败。`engine/test/unit.c` 里的 `test_rope_polls`、`test_rope_key_compare_polls`、`test_long_key_polls` 和 `test_long_ops_polls` 在指定的一次标志读取处停住每个调用，而 `TestInterruptStopsLongBuiltins` 和 `TestInterruptStopsLongKeys`（`internal/cengine`）在生成的引擎里，在它的六个轮询处停住它，每个键用自己的 VM，因为第一次把字符串用作键会把它变成 atom。有理由的试验可以允许更晚的停止：`padEnd` 的前两个，它先用一个 `memcpy` 写字符串的 64 MiB，以及 `padStart` 带 32M 个字符的填充物的第一个，它落在缓冲区的分配里。带一个宽填充物的 `padStart` 的试验在调用的最后 40% 里，也就是把字符串复制进宽缓冲区（`string_buffer_write8_wide_long`），在那里停下最多 16 次轮询。

没有覆盖的，界限是输入的长度：
- 那些返回布尔值、不能报告异常、用 `js_strict_eq2`、`js_same_value` 或 `js_same_value_zero` 的入口对两个相等字符串的比较：对值做 `Object.defineProperty` 和 `Reflect.defineProperty` 的检查，Proxy 的不变式，C API 的 `JS_IsStrictEqual`、`JS_SameValue` 和 `JS_SameValueZero`，等等。
- `string_buffer_end` 最后缩小缓冲区。两个扁平字符串的比较和把长片段复制进字符串缓冲区是覆盖了的（见[下文](#比较和复制很长的字符串时读中断标志)）。
- Map 或 Set 的表翻倍时的重新哈希（800 万个条目时约 1,100 次轮询，默认 128 MiB 的 VM 容纳不下），以及停止之后释放一个很大的结果（800 万个小对象约 1,700 次轮询，同样容纳不下）。

## 开始和结束标签函数在每个长循环里读中断标志

发布版本：v0.30.0。

[RegisterStartTag 和 RegisterEndTag](go-api.zh-CN.md#registerstarttag-和-registerendtag) 的函数，在四个地方遍历长字符串而不读中断标志，所以对长字符串的调用，在 `Interrupt` 或 eval 超时之后还会继续运行。超时 10 ms 时，`TestTagsStop` 在 CI 的 linux/amd64、darwin/arm64 和 darwin/amd64 运行器上，分别在循环开始后 53、60 和 119 ms 才停下，超过了它允许的 50 ms。这四个地方是：

- 对照 React 的标签正则检查标签时扫描整个标签。
- 扫描样式名里不是 ASCII 的字符，发生在写连字符之前，而写连字符会读标志。
- 做好的开始标签和样式名，被一次 `memcpy` 从缓冲区复制成刚好那么长的字符串，几千万个字符。
- `isJavaScriptProtocol` 跳过的 URL 之前的空白，以及它的字母之间的制表符和换行。

现在这两个函数对比一步更长的字符串所做的每个循环，都在每一步之前和最后一步之后读标志，这样一个循环的工作不会延续进下一个循环：转义和样式名的连字符是 4,096 个码元，扫描标签或样式名以及每次复制（长标签、样式名、结束标签、做好的开始标签）是 524,288 个码元（1 MiB 的 16 位码元）。样式值周围和 URL 之前的空白在被跳过时计数：字符串比 4,096 个码元更长时，在它之前读标志，之后每 4,096 个码元读一次，更长的一段在末尾也读。复制进一次调用的缓冲区的长片段，先让缓冲区大到装得下它的全部，这样缓冲区只增长一次。一步或更短的字符串一次做完，不读，和以前一样，所以普通标签完全不读标志。

停止会抛无法捕获的中断，并让 `target` 保持原样：标签完整之后才压入。在创建过程中被停住的样式名或结束标签不保留，下次调用会再造。文本逐字节相同（`compare.sh` 的 `start_tag.js`）。

从 `Interrupt` 到调用结束的时间，在 `TestTagsStop` 每个用例的调用循环被停住 200 次的情况下（16M 到 64M 个字符的字符串），之前和之后：

| `TestTagsStop` 的用例 | linux/amd64，200 次中最长，之前 | 之后 | M4，200 次中第 99 位，之前 | 之后 |
|---|---|---|---|---|
| 要转义的文本，16M 个 `<` | 3.7 ms | 4.6 ms | 10.0 ms | 3.3 ms |
| 没有要转义的文本，16M | 11.0 ms | 3.2 ms | 2.1 ms | 1.2 ms |
| 宽文本，16M | 4.9 ms | 5.1 ms | 2.1 ms | 1.9 ms |
| 要转义的属性，16M 个 `"` | 4.9 ms | 5.0 ms | 8.8 ms | 10.0 ms |
| 64M 个空白里的样式值 | 0.06 ms | 0.05 ms | 0.03 ms | 0.04 ms |
| 16M 的样式名，驼峰 | 16.7 ms | 4.7 ms | 2.8 ms | 0.65 ms |
| 8M 的自定义样式名 | 5.2 ms | 5.9 ms | 7.3 ms | 1.9 ms |
| 32M 的标签 | 19.0 ms | 5.9 ms | 20.6 ms | 11.1 ms |
| 32M 的结束标签 | 6.4 ms | 7.3 ms | 1.9 ms | 16 ms |
| 32M 个空白之后的 URL | 10.5 ms | 3.3 ms | 20.0 ms | 3.6 ms |

调用是在循环开始后 20 到 80 ms 随机时刻被停住的。linux/amd64 的机器在其他方面是空闲的，M4 不是，它偶尔出现的 10 到 28 ms 的停止（两个构建里都有）是机器的负载。修复之后剩下的 3 到 7 ms，大多是释放和分配这次调用几十兆字节的块所花的时间（堆的系统调用），在这两个函数的循环之外。

普通标签不读标志，走和以前同样的循环，每个循环里多一次对长度的测试。用 [measuring.zh-CN.md](../measuring.zh-CN.md) 的方法在 tifa 的页面上测得（16 种布局，2 轮，delta 1%，linux/amd64）：两个函数每次渲染多运行 8 到 33 千条指令，占整个程序的 0.002% 到 0.018%，解释器运行的指令和以前一样多。16 种布局上一次渲染的时间变化是 -0.16%（store）、-0.08%（shop）、+0.41%（MUI）和 +0.21%（bench，各布局之间的离散度是 1.84%），没有一个超过 delta。只看正式布局，四个应用都慢 0.6% 到 1.8%，而对四个短标签各调用 1,000 次的循环慢 2%，多出的时间在这次改动没有碰的函数里。解释器运行同样的指令，所以两者都指向代码落在了哪里。16 个页面的 HTML 相同。


一次调用的界限：它那些一步或更短的字符串（最多 32 个属性、32 个样式值和一段文本，连同它们的名字）一次做完，所以一次调用在两次读取之间最多可以做大约 65 个这样的，最坏是几毫秒的复制。作为文本或样式值给出的 rope，先由 `JS_ToString` 分步拼平，这些步会读标志（见[下一节](#长-rope-分步拼平)）。键（props 最多 32 个，样式最多 32 个）、默认分支的名字（少于 64 个字符）以及名字和结束标签的表（最多 512 个和 256 个条目）都是有界的。

测试：`engine/test/unit-white.c` 里的 `test_tag_work_gaps` 对下面这些数两次读标志之间的工作（`JS_WORK`，和上面的 `test_poll_work_gaps` 一样）：600,000 个字符的标签，524,286 个字符的标签（它的开始标签是一步，一次复制完），524,288 个字符的标签（它的开始标签分步复制），字符串和对象的结束标签，短步长和长步长的自定义与普通样式名，8 位和 16 位的文本以及要转义的属性，样式值周围的空白、URL 之前的空白和 `javascript:` 字母之间的空白，一次长转义之后的一段空白，恰好 4,096 个码元的一段，以及一个短宽值之后的一段。每个都必须把每一段保持在它的步长之内并给出它的总数。`engine/test/unit.c` 里的 `test_tag_polls` 从 C 调用这些函数，处理长标签、文本、属性、样式值、URL、新的样式名和新的结束标签，要求一定数量的标志读取，并在每次调用的第一次读取、中间一次和最后一次读取处停住它：调用抛 `interrupted`，无法捕获，target 不变，同样的调用随后给出 React 的函数给出的东西，而运行时释放后没有泄漏。`TestTagsStop`（`tags_test.go`）通过 Go API 用 eval 超时运行上面的用例。

## 长 rope 分步拼平

发布版本：v0.30.1。

用 `+` 把长字符串连起来得到的字符串是 rope：一棵字符串树，一直保留到有东西需要把字符放在一个块里。那时 rope 被拼平，它的字符串一个接一个复制进新字符串。每个字符串过去用一次 `memcpy` 复制，而中断标志只在两个字符串之间读，所以由两个 32M 个字符的字符串组成的 rope，会在整个复制期间挡住 `Interrupt` 和 eval 超时。超时 10 ms 时，`TestTagsStop` 的“样式值”用例（它 64M 个字符的值是一个 rope），在 CI 的 darwin/amd64 运行器上，调用开始 68 ms 后才停下。在 Apple M4 上，引擎在请求之后最多又运行了 26 次轮询（每次 10,000 个计数）才停下，而先把同样的值拼平的话，第一次轮询就停下。

现在 65,536 个字符或更长的 rope 分步复制（`string_buffer_concat_rope_long`）：两次读标志之间最多 65,536 个字符，rope 的每个字符串算比它的长度多一，和它的哈希一样，第一步之前读一次，最后一步之后再读一次。这一步和 rope 的字符上其他循环用的一步相同，所以在一个字符串中间结束的一步，会在下一个字符串里接着走。当一个宽字符串被追加到一个只容纳不到 65,536 个字符的 8 位缓冲区时，缓冲区立即被加宽，不读标志，所以它的长度算在那一块的步长里。rope 的两种复制都采用它：`js_linearize_string_rope`，它为 `JS_ToString`、`JS_ToPropertyKey`、`ToNumber` 和每个读字符串的内置函数把 rope 拼平，以及 `string_buffer_concat_value`，它把 rope 追加进字符串缓冲区（`String.raw`、`new Function`、`replace` 的替换里的 `$&`、`JSON.stringify` 的间隔）。短于 65,536 个字符的 rope 和以前一样，一次一个字符串地复制，多一次对它长度的测试。

停止会抛无法捕获的中断并释放新字符串。rope 保持原样：只有复制完整之后才让它指向扁平字符串，所以下一次使用会再把它拼平。这两个函数的每个调用方本来就处理复制失败，因为复制本来就可能内存不足。拼平后的字符串逐字节相同。有了这次改动，“样式值”用例在每次运行里都在请求之后的第一次轮询处停下，在 M4 上和在 Rosetta 下都是。

代价：tifa 的页面要拼平 65,536 个字符或更长的 rope，所以它们走新路径。在 linux/amd64 上用 callgrind 数（每个页面 3 次渲染，对比 v0.30.0），字符串缓冲区函数每次渲染多运行 1,160（bench）到 5,973（store）条指令，不到一次渲染 2.14 亿到 14.4 亿条指令的 0.001%，而解释器自己的代码运行的和以前一样。整个程序变化了 -0.50% 到 +0.68%，全部在 tifa 在渲染之后于另一个 goroutine 里运行的年轻代回收上，它们落在被计数的渲染之内还是之外，取决于那个 goroutine 的时机（shop 运行得多一些，store 少一些）。

作为 rope 的 Map 或 Set 的键也是分步哈希的（`hash_string_rope_poll`）。表增长时键的重新哈希（`hash_string_rope`）不是，正如上一节的列表所说。

测试：`engine/test/unit-white.c` 里的 `test_poll_work_gaps` 用 `String` 把 rope 拼平，用 `String.raw` 追加它们：200,000 个和 70,000 个字符的字符串（第一个在一步之后 3,392 个字符处结束），中间夹一个 600 个字符的字符串，短的在前，两个窄字符串之间的一个宽字符串（它的 8 位字符被写进 16 位缓冲区），以及追加进缓冲区的 200,000 个 8 位字符之后的一个宽字符串（缓冲区被加宽），和 40,000 个之后的一个（缓冲区立即被加宽）。每个都必须把每一段保持在 65,536 之内并给出它的总数：字符数加上每个字符串一，以及加宽的字符数。那个测试里其他用例的 rope 在准备阶段就被拼平，这样每个用例只数自己那次调用的工作。`engine/test/unit.c` 里的 `test_rope_flat_polls` 从 C 用 `JS_ToString` 并用 `String.raw` 把 6M 到 10M 个字符的 rope 拼平，要求一定数量的标志读取，并在每个的第一次读取、中间一次和最后一次读取处停住它：调用抛 `interrupted`，无法捕获，rope 仍是 rope，字符相同，同样的调用随后给出扁平字符串，运行时释放后没有泄漏。在这次改动之前，这些调用读标志 2 到 133 次，低于测试的要求。`TestTagsStop`（`tags_test.go`）通过 Go API 运行“样式值”用例。

## repeat 每 65,536 个字符读一次中断标志

发布版本：v0.30.1。

`String.prototype.repeat` 过去每 1,048,576 个字符读一次中断标志，而且只在它的字符串的两次完整复制之间。它一次写一个字符地写一个字符的字符串，每个字符约一个计数（一次轮询 10,000 个计数），所以 `'x'.repeat(1 << 20)` 运行了 105 次轮询而没有读取，更长的字符串在两次读取之间整个被复制（16M 个字符用 13 次轮询）。少于 1,048,576 个字符的调用什么也不读，所以 `'x'.repeat(1e5)` 的循环只在下一次调用时才停，请求之后最多 11 次轮询。

现在 65,536 个字符或更长的结果按每步 65,536 个字符写，和 `padStart` 的填充物一样，第一步之前读一次，最后一步之后再读一次（`js_string_repeat_long`）。超过一个字符的字符串一块一块地复制，一块在字符串或这一步的末尾结束，所以比一步更长的字符串也是分步复制的。更短的结果像以前一样一次写完，不读。停止会抛无法捕获的中断并释放缓冲区。字符串逐字节相同。

代价：tifa 的页面没有一个把字符串重复到 65,536 个字符，所以 `js_string_repeat_long` 在那里不运行（callgrind，每个页面 3 次渲染），而更短的 repeat 运行它以前运行的代码，多一次对长度的测试。

测试：`engine/test/unit-white.c` 里的 `test_poll_work_gaps` 重复一个字符、两个字符、一个 70,000 个字符的字符串（块跨过一步的末尾）和一个宽字符串，并要求每一段都保持在 65,536 之内，总数是结果的长度。`engine/test/unit.c` 里的 `test_string_loop_polls` 要求 16M 个字符的 repeat、一个字符的、两个字符的和一个 8M 的字符串的 repeat 读 255 次标志（之前读 3 到 17 次），在中间停住每一个，并检查这些 repeat 造出了什么。`TestBuiltinWorkStops` 用 eval 超时运行 `'x'.repeat(1e5)` 的循环。

## 编译一个长正则时在每个长循环里读中断标志

发布版本：v0.30.1。

正则解析器在每个项处读中断标志（见[上面](#编译正则计入中断检查)），但是围绕解析的工作，以及一个项内部的循环，不读。一个 13.2M 个字符的模式（`'(?:a|b|c)+d'` 重复 120 万次）运行约 2,300 次轮询（每次 10,000 个周期），其中四段没有读标志：把模式转成 UTF-8（41 次轮询），缓冲区增长时对代码的复制（每次增长一半的几段，最多 45 次轮询），为寄存器扫描代码（`compute_register_count`，1,320 次轮询），以及把代码复制进它的字符串（46 次轮询）。在寄存器扫描里被请求的停止，到来时已经超过了 Go 宿主杀死脚本所依据的 1000 次轮询：调用以 `ErrKilled` 结束，VM 只能 `Close`，而它本该以中断结束。在一个项内部，计数的数字（`a{000…1}`）、`\u{…}` 和组名，类里 `&&` 和 `--` 的操作数，以及 `\q{…}` 的字符串，都是一遍读完，不管多长，而一个 `\q{…}` 的字符串，要和它之前每个哈希和长度相同的字符串比较，也不读标志。正则缓存里的一次查找，对模式的哈希，以及与某个条目的模式的比较，同样是一遍完成。

现在这些循环每一个都分步读标志，停止会抛无法捕获的中断，和解析一样：

- 模式经 `js_string_to_cstring_poll` 变成 UTF-8，这是 `JSON.parse` 的转换，它每 65,536 个字符读一次标志。不带标志 `u` 或 `v` 的模式保持它原来的 CESU-8。
- 代码缓冲区里的空位，由编译器在每次写之前申请，一条指令的所有字节申请一次（`re_dbuf_claim`），而增长的 1 MiB 或更大的块按每次 1 MiB 复制，每次之后读一次（`lre_realloc_code`）。缓冲区不通过它的 realloc 函数调用它：引擎的每个缓冲区都通过同一个指针调用那一个，而创建错误必须到不了任何读标志的函数（`engine/test/cycles.sh`）。标志置位时请求失败，解析器靠标志把这种情况和内存不足区分开。
- 代码的移动（选择分支的 split，量词放在它的原子前面的代码，后行断言的项）一次移动 1 MiB。
- 为寄存器和为带量词的原子扫描代码，为分组扫描模式，以及计数、`\u{…}` 和组名的数字，每 16,384 个字节读一次标志。一次扫描每个字节约一个周期，所以一步不到 2 次轮询。
- `&&` 和 `--` 的每个操作数都读标志，`\q{…}` 的每个字符和每个字符串在被解析、转成小写、并入类、转成代码时也读。在字符串表里的一次查找每 16,384 个码元的链读一次标志，每经过一个字符串算一个，每比较一个字节算一个，因为引擎的 `memcmp` 每个字节花一个周期：哈希和长度相同的字符串，这是模式可以由它们组成的，过去比较时不读标志，在 `TestRegExpCacheStops` 里每加一个字符串，最多要比较 31 个 128 KiB 的字符串。1 MiB 或更大的字符串按每次 1 MiB 复制。
- 代码按每次 1 MiB 复制进它的字符串。
- 缓存每次哈希 65,536 个字符的模式，和 Map 的键的哈希一样，并分步与某个条目的模式比较。在一步之内结束的比较，仍是以前的扁平比较。字符本身就超过缓存字节数的模式不被查找，因为缓存存不下它，而哈希只做一次，用于查找和条目。

写入代码失败（因为停止或内存不足）时，现在会让它之后的偏移保持未修补：解析器过去会在失败的写入本该所在的位置，也就是缓冲区末尾之后，修补选择分支的跳转，以及类的字符串的跳转。

正则编译出和以前逐字节相同的代码，停止会释放编译造出的东西。13.2M 个字符的模式，在 darwin/arm64 上它编译过程中的 214 个位置，以及 linux/amd64 上的 203 个位置所做的每次停止，都在请求后 3 次轮询之内，没有一次杀死 VM。8M 个零的数字、转义和组名在 2 次轮询之内停下，`&&` 和 `--` 的操作数在 1 次之内，在缓存中对一个 900,002 个字符的模式的查找在 7 次之内，哈希的 65,536 个字符的一步，以及 `TestRegExpCacheStops` 里 32 个哈希相同的字符串的类，以前在请求之后 76 和 107 次轮询才停下，现在在 7 次之内，那是它的 1M 个字符转换的一步。

代价：在 linux/amd64 上用 callgrind 数（tifa 每个页面 3 次渲染，对比改动前的引擎），store 每次渲染编译 271 个正则并在缓存里查找 895 次，mui 查找 225 次而不编译，shop 和 bench 两者都没有。store 上的编译和查找每次渲染多运行 110,373 条指令，每次编译约 400 条（每次写之前申请的空位和扫描的步），占一次渲染 14.3 亿条的 0.008%，mui 多运行 12,989 条，每次查找约 56 条（分步的哈希），占 0.002%。转成 UTF-8 的运行情况相同，只是从 `JSON.parse` 挪到了它自己的函数里，解释器自己的代码也一样。整个程序变化了 -0.02%（bench）到 +0.52%（store），其中 +0.52% 全部在 tifa 在渲染之后于另一个 goroutine 里运行的年轻代回收上（`JS_RunYoungGC` 以及它下面的释放和标记），它们落在被计数的渲染之内还是之外，取决于那个 goroutine 的时机。

测试：`engine/test/unit-white.c` 里的 `test_poll_work_gaps` 编译一个由分组组成的 2.2M 个字符的模式，一个带量词的 2M 个字符的分组，一个 2M 个字符的选择分支，一个在它的分组之前被使用的名字，1M 个宽字符，一个计数、一个转义和一个组名各有 2M 个前导零，在缓存里查找一个 900,002 个字符的模式，并编译一个有 32 个哈希和长度相同的字符串的类。两次读取之间的每一段工作都必须保持在步长之内（1 MiB，查找和字符串类是 65,536），项的循环和查找给出它们的总数，其他的不给，因为代码的复制取决于分配器给每个块的空位。`engine/test/unit.c` 里的 `test_regexp_compile_polls` 从 C 编译这些模式，以及 `&&`、`--` 和 `\q{…}` 的长项（一个 2M 个字符的字符串，也带标志 `i`，以及 131,072 个字符串，单独的和在 `&&` 里的），要求一定数量的标志读取（改动之前的引擎对一个项读 2 或 3 次，对其他的只在每个项处读），并在每个的第一次读取、中间一次和最后一次读取处停住它：编译抛 `interrupted`，无法捕获，同样的编译随后给出一个能匹配的正则，运行时释放后没有泄漏。`test_regexp_cache_polls` 对找到模式的查找做同样的事，它过去读标志 0 次。`test_compile_one_failure`（`unit-white`）让三个字符串类的编译的每个请求依次失败：在 AddressSanitizer 下，没有失败写入之后的检查的解析器，在 163 个用例中的 19 个里往缓冲区之外写。`TestRegExpCacheStops`（根包）用 eval 超时和 `Interrupt` 停住 13.2M 个字符的模式的编译，和一个有 32 个哈希和长度相同、32,778 个字符的字符串的类的编译，并把两者都限制在 5 次轮询的共同上限内（`stopPolls`），旧的 41 次和约 1,360 次轮询的几段，以及类的 76 次和 107 次，都过不了这个上限。

## 无论正则的类有多少字符或字符串都读中断标志

发布版本：v0.30.1。

有很多字符的类，或有很多 `\q{…}` 字符串的类，在上面那次改动之后仍有不读标志的几段，其中一段花的时间是 n 乘 n：

- 类的每个字符或范围并进类到目前为止的范围时，是把它们全部重新造一遍（`cr_union_interval`），一遍扫过它们，不读标志。一个 60,000 个互不相邻字符的类，编译要 557,426 次引擎轮询（每次 10,000 个计数），接近它末尾的几遍每遍 18 次轮询，而两个这样的类的交集要 1,126,723 次。
- `\q{…}` 的字符串按长度用 `rqsort` 排序，它不读标志：在 darwin/arm64 上，262,144 个 4 到 67 个字符的字符串最多 146 次轮询。
- 它们的表增长时，一遍移动每个字符串：524,288 个 4 个字符的字符串最多 34 次轮询。一个按另一个的表的顺序填充的列表，只持有前一部分哈希的字符串，所以大多数桶是空的，而遍历空表只在遇到字符串时才读标志：`[[\q{…}]&&[\q{zz}]&&[\q{yy}]]` 里的第二个 `&&`，在第一个没有留下 524,288 个字符串中的任何一个之后，运行了 51 次轮询没有读取。
- 停止结束编译时，字符串被一个个释放：524,288 个字符串最多 139 次轮询。
- 取反的类把它的所有点一遍上移一位：33 万个字符 10 次轮询。

现在：

- 类的最后一个范围之后的字符或范围，加在它的末尾，而从最后一个范围里开始或正好在它结束处开始的，让那个范围变长，所以按顺序的类每个字符花一步。其他的进入它们自己的未排序列表，这个列表用 `rqsort_stop` 排序，合并，并在任何东西读它们之前一次与类的范围合并：任意顺序的类花 n log n 的时间。60,000 个字符的类编译起来最少 51 次轮询，向下的 137 次，交集 115 次。
- 类的范围带着中断标志（`engine/libunicode.h` 里的 `CharRange.stop`，引擎里其他范围是 NULL），类为不区分大小写而造的范围也一样：`cr_op` 和相接范围的合并，在经过超过 4096 个点时每 4096 个点读一次，`cr_invert` 按每次 1 MiB 移动点，两次移动之间读一次。范围的代码每 16,384 个字节读一次标志后写出。
- 字符串用 `rqsort_stop` 排序，它给出 `rqsort` 的顺序并在每一步读标志。增长时的新表按每次 1 MiB 清空，移动每 16,384 个桶和字符串读一次标志：在那里停止会让字符串处于两张表之外，这是安全的，因为不再有东西遍历它们。对表的桶的其他遍历，每个桶读一次标志。
- 字符串取自一起释放的块，第一个 256 字节，之后每个是前一个的两倍，最大 64 KiB，更长的字符串放在自己的块里。被 `&&` 或 `--` 从列表里取出的字符串，一直留在它的块里，直到列表被释放。

正则编译出和以前逐字节相同的代码：上一次改动的 64 个模式，以及另外 37 个带大类的模式（60,000 个字符的向上和向下，相交和相减，不区分大小写，14 万个字符取反，随机顺序，带和不带 `i` 的随机范围，带属性的类，带和不带 `i` 的、有多种长度的 16,384 个字符串，以及字符串类的 `&&` 和 `--`），它们代码的哈希相同。在 60,000 个字符的类和 33 万个取反的类的编译的每次轮询处，以及在字符串类编译过程中的 100 个位置处停止，在 arm64 上请求后 7 次轮询之内，在 amd64 上 4 次之内（那 7 次是把模式转成 UTF-8，按 65,536 个字符一步），原来最多要 310 次之后。

代价：在 linux/amd64 上用 callgrind 数（tifa 每个页面 3 次渲染，对比改动前的引擎）。store 每次渲染编译 271 个正则，它们的编译现在每次渲染少运行 230,981 条指令，每个约少 850 条：类不再为每个字符重新造它的范围，而 `cr_op` 多运行约 500,000 条，它现在是 `cr_regexp_canonicalize` 调用的一个独立函数，原来是内联的。shop、mui 和 bench 不编译正则，它们的正则代码运行的和以前一样。整个程序变化了 -0.00%（bench）到 +0.29%（shop），全部在 tifa 在渲染之后于另一个 goroutine 里运行的年轻代回收和 Go 的回收器上，它们落在被计数的渲染之内还是之外，取决于那个 goroutine 的时机。

测试：`TestInterruptStopsRegExpCompile`（`internal/cengine`，`-tags testhooks`）编译这些：524,288 个 4 个字符的字符串的类，262,144 个 4 到 67 个字符的字符串的类，524,288 个字符串的类与两个不含它们的类相交，60,000 个字符向上的类，同样向下的类，两个这样的类的交集，以及 33 万个字符取反再与一个范围相交的类，在均匀分布于编译过程中的位置停住每次编译，按轮询计（`InterruptAtPoll`），并把每次停止限制在 9 次轮询之内，改动之前的引擎在每个用例里都超过了它。`engine/test/unit.c` 里的 `test_regexp_compile_polls` 从 C 编译这些：60,000 个字符向上的、向下的、取反的和相交的类，33 万个字符取反的类，17,000 个低于 0xFFFF、向下、带 `i` 的字符的类，带和不带 `i` 的、有多种长度的 16,384 个字符串的类，以及一个没有留下字符串的交集后面跟着另一个，并在每个的第一次读取、中间一次、最后一次读取，以及最后一次之前的 1、2、4、8……次处停住它，那里是解析一个类之后的循环读标志的地方：编译抛 `interrupted`，同样的编译随后给出一个能匹配的正则，运行时释放后没有泄漏。`test_poll_work_gaps`（`unit-white`）把 60,000 个字符向下的类的合并，以及 16,384 个字符串的类的表，限制在它们的步长之内。

## BigInt 的长运算读中断标志

发布版本：Unreleased。

一个 BigInt 最多 1,048,576 位，也就是 32,768 个 32 位的 limb（引擎编译时不用 128 位整数，所以每个目标上 limb 都是 32 位）。乘法、除法、乘方，以及在不是 2 的幂的进制下和字符串互转，耗时是 limb 数的平方，而且它们的循环都不读中断标志：`String(10n ** 300000n)` 要跑约 52,000 次引擎轮询（每次 10,000 个计数），在 Apple M 上要 1.9 s，五十万位的乘法或除法约 12,000 次。生成的代码在这些循环里照样轮询，所以 Go 宿主看到了停止请求，50 ms 和 1000 次轮询之后就杀掉了脚本：超时设 20 ms 时，这些调用都在开始后 70 ms 以 `ErrKilled` 结束，VM 只能 `Close`。

现在这些循环每走过 32,768 个 limb 或数字就读一次标志（`quickjs.c` 里的 `js_bigint_poll`，一步是 `JS_BIGINT_MAX_SIZE`），在会越过这一步的那一趟之前读，所以两次读取之间的一段不会超过一步：

- 乘法的每一行（`mp_mul_basecase`），也就是 `*` 和 `**`，乘方是一串乘法，
- 除法的每一行（`mp_divnorm`），也就是 `/` 和 `%`，
- 在不是 2 的幂的进制下转成字符串时的每次除法，以及在 2 的幂进制下的每个数字（`js_bigint_to_string1`：`String`、`toString`、模板字符串、和字符串做 `+`），
- 从十进制字符串转来时的每次乘法，以及从 2 的幂进制字符串转来时的每个数字（`js_bigint_from_string`：对字符串调用 `BigInt`，以及 BigInt 和字符串的比较）。

停下时抛出无法捕获的中断，并释放这次运算造出来的东西。只把 limb 走一遍的循环（加法、移位、位运算、`asUintN` 和 `asIntN`、比较）最多走一步，不读标志。有两处以前把错误丢掉，现在会传出去：乘方里某次乘法失败时，直接返回而没释放之前的积，`**` 每次报 `RangeError: BigInt is too large to allocate` 都漏一块内存（每次停下也会漏）。BigInt 和字符串的 `==` 与 `<`，把字符串转换时的错误当成「字符串不是 BigInt」，给出 `false`，错误还留在那里没处理。合法输入的结果逐位不变。

超时设 20 ms 时，这些调用在 linux/amd64 上现在都在截止时间之后 0.05 到 0.25 ms 停下，也就是请求后 1 到 3 次轮询，以前是在 70 ms 被杀掉。

代价：在 linux/amd64 上用 callgrind 数，和改动前的引擎比一次运算的指令数（一次 `Eval` 跑 1000 次，取 12 次和 2 次 `Eval` 之差）。256 位的乘法多 0.38%（2,081 到 2,089），除法多 0.96%，256 位的 `toString` 多 3.1%（3,276 到 3,379，每次除法一次检查），4096 位的 `toString(16)` 多 0.09%，对 40 位数字的字符串调用 `BigInt`，以及 BigInt 和这个字符串做 `==`，多 2.3%（2,839 到 2,904）。短字符串的 `s|0`（`compare/` 的 `string_to_int.js`），它的 `js_atof` 内联了 `js_bigint_from_string`，多 3 条指令，0.18%。在 EPYC 7B13 的 0 号核上计时（8 次的中位数），同样这些运算从快 26%（256 位乘法）到慢 28%（4096 位的 `toString(16)`）都有，跟着代码落在哪里走：`toString(16)` 的数字循环和以前是同样的指令。tifa 的页面不用 BigInt：两个 bench 页面各渲染一次，改动前 266,528,836 条指令，改动后 266,529,248 条，+0.00%（`compare/engines` 的 `jsbench tifa-ssr` 跑在 callgrind 下）。按 [measuring.md](../measuring.zh-CN.md) 的规程在 shop 的六个页面上计时（16 种布局，2 轮，EPYC 7B13 的 0 号核），它们 P50 之和在各布局上变了 +0.31% [-0.40%, +1.01%]，在正式布局上变了 +0.09% [-1.34%, +1.53%]：对 1% 的 delta 来说没有结论，因为上界超过它 0.01%，也没有哪个页面单独变慢。

测试：`TestBigIntWorkStops`（根包）用 20 ms 超时循环运行上面每一种调用（`String`、10 进制、7 进制和 2 进制的 `toString`、模板字符串、负数、`**`、`*`、`/`、`%`、对十进制字符串调用 `BigInt`、和字符串做 `==` 与 `<`），要求 8 次轮询之内得到无法捕获的中断而不是被杀，之后还能算 `1+1`。改动前的引擎除了 2 进制之外每种都被杀掉。`TestInterruptStopsLongBuiltins`（`internal/cengine`，`-tags testhooks`）在 `toString`、`String`、对字符串调用 `BigInt`、乘法、除法、乘方和与字符串的 `==` 上，在一次 12,000 到 52,000 次轮询的调用里均匀取 6 个位置打断，每次都在 3 次轮询内停下。`engine/test/unit.c` 里的 `test_bigint_polls` 要求每种调用读够一定次数的标志（十万位十进制数的转换要 500 次），在中间停下每一种，检查结果，最后释放运行时时不剩任何内存块，乘方结果过大之后也一样。`test_poll_work_gaps`（`unit-white`）要求乘法、除法和各种转换每段都不超过一步，并核对乘法、除法和二进制数字的总量。

## 把长字符串转成数字时读中断标志

发布版本：Unreleased。

一个字符串最多十亿个字符，把它转成数字或 BigInt 要把这些字符走好几遍：转成 UTF-8，跳过数字前后的空白，在 `js_atof` 里扫描数字，复制一遍，再由 `js_atod` 或 `js_bigint_from_string` 读这些数字。这些循环都不读中断标志。在 linux/amd64 上 `+'1'.repeat(1 << 27)` 一次要 250 到 600 ms，对 128 Mi 个零调用 `BigInt` 要 285 ms。超时设 20 ms 时，`Number`、一元 `+`、`isNaN`、`parseInt`、`parseFloat`、`BigInt`、BigInt 和字符串的 `==` 与 `<`、对数字或空白做 `JSON.parse`、对数字字面量做 `eval`，每一种都在开始后 70 ms 以 `ErrKilled` 被杀掉。

现在这些循环每走过 65,536 个字节读一次标志。扫描一个不知道长度的 C 字符串时，在指针走到 65,536 的整数倍地址处读（`js_poll_at`，一步跨多个字节时用 `js_poll_cross`），所以不用计数。`js_atof`、`js_atod` 和 JSON 数字的各位的循环由同一份函数体编出两份，一份读标志，一份不读，不到 65,536 个字节的字符串或 JSON 文本走不读的那份，也就是以前的代码：

- `skip_spaces`，也就是 `Number`、`parseInt`、`parseFloat` 和 `BigInt` 的数字前后的空白，包括占两三个 UTF-8 字节的空白，
- `js_atof` 里对整数部分、小数部分和指数的数字的扫描，旧式八进制字面量的数字，以及去掉分隔符的数字复制。它现在多拿一个参数，即字符串剩下的字节数，用来选走哪一份，
- `js_atod`（`dtoa.c`）里开头的零、数字和指数的数字，通过新加的最后一个参数传进要读的标志，调用方对 65,536 个字符以上的数字传它，更短的传 NULL。标志被设置时它给出 NaN，调用方再读一次标志，把它和输入本身的 NaN 区分开，
- `js_bigint_from_string` 开头的零，它现在从 `js_atof` 拿字符串的长度，不再调用 `strlen`，
- `JSON.parse` 里数字的各位，以及记号之间的空白。那里的 `\r\n` 现在算两个一字节的空白，而不是一个两字节的空白，结果相同，
- `Number`、`parseInt`、`parseFloat` 和 `BigInt` 把字符串转成 UTF-8 的那一步：65,536 个字符以上的字符串走 `js_string_to_cstring_json`，也就是 `JSON.parse` 用的那份转换的副本，每 65,536 个字符读一次标志，更短的字符串照旧走 `js_string_to_cstring`。

脚本里的数字字面量也走 `js_atof`。停下时抛出无法捕获的中断，并释放 C 字符串和数字的副本。每种输入的结果都不变。

超时设 20 ms 时，对 64 Mi 个字符的字符串做上面每一种调用，在 linux/amd64 上现在都在截止时间后 0.03 到 1.5 ms 停下，离请求 1 到 7 次轮询。以前测试里 24 种调用有 22 种在 70 ms 时被杀掉，另外两种在开始后 66 到 68 ms 才停下，离请求已经超过 5,000 次轮询。

代价：在 linux/amd64 上用 callgrind 计数，按一次操作的指令数，和只做了 BigInt 改动的引擎比（一次 `Eval` 做 1000 次，取 12 次和 2 次 `Eval` 之差）。短字符串的一次转换多 14 到 41 条指令，用在按长度选走哪一份代码，以及现在可能抛错的空白检查上：`+'12345'` 多 1.4%（1,826 到 1,852），`Number(' 3.25e2 ')` 多 0.7%，对它做 `parseFloat` 多 0.8%，`parseInt('12345')` 多 2.2%，对 39 位数字做 `BigInt` 多 0.3%，`compare/` 里的 `s|0` 和 `+s`（`string_to_int.js` 和 `string_to_float.js`）在引擎里分别多 1.8% 和 1.3%。对 6 KB（100 个对象）做 `JSON.parse` 多 0.53%，带缩进的同样内容多 0.82%。tifa 的两个 bench 页面渲染一次，改动前 266,543,139 条指令，改动后 266,681,981 条，+0.05%（`compare/engines` 的 `jsbench tifa-ssr` 的 callgrind）。

测试：`TestNumberConversionStops`（根包）对 64 Mi 个字符的扁平字符串（数字、零、数字前的空白、三字节 UTF-8 的空白、JSON 文本里的 `\r\n`、很长的小数或指数、十六进制数字、十六进制 BigInt 字面量、旧式八进制字面量），用 20 ms 超时循环运行上面每一种转换，要求 8 次轮询之内得到无法捕获的中断而不是被杀（`numberStopPolls`），之后还能算 `1+1`。改动前的引擎每种都失败。`TestNumberConversionLongResults` 检查 200,000 个字符以上的字符串的转换结果，这些字符串越过了循环读标志的位置。`engine/test/unit.c` 里的 `test_number_polls` 要求每种转换一百万个字符的字符串至少读 12 次标志，在中间停下每一种，检查之后的上下文和结果，最后释放运行时时不剩任何内存块。

## 解析很长的源码时读中断标志

发布版本：Unreleased。

脚本可以把十亿个字符的源码交给 `eval`、`Function` 或 `JSON.parse`。`js_parse_init` 会把源码计入中断检查（[见上文](#解析和构建字符串计入中断检查)），但处理函数要到解释器下一次轮询才被调用，而解析器和编译器走过一个很长的记号或很长一段源码的循环都不读标志：开头的 hashbang 行，两个记号之间的空白和换行，注释、标识符、字符串、模板或正则，其中转义 `\u{...}` 的数字，长名字的复制和它的 atom，长记号之后代码的行号和列号，以及点出这个名字的错误消息。在 linux/amd64 上，对 64 Mi 个字符的标识符做一次 `eval` 要 436 ms，对同样长的注释要 225 ms。超时设 20 ms 时，对 64 Mi 个空白、换行、注释字符或标识符字符做 `eval`，都在开始后 70 ms 以 `ErrKilled` 被杀掉，而在扫完很长的标识符、字符串或正则之后才来的停止请求，要再过几千次轮询才停下。

现在这些循环每走过 65,536 个字节读一次标志，在指针走到 65,536 的整数倍处读（`js_poll_at` 和 `js_poll_cross`，和把字符串转成数字时一样），每个字节花得更多的地方每 4,096 个字节读一次（`JS_POLL_SHORT_STEP`）：

- `eval` 和 `Function` 把源码转成 UTF-8 的那一步（`JS_EvalObject`），现在走 `js_string_to_cstring_poll`，也就是 `JSON.parse` 用的转换，这么长的源码每 65,536 个字符读一次。以前 32 Mi 个 `é` 或 16 Mi 个 `　` 的源码在第一个记号之前一口气转完，调用晚 40 ms 才停下，
- 脚本开头的 hashbang 行 `#!`（`skip_shebang`），
- `next_token` 里两个记号之间的空白和换行，占多个 UTF-8 字节的空白和行分隔符，块注释、行注释和 HTML 注释 `-->`。`\r\n` 现在算两个一字节的换行，而不是一个两字节的换行，得到的记号相同，
- `parse_ident`，也就是标识符和私有名，包括其中的转义和多字节字符，不是 ASCII 的字符每 4,096 个字节读一次，因为每个字符都要查一次 Unicode 的表，以及长标识符的缓冲区每次变大时的复制：`ident_realloc` 把 1 MiB 以上的缓冲区每次复制 1 MiB，每步之后读一次，申请新块时把旧块占的空间算进内存上限，和 `string_buffer_realloc2` 对字符串缓冲区的做法一样，以前 `js_realloc` 一口气复制整块，
- `js_parse_string`、`js_parse_template_part` 和 `js_parse_regexp`，也就是脚本里的字符串、模板和正则，包括正则的 flags。存放它们值的缓冲区按会读标志的步子增长，但每一步加上已有的一半，所以最后几步要走过几百万个字符才读一次，
- 字符串、模板、标识符或私有名里码点转义 `\u{...}` 的数字，以及 `simple_next_token` 里的，和正则一样每 16,384 个数字读一次：`lre_parse_escape_poll` 读交给它的标志。以前 `"\u{" + "0".repeat(1 << 27) + "41}"` 要到转义结束才读，
- 长名字的 atom：`JS_NewAtomLen` 把 65,536 字节以上的内容分步解码（`js_new_string_len_long`），放进一开始就够装下全部的缓冲区。每一步解码在这一步里开头的字符，最后一个必要时越过这一步的末尾，下一步从它结束的地方开始，所以对每种文本，包括不是 UTF-8 的字节，分步得到的字符串都和整体解码相同。以前每一步在一个字符的开头字节之前结束，一串不是 UTF-8 的字节跨过它时会多出一个 U+FFFD：解码器把这样一串字节连同后面那个字节当作一个字符。这样一串字节不管多长也分步读，
- `get_line_col`，也就是源码里某处的行号和列号，编译器在代码的每一处都要问（`compute_pc2line_info`），错误也要问它自己的位置，现在每 4,096 个字节读一次。中断时它经过 `get_line_col_cached` 和 `compute_pc2line_info` 把 -1 交给 `resolve_labels`，后者像成功时一样设好函数的代码，交给调用方释放，
- 函数为 `toString` 保存的源码的复制（`js_strndup_source`，每次 1 MiB），以及 `Function.prototype.toString` 对它的解码，
- `json_next_token` 里扩展 JSON 的注释，以及 `json_parse_ident`，也就是 JSON 文本里的单词，
- `simple_next_token`，也就是看当前记号后面那个记号的 `peek_token`，它现在多拿一个要读的标志（`JS_DetectModule` 传 NULL）。标志被设置时它给出 `TOK_EOF`，没有调用方会找这个记号，标志已经设置时一开始就给出，调用方接着走到 `next_token`，后者在同一段空白里读到标志并抛出。

有三个地方不读标志，现在做的事有了上限。检查 `"use strict"` 时把字符串的长度当作 `snprintf` 的精度，而 `snprintf` 会找 NUL 一直找到这个长度：精度现在是它保留的 19 个字节。"unexpected token" 消息给 `snprintf` 的最多是一条消息能装下的 255 个字节。`JS_AtomGetStrRT` 以前把 ASCII 的 atom 本身交给消息，先自己扫一遍，`snprintf` 再扫一遍，现在对 65,536 个字符以上的 atom 给出它复制的前 58 个字符：对这样的名字抛出的 `ReferenceError` 引用 58 个字符，以前引用 254 个，也就是一条消息能留下的全部。

停下时抛出无法捕获的中断。每种源码得到的记号、值以及行号和列号都不变，函数 `toString` 的文本也不变，包括不是 UTF-8 的字节。

没有覆盖的：`JS_DetectModule` 在源码开头找 `import` 和 `export`，不读标志，因为它没有运行时，Go API 也不调用它。长名字或长字符串的缓冲区在末尾缩小、堆要搬动这块内存时，也没有覆盖（见[对长字符串的循环按步读中断标志](#对长字符串的循环按步读中断标志)的末尾）。

eval 超时依次设成一次调用用时的每个六分之一时，这些对 16 Mi 字节源码的解析现在在 linux/amd64 上于截止后 0.04 到 8.7 ms 停下，多数在 3.6 ms 以内，见到请求后最多 11 次轮询。以前在那里，测试的 35 种情况里有 34 种失败：5 种被杀掉，其余的在截止后最多 47 ms 才停下，见到请求后最多过了 4,141 次轮询。

代价：在 linux/amd64 上用 callgrind 计数，比较的是对同一份源码做十次 `eval` 的指令数，对照的是改到[把长字符串转成数字](#把长字符串转成数字时读中断标志)为止的引擎（一次 `Eval`，取 12 次和 2 次之差）。对 1,500 个小函数（209 KB 的 ASCII）做 `eval` 多 0.05%，对 500 行含非 ASCII 的注释、名字和字符串（19 KB）多 1.20%，主要在 `next_token` 和 `js_parse_string` 里，它们要检查一个多字节字符是否跨过了一步，对 1,500 行字符串、模板和正则（122 KB）多 0.17%。tifa 的两个 bench 页面渲染一次，改动前 267,009,683 条指令，改动后 266,708,583 条，-0.11%（`compare/engines` 的 `jsbench tifa-ssr`，用 callgrind 计数）。

测试：`TestParseStops`（根包）造出 16 Mi 字节的扁平源码，内容是空格、制表符、换行、`\r\n`、三字节的空白和行分隔符、单字节和双字节字符的块注释、行注释、HTML 注释、单字节和双字节字符的标识符、私有名、属性名、单字节和三字节字符或转义组成的字符串、指令、模板、带标签的模板、正则、正则的 flags、字符串、模板、私有名和标识符里 16 Mi 个数字的转义 `\u{...}`（在标识符开头、中间和 `async` 之后）、hashbang 行、长行之后的语法错误、`peek_token` 在 `async`、`let` 之后和 `=>` 之前越过的空白和注释，以及给 `JSON.parse` 的一个单词。它先给一次调用计时，再在这段时间的每个六分之一处停下这个调用的循环，要求 16 次轮询之内得到无法捕获的中断而不是被杀（`parseStopPolls`：两步，因为 `peek_token` 在它那一步的末尾读到标志后，`next_token` 还要从头走过同一段，直到它自己的第一步，而长名字的 atom 做哈希和比较时每一步对每个字符做的事更多），每次之后还能算 `1+1`。改动前的引擎在 linux/amd64 上除了正则每种都失败，在 darwin/arm64 上前 28 种每种都失败。`TestParseLongResults` 检查同样几类 200,000 个字符以上的源码的结果、长行之后语法错误的行号和列号，以及两条消息。`TestParseLongRawBytes` 给 `eval` 一个函数的源码，里面有一串跨过一步、最长 300,000 字节的 0x80，要求它的 `toString` 里只有一个 U+FFFD。`engine/test/unit.c` 里的 `test_parse_polls` 要求每次解析一百万字节的源码至少读 12 次标志，在这些读取处停下每一次（每一处，或者均匀分布的 64 处），在 4 MiB 标识符的前 96 次读取处逐一停下它，其中包括它的缓冲区复制时的读取，检查每次之后的上下文和结果，最后释放运行时时不剩任何内存块。`test_long_utf8_decode` 解码 196,608 字节的文本，里面有一串后续字节、过长形式、被截断的序列、五字节形式、代理项、四字节字符等，放在一步末尾附近的 17 个位置上，后面再跟最长 65,541 字节的 0x80，要求 `JS_NewAtomLen` 的名字和 `toString` 里得到的都是整体解码的字符串，并在 4 MiB 这样一串字节的前 64 次读取处逐一停下它的解码。

## 比较和复制很长的字符串时读中断标志

发布版本：Unreleased。

脚本可以持有十亿个字符的字符串，在一次调用里比较或复制它们。两个扁平字符串的 `<`、`<=`、`>` 和 `>=`，以及不带比较函数的数组排序，在 `js_string_compare` 里走过这两个字符串，不读中断标志。`Symbol.for` 对它的键做哈希、和注册表里的键比较，也是这样。把字符串复制进字符串缓冲区（`string_buffer_write8` 和 `string_buffer_write16`）时，`join`、`padEnd`、`replace`、`String.raw`、`Function` 和许多别的函数都用它，它把很长的字符串一口气复制完，只有每字符一字节的字符串写进每字符两字节的缓冲区时除外。在 linux/amd64 上，对两个相同的 64 Mi 个字符的字符串做 `s < s2` 要 40 ms，中途请求停止，要到截止后最多 34 ms、见到请求后 5,610 次轮询才停下。对这样的键做 `Symbol.for` 时请求停止，最多晚 65 ms，复制时晚 31 到 45 ms，见到请求后过了 40 到 52 次轮询。

现在它们每 65,536 个字符读一次标志，按字节复制时每 1 MiB 读一次：

- `js_string_compare_poll` 比较两个都有 65,536 个字符以上的字符串时，走 `js_string_rope_compare`，也就是比较 rope 的函数，它每 65,536 个字符读一次标志。`js_relational_slow`（`<` 和另外几个）和 `js_array_cmp_generic`（不带比较函数的排序）用它。它检查两个长度里较短的那个，比较本来就要用它，所以短字符串只多一次比较和一次分支，照旧比较，
- `Symbol.for` 的键有 65,536 个字符以上时，走 `js_new_long_string_atom`，也就是长 atom 已经在用的分步哈希和比较，它现在多拿一个 atom 的类型（注册表里的键不是字符串 atom），
- `string_buffer_write8` 往 16 位的缓冲区写 65,536 个字符以上，或者往 8 位的缓冲区写 1 MiB 以上时（`string_buffer_write8_long`），前者和以前一样每次复制 65,536 个字符，后者每次用 `memcpy` 复制 1 MiB，每步之后读一次。以前往 8 位缓冲区的复制是一次 `memcpy`。两个分支各自检查长度，这样短字符串的复制保持原来的代码，
- `string_buffer_write16` 写 65,536 个字符以上时（`string_buffer_write16_long`），每次找 65,536 个字符里有没有大于 0xff 的字符、复制 65,536 个字符，每步之后读一次，空间只腾一次，和短字符串一样，
- 替换串的代换（`js_string_GetSubstitution`，供 `replace`、`replaceAll` 和 `RegExp.prototype[Symbol.replace]` 用）找每个 `$` 和 `>` 时用 `string_indexof_char_poll`，它每 65,536 个字符读一次标志，每 1,024 个 `$` 也读一次。后面没有 `>` 的 `$<`，以前对它后面的每个 `$<` 都要再找一遍，用时是替换串长度的平方，现在只找一次，
- 正则的 flags 字符串，`replaceAll`、`matchAll` 以及 `RegExp.prototype[Symbol.match]`、`[Symbol.matchAll]`、`[Symbol.replace]` 和 `[Symbol.split]` 从它的 getter 拿到，可以任意长，现在只读一遍，每 65,536 个字符读一次标志（`js_regexp_flags`），以前每个 flag 都扫一遍，
- `String.raw` 每 1,024 段读一次标志，和 `join` 一样，因为它的 `raw.length` 最大可以到 2^53，`RegExp.prototype[Symbol.replace]` 的两个循环每 1,024 个结果读一次，
- 命名空间导入要给模块的导出名排序（`js_build_module_ns`），现在用 `js_string_compare_poll` 比较、用 `rqsort_stop` 排序，每次比较读一次标志（`exported_names_cmp`），和数组排序一样。以前 `rqsort` 一口气比较两个 64 Mi 个字符的名字，比较失败时答 0，排序接着做。

写入字符串缓冲区现在会在中断处停下，所以写入失败后还接着做的调用方现在立刻离开：`js_string_GetSubstitution` 以前接着在替换串剩下的部分里找 `$`，`String.raw` 接着做到 `raw.length` 的末尾，`replace` 和 `[Symbol.replace]` 接着处理它们的匹配。`"x".replace("x", "a".repeat(1 << 20) + "$$" + "b".repeat(1 << 27))` 在第一次复制时被停下，以前还要接着走过它后面的 128 Mi 个字符。

停下时抛出无法捕获的中断。结果不变。

eval 超时依次设成一次调用用时的每个六分之一时，这些对 64 Mi 个字符的字符串做的调用现在在 linux/amd64 上，见到请求后最多 7 次轮询就停下：比较、排序和 `Symbol.for` 在截止后 0.2 ms 以内，复制在截止后 5 到 10 ms，见到请求后 1 到 3 次轮询。替换、flags 和 `raw.length` 很大的 `String.raw` 在截止后 4.6 ms 内停下。以前这 6 种每种都失败：16 Mi 个 `$$` 和 `$<` 的替换被杀掉，其余的在见到请求后最多 6,813 次轮询才停下。两个导出名各有 64 Mi 个字符、只在最后一个字符不同的模块，对它做命名空间导入，现在在截止后 0.05 ms 内停下，见到请求后最多 6 次轮询，以前要等比较做完、导入进行到 40 ms 才停下，见到请求后最多 5,605 次轮询。

代价：在 linux/amd64 上用 callgrind 计数，比较的是一次 `Eval` 里十次调用的指令数，对照的是改到[解析](#解析很长的源码时读中断标志)为止的引擎（取 12 次和 2 次 `Eval` 之差）。两个短字符串的 `<` 多 0.24%，给 2,000 个短字符串排序多 2.56%（每字符两字节的字符串多 2.66%，每次约 200 条指令的比较里多约 5 条），对 2,000 个短字符串做 `join` 多 2.22%，来自每次复制时对长度的检查，而对它们做 `+=` 不变（-0.20%）。在 2,000 段的文本里用正则做全局 `replace` 多 2.19%，大部分在 `js_string_GetSubstitution` 里，来自对每次写入和剩下要找的长度的检查，对 2,000 个短字符串做 `padEnd` 多 0.14%，做 `Symbol.for` 多 0.21%。tifa 的两个 bench 页面渲染一次，改动前 266,702,384 条指令，改动后 267,024,572 条，+0.12%，一半在 `string_buffer_concat` 里，每复制一个短字符串多 3 条指令，其余大多在 `JSON.parse` 和 `JSON.stringify` 用的 `json_parse_string` 和 `JS_ToQuotedString` 的复制里（`compare/engines` 的 `jsbench tifa-ssr`，用 callgrind 计数）。

测试：`TestStringCompareCopyStops`（根包）对两个 64 Mi 个单字节字符或 32 Mi 个双字节字符的字符串做 `<`、排序，对其中一个做 `Symbol.for`、`join`、`padEnd`、`replace`、`String.raw` 和 `Function`，用 64 Mi 个字符的替换串做 `replace`（1 MiB 之后有 `$$`、没有 `$`、16 Mi 个 `$$`，以及带分组的 16 Ki 个 `$<`），64 Mi 个字符的正则 flags，以及 `raw.length` 为 4 Mi 的 `String.raw`，每种都在新的 VM 里做，因为某个键的第一次 `Symbol.for` 会造出后面几次找到的 atom。它先给一次调用计时，再在这段时间的每个六分之一处停下这个调用的循环，要求 16 次轮询之内得到无法捕获的中断而不是被杀（`copyStopPolls`，也就是解析的上限，因为 `Function` 会解析它复制的源码），每次之后还能算 `1+1`。改动前的引擎在 linux/amd64 上每种都失败，在 darwin/arm64 上前 13 种里除了 `Function` 每种都失败。`TestModuleExportNamesStop` 用同样的方法停下对一个模块的命名空间导入，这个模块的两个导出名各有 64 Mi 个字符、只在最后一个字符不同，每次都在新的 VM 里先放好导出它们的模块，并检查两个名字的顺序。`TestStringCompareCopyLongResults` 检查 200,000 个字符以上的字符串做比较、排序、取键和复制的结果，以及替换串里的 `$`、后面有和没有 `>` 的 `$<`、`String.raw` 和 70,001 个字符的 flags 字符串的结果。`engine/test/unit.c` 里的 `test_string_copy_polls` 要求对一百万个字符的字符串（按字节复制时 16 Mi）做的每次比较、取键和复制至少读 12 次标志，在这些读取处停下每一次（每一处，或者均匀分布的 64 处），检查每次之后的上下文和结果，最后释放运行时时不剩任何内存块。改动前的引擎在它的 10 个调用里有 9 个失败。排序留给 Go 的测试：原生宿主会设置它读的那个标志，而排序也会读它自己的停止标志。`test_module_export_order` 检查两个一百万个字符的导出名和打乱顺序的 3,000 个短导出名，从命名空间导入出来时按字符串的顺序排列。

## 改变很大的 ArrayBuffer 的大小时读中断标志

发布版本：Unreleased。

`ArrayBuffer.prototype.resize` 和 `transfer` 用 `js_realloc` 改缓冲区那块内存的大小。`heap_realloc` 没法在原地改一块内存的大小时，堆就搬动这块内存：专用 chunk 里的块缩到不足 chunk 的一半时，在每个系统上都要搬，块长得超出 chunk、而宿主不能重映射 chunk 时（darwin 和 windows）要搬，共享 chunk 里后面没有空位的块也要搬。它用一次 `memcpy` 复制整块，`resize` 和 `transfer` 接着用一次 `memset` 清零缓冲区多出来的字节。两处都不读中断标志。把 256 MiB 的 `ArrayBuffer` 先 `resize` 到四分之一再改回来，在 linux/amd64 上约 150 ms，要复制 64 MiB、清零 192 MiB：eval 超时依次设成这次调用的每个六分之一时，5 次停止里有 4 次在约 143 ms、清零做完之后才停下，见到请求后过了 136 到 767 次轮询，`transfer` 的 5 次里也有 4 次这样。

现在：

- 对内存归引擎管的缓冲区，`resize` 和 `transfer` 用 `js_array_buffer_realloc` 改这块内存的大小，它只在这一次调用期间把中断标志的地址交给堆（`JSHeap.stop`）。这时 `heap_realloc` 搬动一块内存时每次复制 1 MiB（`heap_copy`，`HEAP_COPY_STEP`），复制量在 1 MiB 以上时，每步之前读一次标志。标志被设置时，堆把新块还回去，专用 chunk 立刻还给宿主，然后像拒绝一次改大小那样失败：旧块留在原处，内容、大小和计数都不变。它设置 `JSHeap.stopped`，于是 `js_heap_realloc` 不再把前端缓存还回去再试一次，`js_array_buffer_realloc` 像别处读到标志时一样抛出无法捕获的中断，不抛内存不足的错误。
- 它们清零缓冲区多出来的字节时每次清 1 MiB，每步之前读一次标志（`js_array_buffer_clear`）。在这里停下时，缓冲区保持原来的长度，不会被分离，用的是它的块（这块可能已经搬过、变大了），它的视图跟着这块走。

为什么只有这两处：停止就是一次失败的改大小，`resize` 和 `transfer` 会处理。`resize` 留着它的块和长度，`transfer` 释放它造出的缓冲区，旧的保持原样。`js_realloc` 的其他调用方只在内存用完时才见到失败，每次搬动都能停的话，这种失败在只在内存上限附近测过的路径上就会常见，调用方在失败后自己造错误的地方，还会把有的中断变成内存不足的错误。所以堆对别的块都不读标志，`js_array_buffer_realloc` 的调用之外 `JSHeap.stop` 是 NULL。造错误和原来一样不读标志（`engine/test/cycles.sh`），而堆里的读取是一次读内存，cycles.sh 看不到，所以 `test_error_reads_no_flag` 检查造一个栈有 4 MiB 的错误时读标志 0 次。不到 1 MiB 的复制还是原来的 `memcpy`。原生测试的 `asan` 构建用的分配器（`engine/test/heap-system.c`）以同样的步子搬动 1 MiB 以上、要变大的块，因为系统的 `realloc` 停不下来，缩小则交给这个 `realloc`。

eval 超时依次设成一次调用用时的每个六分之一时，把 256 MiB 的缓冲区 `resize` 或 `transfer` 到四分之一再改回来，现在在 linux/amd64 上见到请求后 1 到 3 次轮询就停下，后三次在截止后 0.6 ms 以内，前两次在截止后 4.5 到 8.1 ms。

代价：不到 1 MiB 的复制还是原来的 `memcpy`，不到 1 MiB 的清零还是原来的 `memset`，`js_array_buffer_realloc` 在改大小前后多三次写入，所以一次改大小在堆里只多一次比较和一次对 `stopped` 的写入。在 linux/amd64 上用 callgrind 计数（`compare/engines` 的 `jsbench tifa-ssr`，取 12 次和 2 次渲染之差），tifa 的两个 bench 页面渲染一次，引擎的指令改动前 265,290,640 条，改动后 265,227,430 条，-0.02%：`heap_realloc` 多 196 条，解释器少约 63,000 条，它生成的代码会随周围的 C 改变。tifa 的每个页面渲染出的 HTML 都不变。


没有覆盖的：按字节或元素走的循环，受脚本造出的东西的大小限制，也就受内存上限限制，但不读标志。在 linux/amd64 上超时设 10 ms 时，下面前四种的循环都在见到请求后 1000 次轮询被杀掉：
- 新的 `ArrayBuffer` 或类型化数组的清零（`new ArrayBuffer(1 << 30)` 要 576 ms），
- `ArrayBuffer.prototype.slice`、`TypedArray.prototype.slice` 和用另一个类型化数组造类型化数组时的复制（512 MiB 约 320 ms），
- 快速数组的 `Array.prototype.slice`（32 Mi 个元素 410 ms），
- 列出对象的键时（比如 `Object.keys`）给它的下标键排序（`num_keys_cmp` 配 `rqsort`，4 Mi 个键 1.3 s），
- `TypedArray.prototype.set`，一次 `memmove`，512 MiB 要 35 ms，它一直做到结束，没有被杀，
- 别的大块内存的搬动，比如长数组的元素、大 Map 的表、长字符串在末尾的缩小，一次 `memcpy`，最多是这块内存的大小，
- `JS_DetectModule` 在源码开头找 `import` 和 `export`，不读标志，因为它没有运行时。Go API 不调用它。
- 内存由宿主给出、带自己的释放函数（`JS_NewArrayBuffer`）的缓冲区 `transfer` 到新长度时，造一个整块清零的新缓冲区，再用一次 `memcpy` 把旧的复制进去。`resize` 不接受这种缓冲区，Go API 也不造这种缓冲区，
- `resize` 或 `transfer` 之后更新缓冲区的视图，每个视图一步，受这些视图占的内存限制。

测试：`TestArrayBufferMoveStops`（根包）给把 256 MiB 的 `ArrayBuffer` `resize` 和 `transfer` 到四分之一再改回来计时，再在这段时间的每个六分之一处停下这个调用的循环，每次都在新的 VM 里，要求 16 次轮询之内得到无法捕获的中断而不是被杀（`copyStopPolls`），缓冲区是两个长度之一、字节还在、没有被分离，调用前造的视图（一个定长的和一个跟随长度的 `Uint8Array`，一个 `DataView`）跟着它的块走，长度和 `maxByteLength` 都对，`transfer` 分离了缓冲区时视图为空，之后还能再做一次这个调用。改动前的引擎每种的 5 次停止里有 4 次失败。`engine/test/unit.c` 里的 `test_heap_move_polls` 要求把 32 MiB 的缓冲区 `resize` 和 `transfer` 到四分之一再改回来至少读 32 次标志，在每次读取处停下，检查调用以 `interrupted` 结束而不是以内存不足的错误结束，检查之后的缓冲区和这些视图，检查停在短长度的缓冲区长回来的字节是零，最后释放运行时，不剩一块内存。`engine/test/heap-test.c` 里的 `scenario_move_stop` 在每次读标志处停下一个要搬动的专用块的变大和缩小，要求失败、`stopped` 已设置，堆、它的 chunk 和这块都和原来一样（见 [allocator.md](../allocator.zh-CN.md#测试)）。`test_error_reads_no_flag` 在一个 C 函数里造错误，标志在第一次读取时就会被置上，栈超过 4 MiB，要求一次也不读、栈完整。

## normalize 和 Map 变大时的内存不足

发布版本：Unreleased。

`String.prototype.normalize` 把字符串分解进一个会变大的缓冲区（`to_nfd`）。变大失败时，`unicode_normalize` 返回失败却不释放这个缓冲区，`js_string_normalize1` 把失败返回出去，也不抛异常：调用失败了，却没有挂着的异常，Go API 没法把它报告成内存不足，运行时也永远留着这块内存。对 `'ﬃ'.repeat(300).normalize('NFKD')` 在从零到 16 KiB 的每个剩余空间下扫一遍，有 40 个空间失败时抛出的异常不是无法捕获的，158 个运行时释放时还有内存块在用。上游 QuickJS 是同样的代码（commit `092277ac`）。

Map 或 Set 的记录数到了哈希表槽数的两倍时，就把表扩大一倍（`map_hash_resize`）。扩大用的是 `js_realloc`，它失败时会抛出内存不足的错误，可 Map 带着原来的表接着用，`set` 和 `add` 照常返回，于是错误挂在一个成功了的调用下面，下一次调用就带着它失败，尽管 Map 是完整的。`map_add_record` 刚放进表里的记录还没有值，而造错误可能触发一次垃圾回收，回收会去看各条记录的值。上游 QuickJS 也是同样的代码。

现在 `unicode_normalize` 失败时释放缓冲区，`js_string_normalize1` 为它抛出内存不足的错误，`map_hash_resize` 用不抛异常的 `js_realloc_rt` 扩大表，失败时留着原来的表，`map_add_record` 在把记录放进表之前先把它的值设成 `undefined`。

没扩大的表就是 Map 原来那张完整的表，查找要走更长的链，直到后面某次添加把表扩大。代价是 Map 或 Set 每条新记录多一次写入。在 linux/amd64 上用 callgrind 计数（`compare/engines` 的 `jsbench tifa-ssr`，取 12 次和 2 次渲染之差，只算 `internal/cengine` 的函数），tifa 的两个 bench 页面渲染一次，引擎的指令改动前 265,226,497 条，改动后 265,227,872 条，+0.00%：`map_add_record` 多 110 条。tifa 的每个页面渲染出的 HTML 都不变。

测试：`engine/test/unit-oom.c` 里的 `test_normalize_oom` 在从零到 16 KiB 的每个剩余空间下，以及堆满时的每个空间下，扫 `normalize`，要求得到结果或无法捕获的内存不足错误，内存回来后再得到结果，最后不剩一块内存。`test_map_grow_oom` 从 C 调用一个函数，给有 255 条记录的 Map 加第 256 条，这会把表从 1 KiB 扩大到 2 KiB，剩余空间取从零到 2 KiB 的每个值，以及堆满时的每个空间。它要求得到大小或无法捕获的错误，调用成功时没有挂着的异常，内存回来后每条记录都在，最后不剩一块内存，还要求某个放不下扩大的空间（不到 1 KiB，或者堆满后没有还回 2 KiB 的块）能让调用成功。改动前的引擎两项都失败：没有一个放不下扩大的空间能让第 256 次 `set` 成功。

## 没有调用的循环也会在挂起的无法捕获的异常处结束

发布版本：Unreleased。

内置函数遇到无法捕获的异常时，可以只把它记下来，然后像没出错一样返回。promise 的 resolve 函数拿到一个 thenable，它的 `then` getter 内存不足，resolve 函数就让 promise 被拒绝，然后返回 `undefined`（`js_promise_resolve_function_call`）。在第一个 `await` 之前失败的 async 函数返回它的 promise，异步生成器的 `next`、说明符转换失败的 `import()`、由同步迭代器造出的异步迭代器的 `next` 也一样。它们都用 `js_get_exception` 拿异常的一份副本，这个函数让无法捕获的异常继续挂起，然后它们要么不经调用就拒绝 promise，要么像上游那样不管调用拒绝函数失败了没有。脚本带着挂起的异常接着运行。它的下一次调用会失败（`js_call_checks`），可是没有调用的循环只读中断标志，而没有谁置过这个标志。所以没设超时的时候，`res({ get then() { /* 内存不足 */ } }); for (;;) {}` 会一直运行下去，getter 里调用的 Go 函数 panic 之后，同样的循环也一样。设了超时，`Interrupt` 和杀死前的宽限期也要到截止时间才起作用。

现在只要有无法捕获的异常挂起，引擎就在中断标志里保持 2（`quickjs.c` 里的 `JS_INTERRUPT_UNCATCHABLE`）。`JS_SetUncatchableException` 按它留下的状态置上或清掉它，`JS_GetException` 取走异常时清掉它。这样每个读标志的地方都会停下：循环的向后跳转立刻失败，调用以挂起的那个异常结束，也就是内存不足的错误或 Go 函数的 panic。有异常挂起时，`JS_ThrowInterrupted` 不再造 `interrupted` 错误，因为结束调用的是挂起的那个。宿主的停止仍然是 1，它整个写进标志，宿主仍然在没有异常挂起、从 Go 进入引擎时清掉标志，所以 `gohost` 不用改。`engine/quickjs.h` 里 `JS_GetInterruptFlag` 的说明写了宿主可以写什么。

这一位在状态变化的地方置上，因为只有引擎知道异常什么时候挂起并变成无法捕获，而这个状态只在这两个函数里变：别处对挂起异常的写入（解释器的 `catch`、迭代器的关闭）只会取走可以捕获的异常。解释器本来就在每次向后跳转时读标志，所以那里什么也没加，循环在下一次跳转就停下，不用等宿主下一次轮询，那可能要再过 10,000 次计数。改成让这些内置函数各自返回异常，要改上游代码里大约 20 处，上游以后每个加了这种地方的 commit 也都要再改，而在 Go 的轮询里检查，原生宿主和 C 的其他宿主就都没有这个保护。

代价是 `JS_GetException` 和 `JS_SetUncatchableException` 里多几条指令，它们只在取走异常或把异常设成无法捕获时运行，不在不抛异常的路径上。解释器和它的栈帧都不变（amd64 上 $496，arm64 上 $520），脚本能递归的深度也不变。

测试：`engine/test/unit-oom.c` 里的 `test_uncatchable_then_loop` 让以下几处内存不足：交给 resolve 函数的 thenable 的 `then` getter，第一个 `await` 之前的 async 函数，异步生成器，`import()` 说明符的转换，以及从任务里调用的 async 函数，每处之后都跟着 `for (;;) {}`。它要求宿主停下循环之前（`host_poll_stop_after`，读 4Mi 次标志）就得到无法捕获的内存不足错误，取走异常后标志为 0，之后还能跑一个循环。`test_uncatchable_flag_bit` 要求标志里的 2 恰好在有无法捕获的异常挂起时存在：由 `JS_SetUncatchableException` 置上，由 `JS_GetException` 和把异常改成可以捕获时清掉，可以捕获的异常或没有异常挂起时从不置上，而宿主的 1 在每一步都保留。`TestUncatchablePendingEndsLoop`（`uncatchable_return_test.go`）在不设超时时做前四种，分别用内存不足错误和一个会 panic 的 Go 函数，要求得到这个错误或 panic，没有挂起的异常，之后还能跑一个循环。改动之前，两个测试的每一种都一直运行，直到宿主把它停下。

## 异常关闭迭代器时，迭代器 return 方法里的内存不足

发布版本：v0.29.11。

离开 `for...of` 循环或数组模式的默认值的异常，会关闭迭代器：解释器在异常挂起的情况下运行它的 `return` 方法，然后在同一个函数里找 `catch` 或 `finally`。它是否要找，是在关闭之前一次决定的。当 `return` 方法内存不足时，内存不足错误取代了那个异常，同一个函数的 `catch` 接住了它，所以脚本可以捕获内存不足。中断不会这样被捕获：标志保持置位，`catch` 一开始解释器就会再读到它。

现在展开在关闭之后马上再读一次标志，而当有无法捕获的异常挂起时就不再找了，于是调用以它结束。栈上剩下的东西，由查找什么也没找到时释放它们的同一段代码释放。更外层循环的迭代器不关闭，和任何无法捕获的异常一样。上游 QuickJS 没有无法捕获的内存不足，它的内存不足错误按设计是可以在那里被捕获的。

这个检查是对展开手里已有的一个标志做一次测试，在只有异常离开迭代器时才运行的路径上。解释器的栈帧保持 amd64 上 $496、arm64 上 $504。

测试：`engine/test/unit-white.c` 里的 `test_iterator_close_oom` 用 `throw` 离开一个循环和一个模式，以及在生成器里、async 函数里和 `finally` 块之下的一个循环，迭代器的 `return` 方法要分配内存，并让分配器的每次调用依次失败：运行按顺序给出关闭和异常，或者以内存不足错误失败。

## 字节码调用在 eval 超时内转换结果

发布版本：Unreleased。

`EvalBytecode` 和 `EvalSharedBytecode` 在 eval 超时内运行字节码，却在调用结束之后才把结果转成 Go 值，这时既没有超时，也不会被杀死。这次转换会运行 javascript：对象要转成 JSON，会运行它的 `toJSON` 和 getter，BigInt 会运行 `BigInt.prototype.toString`。所以 `({ toJSON() { for (;;) {} } })` 的字节码不管超时设成多少，都会让调用永远挂住，`Interrupt` 也停不下它。字节码的读取同样在调用之外。

现在四个字节码方法（`EvalBytecode`、`EvalBytecodeValue`、`EvalSharedBytecode`、`EvalSharedBytecodeValue`）从读取字节码到转换结束都是一次进入 javascript 的调用，和 `Eval` 一样，共用它的时间。被杀死后只能 `Close` 的 VM 得到被杀死的 VM 的错误，和以前一样。

常见路径的工作量不变：原来读取和运行各进入引擎一次，现在只进入一次。

测试：`TestAPIEntriesHaveTheEvalTimeout`（`apitimeout_test.go`）在 10 ms 的超时下，对 `toJSON` 循环 300 ms 的对象和 `toString` 循环 300 ms 的 BigInt 运行 `EvalBytecode`，对这个对象运行 `EvalSharedBytecode`，要求在 150 ms 内返回被中断的错误。改动之前每一个都跑满 300 ms，而且不返回错误。

## 读取异常时遇到的无法捕获的异常结束调用

发布版本：Unreleased。

为了报告脚本抛出的异常，VM 要读取它：通过它的 `toString` 得到字符串形式，再读 `name`、`message`、`stack`、`lineNumber`、`columnNumber` 和 `fileName`，这些都可以是 getter。这会运行 javascript，VM 过去把这段 javascript 抛出的任何东西都丢掉，把这个字段留空，这样每次读都会再抛的值也能被报告。中断、eval 超时和内存不足也被这样丢掉。所以在超时下，`throw { toString() { for (;;) {} } }` 返回的 `*Error` 所有字段都为空，`Uncatchable` 和 `Interrupted` 都没有设置。在 Go 函数里更糟：参数转换遇到异常（一个会抛的 `toJSON`），读这个异常时内存不足，内存不足的错误被丢掉，转换改抛一个可以捕获的 `TypeError`，脚本接住它，一直运行到结束。

现在每读一个字段都会检查它抛出了什么。脚本抛出的仍然丢掉，字段留空。无法捕获的异常保持挂起：读取停下，调用取出这个异常，替代原来在读的那个，所以调用以被中断或内存不足的错误结束，`Uncatchable` 已设置，和同样的事发生在别处时一样。在 javascript 调用的 Go 函数里，它一直挂起到函数返回，所以调用这个函数的脚本也会结束（[Go 函数里的中断和内存不足](#go-函数里的中断和内存不足)）。读完最后一个字段后，还会检查有没有只记录错误的内建函数留下挂起的无法捕获的异常（[中断无法穿过 promise 或迭代器被捕获](#中断无法穿过-promise-或迭代器被捕获)）。

`ErrorFromValue` 也一样：读取被这样停住时，它返回让它停下的错误，设置 `Uncatchable` 以及 `Interrupted` 或 `OutOfMemory`，替代它那个值的各个字段。它过去把被超时截断的字段留空（[每个能运行 javascript 的方法都有 eval 超时](#每个能运行-javascript-的方法都有-eval-超时)）。

代价：读取一个异常多进入引擎一次，在最后一个字段之后检查标志，丢弃读取抛出的东西之前再进入一次。两者都不在不抛异常的路径上。

测试：`TestUncatchableReadingAnException`（`hostuncatchable_test.go`）在脚本里，以及在 Go 函数参数的转换里，用超时停住被抛出值的 `toString` 和 `message` getter 的读取，用内存不足停住它的 `toString`，要求得到被中断或内存不足的错误，并且不留下挂起的异常。改动之前，带参数的脚本运行到结束并返回 42，其他的返回一个不是无法捕获的错误。`TestErrorFromValueTimeout` 和 `TestAPIEntriesHaveTheEvalTimeout`（`apitimeout_test.go`）要求 `ErrorFromValue`，以及 `SetProperty`、`RegisterFunc` 和其他 `Register` 方法读取错误时，都返回被中断的错误。

## Intl 读不了的字符串参数会结束调用

发布版本：Unreleased。

`Intl.NumberFormat` 的 `format` 和 `formatToParts` 拿到一个 VM 没有内存去读的字符串时，现在以内存不足的错误结束调用，原来是在 Go 里 panic。用 `+` 拼出来的字符串（rope）在 Go 读它之前要先拼接成一整段，拼接用的内存算在 VM 的上限里。拼接失败时，`Args.String` 说这个参数不是字符串，格式化器既没拿到数字也没拿到字符串，于是以 `intl: unexpected number bridge value` panic，这个 panic 一直传到调用 `Eval` 的 Go 代码里。`intl` 和 `temporal` 的其他 Builtin 也一样把这种参数当成空字符串接着干，白做一遍活，最后调用才以内存不足的错误结束。

现在这两个包的每个 Builtin 都由 `intlhook.NewBuiltin` 创建，用 `intlhook.String` 和 `intlhook.WTF8` 读字符串（`internal/intlhook/args.go`）。读取失败时 Builtin 立刻停下，调用以挂起的错误结束：内存不足，或者拼接期间来了 `Interrupt` 或 eval 超时时的中断。没有失败的读取返回的就是 `Args.String` 返回的东西，判断失败的检查只对不是字符串的参数运行，而且在 Go 里做，所以成功的调用格式化结果和以前一样。构造函数用来查找格式化器的键，现在先用一次检查找出 undefined 的选项（大多数选项都是），再试其他类型，所以 `new Intl.NumberFormat` 和 `new Intl.DateTimeFormat` 比这些改动之前少用 2% 到 3% 的时间，`format` 不变（`intl` 的 `BenchmarkFormat`，在 GCP 的 0 和 4 号核上交替各跑六次：en-US 的 NumberFormat 是 4,448 对 4,313 ns，DateTimeFormat 是 4,672 对 4,583 ns）。

测试：`intl/limits_test.go` 里的 `TestStringArgumentOutOfMemory`（在限额 16 MiB 的 VM 里，对 32 MiB 的 rope 调用 NumberFormat、它的构造函数、`getCanonicalLocales`、Collator、`localeCompare`、Segmenter 和 `toLocaleUpperCase`），以及 `temporal/limits_test.go` 里的同名测试（`PlainDate.from`、`Duration.from`、`toLocaleString`）。

## Intl 在长列表的循环里读中断标志

发布版本：Unreleased。

`Intl.getCanonicalLocales`、`supportedLocalesOf`、拿到 locale 列表的每个 Intl 构造函数和 `toLocaleString`，以及 `Intl.ListFormat` 的 `format` 和 `formatToParts`，现在不管列表多长都会在 `Interrupt` 和 eval 超时时停下。它们在 Go 里做的活不读中断标志，所以长列表会把停下推迟到 Go 做完为止。`getCanonicalLocales` 找重复还要把每个标签和它前面的所有标签比一遍：10 万个互不相同的标签大约要比较 50 亿次，在 GCP 上要 8.5 秒，什么超时都打断不了。

现在用一个集合找重复，按顺序保留每个标签第一次出现的那个，这次调用只要 0.32 秒。脚本传进来的列表上的每个循环每 256 轮调用一次 `intlhook.Check`（`internal/intlhook/args.go`）：读列表，把每个标签变成规范形式，把标签和某个服务的 locale 匹配，拼接列表的各项，以及构造结果的数组。`Check` 问 `vmhook.Stop`（`internal/vmhook`，见 [architecture.md](../architecture.zh-CN.md#eval-超时和-interrupt)），它像引擎自己的轮询那样读 VM 的截止时间和中断标志。调用该结束时，它抛出无法捕获的错误并让 Builtin 停下。已经造出 javascript 值的循环自己问 `vmhook.Stop`，返回前先释放这些值。超时设为 20 ms 时，这些调用在 1,048,576 个标签或项的列表上现在都在开始后 20 到 60 ms 停下，原来光是 Go 的活就要跑 0.2 到 3.5 秒。这些检查按标签和项计数，不按字节：单独一个很长的标签或项，在 Go 里读入、变成规范形式和匹配时仍然不检查 VM，占的内存也不算在它的上限里，比如在 M 系列 Mac 上对 16 MiB 的私有用途标签调用 `new Intl.NumberFormat(tag)` 要 0.2 秒，分配 289 MiB。

把标签和某个服务的 locale 匹配时一次处理 256 个标签：一段里如果没有这个服务有的 locale 就跳过，答案就是列表剩下部分的答案，因为 ResolveLocale 取的是它找到的第一个标签。不超过 256 个标签的列表（页面传的就是这种）走的还是原来的路，每个答案都一样。

测试：`intl/limits_test.go` 里的 `TestLongListTimeout`（`getCanonicalLocales`、`supportedLocalesOf`、构造函数的匹配、ListFormat 的各部分和结果的数组，每个都用在 Go 里造好的列表，这样时间里没有一点是造列表的 javascript）。

## fmt 的函数在输出放不下时结束调用

发布版本：Unreleased。

包 `fmt` 的 `fmt.sprintf`、`fmt.printf`、`fmt.sprint` 和 `fmt.println`，在输出可能放不进 VM 在内存上限下还剩的空间时，现在会在 Go 造出输出之前以无法捕获的内存不足错误结束调用。Go 的 fmt 先造出一次调用的全部输出，再返回或写出去，而很短的格式就能要很长的输出：`fmt.sprintf("%1000000[1]s".repeat(256), "")` 的格式只有 3 KiB，要的却是 256 MB。在限额 16 MiB 的 VM 里，Go 先分配了 1,210 MiB，在 GCP 上花了 1.4 秒，VM 才拒绝这个字符串，而 `printf` 会把它全部写到 stdout。

每个函数先从格式和参数算出输出字节数的上界，不去造输出（`fmt/bound.go`）。算上界时按 fmt 的方式读格式，所以知道每个动词取哪个参数、宽度和精度是多少，并按每个动词能把参数变成多长来计算：字符串或对象的 json 最多是自身长度的五倍（`%q` 和 `% #x`），数字最多一千字节左右，都加上宽度，精度能让它变长时再加上精度。输出让 Go 的 fmt 分配的内存比输出本身多，检查把它整个算进去，因为调用返回之前 Go 可能一点都没有回收：fmt 的缓冲区靠 `append` 增长到原来的至少 1.25 倍，靠补齐增长到两倍，所以它用过的各个缓冲区加起来最多是输出的 8 倍，`Sprintf` 再把缓冲区复制成要返回的字符串，给字符串加引号或写浮点数的动词先在自己的切片里造出字节，这些切片也这样增长。所以 Go 分配的内存最多是上界的 16 倍（`fmt/fmt.go` 里的 `allocated`，注释里按 Go 的 fmt 和切片的增长方式推出了这个数），测试里的长输出实际分配最多是上界的 10.9 倍。Go 同一时刻占着的内存要少一些，但按它来检查是守不住的：调用期间没有回收时，对 64 KiB 的字符串做 `"%[1]s".repeat(33)`，Go 分配了上界的 6.8 倍。不管输出多长，Go 的 fmt 还要分配同样的一份：它的 printer，几百字节，回收之后还有 printer 池的槽位，每个 P 128 字节，`GOMAXPROCS` 为 64 时 `fmt.sprintf("")` 分配了 9,656 字节。所以检查另加 1 KiB 和每个 P 256 字节（`budget`）。Go 运行时为它的池做的准备不算在内：回收之后，程序的每个池第一次用到时，会被重新放进运行时的池列表，这个列表随程序用的池的多少增长，和脚本要什么无关。VM 有内存上限、这个总量又超过 `vmhook.Room`（`internal/vmhook`）报告的剩余空间时，函数用 `vmhook.OutOfMemory` 抛出错误，什么都不造。上界是从格式和参数算出来的，不是从输出算的，可能远大于输出：参数比写出来的部分长时，比如被精度截短的字符串，或者宽度或精度没被用上时，比如动词不适用于参数（`fmt.sprintf("%1000000c", 5n)`），或者精度为 0 时写出的零（对 `0n` 做 `%1000000.0d`）。内存上限很紧时，这样的调用可能被拒绝。上界只占剩余空间一小部分的调用和原来一样运行。没有内存上限的 VM 上，每次调用都和原来一样。

上界也跟着 fmt 算进它的错误文本。`%w` 只有 `Errorf` 才读，在 `sprintf` 里 fmt 用 Go 的反射把参数写进错误文本，不调用 `String` 或 `Format` 方法：`big.Int` 写成它的 64 位字的列表，每个字都按宽度和精度补齐，`%#w` 还会像 `%#v` 那样给字符串或对象的 json 加引号转义。`fmt.sprintf("%1000000w", 1n << 16384n)` 要 257 MB，上界只算了 1 MB，对 1 MiB 的控制字符做 `"%#[1]w".repeat(8)` 要 32 MiB，上界只算了 8 MiB。现在上界把每个字和引号转义都算进去（`sizeArg`）。

`%T` 写的是参数类型的名字，不管参数里装着什么，`%p` 写的是对象或 big int 的地址，所以两者都不随参数变长。原来上界按参数的长度来算它们，在内存上限下只剩 2 MiB 的 VM 里，对 1 MiB 的字符串 s 做 `fmt.sprintf("%T", s)` 会以内存不足错误结束，而它写出的只是 `string`。现在上界对 `%T` 只算宽度再加几个字节，因为精度只会截短类型名，所以 `fmt.sprintf("%.1000000T", 0)` 在任何 VM 里都写出 `int`，对 `%p` 算宽度、精度再加几个字节。

精度只在某些动词里让数字变长，对字符串和 `%T` 写的类型名只会截短。原来上界对 `%T` 以外的每个动词都算上精度，所以在剩余空间不到 16 MB 的 VM 里，写出 `true` 的 `fmt.sprintf("%.1000000t", true)` 会以内存不足错误结束，对数字做 `%.1000000c` 和 `%.1000000q` 也一样。现在上界只在 Go 的 fmt 按精度补齐的地方算精度（`fmt/bound.go` 里的 `precGrows`，读自 `fmt/print.go`、`fmt/format.go` 和 `math/big` 的 `Int.Format`，从 Go 1.26.6 到 1.27 都一样）：整数或 big int 的 `%d`、`%b`、`%o`、`%O`、`%x`、`%X` 和 `%v`，整数的 `%U`，big int 的 `%s`，浮点数的 `%e`、`%E`、`%f`、`%F`、`%x` 和 `%X`，带 `#` 的 `%g` 和 `%G`，对象或 big int 的 `%p`，big int 的 `%w`，以及不适用于整数、或带 `#` 时不适用于浮点数的动词，它们把参数按 `%v` 写进错误文本。NaN 和无穷大在任何动词里都不用精度，写出来就是 `NaN`、`+Inf` 和 `-Inf`。不补齐时，带精度的浮点数最多写出 767 位有效数字，所以浮点数的上界现在是宽度再加 1 KiB。

fmt 读下标时从 `[` 一直读到它后面第一个 `]`，所以一个格式里有很多后面没有 `]` 的 `[` 时，算上界和 fmt 自己花的时间都随长度的平方增长：`"%[x".repeat(1000000)` 在 Go 里要几分钟，期间不检查 VM。现在上界先找到最后一个 `]` 在哪，交给 fmt 的格式里把每个这样的 `[` 换成 `[]`，fmt 把它读成同一个位置上同样不是数字的下标：输出一样，这次调用现在只要 34 ms。格式最多增长从第一个这样的 `[` 到结尾的字节数的一半，上界在造出新格式之前先检查它放不放得进 VM 剩下的空间。

上界是在干活之前算出来的，不是边造输出边设的限制，因为 Go 的 fmt 先在自己的缓冲区里造出全部输出，才交给 writer：一个到了限额就停的 writer 要等输出全在内存里了才看得到它。按 fmt 的方式读格式，是事先知道大小的唯一办法。`TestSizeAtLeastOutput` 保证它是对的：它把上界和上界交给 fmt 的格式，同运行测试的这个 Go 的 fmt 的输出比较，换了一个读格式方式不同的 Go，这个测试就会失败。

上界做不到的是在超时时结束一次很长的调用。算上界要把格式读一遍，时间和格式长度成正比，之后 Go 的 fmt 造输出时也不检查 VM，所以 `Interrupt` 和 eval 超时要等这些做完才结束调用：对 1 MiB 的控制字符做 `"%[1]q".repeat(16)` 要 0.13 秒，而输出的长度只受内存上限约束。

`printf` 和 `println` 写到 `os.Stdout`，会阻塞的写入（比如写一个满了又没人读的管道）仍然会卡住调用，直到写完：Go 运行时正在做的写入，`Interrupt` 和 eval 超时都结束不了。要结束它，这个包得接收一个可以取消的 writer，这是 API 的改动，所以 `Register` 的文档写明了这一点。包 `fmt` 是 modernc.org/quickjs 原有的一个小便利，供写程序时让脚本打印东西，tifa 不用它。

测试：`fmt/limits_test.go` 里的 `TestOutputLimit`（宽度、`*` 宽度、精度、`%q` 和 `sprint` 要的超过 16 MiB 的 VM 所有，Go 里的分配少于 64 MiB，以及一次放得下的调用）和 `TestSizeAtLeastOutput`（对大约 15,000 个用到各种标志、下标、宽度和精度的格式，在 VM 给 Go 函数的每种类型的参数上，把上界和 fmt 的输出比较，其中有长 big int 和字符串的 `%w`，并检查上界交给 fmt 的格式造出同样的输出），`TestShortFormats`（由 `%[]1x*.` 组成、不超过 6 字节的每个格式，以及格式增长了多少），`TestUnclosedIndexes`（那一百万个 "%[x"），`TestUnclosedIndexesRoom`（增长之后放不下的格式）、`TestTypeAndPointer`（在剩余空间很少的 VM 里对长字符串、对象和 big int 做 `%T` 和 `%p`，精度为一百万的 `%T`，以及它们的上界），`TestPrecision`（从 `A` 到 `z` 的每个动词，不带标志、带 `#`、`+` 和 `# `，精度为一百万，在每种参数上，其中有 NaN 和无穷大：上界装得下输出，输出短时上界也短，在剩余 2 MiB 的 VM 里短输出照常造出，长输出结束调用）和 `TestOutputAllocatedUnderBudget`（各种长输出下，以及在缓冲区增长、Go 向上取整最多的那些长度上，中间不回收时输出让 Go 的 fmt 分配的内存，对照上界的 16 倍，以及在 `GOMAXPROCS` 为 1、2、8 和 64 时的空输出和短输出，对照这个总量）。
