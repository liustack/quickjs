# C 引擎之前的数字记录

[English](history.md) · 简体中文

这里是到 v0.28 为止所用引擎（ccgo 把 QuickJS 翻译成 Go）的测量，以及 v0.29.0 切换到 C 引擎时的测量。那个引擎已经删掉，所以这里没有一条在描述 liustack/quickjs 现在怎么运行。留着它们，是因为这些数字记录了有些事为什么是现在这样，读者有时需要查一个数。C 引擎的速度和怎样测量一个改动，见 [performance.zh-CN.md](performance.zh-CN.md)。

这几节里 `lib` 指 ccgo 引擎（它所在的 `lib/` 文件夹），「with PGO」指 tifa 用那个引擎上收集的引擎 profile 构建，58 个已知 test262 错误这类数字是当天的数字（现在是 33 个）。

在 tifa 里测的整个版本：

- v0.26.13 渲染时间是 v0.26.12 的 0.823（8 轮里 0.821 到 0.825）。
- v0.26.15 渲染时间是 v0.26.14 的 0.859，两者都重新收集了 profile（6 轮里 0.857 到 0.861），没有 PGO 是 0.843。6 个 VM 跑在 3 个物理核上，整个请求能服务的数量是原来的 1.17 倍。在 Apple M4 上，没有 PGO，一个 VM 每秒渲染 108 页，原来是 84 到 86 页，10 个 VM 是 532 到 549 页，原来是 288 到 305 页，是原来的 1.80 到 1.88 倍。
- v0.26.16 还没有在 tifa 里作为整个版本测过。它的改动已经在上面各行里逐项测过。

内存上的代价：v0.26.16 让商店的一个 VM 在一次 GC 后多占 722 KiB（8.03 MiB，原来是 7.33），其中 647 KiB 是留存的 shape。自 v0.26.15 起，非 linux 上每个 VM 最多留着 1 MiB 的 TLS 栈。


### 对比 liustack/quickjs 起步时的引擎

2026-10-20 在 tifa 里测的，对比 `modernc.org/quickjs` v0.25.0 加 libquickjs v0.13.1，用同一个 SSR bundle 和宿主程序（tifa 的 [docs/studies/moejs.md](https://github.com/liustack/tifa/blob/main/docs/studies/moejs.md)）：光是到 v0.26.15 为止的引擎改动，渲染就是原来的 1.63 到 1.66 倍快。再加上 tifa 的 Vite 插件重写和 PGO，页面渲染比两样都没有的原引擎快 2.07 倍。

## Intl 格式化

v0.27.0，对比 main `641e996`，tifa 商店用 `fb31f616`。共用的 go-intl 格式化器使用[编译好的方案和直接输出字符串](changes/time-and-intl.zh-CN.md#编译好的-intl-格式化计划)。固定输入的 NumberFormat 用例比 main 少 41% 到 42% 时间，DateTimeFormat 少 28% 到 37%。[完整的调用表](changes/time-and-intl.zh-CN.md#针对性的计时和内存代价)包括构造、未缓存的解析、分配和内存开销。

十个商店页在 AMD EPYC 7B13、Linux、Go 1.27.2、`CGO_ENABLED=0`、`-pgo=off` 下测量。两个构建使用同一个 SSR bundle 和抓下来的同一批导航输入。驱动程序仿照 BenchmarkShop：一个 VM，256 次热身渲染，然后每页 200 次计时渲染，在 main 和分支交替的六轮里各做一遍。它包括六个工作台页，加上两种语言的商店列表页和商品页。HTTP 和取数据在计时之外。只把路由器的 `u:` 时间戳遮掉后，HTML 完全相同。

每个引擎在 CPU 1 上以 nice 19 运行，同伴核 5 空闲，放在 4 GiB、无 swap 的 systemd scope 里。只有当两个 CPU 连续三秒都低于 1% 繁忙才开始一次运行。如果同伴核 5 平均至少 1% 繁忙，或者在某个一秒样本里达到 5%，或者 CPU 1 上有别的应用在运行，样本就作废并重做。第 1 到 5 轮每个构建在一个进程里跑完十个子基准。第 6 轮单独调用每一页，并让两个构建在该页上交替，这样该页之外的活动不会使它的样本作废。每个子基准仍然创建自己的 VM 池，用相同的热身和样本数。表里每页每个构建用六个有效样本。数值是每轮 P50 的中位数，括号内是最小和最大值。比值小于 1 表示分支更好。最后一列在每轮内把两个构建配对。

## 原生 C 上的补丁开销

这一节在原生 C 构建上测了 ccgo 引擎的补丁（`quickjs.diff`，现已删除）。留着它，是因为它记录了 C 树里为什么一直开着 computed goto。

2026-10-22 测量，用固定的 Bellard 源码 `3d5e064e9dd67c70f7962836505a7fa067bf0a4e` 和 liustack/quickjs 的 `620658c`。旧的 C 补丁无条件把 `DIRECT_DISPATCH` 设成 0。这个翻译设置早于 liustack/quickjs 的异常处理改动。所以原生 C 当时用一个中央 switch 代替上游的 computed goto 分发。

保留下来的修复只对 `__CCGO__` 和 `__EMSCRIPTEN__` 关掉 computed goto。原生预处理的结果和测过的原生 computed goto 变体完全一样。ccgo 仍然走 switch 分支，提交进仓库的 Go 引擎没有变。它的增量行为开销要单独测，不能套用原生 C 的百分比。原生 C 限制的是栈字节数，不是递归调用次数。另做了一个 1 MiB 的递归探测，旧的 gcc 补丁下能到 1423 次调用，原生 computed goto 下是 1393，clang 下是 1926 对 1073。两者抛出同一个 RangeError 和同一条信息。Go 的 TLS 槽检查和深度约定没有变。

### 这些行为改动对 Go 引擎的开销

分发的修复没有影响到 Go：ccgo 一直生成 switch，生成的 Go 没变。这些行为改动本身在 Go 里通过 `fixlib` 实现。为了估价，诊断构建让 `_js_uncatchable_pending` 返回 false，关掉延迟的回溯辅助函数让栈立即生成，或者两样都做。中断轮询和 OOM 标志保留。这些构建破坏了行为，不能发布。

所有宿主都是静态 `CGO_ENABLED=0` 构建，`-pgo=off`，Go 1.27.2，tifa `b1cb68f6`。V8 的计数覆盖上面那个固定工作量的整个进程。SSR 的计数是每页在两次热身后渲染两次，商店的六个工作台页或四个 MUI 页放在一个 VM 里，只在渲染循环外加 Callgrind 客户端请求来计数。结束时再数一遍基线，商店移动了 0.008%，MUI 移动了 0.006%。

tifa 的接线相对它之前的 C 引擎改了什么，用 callgrind 每次渲染的指令数（12 次渲染一页的一次运行减去 2 次渲染的运行，这样加载抵消掉）和 8 个位置上的时间来衡量（两边的引擎都是 main 的 09e731a3）：

- **javascript 交给 Go 的字符串，在引擎存放它们的地方直接读**：包括一次渲染的结果、对象的 JSON 和 Go 函数的参数。`JS_ToCStringLen2` 会对任何非 ASCII 字符串在 VM 的内存里做一份 UTF-8 拷贝（16 位字符串每个单元 3 字节），VM 没空间时会因内存不足而失败。rope（几段字符串连成的树，读的时候才拼成一段） 先被拼起来。16 位字符串一趟转成 UTF-8，在单元是 ASCII 或全部来自 U+0800 的地方一次处理四个，写进一个会复用的缓冲区，然后拷贝一次。先数字节再转，需要两趟，比 C 还慢：商店页是中文，指令多 1.05%。一趟的做法在商店一次渲染里用 103 万条指令，C 版本用 134 万条：商店少 0.22%，MUI 和 bench 页少 0.03%。
- **emotion 的哈希**（tifa 给 `@emotion/hash` 写的 Builtin）在引擎存放 8 位和 16 位字符串的地方直接读，并按 JavaScript 里两半相乘的结果用 32 位乘法：一次 MUI 页渲染从 510 万条指令降到 110 万条，占这次渲染的 1.86%。
- **tifa 在 Load 时一次取好 `startRender` 和它的读取函数**，原来每次渲染编译三个小脚本：指令少 0.07% 到 0.14%。
- **tifa 用 `ReleaseMemory` 把内存还回去**：Load 之后所有空闲内存（商店 2.1 MB，MUI 1.0 MB），以及一次完整 GC 之后，超出到下一次 GC 之前这些渲染所需的部分。加载好的 VM 少占 0.2 到 0.4 MiB。渲染之后空闲内存又被用上，完整 GC 只会还回在 GC 阈值降回来之后，某次大渲染一次性多占的那部分。

合起来：商店指令少 0.37%，时间 0.994（8 个位置里 7 个更快），MUI 少 1.96%，0.984（8 个全部），bench 页少 0.12%，0.994（8 个里 7 个）。每一项都低于规则里要按时间算的 2%，也没有更慢的。

测过但放着没做的（C 引擎上一次渲染的占比，来自 callgrind）：

- **Builtin 调用的路径**（`hostCall`、`callBuiltin`、读参数和生成结果）加上 Builtin 自己的工作，占商店一次渲染的 0.34%，在 MUI 渲染里除了哈希之外约占 0.2%。
- **在 Go 里拼 rope**，代替 `JS_ToString`：拼接占商店一次渲染的 0.33%，MUI 的 0.23%。在 Go 里遍历各段仍要读每个字符，所以只能省其中一部分。
- **把 AsyncContext 做成 C**：它的 Builtins 占一次渲染不到 0.05%。
- **轮询**：`host_poll` 占一次渲染的 0.06% 到 0.16%。

**长时间运行。** 2 个 VM，2 个调用方，18 页轮流渲染不停顿，每 5 分钟有 3 秒没人渲染，让池把 VM 的空闲内存还回去（共 60 次，每个 VM 30 次）。内存每分钟读一次。

## 在旧引擎上试过但没做的

和 [performance.md](performance.zh-CN.md#试过但没做的) 里同类的清单，针对 ccgo 翻译出来的引擎。大多数跟它的 TLS 栈（libc 栈里的一块，翻译后用来存放那些取了地址的 C 函数局部变量）、它的 libc 分配器和它的 Go 解释器循环有关，C 引擎里这些都不存在。

- **去掉另外 135 个小函数的 TLS 栈帧**（TLS 栈帧是 libc 的 TLS 栈里的一块，Go 翻译在这里存放函数里被取了地址的 C 局部变量）：约 0.24% 的渲染时间，小到测不出，却要多维护 135 个条目。
- **让一次调用超过 768 字节的空间也放进它的 TLS 栈帧**：1024 字节只多覆盖 0.02% 的调用，却让 Linux 上每个调用深度保留的块从 2 KB 翻倍到 4 KB。
- **非 linux 上每个 VM 只留 256 KiB 的 TLS 栈**：不够。Apple M4 上 10 个 VM 每秒渲染 315 页，等锁 4.2%，而用 1 MiB 时是 437.8 到 481.6，因为渲染会用到 TLS 栈更深的地方。
- **把很少用的操作码移出解释器循环**：在 amd64 上单独做最多 8%，这个上限是把商店从不执行的操作码的 56 个处理函数换成空桩测出来的，但在把 15 个值留在栈槽里的重写之上只有 1.4%，在 arm64 上只有 0.5%。它需要把循环的局部变量搬进一个结构体。
- **在 realloc 里移动小块时不经过 malloc 和 free**：在 js_malloc 取缓存块的基础上，studio 列表页指令少 0.23%，太小，不值得为它再加一条 fixlib 规则。
- **前置缓存里每个大小保留 1024 个块，而不是 256 个**：studio 列表页每次渲染的未命中从 19.7k 降到 18.6k。它们来自渲染期间堆在增长，不是来自链表满了。
- **解释器循环里给 `===` 一条快速路径**：慢 1.0% 到 1.3%，用 v0.26.14 和 PGO 测的。解释器函数太大，Go 只把最小的函数内联进去，所以那里每多一个辅助函数就多一次真正的调用。
- **把中断倒计时放进一个单独的小函数**：没有变化（0.998 到 1.001 倍时间），用 v0.26.14，原因相同。v0.26.16 改成通过 `pollDue` 内联地写倒计时，Go 会内联它，有 PGO 时收益 0.6%。
- **像 v0.26.16 对 `set_value` 做的那样，在解释器里直接写出 `JS_FreeAtom` 和 `is_strict_mode`**：看不出和噪声的区别，所以它们仍是调用。
- **用 2 次写入而不是 9 次写入新对象的位字段**：没有变化（0.991 到 1.010）。时间花在第一次写新对象的缓存未命中上，写入变少只是把它挪了位置。v0.26.17 之后又试了一次，在 `JS_NewObjectFromShape`、`JS_NewArray` 等里每段位字段只写一次：指令少 0.3%，但 tifa 的 bench 页用了 1.010 倍时间（8 轮里 1.005 到 1.030，三个构建的地址不同）。
- **大调用的空间从每个运行时一个栈里取**：参数、局部变量和栈需要超过 768 字节的调用会 malloc 它们，tifa 的 bench 页一次渲染约 6000 次，要经过 libc 的分配器和它的锁。改成从每个运行时一块 64 KiB 的区域里切（因为调用按相反顺序返回），省下的指令和切分本身的开销一样多，单个 VM 时锁没有竞争，bench 页用了 1.009 倍时间（8 轮里 0.998 到 1.020，六个构建的地址不同），商店 1.003。
- **不通过调用取 `JS_CallInternal` 的 TLS 栈帧**：Go 不会把快速路径内联进解释器，在它的各个返回处内联的释放操作让 tifa 的 bench 页渲染多用了 1.6% 时间。linux 上不通过调用取 TLS 栈帧把它省掉了。
- **每个 VM 一个 libc 分配器**，为了避开它的全局锁：Linux 上 8 个 VM 时这把锁花掉 0.4% 到 0.9% 的 CPU，而自 v0.26.15 起，Apple M4 上 10 个 VM 等锁约占 0.7% 的时间。
