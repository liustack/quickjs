# 测量一个改动

[English](measuring.md) · 简体中文

为速度做的改动，要靠给 tifa 的页面计时来判断，每次都用同一种办法。本页是规程，是它的默认值，是一批效应已知的运行给出了什么，以及它做不到什么。工具是 `go tool measure bench`（命令见 [testing.md](testing.zh-CN.md#给两个构建计时对比)）。

结果只对测它的那台机器成立。linux/amd64 上的结果对 darwin/arm64 什么也说明不了，下面的布局也只在 amd64 上有。

## 规程

1. **先把问题定下来。** 写下机器、页面、指标，以及要紧的退步量 delta。默认是 delta = 1%，针对应用每个页面的 P50 之和，在 GCP 的机器上（AMD EPYC 7B13，Zen 3）。计时做决定。指令数用来解释。
2. **每一边都构建 16 个规程布局**（`bench build`，`-positions protocol`，默认）。布局移动代码而不改变它，用三个数写成 `shift.front.shift2`（`64.16.2208`），shift2 为 0 时写成 `shift.front`：
   - front：在解释器函数体开头放 0、16、32 或 48 个字节的 NOP，这样函数体占据它那个 64 字节块里每一个 16 字节的位置。这些 NOP 会把解释器代码后面的常量池和函数体一起移动，而 `JS_RegvmRun` 用 `XORPD` 读其中一个池（给 double 取负），池不在 16 字节对齐上就会出错。所以 8、24、40 或 56 的 front 会造出产品永远不会有的二进制，脚本一给 double 取负就崩溃：`bench build` 和 xform 都会拒绝它，
   - shift：在二进制保留的第一个引擎函数之后放的 NOP 字节数。它后面直到正则匹配器的函数（堆、libc、正则编译器）恰好移动 shift 那么多，移到别的 64 字节块里，也移到所在 4 KiB 页的另一个位置。匹配器按 64 字节对齐，所以它会把不是 64 的倍数的那部分 shift 吃进它前面的填充里，移动 64 的倍数，且在 shift 的 32 字节之内。
   - shift2：在正则匹配器（`lre_exec_backtrack`）之后放的 NOP 字节数。匹配器到解释器之间的函数（包括分配器和对象创建）恰好移动匹配器移动的量加 shift2 那么多。Go 把函数放在 32 字节的边界上，所以 shift2 取 32 的倍数，那段代码在 64 字节块里只有两个位置：正式的位置，和晚 32 字节的位置。匹配器移动的是 64 的倍数，所以这段代码对 64 取模的位置就是 shift2 的。按 64 字节对齐的解释器（生成器的 `-align64` 点了它的名时）会把不是 64 的倍数的那部分 shift2 吃进它自己的填充里，所以解释器和它之后的代码移动 64 的倍数，不跟着这个半块走，它们对 64 取模的位置来自 front。寄存器式循环 `JS_RegvmRun` 不按 64 字节对齐（它的函数体跟在 `PCALIGN $16` 之后，见 [performance.zh-CN.md](performance.zh-CN.md#接下来)）：它恰好跟着前面的函数移动这个和，所以它对 64 取模的位置是 front 加上 shift2 的那个半块，16 个布局把它的函数体放在它的 4 个位置上，每个 4 次。

   所以引擎有三段，每段对 64 取模有两个位置之一（Go 把函数放在 32 字节的边界上）：匹配器之前的一段跟着 shift，匹配器到解释器之间的一段跟着 shift2，解释器和它之后的代码跟着 front。这一组是 4 个 front 各出现 4 次，配 16 个 shift 和 16 个 shift2（表是 `internal/measure/bench/positions.go` 里的 `protocolShifts` 和 `protocolShifts2`），正式布局两个都没有。第 4k 到 4k+3 个布局的 front 是 16k，每一组里 shift 和 shift2 是否落在 64 字节块里的 32 字节处，4 种组合各出现一次，所以 front 的 2 个二进制位和两个 shift 的 2 个二进制位正好组成这 16 个布局，每种一次。所以没有哪一段对 64 取模的位置跟着另一段走。寄存器式循环在 32 字节的边界上，它在一行里的 4 个位置各出现 4 次，其中 shift2 的两个半块各 2 次。16 个 shift 是 4 KiB 页里 16 个不同的位置，和下一个相差都不到 512 字节，shift 加 shift2 的和也是（匹配器可能给这个和减去或加上 32 字节）。没有哪个 shift 是 32，因为匹配器可能把它整个吃掉。布局 0.0 是正式二进制，也就是发布出去的那个。布局数、构建数和计时的块数与加第二个 shift 之前相同。

   `bench build` 把每个布局和同一边的正式二进制核对（组里没有 0.0 时，它在 `.work` 里构建一个）。匹配器移动了 64 的倍数，且在 shift 的 32 字节之内（没有 shift 时完全不动，一个被对齐整个吃掉的 shift 会让构建失败）。shift 所放的那个函数（默认是二进制保留的第一个引擎函数，除非构建指定了别的）之后、匹配器之前的每个引擎函数恰好移动了 shift，那个函数和它之前的没有动。有两个符号同名的 pad 在函数里找不到，构建会失败并给出说明。正式二进制里匹配器到解释器之间的每个引擎函数（约 400 个）都恰好移动了匹配器移动的量加 shift2，且至少找到一个。解释器恰好跟着它前面的函数移动这个和，或者在它按 64 字节对齐且有 shift2 时，移动在这个和的 32 字节之内的 64 的倍数（解释器的对齐吃掉了 32 的 shift2 是可以的，因为中间的函数确实移动了）。解释器的函数体和 10 个热点处理函数在其中的位置，比在正式二进制里晚 `front` 个字节，所以它们对 64 取模的位置，等于正式的位置加上 front。没落到那里的布局会让构建失败。它把地址写进 `layouts.tsv`，每个二进制一行，带文件的 SHA-256，重新构建的二进制会替换它那一行。
3. **在均衡的块里计时**（`bench run`）。一个块是每一边在一个布局上，一个接一个。块的顺序随机，正式布局每轮 3 次。块里各边的顺序，在双数轮里随机，下一轮里按相反的顺序。默认 2 轮。顺序由这次运行的实验 id 抽出（见下面的清单），所以新的运行得到新的顺序，而在同一个文件里接着做的运行保持它自己的顺序。

   每个进程之前，工具都会丢掉它的二进制缓存的页（`-fresh-pages`，linux 上默认开启）：它同步文件，让内核丢掉它的页（`fadvise DONTNEED`），然后用 `mincore` 检查没有一页还在内存里，还有就报错停下。之后内核把二进制重新读进它自己挑的页，那些页可能是原来的，也可能不是。每条记录都写明是否要求了新页（`fresh_pages`）以及检查是否通过（`fresh_verified`）。没有它的话，一个二进制会在它被缓存期间一直保留它第一次被读入时得到的物理页，同样字节的两份副本，在正式布局上计时能差到 2.7%，每次如此。
4. **为这次运行保留一份清单。** `bench run -out FILE` 在第一个进程之前写出 `FILE.manifest.json`：一个随机的实验 id，计划（各边、布局、轮数、每轮的正式块数、新页），每个二进制的 SHA-256，以及会改变一个进程所测内容的设置（命令行、写成绝对路径的目录、环境、核、干扰上限）。它记录的环境是进程的整个环境：shell 的 HOME、PATH 和 TMPDIR，以及 `-env` 给的。shell 里别的东西都到不了它们，工具还会点出它丢掉的 shell 里的 GO* 和 TIFA_* 变量。在同一个文件里接着做的运行必须与它一致：别的二进制、别的环境（比如另一个 GOMAXPROCS、GOGC 或 TIFA_WARM）、别的目录或别的布局都会让它停下。可以加更多的轮数（`-round0`）。有记录而没有清单的文件会被拒绝。每条记录都带着实验 id。
5. **被干扰的块整块重跑。** 当一个块的某个进程运行期间，兄弟超线程忙了超过 5%，其他工作占了计时核超过 5%，或者宿主偷走了它超过 1%，这个块就重新运行，最多 `-tries`（3）次。每条记录都保留它的开始时间、槽位、顺序、第几次尝试、会话、被偷走的时间和其他核的负载（`machine_pct`，100 表示一个核），因为其他核上的构建共用 L3 缓存，并不是重跑的理由（见下）。
6. **整个单元地判断**（`bench judge`）。分析的单位是一个布局、一次重复在第 2k 轮和第 2k+1 轮的两个块，两轮里两边的运行顺序相反。judge 按清单里的计划读记录，从不按文件里碰巧有什么来读：
   - 失败的进程，重复的记录，另一个实验的或计划之外的记录，没有指标或指标不是有限正数的记录，或者两边在不同会话、用不同页面设置、或者在两轮里顺序相同的块，都是问题。有任何问题就什么也不判断。
   - 一个块按它的最后一次尝试算。如果那次尝试有计划里的每一边，并且没有一边受过干扰，它就可用。一个单元只有在它的两个块都可用时才使用，否则就丢掉，并列出原因。
   - 当计划里的每个布局都有一个可用的单元，并且正式布局有 2 个（计划少于 2 个时，则是它计划的全部）时，这次运行才算完整。不完整的运行没有结论：judge 把它的数字作为描述打印出来，不带结论列，也不带关于正式布局的说明，并列出缺了什么。用更高的 `-tries` 再运行同样的命令就能完成它：丢掉的块重新运行，其余的保留。
7. **读一个单元的数字。** 每个块给出指标的 y = ln(new/base)。一个单元给出 d，即它的两个 y 的均值，两边顺序的影响在其中抵消了，以及 o，即新的一边先运行时的 y 减去基准先运行时的 y。judge 并排报告：
   - **正式布局**：它的各单元的均值 d，带一个 t 区间，用的是对所有单元合并的运行误差，
   - **布局均值**：计划里每个布局以同样的权重，带布局均值的离散程度的 t 区间（L-1 个自由度），
   - **仅这些布局**：同样的均值，只带运行误差，也就是这些布局本身测得多好，
   - **运行标准差**：去掉顺序效应之后，一个块的 y 的标准差，由各单元之间 o 的离散程度得出，
   - **布局标准差**：真实效应在不同布局之间看起来相差多少，也就是布局均值的离散程度减去运行误差能解释的部分，
   - **顺序效应**：o 的均值，带它的标准误。

   **布局均值做决定，正式布局单独报告。** 它的区间把 16 个布局当作一个随机样本，仿佛它们是一次改动可能落到的位置的随机样本。其实不是：它们是一组固定的集合，选出来是为了覆盖函数体的各个 8 字节位置和页内偏移，所以这个区间是一个模型，不是抽样的保证（见[已知限制](#已知限制)）。运行标准差和布局标准差都是描述性的估计。它们假设在去掉顺序效应之后，所有块的运行误差互相独立且方差相同，而布局标准差为 0 只说明布局均值的离散程度没有超过运行误差能解释的，不说明这个改动在每个布局上的表现都一样。
8. **对着 delta 读结论。** 设改动的 95% 区间是 [lo, hi]：
   - 更快：hi 小于 0，
   - 更慢：lo 大于 0（hi 也小于 delta 时是"更慢，但不到 delta"），
   - 没有超过 delta 的退步：区间包含 0 且 hi 小于 delta，
   - 无法定论：区间伸到了 delta 之外，
   - 不完整：这次运行不完整（第 6 步）。

   "没有超过 delta 的退步"是唯一说明一个改动没有损失要紧东西的结论。一个包含 0 又伸到 delta 之外的区间，并不说明改动是中性的：它说明这次测量分辨不出来。

   当正式布局更慢时，judge 会在表下面说明，哪怕布局均值并没有变慢：整个区间都超过 delta 时说"**The formal layout is slower by more than delta**"，高于 0 时说"**The formal layout is slower**"。布局均值抵消不了这一点：发布出去的二进制会更慢。
9. **旁边用 callgrind 计数，永远不要拿它代替计时**（`bench cg -small 0 -big 3 -dumps -sim`）。每个二进制一个进程，先热身每个页面，然后只数基准用客户端请求标出的那个窗口，也就是每个页面 3 次渲染（见 [testing.md](testing.zh-CN.md#给两个构建计时对比)）。表里显示整个程序和解释器自己的代码：指令数，分支数，预测错的分支数和缓存未命中数，原始文件也保留。callgrind 的预测器和缓存是对旧硬件的模型，不是对 Zen 3 的，所以它的未命中数上升，是该看得更仔细的理由，不是结论。计数和计时不一致时，继续测。两者谁也推翻不了谁。
10. **在新数据上确认胜出者。** 试了几个变体并保留其中一个时，在引用它之前，用一次新的运行再给它计时（新文件，因此有新的实验 id 和新的顺序）。judge 比较的是一个应用上的一对边。它不对多个应用或多对边做校正：当一个改动在 4 个应用上各按 95% 判断时，某个应用出现假的"更慢"或"更快"的概率最高约五分之一（1 - 0.95^4），所以单独一个应用的偏差只是很弱的证据。

## 默认值和原因

| 设置 | 默认值 | 原因 |
| --- | --- | --- |
| 布局 | 16（`-positions protocol`） | 布局之间的离散是误差的大部分，只有更多的布局才能缩小它。4 个 front 覆盖函数体在它的块里的每一个 16 字节位置（中间的 8 字节位置会被拒绝，见规程），shift 把其他函数移到别的块和页内偏移，第二个 shift 对匹配器到解释器之间的代码做同样的事。 |
| 轮数 | 2（`-rounds 2`） | 两轮每个布局得到一个单元，每一边在每种顺序里各一次。4 轮只缩小误差里属于运行的那部分：在下表中，改动在每个布局上都一样时，80% 的时候能发现的改动从约 0.8% 降到 0.6%，但对引擎的一个真实改动，在 bench 上只从约 0.9% 降到 0.7%。对真实的改动，多加布局比多加轮数更值。 |
| 每轮的正式块数 | 3（`-formal-reps 3`） | 正式布局得到 3 个单元，足够它自己的区间，也足够一次运行丢掉其中一个后仍然完整。 |
| 每页的渲染次数 | 热身 8 次，然后计时 20 次（`TIFA_WARM=8`、`-test.benchtime 20x`），取 P50 | 一个进程的 P50 之和与下一个进程的相差约 1%（下面的运行标准差），比布局之间的 4% 到 5% 小得多。 |
| delta | 1%（`-delta 0.01`） | 大致是 2 轮能显示出来的对引擎的最小真实改动（在 bench、mui 和 storefront 上是 0.9% 到 1.1%，在 shop 上是 1.2%，见下表）。对 0.5%，用新页的 15 次 A/A 比较里有 7 次无法定论。对 1%，15 次全都说"没有超过 delta 的退步"。只有在布局更多，或者改动不可能移动代码（Go 宿主、构建标志）时，才要求 0.5%。 |
| 置信度 | 95%（`-alpha 0.05`） | 一次比较一次。工具不对多个应用做校正（第 10 步）。 |
| 干扰 | 兄弟或其他工作占计时核超过 5%，被偷走超过 1%，最多重试 3 次 | 兄弟超线程忙了超过 2% 的那些配对，离散程度是安静配对的 5 倍。至少 3 个 tick 的 5%，能让还在做构建的机器上的重跑次数保持在可承受的范围。 |
| 一个进程 | 一个 VM（`GOMAXPROCS=1`），在一个核上，它的兄弟空闲（`taskset`、`-cpu`、`-sib`），在 `flock` 下以 `nice 19` 运行 | 计时独占的单位是这一对超线程。 |

## 一批运行给出了什么

2026-11-01 在 GCP 的机器上测的，计时在 cpu 2 上，cpu 6 空闲，取每个页面 P50 之和，用现在的 judge 重新读过。那天的大部分时间，其他核上有别的工作在运行（1.5 到 4 个核忙着，是构建和 callgrind），最后几次运行时安静一些。每次运行是 16 个布局上的 2 轮。这些运行早于第二个 shift（它们的布局只有 front 和 shift）、`mincore` 检查和清单：它们要求了新页，但没有检查，它们的计划靠标志交给 judge（`-rounds 2 -formal-reps 3`）。这些数字是一台机器上的一批。它们说明这套规程可以工作，不是它会一直保持的比率。

有三次运行按第 6 步的规则是不完整的，因为重试 3 次后仍被干扰的块，让一些布局没有单元：bench 上第一次所有边的运行（18 个单元里有 8 个）和 shop 上的（18 个里有 11 个），以及繁忙的机器上不带新页的复制测试（18 个里有 17 个）。它们没有结论，下面的计数里不含它们。

**没有改动的运行（A/A）。** 同一个二进制复制成第二个名字，它的三份副本，以及从第二个克隆、用空的 Go 缓存重新构建的同一个提交（字节不同，每个函数的地址相同）。

| 应用 | 完整的运行 | 比较次数 | 新页 | 布局均值说更快或更慢的次数 | 正式布局说更快或更慢的次数 |
| --- | ---: | ---: | --- | ---: | ---: |
| bench | 1 | 6 | 没有 | 0 | 5 |
| bench | 3 | 13 | 有 | 0 | 0 |
| mui | 1 | 1 | 有 | 0 | 0 |
| storefront | 1 | 1 | 有 | 0 | 0 |

这一批里，布局均值在 21 次 A/A 比较中给出 0 次假阳性，它的区间每次都包含 0。同一次运行里的比较共用各边，所以它们并不独立，21 次也说明不了假阳性率。

加上第二个 shift 之后（2026-11-07，GCP，shop，cpu 0 空闲兄弟核 4，同一个二进制复制成另一个名字，16 个布局，2 轮，18 个单元全部可用，没有块因干扰重跑），各页面之和的布局均值是 -0.29% [-0.59%, +0.01%]，结论是"没有超过 delta 的退步"，区间包含 0。正式布局是 -0.01% [-0.58%, +0.57%]。这是一次运行，说明新布局下工具仍然正常，不是比率。

只看正式布局，在不带新页的 6 次 A/A 比较中，有 5 次说"更快"或"更慢"，最多差 2.7%，两次超过 delta，而带新页的 15 次里一次也没有。原因在物理页：二进制的一份副本保留着它第一次被读入时得到的页，那些页让它稳定地比同样字节的另一份副本更快或更慢。在一次会话之内，这个差距在每个进程里都一样，所以正式布局的各单元彼此一致，区间很窄，却是错的。每个进程之前丢掉页，就把这个差距变成了运行之间的误差：在复制测试上，在安静的机器上连续运行，运行标准差从约 0.7% 升到 1.35%，A/A 的布局标准差从约 1.2% 降到 0.4%（取每次运行的 6 次比较的均方根）。从第二个克隆重新构建的二进制，作用就像多了一份副本。

**已知的变慢。** 在基准本身里，每次计时的渲染之后，在时钟上空转，目标是热身渲染中位数的 0.5% 或 1%（边 `s5` 和 `s10`），所以引擎代码和它的布局与基准的相同。空转量就是目标注入量：它按每个进程热身渲染的中位数设定，所以 P50 的真实变化接近它，但不恰好等于它。

| 目标注入量 | 完整的运行 | 比较次数 | 布局均值说"更慢"的次数 | 它的区间包含目标的次数 |
| --- | ---: | ---: | ---: | ---: |
| +0.5% | 1（bench，新页） | 3 | 2 | 3 |
| +1% | 1（bench，新页） | 2 | 2 | 2 |

完整的运行里，目标已知的布局均值区间有 26 个（包括 A/A），没有一个漏掉目标。在繁忙的机器上不带新页时，那些本来会显示出漏掉或变慢的运行，是不完整的那些。

**每个应用能显示出的最小改动。** 根据模型和方差估计得出的近似检验力：布局均值在 95% 下 80% 的时候能发现的改动（15 个自由度的 t 分位数），来自带新页的 A/A 比较的运行标准差和布局标准差。它的好坏取决于第 7 步的模型和背后的估计，没有用模拟或重复运行验证过。第一列针对在每个布局上都一样的改动。对引擎的真实改动还会移动代码，第二列取在那个应用上真实改动中见过的最大布局标准差。

| 应用 | 运行标准差 | A/A 布局标准差 | 真实改动的布局标准差 | 2 轮：每个布局都一样 | 2 轮：真实改动 | 4 轮：每个布局都一样 | 4 轮：真实改动 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| bench | 1.41% | 0.44% | 0.66%（xw） | 0.80% | 0.88% | 0.61% | 0.71% |
| shop | 0.96% | 0（假定） | 1.49%（drop_get_arg0） | 0.50% | 1.22% | 0.35% | 1.17% |
| mui | 1.04% | 0.43% | 1.25%（C） | 0.63% | 1.08% | 0.50% | 1.01% |
| storefront | 0.96% | 0 | 0.99%（C） | 0.50% | 0.90% | 0.35% | 0.82% |

shop 没有带新页的完整 A/A 运行：它的运行标准差取自安静机器上 drop_get_arg0 的那个。用 32 个布局代替 16 个（给 `-positions` 手工多加 16 个 shift），按同一个模型，在 2 轮下能看到约 0.6% 到 0.85% 的真实改动。这没有跑过。

**Callgrind。** 客户端请求的窗口，对同一个二进制给出的计数，在 bench 上相同，误差在 0.002% 以内。在 shop 上，整个程序变动了 0.06%（Go 一侧：回收器和调度器），解释器自己的代码变动不到 0.01%。改为对窗口里的 Go 函数做 toggle，则丢掉了一个二进制 0.8% 的计数和另一个的 7%，把一个热点处理函数里的额外工作（指令数 +0.05%）变成了 -6.7%。

## 读一个结果

`bench judge -in FILE -kind APP -base base -new new` 打印这次运行是否完整，一行是各页面之和（它做决定），再每个页面一行（它做解释）。`-detail` 会加上每个布局以及它的每个单元。

- **先看完整。** "INCOMPLETE, no verdict"表示有些布局没有可用的单元。提高 `-tries` 再运行。不要把不完整运行的数字当作结果来读。
- **读各页面之和的布局均值。** 带自己结论的页面行，是好几个检验中的一个。用它说明改动作用在哪里，不要用它说明改动是不是真的。
- **旁边看正式布局。** 正式布局是今天发布出去的二进制，但是下一次对任何引擎函数的改动，又会移动代码。当正式布局说"更慢"而布局均值没有时，说明这个改动在这次构建里碰上了一个坏位置：它发布出去会更慢，而下一次构建可能不会。judge 在表下面标出这一点，这样它不会在均值里丢掉。在这一批里，storefront 上的 C 在正式布局是 +1.1%，在各布局上是 +0.3%，shop 上的 drop_get_arg0 在正式布局是 +2.4%（超过 delta），在各布局上是 +1.3%。
- **布局标准差和运行标准差对比。** 布局标准差远大于运行标准差，说明这个改动是通过代码落在哪里起作用的（它把一个热点循环移过了块的边界，或者让函数体变大）。那样的话，布局均值是诚实的数字，正式布局的数字只是运气。布局标准差接近 0，并不能说明相反的情况（第 7 步）。
- **顺序效应。** o 的均值。各单元把它从自己的均值里去掉了，所以非零的顺序效应不会让结论产生偏差，但一个离 0 很远的值说明有东西从一个进程带到了下一个进程（页缓存、时钟频率）。
- **重跑和丢掉的单元。** 表下面的几行说明有多少次尝试重新运行了，丢掉了哪些单元以及为什么。重跑很多说明机器很忙。
- **旁边看 callgrind。** 整个程序和解释器自己的代码的指令数变化，说明这个改动做了什么。指令数下降而时间没降，说明代价转移到了等待上（未命中、预测错的分支）。callgrind 不模拟 Zen 3，所以把它的未命中数当作提示来读。

## 已知限制

- **解释器函数体之外的代码，在 64 字节块里有两个位置，不是八个。** Go 把函数放在 32 字节的边界上，所以 shift 按 32 的倍数整个移动函数，那里的一条指令对 64 取模要么在正式的位置，要么晚 32 字节。这是函数的排布方式，不是布局的缺口。解释器函数体那些 8 字节的位置来自 front，它是那一个函数里面的 NOP。
- **解释器之后的代码对 64 取模只跟着 front 走。** 它随解释器移动 64 的倍数，所以 shift 和 shift2 只改变它的页内偏移。
- **这些布局是一组固定的集合，不是随机样本。** 布局均值的区间借用随机样本的模型，来说明效应在其他布局上可能差多远。没有任何东西表明这 16 个布局代表了以后的改动会落到的位置。每次运行随机抽取布局，才能让这个模型成立，而工具没有这样做。
- **运行标准差和布局标准差是一个模型下的估计。** 它们假设在去掉顺序效应之后，运行误差独立且方差相同。取决于布局、取决于哪一边或取决于一天中什么时间的误差，会不带符号地进入其中一个。
- **检验力表来自那个模型。** 它没有用模拟或许多次重复运行验证过。
- **不对多个应用或多对边做校正。** 每个结论都是一次 95% 的比较。
- **新页并不挑选物理页。** 检查说明的是旧页离开了页缓存，不说明新页落在哪里。
- **哪些因素不能解释同一个二进制在同一布局下的离散。** 在 C 引擎上测的（`q_array_read`，一个二进制的 40 到 48 个进程）：
  - 关掉地址随机化，或者改变环境的长度，什么也不变：每种情况下，约每 17 个进程中有 1 个慢 5% 到 25%。这个离散属于布局：四个布局里，一个稳定（753 到 756 ms），一个的范围是 715 到 966 ms，关掉随机化时也是这样。
  - goroutine 栈的位置没有关系。栈移动 31 个偏移（一行里的全部 64 个位置，以及 4 KiB 内每隔 256 字节），`q_array_read` 的变化在 1.5% 以内，`c_string_concat` 在 1.1% 以内。
  - 兄弟超线程有关系：最慢的两个进程（慢 77% 和 52%）是在它忙的时候运行的，这就是规则要求它空闲的原因。
  - 对齐得更多，平均来说没有帮助。链接器的 `-funcalign=64` 在 4 个脚本上给出的时间几何平均是 1.013，`-funcalign=128` 是 1.037。所有函数按 64 字节对齐给出 1.012，保留 `llc` 在 `JS_CallInternal` 里写的那 319 个 16 字节对齐给出 1.034 到 1.038。每个函数和函数体都按 64 字节对齐时，`q_int_arith` 随位置的离散从 11.5% 降到 2.8%，但 `q_prop_read` 快了 4.5%，`q_array_read` 慢了 10% 到 15%，`JS_CallInternal` 增大了 20%（116,699 字节增到 140,490 字节），每次调用多约 8 条空操作。最后保留的是下面函数体的固定位置。

## 什么时候不要信一个结果

- **judge 报告了问题或者运行不完整。** 它遇到失败的进程、重复的记录、另一个实验的记录、缺一边或跨两个会话的块、缺失、为零、为负或不是有限数的指标，或者各边报告的页面不同，都会停下。修正这次运行，不要去改记录。
- **各边不是在同样的块里计时的。** 只比较同一个文件里、同一次运行里计时的各边。两天的两个文件，或者两台机器的两个文件，相差的幅度会超过这套规程想测的那些改动。清单会拒绝在同一个文件里用别的二进制或设置接着做。
- **效应小于这个应用能显示的最小值**（见上表）。那里的无法定论是预期的答案，不是失败。只有当让区间变宽的是运行标准差而不是布局标准差时，才多跑几轮（更多的轮数只缩小属于运行的那部分）。
- **其他核很忙。** 其他核上的构建和 callgrind 与计时核共用 L3 缓存和内存总线，而干扰检查看不到这一点（它只读计时核和它的兄弟）。每条记录都保留 `machine_pct`。当基准和新的一边运行时的负载差别很大，或者负载在运行期间忽来忽去时，在安静的机器上重新计时。
- **多次尝试里的胜出者。** 几次尝试中结果最好的那个变体，平均来说，运气比实力好。引用它之前，用一次新的运行再给它计时。
- **另一台机器或另一种架构。** 这些数字属于 GCP 的机器（Zen 3，每核 2 个超线程）。它们对 darwin/arm64（没有布局）或另一台 x86 机器什么也说明不了。在那里测量前，先做一次 A/A 运行。
- **改了工具、测试框架或机器之后。** 先做一次 A/A（同一个二进制复制成第二个名字），检查它说"没有超过 delta 的退步"，并且它的区间包含 0。
